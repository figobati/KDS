# 第八部分：终端客户端

## 12. 终端形态与优化

| 终端 | 技术 | 说明 |
|------|------|------|
| Win10 Master | WPF + WebView2 | Kestrel + SQLite + 本地 UI（**要求 Win10 1809+**） |
| Win10 Worker | WPF + WebView2 | 连 Master，不碰数据库 |
| **Win7** | **Edge 109 浏览器（kiosk）** | **只能做 BS 终端**——.NET 10 不支持 Win7，**不能装 WPF 客户端** |
| Android / iOS | 浏览器 BS 终端（V1）/ MAUI（评估） | SignalR + 本地缓存 |

**性能优化要点**（MAUI 或 Web 大列表场景）：

- 列表虚拟化（CollectionView / 虚拟滚动），避免一次渲染上千行；
- **delta 推送局部更新**：按 `DetailId` 更新单行，禁止整表重绘；
- 全局单一计时器（`DispatcherTimer` / `requestAnimationFrame`）统一刷新所有时长文本，禁止每行一个计时器；
- 传输可选 MessagePack 压缩（大屏全量拉取场景）；
- 本地 SQLite / IndexedDB 离线缓存当前视图数据；
- Android `KeepScreenOn` 常亮，避免后厨熄屏；
- 终端与服务端时间校准：以 `ServerNow` 为基准本地自增。

## 13. 非功能需求

### 13.1 技术栈与兼容性

1. 后端 Master 服务：**.NET 10（LTS）** + **C# 14**；**Win 客户端（WPF + WebView2）要求 Win10 1809+**；
2. **Win7 只能作为浏览器终端**（Edge 109 kiosk 访问 Master）——**.NET 10 已不支持 Win7，不可在 Win7 上部署 WPF 客户端**；
3. 浏览器终端：Win7 上限 Edge 109；Win10+ 建议最新版 Edge/Chrome；
4. 数据库：门店 **SQLite**（默认）或 **SQL Server 2016+**；**不支持 SQL Server 2000 / 2005 / 2008**（原因见 §8.3）；
5. 数据访问：**EF Core 10 为主（写 + 迁移）+ Dapper 为辅（读 / 报表 / 批量）**，边界规则见 §8.4；
6. **不启用 `PublishAot` / 强裁剪**：EF Core 依赖反射与动态代理，AOT 兼容成本高；发布用框架依赖或自包含（`SelfContained`）即可。

### 13.2 网络与离线

1. 局域网运行，支持**离线营业**，断网恢复自动重连；
2. 实时推送 WebSocket + **本机轻量轮询兜底**（默认 15 秒 ± 抖动），三层防漏单策略见 §2.10；
3. 终端断网期间**只浏览不提交**，恢复后自动全量刷新；
4. POS 断网不影响 KDS 已接收订单的制作与划单；
5. **数据完整性承诺（广播模式前提）**：任一屏幕在**网络正常**的情况下，漏推窗口 ≤ `PollingIntervalSeconds`（默认 15s）；超过 `DataStaleSeconds`（90s）无权威数据必须显式提示用户，不允许静默展示过期数据。

### 13.3 一致性与并发

1. **乐观锁 + 版本号**：`OrderHeader.Version`、`OrderDetail.Version` 双表版本字段，并发划单防冲突；
2. 多终端状态广播同步，`Revision` 单调递增防乱序，并作为**漏单检测依据**（§2.10）；
3. 事件幂等（`EventId`）+ 操作幂等（`ClientEventId`）+ 变更应用幂等（按 `DetailId` upsert）；
4. 出站回执 Outbox 保证不丢（§10.4）。

### 13.5 安全

1. **终端鉴权**：`deviceKey` 与 `TerminalConfig.DeviceKey` 比对（V1 必须）；**屏会话令牌与终端绑定**，换机即失效；
2. **接口鉴权**：账号 + 会话令牌（V1 必须）；账号体系、登录页、**屏无感登录**见 **§13.11**；
3. 传输：局域网内 V1 可用 HTTP，若跨网段或客户要求则启用 HTTPS / MQTT TLS；
4. 审计：所有状态变更写 `OperationLog`，POS 事件写 `EventLog`，不可静默丢弃；
5. 数据：SQLite 文件访问权限限制为服务账户；
6. 口令与密码：登录口令**只存哈希**（PBKDF2/Argon2），连接串密码用 **DPAPI**（§13.10.5），两者都不明文落盘。

### 13.6 数据量与保留策略

> **核心原则：明细可以清，统计必须留。** 订单明细是"体积大、价值随时间衰减"的数据；运营指标是"体积小、价值随时间增长"的数据。所以**清明细之前先预聚合**，一年后明细没了，但"去年 10 月平均出餐 18 分钟"还能查。

#### 13.6.1 五层数据模型（保留期差异巨大）

| 层 | 数据 | 体积 | 默认保留 | 价值走势 |
|:--:|------|:----:|----------|----------|
| **L1 明细层** | `OrderDetail`（含 `OrderHeader`） | **大**（1,500 行/日） | **主库 90 天 → 移入历史库（永久）**（§14.1.3） | 递降 |
| **L2 索引层** | `OrderHeader` 摘要（单号 / 桌台 / 金额级信息） | 小 | **1 年**，之后同样移入历史库 | 平 |
| **L3 统计层** | `DailyStoreStat` / `DailyDimStat`（§9.22 / §9.23） | **极小**（几十行/日） | **永久（主库）** | **递增** |
| **L4 日志层** | `EventLog` 30 天 / `OperationLog` 180 天 | 中 | 短期 | 递降 |
| **L5 历史层** | 本地按月归档卷（`ArchiveVolume`） | 25~30 MB/月 | **永久保留**（默认 `MoveToArchive`） | 平 |

> **为什么 L1 和 L2 分开**：门店半年后要查"上个月那单 3821 结了多少"，只需要订单头，不需要每道菜的状态流转。留着订单头成本几乎为零，能救很多"查单"场景。

#### 13.6.2 保留期一览表

| 数据 | 默认保留 | 清理策略 |
|------|----------|----------|
| 进行中订单 / 明细 | 永久（直至终态） | 不清理 |
| **`OrderDetail`（终态，L1）** | **主库 90 天** | **移动到历史库**（MOVE，非删除；§14.1.3） |
| **`OrderHeader`（终态，L2）** | **主库 1 年** | 之后同样移入历史库 |
| **`ArchiveVolume`（L5 历史卷）** | **永久** | 默认不删；仅 `MoveAndDeleteAfterUpload` 模式下云端确认后满 30 天删卷 |
| **`DailyStoreStat` / `DailyDimStat`（L3）** | **永久** | **永不清理**（体积可忽略） |
| `EventLog` | 30 天 | 定时清理 |
| `OperationLog` | 180 天 | 定时清理 |
| `OutboxMessage`（`Sent`） | 7 天 | 定时批量清理（每批 1,000 条，§9.14.1） |
| `OutboxMessage`（`DeadLetter`） | **90 天** | **先告警、人工重放/关闭；过期须先导出 CSV 再删** |
| `PrintJob`（`Success`） | 30 天 | 定时清理 |
| `PrintJob`（`DeadLetter`） | 90 天 | 同死信策略，人工补打后关闭 |
| 语音 / 提示记录 | 不留存 | — |

**清理任务统一要求**：① 批量删除（每批 1,000），避免长事务锁库影响出餐；② 默认在**非营业时段**（04:00）执行；③ 每条清理任务记 `OperationLog`（删了多少行、耗时），便于排查"数据怎么少了"；④ **SQLite 需定期 `PRAGMA optimize` + 季度 `VACUUM`**——SQLite 删除不释放文件空间，不 VACUUM 则库文件只涨不跌。

#### 13.6.3 预聚合：让统计脱离明细独立存活

**执行时机**：每日 **03:00** 聚合前一日数据（T+1），聚合成功后才允许当日 04:00 的清理任务推进。

**聚合维度**（写进 L3 两张表，字段见 §9.22 / §9.23）

| 维度 | 指标 | 用途 |
|------|------|------|
| **门店 × 日期** | 总单量、总明细数、总份数、退菜数、赠菜数、平均出餐时长（P50/P90/最大）、超时率、就餐人数、桌台数、翻台率 | 店长日报 / 月度趋势 |
| **档口 × 日期 × 阶段** | 产量（明细数/份数）、平均阶段时长、超时数、P90 时长 | 各档口绩效与瓶颈定位 |
| **品项 × 日期** | 销量（份数）、平均时长、退菜率 | 菜品排行、慢菜识别 |
| **时段 × 日期**（可选，按小时） | 单量、峰值并发 | 排班与设备容量 |

> **口径必须是"预聚合 = 从明细算一次"**：报表查询当日走明细实时算，查历史走 `DailyDimStat`；两处口径由**同一个聚合器**产出，禁止各写一套（同 §2.11 路由自检的教训）。

#### 13.6.4 归档卷：完整实现说明

> **一句话**：归档卷是"**按月切分、与主库同 schema 的只读 SQLite 文件**"。主库存不下的历史订单被 **MOVE**（不是 COPY+DELETE）进去，之后按月份 ATTACH 只读查询。数据永不销毁（默认模式），主库始终瘦。

**① 目录与命名**

```
{AppDir}/data/kds.db                                   ← 主库（热数据）
{AppDir}/data/archive/2026/2026-10/orders-2026-10.db   ← 归档卷（按月）
{AppDir}/data/archive/2026/2026-10/orders-2026-10.db-wal / -shm  ← 写入期临时文件
{AppDir}/data/archive/2026/2026-10/orders-2026-10.db.gz        ← 上传压缩副本（可选）
```

| 规则 | 说明 |
|------|------|
| 按月一卷 | 卷内只放该月**终态**订单（`CompletedAt` 落在该月） |
| 年度子目录 | 避免单目录几百个文件拖慢文件系统枚举 |
| 卷文件自包含 | 卷内有 `ArchiveMeta` 表（见 ④），**不依赖外部清单文件**——卷被单独拷走后仍能自解释 |

**② 卷的状态机**
```
Writing ──月末封卷──► Sealed ──上传成功──► Uploaded
   │                    │                    │
   │                    └──校验失败──► Corrupted
   │                                         │
   └──写失败/损坏──► Corrupted          （Delete 模式下）──► Deleted
```

| 状态 | 可写 | 可查 | 说明 |
|:----:|:----:|:----:|------|
| `Writing` | ✅ | ✅ | 当月正在追加；只允许写入、不允许删除 |
| `Sealed` | ❌ | ✅ | 封卷后**禁止任何写入**（含补录）；索引已建、已校验 |
| `Uploaded` | ❌ | ✅ | 已上传云端，本地仍保留（默认模式） |
| `Corrupted` | ❌ | ⚠️ | 损坏，尝试用云端副本或备份恢复 |
| `Deleted` | ❌ | ❌ | 仅 `MoveAndDeleteAfterUpload` 模式，云端确认后删除 |

> **封卷后不可写是硬约束**：允许跨月继续写会让"一个月的数据散在多个卷"，查询要合并 N 个文件，逻辑复杂到没人维护。补录需求通过"重开一个补录卷"解决（`orders-2026-10-patch1.db`），而不是往已封卷里塞。

**③ 迁移（MOVE）流程——关键在"不依赖跨库原子性"**

> ⚠️ **SQLite 的坑**：跨 `ATTACH` 库的事务**只有在主库 journal_mode 不是 WAL 时才保证原子**。后厨高并发场景主库通常开 **WAL**（为了读写不互斥），此时"写卷 + 删主库"跨库提交**不保证原子**。所以本设计**不依赖跨库事务**，改用「幂等写 + 后删 + 水位」的补偿模型。
> ✅ **SQL Server 主库则不同**：同实例跨库写入**在一个事务里是原子的**（`INSERT INTO ArchiveDB.dbo.x SELECT … FROM KdsDb.dbo.y` + `DELETE`），`SqlServerArchiveStore` 可直接一步提交；但**仍保留水位字段**，用于断点续跑与审计追踪（§8.2）。

```
清理任务（营业日结束后 + 60 分钟窗口内，§2.13.4；严禁营业中执行）：
 1) 选批：从主库取终态订单，条件
       所有明细 StageStatus ∈ {Completed, Cancelled, Skipped}
       且 BusinessDate < 当前营业日 - OrderRetentionDays     ← 按营业日，不按 CompletedAt 自然时间
       且 BusinessDate ≥ 卷的水位（LastMovedBusinessDate）
    每批 N 单（默认 200 单，约 1000 明细）
 2) ATTACH 卷（可写）
 3) 事务 T1（仅写卷，幂等）：
       INSERT OR IGNORE INTO a.OrderHeader  ... SELECT ... FROM main.OrderHeader WHERE OrderId IN (...)
       INSERT OR IGNORE INTO a.OrderDetail  ...
       INSERT OR IGNORE INTO a.OperationLog ...（若日志仍在保留期内）
    COMMIT
 4) 校验：卷内该批行数 == 主库该批行数（含明细数）；不等 → 放弃该批，告警，不删主库
 5) 事务 T2（仅删主库）：
       DELETE FROM main.OrderDetail WHERE OrderId IN (...)
       DELETE FROM main.OrderHeader WHERE OrderId IN (...)
    COMMIT
 6) 更新 ArchiveVolume.LastMovedBusinessDate = 本批最大 BusinessDate（水位）
 7) 循环直到无可移数据
```

| 为什么这样设计 | 说明 |
|----------------|------|
| **每批小事务** | 200 单/批，避免长事务持有写锁影响出餐；崩溃最多重做一批 |
| **`INSERT OR IGNORE`** | 崩溃后重跑同批不会产生重复（主键 `OrderId`/`DetailId` 天然幂等） |
| **先写卷、后删主库** | 顺序不可颠倒：先删后写，一旦写失败就永久丢数据 |
| **水位 `LastMovedBusinessDate`** | 断点续跑的依据；**用营业日而非时间戳**，与选批条件同源，跨零点不会漏批/重批 |
| **删主库前再校验行数** | 唯一的"防错保护"：卷里没写全就不许删主库 |
| **只移终态** | 进行中订单永不移（`StageStatus` 未完结的先跳过，下轮再试） |
| **按 `BusinessDate` 分卷** | 卷的月份 = `BusinessDate` 的月份，**不是 `CompletedAt` 的自然月**（§2.13.5）——否则月末跨零点的营业日会被劈到两个卷 |

**④ 卷内结构（`ArchiveMeta` + 数据表子集）**

```sql
-- 卷自描述元数据（单行）
CREATE TABLE ArchiveMeta (
  VolumeMonth TEXT NOT NULL,        -- '2026-10'
  SchemaVersion INTEGER NOT NULL,   -- 与主库 schema 版本对齐
  SealedAt TEXT,                    -- 封卷时间（空 = 仍在写）
  RowCountOrder INTEGER,
  RowCountDetail INTEGER,
  Checksum TEXT,                    -- 封卷时计算（见 ⑤）
  KdsVersion TEXT                   -- 生成该卷的程序版本
);

-- 数据表：与主库同字段的**子集**（去掉未来才会用到的列），但**类型与 GUID 格式完全一致**
-- OrderHeader / OrderDetail / OperationLog（可选）
```

| 取舍 | 说明 |
|------|------|
| **同 schema 而非自定义结构** | 查询代码零改造，直接 `SELECT ... FROM a.OrderHeader` |
| **不含配置表** | 配置在主库永久保留，卷只存业务数据 |
| **`SchemaVersion` 必须存** | 主库升级后旧卷结构可能落后，查询层据此做兼容映射 |

**⑤ 封卷（月末 + 次月首次运行）**

```
1) 校验无 `Writing` 状态遗留（该月所有迁移已完成）
2) 建索引（一次性）：
     IX_Archive_Order_Time, IX_Archive_Order_No,
     IX_Archive_Detail_Order, IX_Archive_Detail_Time
3) ANALYZE（更新统计信息，提升查询计划质量）
4) PRAGMA integrity_check（必须返回 ok）
5) 计算 Checksum = SHA256(按 (OrderId) 排序后逐行序列化的 OrderHeader + OrderDetail)
6) 写 ArchiveMeta（SealedAt / 行数 / Checksum）
7) ArchiveVolume.Status = Sealed
8) 可选：VACUUM 卷文件（去除写入期碎片，通常能缩小 10~20%）
```

> **索引在建好之后才封卷**：索引随数据写入维护的成本，远高于"批量导入完成后一次性建索引"。一个月 4.5 万明细，事后建索引通常是几百毫秒级。

**⑥ 校验与完整性**

| 校验层 | 做法 | 失败处理 |
|--------|------|----------|
| 迁移即时校验 | 每批"卷内行数 == 主库行数"（头 + 明细分别比） | 放弃该批，不删主库，告警 `ARCHIVE_ROW_MISMATCH` |
| 封卷校验 | `PRAGMA integrity_check` + Checksum | 置 `Corrupted`，尝试从备份重做该卷 |
| 定期巡检 | 每月校验历史卷 `Checksum`（抽样或全量） | 标记 `Corrupted` + 告警 `ARCHIVE_CHECKSUM_FAILED` |
| 查询期校验 | 卷打不开 / 表缺失 → 抛明确错误 | **不允许静默返回空结果**（否则被误读成"这单不存在"） |

**⑦ 查询（READ-ONLY ATTACH）**

```sql
ATTACH 'file:{AppDir}/data/archive/2026/2026-10/orders-2026-10.db?mode=ro' AS a;
-- 连接需开启 URI 支持：SqliteConnectionStringBuilder { Mode = ReadOnly, Uri = true }

-- 按时间段查订单（必命中 IX_Archive_Order_Time）
SELECT * FROM a.OrderHeader
 WHERE CompletedAt >= @from AND CompletedAt < @to
 ORDER BY CompletedAt DESC LIMIT @page OFFSET @skip;
```

| 规则 | 说明 |
|------|------|
| 只读挂载 | `mode=ro`，防止误写/误删；进程崩溃也不会留下 `-wal` |
| **必须带索引条件** | 查询无 `CompletedAt` 区间或 `PosOrderNo` 时**直接拒绝**并提示（禁止全卷扫描） |
| 跨卷合并 | 同时最多 ATTACH 3 卷；更多则逐卷查询后内存合并排序 |
| 分页 | 默认 50 条/页，避免一次拉几万行 |
| ATTACH 生命周期 | 查询结束立即 `DETACH`，不长期持有文件句柄（否则删除/上传会失败） |

**⑧ 与备份、上传、删除的关系**

| 动作 | 规则 |
|------|------|
| **备份** | 每日备份含**主库 + 卷清单**；卷文件本身按月做**增量冷备**（卷封卷后内容不再变，适合一次性备份） |
| 上传 | 封卷后非营业时段按 §14.2.4 分片上传；上传前压缩 `gzip`（20~40 MB → 5~12 MB） |
| 删除 | **默认不删**。仅在 `MoveAndDeleteAfterUpload` 模式下，云端回执校验通过且满 `LocalBufferDaysAfterUpload` 天才删；删除前先记 `OperationLog` |
| 手工操作 | 管理端提供"封卷/重校验/导出/删除"四个动作，**删除必须二次确认 + 输入月份**（防误点） |

**⑨ 故障场景与恢复**

| 场景 | 表现 | 恢复 |
|------|------|------|
| 迁移中途断电 | 卷里有数据、主库没删（或删了一部分） | 重启后按水位重跑：`INSERT OR IGNORE` 幂等，删主库按 `OrderId` 重删；结果一致 |
| 写卷失败（磁盘满） | 该批校验不过 | 跳过该批 + 告警 `ARCHIVE_WRITE_FAILED`，主库不动；清空间后自动续跑 |
| 封卷时崩溃 | 卷停在 `Writing`，索引可能部分建好 | 下次启动检测：`Writing` 且当月已过 → 重建索引 + 重新校验 + 封卷（幂等重做） |
| 卷文件被误删 | 卷缺失 | 提示"该月归档缺失"，提供从备份恢复入口；`DailyStat` 统计不受影响（§14.1.6） |
| 卷损坏 | `integrity_check` 失败 | 置 `Corrupted`，从备份或云端副本恢复；恢复前该月查询明确报错（不返回空） |
| 上传失败 | 卷仍 `Sealed` | 保持本地卷，指数退避重试；连续 3 次失败告警并停止（§14.2.4） |

**⑩ 性能与营业影响**

| 项 | 设计 |
|----|------|
| 执行窗口 | 仅 `CleanupHour`（默认 04:00）之后、营业开始前；窗口不足则少移几批，**不跨营业时段** |
| 批量 | 200 单/批，单批耗时通常 < 500ms，写锁持有时间极短 |
| WAL | 主库保持 WAL，读写不互斥；批量删产生的 WAL 增长在每批 COMMIT 后自动 checkpoint |
| 空间回收 | 主库删除后**不立即 VACUUM**（会长时间锁库）；每周 `PRAGMA incremental_vacuum`（若开 `auto_vacuum=INCREMENTAL`），季度低峰做一次完整 `VACUUM` |
| 磁盘规划 | 主库 ≤ 500 MB + 卷 30 MB/月（一年 360 MB）→ 建议预留 2 GB 数据目录 |

**⑪ 测试要点（必须覆盖）**

| # | 用例 | 期望 |
|---|------|------|
| 1 | 迁移中途杀进程再启动 | 无重复、无丢失，水位正确续跑 |
| 2 | 卷写入失败（模拟磁盘满） | 主库数据完整保留，无删除 |
| 3 | 同批重跑两次 | 卷内行数不变（幂等） |
| 4 | 跨月边界（月末 23:59 完成的订单） | 落在正确月份的卷 |
| 5 | 跨卷查询（3 个月） | 结果正确、按时间排序、分页正确 |
| 6 | 卷损坏后查询 | 明确报错，**不返回空列表** |
| 7 | 封卷后尝试写入 | 被拒绝并记日志 |
| 8 | 主库升级 schema 后查旧卷 | 按 `SchemaVersion` 兼容读取 |

**⑫ 与"清明细"的关系（回到最初的动机）**

```
主库 90 天 ──MOVE──► 归档卷（永久）──上传──► 云端（可选）
   │                     │
   └─ 主库瘦身            └─ 本地仍可查（ATTACH）
   
统计（DailyStoreStat / DailyDimStat）在主库永久保留 → 趋势报表永不依赖卷
```

> **归档卷不是"删除的中间态"，而是"数据的第二个家"**。它同时满足三个诉求：主库不涨、本地能查、云端有备份。真正会"消失"的只有管理员手动删除卷这一种情况，而那是显式操作。


#### 13.6.5 配置项（`StoreConfig`）

> ⚠️ **本节只列"保留与清理"相关的 7 个字段**；`StoreConfig` 的**唯一权威定义在 §9.1**（含全部字段与默认值），本节不复述其它字段。
> 新增/修改字段请改 §9.1，并在此仅补充"为什么这样保留"的业务理由（如有）。

| 字段 | 默认 | 说明 |
|------|:----:|------|
| `OrderRetentionDays` | 90 | 明细保留天数（可选 30 / 90 / 180，更长需评估磁盘） |
| `OrderHeaderRetentionDays` | 365 | 订单头保留天数 |
| `AutoCleanupEnabled` | 1 | **清理总开关**——门店想"自己备份完再清"时可关 |
| `ArchiveEnabled` | 1 | 归档开关（关闭时**禁止清理明细**，只允许清理日志/Outbox） |
| `StatAggregateHour` | 3 | 预聚合执行小时 |
| `CleanupHour` | 4 | 清理执行小时 |
| `DbSizeWarnMb` | 2048 | DB 文件超此大小告警（提示调整保留期或扩容） |

> **`AutoCleanupEnabled = 0` 不是"永久不成长"的借口**：关闭后系统仍会监控 DB 大小，超 `DbSizeWarnMb` 持续告警。

#### 13.6.6 容量估算与演进

**单店基线（日 300 单 × 5 明细 ≈ 1,500 明细/日）**

| 层 | 90 天量 | 1 年量 | 折算体积（SQLite） |
|----|---------|--------|--------------------|
| L1 明细 | 13.5 万行 | — | ≈ 80~120 MB |
| L2 订单头 | — | 11 万行 | ≈ 30 MB |
| L3 统计 | 90 × (1 + 档口 N + 品项 M) | 365 × 同 | **< 10 MB** |
| L4 日志 | `EventLog` 5 万 + `OperationLog` | — | ≈ 40 MB |
| **合计** | — | — | **主库稳定在 200~400 MB** |

> **L3 才是长期资产**：一天几十行、一年不到 1 MB，永久保留零压力——**这是"清明细"敢做的前提**。
> 若门店要求保留 2 年明细（如连锁审计），建议**按月分库**（主库只留 90 天，历史月份直接挂归档库查询），而不是把主库撑到几 GB。

#### 13.6.7 运营报表支撑（对齐管理端报表原型）

> 管理端要出四类报表：**① KPI 概览 + 菜品排行榜**（聚合）、**② 超时明细**、**③ 催单明细**、**④ 退菜明细**（明细级）。
> 本节固定：**每张报表的每个字段从哪来**，以及聚合口径。

**① 聚合报表（走 L3，毫秒级，与明细是否已归档无关）**

| 报表元素 | 数据来源 | 口径 |
|----------|----------|------|
| 出品数 | `DailyStoreStat.TotalQty` | **份数**合计 |
| 退单数 | `DailyStoreStat.CancelledQty` | **份数**（不是条数） |
| 催单数 | `DailyStoreStat.RemindQty` | 份数（`RemindCount` 是条数，UI 需标单位） |
| 超时数 | `DailyStoreStat.TimeoutQty` | 份数 |
| 退菜金额 | `DailyStoreStat.CancelledAmount` | 依赖 POS 推 `Amount`，缺失则显示"—"而非 0（避免误导） |
| "较 7 日均值上升/下降" | L3 前 7 个**营业日**同期数据 | `(今日 - 前 7 日均值) / 前 7 日均值`；**日均的分母取 `CompareDivisorMode`**（默认 `EffectiveDays`，见 §13.6.8 ②）；**必须同餐段对比**（选了"午餐"就只比前 7 天午餐） |
| 菜品排行榜（退单/催单/易超时/热销） | `DailyDimStat`（`Dimension = Item`） | 分别按 `CancelledQty` / `RemindQty` / `TimeoutQty` / `TotalQty` 降序取 Top10 |
| 排行百分比 | `该品项值 / 当期该列全店合计` | 分母是**同一筛选条件下全店合计**，不是全菜单 |
| 日期筛选（今天/近7天/近30天/自定义） | `BusinessDate` 区间（§2.13.5） | "今天" = 当前营业日 |
| 餐段筛选（全部/早餐/午餐/晚餐） | `DailyDimStat`（`Dimension = MealPeriod`） | 需按餐段聚合一份（已有该维度） |

**②③④ 明细报表（走 `OrderDetail`，90 天内实时；更早走归档卷）**

| 报表列 | 数据来源 | 现状 |
|--------|----------|:----:|
| 单号 | `OrderHeader.PosOrderNo` | ✅ 已有 |
| 台号 | `OrderDetail.TableNo` / `OrderTableRel.TableCodeSnapshot` | ✅ 已有 |
| **服务员** | `OrderDetail.WaiterName` | 🆕 **本次新增**（POS 推送） |
| 菜品名称 | `OrderDetail.DishName` | ✅ 已有 |
| **数量 / 单价 / 小计** | `OrderDetail.Qty` / **`UnitPrice`** / **`Amount`** | 🆕 金额两项**新增**（POS 推送） |
| 下单时间 | `OrderDetail.OrderCreateTime` | ✅ 已有 |
| 划单时间 | `OrderDetail.StageCompleteTime` | ✅ 已有 |

**金额字段的边界（必须写清）**

| 规则 | 说明 |
|------|------|
| **KDS 不做金额计算** | `UnitPrice` / `Amount` 由 POS 推送，KDS **只存与求和展示**，不参与任何折扣、税费、找零逻辑 |
| 权威在 POS | 报表金额与 POS 账单不一致时，**以 POS 为准**；KDS 报表页需标注"金额数据来自 POS" |
| 缺失处理 | POS 未推金额 → `Amount` 为空 → 报表显示"—"，**不显示 0**（0 会被误读成"免费"） |
| 改价 | POS 推 `Order.Update` 更新 `Amount`；已归档数据不追改（归档是不可变快照） |

#### 13.6.8 报表口径细则（按产品批注定稿）

> 本节把报表原型的每一条规则落成**可执行口径**。凡与本节冲突的实现一律以本节为准。

**① 筛选交互与范围约束**

> **UI 与后台分离**：**界面文案用日常说法**（今天 / 最近 5 日 / 最近 3 月 / 最近 30 日…），**不出现"营业日""营业月"字样**；**后台一律按营业日 / 营业月筛选**。用户不需要理解营业日概念，但数字必须是营业日口径。

**UI 文案 → 后台口径映射（实现必须照此换算）**

| UI 按钮 | 后台口径 | 跨度 |
|---------|----------|------|
| **今天** | 当前营业日 | 1 个营业日 |
| **最近 5 日** | 最近 **5 个营业日** | 5 |
| **最近 7 日** | 最近 7 个营业日 | 7 |
| **最近 30 日** | 最近 30 个营业日 | 30 |
| **最近 3 月** | 当前营业月 + 前 2 个营业月（= 最近 **3 个营业月**） | ≤ 92 个营业日 |
| **选择日期** | 用户选的营业日区间 | ≤ 该营业月营业日数 |

| 项 | 规则 |
|----|------|
| 预设按钮 | `[今天]` / `[最近5日]` / `[最近7日]` / `[最近30日]` / `[最近3月]` —— **单选互斥** |
| 自定义 | 点 `[选择日期]` → 弹日历；支持**选中单日**与**拖拽选区间** |
| **自定义范围约束** | **仅限同一营业月内**（`8.1~8.31` ✔ / `7.20~8.15` ✘），上限 = 该营业月的营业日数（28~31） |
| 预设可跨月 | 预设由产品固定，**允许跨营业月**（`[最近3月]` 必然跨月）；自定义由用户任意拖拽，故限制同月 |
| 约束目的 | 防止自定义选 2 年导致跨大量归档卷、拖垮管理端 |
| **UI 文案规范** | 一律用"日 / 月"，**禁止**在按钮、卡片、表头、页脚出现"营业日/营业月"字样（内部文档与技术日志可用） |

**② 对比口径（两套公式，按选择模式切换）**

| 模式 | 卡片展示 | 对比基准 | 对比文案 |
|------|----------|----------|----------|
| **单日**（`[今天]` 或自定义单日） | 当日**合计值** | **前 7 个营业日**同餐别日均值 = `SUM(前7个营业日同餐别该指标) / 分母` | `↑ 较 7 日均值上升` / `↓ 下降` |
| **区间**（`[近7天]` / `[近30天]` / 自定义区间） | 区间**合计值** | **上一个等长营业日区间**：`N = 区间内营业日数`，上周期 = 从区间起点往前数 `N` 个营业日 | `↑ 较上周期上升` / `↓ 下降` |

**分母模式（`StoreConfig.CompareDivisorMode`）**

| 取值 | 分母 | 适用 |
|------|------|------|
| **`EffectiveDays`（默认）** | 前 7 个营业日中**实际有数据的天数** | 新店第 4~7 天不会出现"暴涨假象" |
| `FixedSeven` | 固定 7（严格按批注） | 开业满 7 个营业日后两者结果一致 |

> **为什么默认 `EffectiveDays`**：新店第 4 天只有 3 天历史，`SUM/7` 会把基准压低约 43%，必然显示"暴涨"。满 7 个营业日后两种模式等价，所以默认选用更稳的一种。若产品要求严格 `/7`，把该配置改为 `FixedSeven` 即可。

**示例对照**

```
单日：选营业日 7/29 午餐 → 当日退单 8 份；前 7 个营业日午餐日均 = 3 份 → ↑ 上升
区间：选 7/23~7/29（7 个营业日）合计 45 份；上周期 7/16~7/22 合计 52 份 → ↓ 下降
       （比的是**合计**，不是日均）
区间：选近 30 天 = 最近 30 个营业日 合计 120 份；上周期（再往前 30 个营业日）98 份 → ↑ 上升
```

> **两套公式不可混用**：单日比"日均"、区间比"上周期合计"。这是为了避免"选 30 天时拿日均去比"造成数值失真。

**③ 餐别基准**

| 规则 | 说明 |
|------|------|
| 默认值 | **餐别默认选中「全部」** |
| 基准同源 | 选「午餐」→ 只取午餐时段数据；**对比基准也取前 7 天午餐**，不混入晚餐 |
| 实现 | 聚合与对比都在 `MealPeriod` 维度内完成（§9.23），禁止"先算全店再按比例折算" |

**④ KPI 卡片**

| 场景 | 展示 |
|------|------|
| 单日有数据 | 合计值 + `较 7 日均值` 涨跌 |
| 区间有数据 | 合计值 + `较上周期` 涨跌 |
| 当日无数据 | 显示 `--` |
| 新店不足 3 天 | 显示「数据不足，暂无对比」 |

**⑤ 排行榜（4 张卡，**全部按「份数」不按「次数」**）**

| 榜单 | 口径 | 数据字段 |
|------|------|----------|
| 退单菜品 | 该菜**被退的份数之和**（同一菜退 3 次、各退 3/2/3 份 → **8 份**，不是 3 次） | `DailyDimStat(CancelledQty)` |
| 催单菜品 | 该菜**被催的份数之和** | `DailyDimStat(RemindQty)` |
| 易超时菜品 | 该菜**超时出品的份数之和** | `DailyDimStat(TimeoutQty)` |
| 热销菜品 | 该菜**已出品的份数之和**（注意：是**已出品**，不是下单份数） | `DailyDimStat(OutputQty)` |

> **榜单范围：包含饮品、酒水、套餐子项等全部品项**（产品已确认）。
> 即"菜品排行榜"里的"菜品"是**广义菜单条目**——可乐、啤酒、果汁与宫保鸡丁同列榜单，因为它们都是 `DishItem`、都产出"份数"。
> 若后续需要**分品类榜**（菜品榜 / 饮品榜 / 酒水榜），用 `Dimension = Item` 再加 `DishTypeId` 分组即可，**不改本表结构**。

| 规则 | 说明 |
|------|------|
| 排序 | 按份数**降序**，默认展示**前 10** |
| **占比** | `单品份数 ÷ 当期全店该类总份数 × 100%` |
| **分母固定** | 分母恒为**全店该类总份数**，**不是前 10 之和**（只显示前 10，占比仍是相对全店） |
| 不足 10 条 | 有多少展示多少 |
| 无数据 | 显示「暂无数据」（不显示空框） |

**⑥ 数据刷新与"数据更新时间"**

| 项 | 规则 |
|----|------|
| 刷新频率 | **每 5 分钟**自动刷新一次；**打开页面立即刷新一次** |
| 页面显示 | 底部显示「数据更新时间」= **最近一次同步成功的时间**（含义：数据最多延迟 5 分钟） |
| 显示位置 | 主页面 + 退菜 / 催单 / 超时明细表底部**都显示** |
| 实现 | 报表接口带 `DataUpdatedAt` 字段；**同一页面内所有查询必须用同一份快照**，避免"卡片是 10:00 的、明细是 10:05 的" |

> **这要求报表走"快照"而不是"每次实时算"**：详见 ⑧。

**⑦ 异常与新店判定**

| 场景 | 处理 |
|------|------|
| 当日无数据 | 卡片 `--`；排行榜「暂无数据」 |
| 门店首营业日距今 < 3 天 | 「数据不足，暂无对比」（**不做涨跌**） |
| 排行榜不足 N 条 | 有多少展示多少 |
| 门店首营业日 | `StoreConfig.FirstBusinessDate`（首个营业日，用于"新店"判定） |

**⑧ 报表快照（支撑"5 分钟刷新 + 更新时间"）**

```
后台每 5 分钟（或首次访问时）刷新一次报表快照：
  当日/区间聚合 → 计算结果缓存（含 DataUpdatedAt、对比基准、各榜单）
页面 → 只读缓存，不直接查明细
```

| 收益 | 说明 |
|------|------|
| 同一页面数据一致 | 卡片 / 榜单 / 明细页脚不会出现"两个时间点"的数字 |
| 合计行稳定 | 翻页不重算，`Summary` 永远一致 |
| 与"更新时间"语义一致 | 页脚时间 = 快照时间，用户能预期"最多延迟 5 分钟" |
| 降低 DB 压力 | 20 个管理端同时看报表不会打爆明细表 |

> **快照实现**：进程内缓存（`IMemoryCache`，key 含 `StoreId + 日期区间 + 餐别`，TTL 5 分钟）+ 首次访问同步生成。**不落库**（体积小、可重算）。

**⑨ 日期口径：后台一律营业日 / 营业月，UI 不做强调（定稿）**

> **产品已确认**：统计严格按**营业日**与**营业月**（原批注"自然月"为笔误）；但**界面文案用日常说法**（今天 / 最近 5 日 / 最近 3 月），**不出现"营业日/营业月"字样**。用户不需要理解营业日概念，只需数字正确。

| 项 | 后台口径 | UI 呈现 |
|----|----------|---------|
| 「今天」 | **当前营业日**（凌晨 2 点打开时是正在营业的这一日，不是自然日） | `今天` |
| 「最近 5/7/30 日」 | 最近 5 / 7 / 30 个**营业日**（跳过闭店日，§2.13.1a） | `最近5日` / `最近7日` / `最近30日` |
| 「最近 3 月」 | 最近 3 个**营业月**（≤92 个营业日） | `最近3月` |
| 自定义区间 | 同一**营业月**内的营业日区间 | 日历选日期 |
| 月度报表 / 归档卷 | **营业月**：`2026-10` = `[10-01 06:00, 11-01 06:00)` | 月份选择器 |
| 报表页脚 | 只显示「数据更新时间」 | **不显示"营业日"字样** |
| 技术日志 / 健康检查 | 可写 `BusinessDate` / 营业月 | —（内部使用） |

> **不做"按自然日的第二套聚合"**：两套口径并存会导致同一门店数字永远对不上，凌晨订单会被劈到两天。营业日是唯一基准，只是**不在 UI 上暴露这个概念**。
> **对账场景的内部说明**：若财务拿 POS 自然月账单来对，月末最后 6 小时会有归属差异——这是**客服话术**要准备的，不是 UI 要显示的内容。

### 13.9 日志管理（文件日志 + 数据库日志）

> **一句话**：**文件日志按天滚动、超期自动删；数据库日志（SQL Server 的 LDF / SQLite 的 WAL）只监控、不自动收缩。**
> 这两件事必须分开管——**把 LDF 当文件日志去定期删，是最典型的"把库搞坏"的方式。**

#### 13.9.1 应用文件日志（KDS 自己产生的）

**目录结构**（全部在数据盘，不占系统盘）

```
%ProgramData%\Kds\
├── data\                       # 数据库文件（SQLite 时）
├── backup\                     # 自动备份
└── logs\                       # ★ 文件日志根目录
    ├── app\        kds-app-20261021.log        应用主日志（含 TraceId）
    ├── http\       kds-http-20261021.log       入站/出站请求摘要（不含正文）
    ├── print\      kds-print-20261021.log      打印任务与失败原因
    ├── db\         kds-db-20261021.log         慢查询（> 200ms）
    ├── crash\      kds-crash-20261021.log      未处理异常 / 进程崩溃（保留更久）
    └── archive\                                 压缩后的历史日志（.zip）
```

**按天生成规则**

| 项 | 规则 |
|----|------|
| 文件命名 | `kds-<类别>-yyyyMMdd.log`，**日期取自门店时区**（不是 UTC，避免跨日错位） |
| 滚动时机 | **每天 00:00 本地时间滚动**（不是营业日边界——日志按自然日更符合排查直觉） |
| **跨日活文件** | 进程持续写入时，新的一天写新文件；**不重启**（用日期后缀判定，不靠文件句柄） |
| 单文件大小上限 | 100MB；超出则加序号 `kds-app-20261021-1.log`（防单日暴涨打满磁盘） |
| 编码 | UTF-8（无 BOM） |
| 格式 | **结构化单行 JSON**（便于 grep 与导入分析）：`{"ts":"2026-10-21T12:03:15.123+08:00","lvl":"Warn","cat":"Order","traceId":"...","msg":"..."}` |

**定期清理规则**

| 项 | 默认 | 说明 |
|----|:----:|------|
| **保留天数** | **30 天** | `LogRetentionDays`，最小 7 天（低于 7 天不允许保存） |
| **压缩** | 超过 **7 天**自动压缩为 `.zip` 移入 `archive\` | `LogCompressAfterDays`；压缩比通常 10:1，显著省空间 |
| **总容量上限** | **2048MB** | `LogMaxTotalMb`；超限时**从最老的开始删**（不管天数） |
| 崩溃日志保留 | **90 天** | 单独策略，供事后分析 |
| 清理时机 | 每日**维护窗口**（§2.13 营业日边界后） | **营业中不清理**，避免 IO 抖动 |
| 判定依据 | **按文件名中的日期**，不依赖文件修改时间 | 依赖 mtime 在拷贝/还原后会被改乱 |
| 删除方式 | 整文件删除，不截断 | — |

**内容规范（写日志时的红线）**

| 规则 | 原因 |
|------|------|
| ❌ **不记录密码、Token、`HqStoreToken`、连接串** | 日志会被导出给支持人员 |
| ❌ 不记录完整 POS 报文正文（只记 `EventType` + `EventId` + 长度） | 正文进 `EventLog` 表，日志只留索引线索 |
| ✅ 每条日志带 **`TraceId`** | 与 `EventLog` / `OperationLog` 串联 |
| ✅ 异常记**堆栈**但截断到 8KB | 防单条日志撑爆文件 |
| ✅ 级别生产默认 **Information**，可临时调 Debug（**24 小时后自动回落**，防忘记关） | Debug 会显著增加 IO |

**一键诊断包（支持排障用）**

```
管理端【导出诊断包】→ kds-diag-20261021-1203.zip
├── logs\*.log             最近 3 天（已脱敏：连接串/Token 替换为 ***）
├── health.json            健康检查快照
├── config-snapshot.json   配置快照（§11.7.6）
├── db-meta.json           表行数、库文件大小、LDF 使用率
└── manifest.txt           版本号、部署形态、终端清单
```

> **脱敏必须在打包时做**，不能指望用户自己删——现场没人会去删。

#### 13.9.2 SQL Server 数据库日志（LDF）—— **只监控，不自动收缩**

> **最重要的原则**：**LDF 不是"日志文件"，它是数据库的事务日志，直接 SHRINK 或删除会导致数据损坏或日志链断裂。KDS 永不自动收缩。**

**建库时一次性设定（KDS 建库脚本负责）**

| 设定 | 值 | 理由 |
|------|----|------|
| **恢复模式** | **`SIMPLE`（默认）** | 日志自动截断，**不需要日志备份**，不会因忘备份而涨满磁盘 |
| 日志文件 `MAXSIZE` | **4096MB** | 设上限，宁可报错也不要涨满整块盘（涨满盘会连带 POS 一起挂） |
| `FILEGROWTH` | **512MB** | 固定增量比百分比更可预测 |
| 日志文件位置 | **独立于数据文件的分区/磁盘** | IO 隔离 |

```sql
-- 建库参考（KDS 安装时执行）
ALTER DATABASE Kds_xxx SET RECOVERY SIMPLE;
ALTER DATABASE Kds_xxx MODIFY FILE (NAME = N'Kds_xxx_log', MAXSIZE = 4096MB, FILEGROWTH = 512MB);
```

**为什么默认 `SIMPLE` 而不是 `FULL`**

| 维度 | `SIMPLE` | `FULL` |
|------|----------|--------|
| 日志清理 | **自动截断**，无需干预 | **必须定期日志备份**，否则无限增长 |
| 时间点恢复 | ❌ 只能恢复到上次备份 | ✅ 可恢复到任意时刻 |
| 运维风险 | **低**（不会因忘记备份而爆盘） | **高**（最常见事故：忘配日志备份 → LDF 涨到几百 GB → 整台服务器不可用） |
| 对本项目的适配 | ✅ KDS 是**当日作业系统**，历史明细进归档卷（永久），SQL Server 只留 90 天热数据 | 仅在客户要求同城容灾时考虑 |

> **若客户强制要求 `FULL`**：**必须同时配置日志备份作业**（建议每小时一次），并在实施检查表中确认已生效。**没有日志备份作业就开 `FULL` = 定时炸弹**，这种情况一律拒绝。

**KDS 做什么 / 不做什么**

| 项 | KDS 行为 |
|----|----------|
| ✅ 建库时设恢复模式与 `MAXSIZE` | 一次性 |
| ✅ **每日检查 LDF 大小与使用率**，超阈值告警 | `DbLogWarnMb`（默认 2048MB） |
| ✅ **健康检查给出诊断**：若日志不再截断，查 `sys.databases.log_reuse_wait_desc` 并翻译成人话 | 见下方诊断表 |
| ✅ 提供管理端"数据库维护"页显示 LDF 状态 | 只读展示 |
| ❌ **自动 `SHRINKFILE`** | 会产生碎片，且日志很快又涨回去 |
| ❌ **删除/改名 `.ldf` 文件** | 直接损坏数据库 |
| ❌ 自动切换恢复模式 | 属于 DBA 决策 |

**LDF 异常增长的诊断表（写进健康检查提示）**

| `log_reuse_wait_desc` | 含义 | 处置 |
|----------------------|------|------|
| `LOG_BACKUP` | 等着做日志备份 | 若恢复模式是 `FULL` 且无日志备份作业 → **改 `SIMPLE` 或补上日志备份** |
| `ACTIVE_TRANSACTION` | 有长事务未提交 | 查最长事务（`sys.dm_tran_active_transactions`）；**检查归档 MOVE 是否忘了分批提交** |
| `REPLICATION` / `AVAILABILITY_REPLICA` | 有复制/可用性组未同步 | 联系 DBA |
| `CHECKPOINT` | 尚未 checkpoint | 正常，稍等 |
| `NOTHING` | 无阻塞，日志可重用 | 正常 |

> **和性能设计的呼应**：归档 MOVE **必须分批提交**（每 5000 行一次）。长事务不提交会阻止日志截断，这是 KDS 自己最可能造成 LDF 异常增长的原因。

**每日自动核对（防事后被改）**

客户的 DBA 或 POS 厂商做备份策略时，**很可能事后把恢复模式改成 `FULL`**，而 KDS 收不到任何通知。因此每日维护窗口（§13.9.4 第 ③ 步）自动核对两项：

| 检查项 | 判定 | 级别 | 提示 |
|--------|------|:----:|------|
| `DB_RECOVERY_MODE_CHANGED` | 实际恢复模式 ≠ `StoreConfig.SqlServerRecoveryMode` | **Warn** | "数据库恢复模式已变为 FULL。若无日志备份作业，LDF 会持续增长直至磁盘满，请确认" |
| `DB_LOG_GROWING` | LDF 大小 > `DbLogWarnMb`（默认 2048MB） | **Warn** | 附带 `log_reuse_wait_desc` 的翻译与处置建议（见上表） |

> 这两个检查**只告警、不自动改**——恢复模式是 DBA 决策，KDS 擅自改可能破坏客户既有的备份策略。

#### 13.9.3 SQLite 数据库日志（WAL）—— 自动管理

| 项 | 规则 |
|----|------|
| 相关文件 | `.db-wal`（写前日志）、`.db-shm`（共享内存索引） |
| **自动 checkpoint** | `wal_autocheckpoint` 默认 1000 页（约 4MB）；无需干预 |
| **定期强制回收** | 维护窗口执行 `PRAGMA wal_checkpoint(TRUNCATE)`，把 WAL 截断为空 |
| 告警阈值 | WAL 文件 > **200MB** → 说明 checkpoint 失效（可能有长读事务），告警 |
| 备份 | **不备份 WAL**；用 `VACUUM INTO` 生成一致性快照文件（§性能设计 §2.1） |
| ❌ 禁止 | 手工删除 `.db-wal` 文件（会丢已提交事务） |

#### 13.9.4 统一清理调度（每日维护窗口）

```
营业日边界后 + MaintenanceWindowStartMinute（默认 30 分钟）开始
│
├─ ① 文件日志：滚动 → 压缩 >7 天 → 删除 >30 天 / 超总容量
├─ ② SQLite：wal_checkpoint(TRUNCATE) → incremental_vacuum
├─ ③ 数据库日志检查：LDF 大小与 log_reuse_wait_desc（SQL Server）/ WAL 大小（SQLite）→ 超阈值告警
├─ ④ 数据保留清理：L1 明细 90 天 → 归档卷；L2 订单头 1 年；L4 日志表 30~180 天（§13.6）
├─ ⑤ 统计聚合：生成昨日 DailyStoreStat / DailyDimStat
└─ ⑥ 写维护记录（成功/失败/耗时/删除量），失败则健康检查报错
```

| 约束 | 说明 |
|------|------|
| **互斥执行** | 六步串行，**不并发**（SQLite 单写者，并发只会互相等） |
| **单项超时** | 每步 10 分钟超时；超时记 `Warning` 并继续下一步（不能因为清日志卡住整个维护） |
| **幂等** | 每一步都可重复执行无副作用 |
| **营业中不跑** | 若检测到窗口内有活动订单，**跳过并顺延**（不硬跑） |
| **失败可见** | 维护失败必须进健康检查页，**不能静默** |

#### 13.9.5 配置项（落 `StoreConfig`）

| 字段 | 默认 | 说明 |
|------|:----:|------|
| `LogRetentionDays` | **30** | 文件日志保留天数（最小 7） |
| `LogMaxTotalMb` | **2048** | 日志目录总容量上限，超限从最老删 |
| `LogCompressAfterDays` | **7** | 超过 N 天压缩归档 |
| `CrashLogRetentionDays` | **90** | 崩溃日志保留天数 |
| `LogLevel` | `Information` | 生产默认；调 Debug 后 **24h 自动回落** |
| `SlowQueryThresholdMs` | **200** | 慢查询日志阈值 |
| `DbLogWarnMb` | **2048** | 数据库日志（LDF/WAL）告警阈值 |
| `SqlServerRecoveryMode` | `SIMPLE` | 仅作记录与检查；实际由建库脚本设定 |
| `MaintenanceWindowStartMinute` | 30 | 已在 §9.1 |

#### 13.9.6 磁盘空间保护（最终防线）

| 措施 | 说明 |
|------|------|
| 日志目录独立 | 放数据盘，不与数据库同分区争空间 |
| 分层告警 | 磁盘可用 < 20% 告警、< 10% 严重、< 5% **写入保护**（暂停非关键日志写入，只留 Error） |
| LDF `MAXSIZE` | 宁可 SQL Server 报"日志已满"（可恢复），也不要涨满整块盘（连带 POS 挂） |
| 清理优先级 | 磁盘告急时：**压缩归档 → 删最老日志 → 删归档备份副本**；**永不删数据库文件** |


### 13.10 数据库初始化：自动建库与图形化配置

> **结论先给**：
> **SQLite = 全自动**（文件不存在就建库 + 迁移 + 种子，用户零操作）。
> **SQL Server = 图形化向导**（指定连接 → **检测** → 选择"自动建库"或"使用已有库" → 执行）。
> **绝不要求实施人员手敲 `CREATE DATABASE` 脚本**——那正是最容易漏掉 `SIMPLE` / `MAXSIZE` / `RCSI` 的环节（§13.9.2）。

#### 13.10.1 SQLite：全自动建库

**首次启动流程（用户零操作）**

```
启动
 ├─ 读 %ProgramData%\Kds\connection.json
 │   └─ 无 / provider = Sqlite
 ├─ 检查 %ProgramData%\Kds\data\kds.db
 │   ├─ 不存在 → ① 建目录  ② 建库文件（page_size=4096, auto_vacuum=INCREMENTAL）
 │   │          ③ EF Core 迁移（26 张表） ④ 写种子  ⑤ 记日志
 │   └─ 存在   → 比对 __EFMigrationsHistory 与程序内置版本
 │               ├─ 一致 → 正常启动
 │               └─ 落后 → ① 自动备份（VACUUM INTO）② 迁移 ③ 失败则回滚到备份并拒绝启动
 └─ 启动 Kestrel + 加载内存投影
```

| 规则 | 说明 |
|------|------|
| 目录权限 | 首次创建时校验运行账号可写；不可写则弹"请以管理员运行一次"并退出 |
| **迁移前必须备份** | `backup\pre-migrate-yyyyMMddHHmmss.db`，保留最近 5 份 |
| 迁移失败 | **还原备份 + 拒绝启动**（不允许带着半迁移的库对外服务） |
| 幂等 | 重复启动不重建、不重复写种子（种子按业务键判存在） |
| 建库参数 | `page_size` / `auto_vacuum` **创建后不可改**，必须在建库时定死（§性能设计 §3.1） |

#### 13.10.2 SQL Server：图形化向导（**含检测**）

**触发时机**：Master 启动时检测到 `connection.json` 缺失 / provider 为 SqlServer 但连不上 / 用户主动打开 `Kds.DbSetup.exe`。

**向导五步**

                                    [ 测试连接 ]
【第 3 步】检测结果（逐项 ✓ / ✗ / ⚠）   ← 见 13.10.3

   ● 自动建库（需要 dbcreator 权限）
        ☑ 恢复模式设为 SIMPLE

【第 5 步】执行（带进度与结果）
   创建数据库 Kds_S001 ………………… ✓

   开启 RCSI ……………………………… ✓

#### 13.10.3 检测项清单（**不是"连接失败"四个字，而是逐项可读**）

| # | 检测项 | 判据 | 失败时的可读提示 |
|:-:|--------|------|------------------|
| 1 | **网络可达** | TCP 连目标端口（默认 1433；命名实例走 SQL Browser UDP 1434 解析） | "无法连接 `192.168.1.10:1433`（超时 3s）。请确认：① 实例已启动 ② 防火墙放行 1433 ③ 命名实例需开 SQL Browser" |
| 2 | **登录成功** | 用给定凭据 Open 连接 | "登录失败：账号或密码错误 / 该账号被禁用 / 仅允许 Windows 认证" |
| 3 | **实例版本** | `SERVERPROPERTY('ProductVersion')` | "实例版本 10.0（SQL Server 2008），**KDS 最低要求 2012**。方案见 §8.3.4（首选：门店改用 SQLite）" |
| 4 | **实例版本上限提示** | 2012/2014 | "实例为 2012/2014，可运行但不推荐（建议 2016+）"（**Warn 不阻断**） |
| 5 | **建库权限** | `HAS_PERMS_BY_NAME(NULL,NULL,'CREATE ANY DATABASE')=1` 或 `IS_SRVROLEMEMBER('dbcreator')=1` | "当前账号无建库权限。可改用【使用已有库】，或请 DBA 授予 `dbcreator`" |
| 6 | **目标库是否已存在** | `DB_ID(@db) IS NOT NULL` | 已存在 → "库已存在：将执行迁移（不改恢复模式）。若要重建请先确认数据" |
| 7 | **库内权限**（使用已有库时） | 该库 `db_owner` 或建表权限 | "账号对该库无足够权限，迁移会失败。请授予 `db_owner`" |
| 8 | **磁盘空间** | 目标实例默认数据目录所在盘剩余 | "`D:\` 剩余 1.2GB（建议 ≥ 2GB）。日志与数据将持续增长" （Warn） |
| 9 | **排序规则** | `DATABASEPROPERTYEX(...,'Collation')` | 已存在库 → 展示实际 collation 供核对（不影响功能，仅提示） |
| 10 | **加密/TLS** | 尝试加密连接 | "服务器不支持加密连接，已降级为明文（内网可接受；跨网段请升级实例证书）"（Warn） |
| 11 | **RCSI 现状** | `is_read_committed_snapshot_on` | 已存在库且为 0 → "建议开启（需独占连接），否则报表会阻塞划单"（Warn + 一键开启按钮） |
| 12 | **恢复模式现状** | `recovery_model_desc` | 已存在库且为 `FULL` → "该库为 FULL 模式。**若无日志备份作业，LDF 会无限增长**（§13.9.2）。建议改 SIMPLE 或确认已配日志备份"（**Warn + 需勾选确认**） |

> **Warn 与 Error 的区分**：Error（1/2/3/5/7）**阻断**建库；Warn（4/8/9/10/11/12）**不阻断但必须显示，并在实施单上签收**。

#### 13.10.4 自动建库执行的完整脚本（**由程序执行，人不用敲**）

```sql
-- ① 建库（排序规则显式指定，不继承实例默认）
CREATE DATABASE [Kds_S001] COLLATE Chinese_PRC_CI_AS;

-- ② 恢复模式 SIMPLE（日志自动截断，无需日志备份作业）
ALTER DATABASE [Kds_S001] SET RECOVERY SIMPLE;

-- ③ 日志文件上限与增长方式（防止涨满整块盘）
ALTER DATABASE [Kds_S001] MODIFY FILE (
    NAME = N'Kds_S001_log', MAXSIZE = 4096MB, FILEGROWTH = 512MB);

-- ④ 读写不互斥（报表不阻塞划单）
ALTER DATABASE [Kds_S001] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;

-- ⑤ EF Core 迁移（29 张表 + 72 索引）
-- ⑥ 种子数据（StoreConfig / 5 个语音模板 / 3 个打印模板）
```

| 规则 | 说明 |
|------|------|
| **幂等** | 每步先判存在；重复执行为 no-op |
| **顺序固定** | ②③④ 必须在迁移**之前**（否则迁移期间的高并发写会狂涨日志） |
| **④ 需独占** | `RCSI ON` 会短暂独占库；**新建库时无用户，无影响**；已存在库时要提示"需短暂独占" |
| **失败不删库** | 建库中途失败**不自动 DROP**（怕误删客户数据）；保留半成品并提示手工处理 |
| **建完立刻自检** | 建完库自动跑 §13.10.3 的第 11/12 项反向确认（应显示 SIMPLE + RCSI=1）**并截图存档** |

#### 13.10.5 连接信息保存（**不进数据库、不明文**）

> 鸡生蛋问题：连接信息不能存在数据库里。所以独立文件 + 加密。

```
%ProgramData%\Kds\connection.json
{
  "schemaVersion": 1,
  "provider": "SqlServer",              // 或 "Sqlite"
  "server": "192.168.1.10\\SQLEXPRESS",
  "database": "Kds_S001",
  "authMode": "SqlLogin",               // SqlLogin / Windows
  "user": "kds_user",
  "passwordProtected": "AQAAANCMnd8BFdERjHoAwE...",   // DPAPI 加密后的 Base64
  "encrypt": true,
  "configuredAt": "2026-10-21T09:12:33+08:00",
  "configuredBy": "SETUP-TOOL",
  "sqlitePath": null
}
```

| 规则 | 说明 |
|------|------|
| **密码用 DPAPI 加密** | `ProtectedData.Protect(..., DataProtectionScope.LocalMachine)`；同一台机器可解，**拷贝到别的机器解不开**（也防止配置文件外泄直接可用） |
| 文件 ACL | 仅 **运行账号 + Administrators** 可读 |
| **不写进 `appsettings.json`** | 避免被运维模板覆盖、被 Git 提交 |
| 环境变量覆盖 | 支持 `KDS_DB_CONNECTION`（自动化部署/Docker secret 用），**优先级高于文件** |
| 改配置需停服 | 运行时**只允许检测**，不允许改（改后必须重启 Master）；修改入口是独立的 `Kds.DbSetup.exe` |
| 明文日志禁令 | 日志与诊断包中，连接串与密码一律替换为 `***`（§13.9.1） |

#### 13.10.6 管理端 vs 独立工具的分工

| 能力 | 管理端（运行中） | `Kds.DbSetup.exe`（停服） |
|------|:---------------:|:-------------------------:|
| 查看当前连接信息（密码掩码） | ✅ | ✅ |
| **检测连接与健康项**（§13.10.3 全 12 项） | ✅ **只读检测** | ✅ |
| 修改连接参数 | ❌ | ✅ |
| 自动建库 / 迁移 | ❌ | ✅ |
| 备份 / 还原 | ✅ | ✅ |
| 切换 SQLite ↔ SQL Server | ❌ | ✅（含数据迁移向导，§选型指南 6） |

> **为什么改连接必须停服**：运行中切换数据源会导致内存投影与库不一致、Outbox 待发表错乱。**宁可让实施多跑一个工具，也不要运行期换库。**



### 13.11 登录与账号体系

> **身份模型分两层，不要混在一起**：
> **① 屏级登录（长期会话）** —— 这块屏"归谁管"。首次登录，之后**无感自动登录**，除非手动退出。
> **② 当前操作人（可快速切换）** —— 这一手"具体是谁划的"。屏上点选，不验证密码。
> 两者都要，因为**一块屏常有多个师傅轮流用**，但每天让每人退出再登录是不可接受的。

#### 13.11.1 三类访问者的认证方式

| 访问者 | 首次 | 之后 | 会话形态 |
|--------|------|------|----------|
| **作业屏（切配/制作/传菜/综合屏）** | **必须登录**（账号 + 密码/PIN） | **无感自动登录**（持长期令牌，打开即用） | **屏会话**：长期（默认 30 天，可配"永久"），无闲置超时 |
| **管理端** | 必须登录 | **不做无感**（每次浏览器新开需登录） | **管理会话**：闲置 30 分钟 + 绝对 12 小时 |
| **`Kds.DbSetup.exe`** | Windows 管理员身份（UAC 提权） | — | 本机进程，无会话 |

**为什么作业屏要登录，但要能无感**

| 若完全不登录（旧方案） | 若每次都要登录 | **本方案** |
|---|---|---|
| 不知道这块屏归谁管，令牌/权限无法落地 | 师傅嫌麻烦 → **一直挂着别人账号** → 审计全错 | 首次配一次，之后无感；**退出才需重登** |

> **"无感"是安全与可用的折中**：屏是**固定工位设备 + 物理在场**，长期令牌的风险可控；而"每次输密码"必然被现场绕过，反而更不安全。
> **管理端不做无感**：它可能在办公室或远程访问，必须短会话。

#### 13.11.2 屏会话与无感登录（**核心机制**）

**令牌形式：不是"记住密码"，是设备令牌（Device Token）**

| 项 | 设计 |
|----|------|
| 令牌内容 | **随机不透明串**（32 字节 Base64Url）；服务端只存 **SHA256 哈希**（`UserSession.TokenHash`），**不存明文** |
| **绑定终端** | 令牌与 `TerminalId` + `DeviceKey` 绑定；**拷到别的机器直接失效**（这是把 localStorage 泄露风险压住的关键） |
| 有效期 | `ScreenSessionDays`（默认 **30 天**，可配 7~365，**0 = 永久直到手动退出**） |
| **轮转** | 每次自动登录成功 → **签发新令牌、作废旧令牌**（`ScreenTokenRotation` 默认开）；被窃取的旧令牌只能用一次且立即暴露 |
| 闲置超时 | **无**（屏是常开的，闲置超时会导致上班第一件事是重新登录） |
| 存储位置 | 浏览器：`localStorage`（见下方风险说明）；Win 客户端：本地文件 + **DPAPI 加密**（更安全） |
| 存储内容 | 只存令牌串与 `terminalCode`，**绝不存密码** |

**自动登录流程**

```
打开作业屏
  ├─ 读本地 deviceToken
  │   ├─ 无 → 【登录页】（屏版）
  │   └─ 有 → POST /api/Auth/DeviceLogin { deviceToken, terminalCode, deviceKey }
  │            ├─ ✅ 成功 → 换发新令牌 → 直接进作业屏（无感，< 300ms）
  │            └─ ❌ 失败 → 清本地令牌 → 【登录页】+ 说明原因
  └─ 进屏后：右上角显示"当前：张师傅 [换人] [退出登录]"
```

| 自动登录失败原因 | 处理 |
|------------------|------|
| 令牌过期（超 30 天） | 回登录页，提示"登录已过期，请重新登录" |
| 令牌被撤销（管理端踢下线 / 手动退出） | 回登录页 |
| 账号被停用 / 改了密码 | 回登录页，提示"账号状态已变更" |
| **终端不匹配**（换了机器 / `DeviceKey` 重置） | 回登录页，提示"本终端需重新绑定" |
| 服务端不可达 | **允许进入"只读离线态"**：显示上次缓存的屏数据 + 顶部黄条"未登录/离线"，**禁止所有写操作**；恢复后自动重试 |

> **最后一条很重要**：如果 Master 临时重启或网络抖动就让屏退回登录页，师傅会以为系统坏了。所以**离线时降级为只读**，恢复后自动无感登录成功，用户无感。

**"记住密码"式的风险与缓解**

| 风险 | 缓解 |
|------|------|
| 浏览器 `localStorage` 被 XSS 读取 | ① 令牌**绑定终端**，换机无效；② 每次登录**轮转**；③ 管理端可**远程撤销**；④ 屏不渲染任何用户输入的 HTML（无富文本/无外链） |
| 屏被偷走 | 令牌绑定 `DeviceKey`，换机器失效；管理端可立即撤销 |
| 离职员工仍持有令牌 | Owner 在管理端**停用账号 → 所有会话立即失效**（§13.11.4） |

**为什么允许 localStorage**：屏必须能"打开即用"，令牌必须落在客户端。既然无法避免，就把它的**可用性压到最低**（绑终端 + 轮转 + 可撤销 + 停用即失效）。Win 客户端走 DPAPI 加密文件，是更优路径——**有条件的门店优先用 Win 客户端**。

#### 13.11.3 手动退出（**唯一需要重新登录的动作**）

| 行为 | 说明 |
|------|------|
| 位置 | 屏右上角【退出登录】，点击后**确认一次**（防误点） |
| 动作 | ① 服务端**撤销该会话**（`UserSession.RevokedAt`）② 清本地令牌 ③ 回登录页 |
| 提示 | "已退出，下次打开需重新登录" |
| ❌ 不做 | 不清令牌只回登录页（下次又自动登录 = 假退出） |
| 交接班 | 若是**同一块屏换人（不是换账号）**，用【换人】即可，**不必退出登录** |

#### 13.11.4 会话管理（Owner 可远程踢下线）

管理端【在线会话】页：

| 列 | 内容 |
|----|------|
| 终端 / 设备 | `TerminalCode` + `TerminalName` |
| 登录账号 | `DisplayName (UserName)` |
| 会话类型 | 屏会话 / 管理会话 |
| 最后活动 | `LastSeenAt` |
| 到期 | `ExpiresAt` |
| 操作 | **【强制下线】**（撤销会话） |

| 规则 | 说明 |
|------|------|
| 谁可强制下线 | **Owner**（Manager 只看不可操作） |
| 停用账号 | **该账号所有会话立即失效**（不等过期） |
| 改密码 | 同上，**所有会话立即失效** |
| 改角色 | 同上（避免旧会话带着旧权限继续用） |
| 删除/重置终端 `DeviceKey` | 该终端所有屏会话失效 |

#### 13.11.5 角色与权限（V1 三级 + 屏账号）

**账号类型（`AccountType`）**

| 类型 | 能登录 | 有密码 | 说明 |
|------|--------|:------:|------|
| **`Admin`** | 管理端 ✅ + 作业屏 ✅ | ✅ | 店长、值班经理、只看数的老板 |
| **`Operator`** | **仅作业屏** ✅ / 管理端 ❌ | ✅ | 师傅、传菜员——**用于屏登录** |

| 角色 | 能做什么 | 不能做什么 |
|------|----------|-----------|
| **`Owner`（店长 / 管理员）** | 全部配置、账号管理、报表、撤销他人操作、数据库设置 | — |
| **`Manager`（值班经理）** | 报表、撤销、报损、沽清申请、恢复已清理、补打、导诊断包 | ❌ 改档口/屏/菜单/账号、❌ 数据库设置 |
| **`Viewer`（老板看数）** | 只看报表与看板 | ❌ 任何写操作 |

| 权限点 | Owner | Manager | Viewer | Operator（屏账号） |
|--------|:-----:|:-------:|:------:|:------------------:|
| 作业屏划单 / 撤销**自己**的操作 | ✅ | ✅ | ❌ | **✅** |
| 屏上换人 | ✅ | ✅ | ❌ | ✅ |
| 查报表 / 看板 | ✅ | ✅ | ✅ | ❌ |
| 撤销**他人**操作 | ✅ | ✅ | ❌ | ❌ |
| 报损 / 沽清申请 / 恢复已清理 | ✅ | ✅ | ❌ | ❌ |
| 补打单据 | ✅ | ✅ | ❌ | ❌ |
| 改档口 / 屏绑定 / 菜单 / 模板 | ✅ | ❌ | ❌ | ❌ |
| 账号管理 / 在线会话 | ✅ | ❌ | ❌ | ❌ |
| 数据库设置 / 备份还原 | ✅ | ❌ | ❌ | ❌ |
| 导出诊断包 | ✅ | ✅ | ❌ | ❌ |

> **`Operator` 的权限边界就是"划单 + 撤自己的"**——它拿不到任何管理端能力，即使令牌泄露影响也有限。
> **V1 不做"按档口的数据权限"**；**V2** 若上总部多店再引入。

#### 13.11.7 会话令牌的技术约束

| 项 | 屏会话 | 管理会话 |
|----|--------|----------|
| 载体 | `localStorage`（浏览器）/ DPAPI 文件（Win 客户端） | **`httpOnly` + `SameSite=Lax` Cookie** |
| 服务端记录 | `UserSession` 表（存哈希） | 同表 |
| 闲置超时 | **无** | 30 分钟（滑动续期） |
| 绝对上限 | `ScreenSessionDays`（30 天 / 0=永久） | **12 小时** |
| 轮转 | 每次自动登录换新 | 登录时签发 |
| 撤销 | 手动退出 / 踢下线 / 停用 / 改密 / 改角色 | 同 |
| CSRF | 不适用（非 Cookie） | 写操作要求 `X-Kds-Request: 1` 头 |
| 令牌可见性 | 客户端可见（不可避免） | 不可被 JS 读取（httpOnly） |

#### 13.11.8 初始密码与口令策略

| 项 | 规则 |
|----|------|
| 初始管理员 | §13.12 向导创建，**强制设置非默认密码**（禁止 `admin/123456`） |
| 密码长度 | `Admin`：**≥ 8 位**（`PasswordMinLength`）；**`Operator`：≥ 6 位，允许纯数字/PIN**（`AllowScreenPinLogin` 关闭时 ≥ 8 位且含字母） |
| 复杂度 | 默认要求字母 + 数字（`PasswordRequireComplex`）；**PIN 模式跳过** |
| 存储 | **PBKDF2-HMAC-SHA256（≥ 100,000 次）或 Argon2id**，每账号独立盐，存 `PasswordIterations` 便于日后升级 |
| 重置 | Owner 可重置他人密码（生成临时密码，**首登强制修改**）；**Owner 忘密码** → 本机 `Kds.DbSetup.exe` 的"重置管理员"（需 UAC） |
| 改密后 | **该账号所有会话（含屏会话）立即失效** → 屏会回登录页 |

> **为什么 Owner 忘密码要靠本机工具**：否则只能留后门（万能密码/重置链接），而后厨门店没有邮件系统。本机 + UAC 提权是唯一可信路径，且要求物理在场。

#### 13.11.9 「换人」与登录的关系（**两个概念，都要**）

| | 屏登录 | 【换人】 |
|---|--------|----------|
| 粒度 | **一块屏 = 一个长期会话** | **一次操作 = 一个人** |
| 验证 | 首次要密码/PIN | **不验证**，点选即切 |
| 变更频率 | 极低（除非手动退出） | 每班多次 |
| 审计用途 | 谁有权操作这块屏 | `OperationLog.OperatorName` |

```
┌──────────────────────────────────────────┐
│ 切配屏1        TERM-001    张师傅 [换人] [退出]│
└──────────────────────────────────────────┘
```

| 行为 | 说明 |
|------|------|
| 点【换人】 | 弹 `Operator` 名单（`IsRosterVisible = 1`），点选即切，**不验证密码** |
| 切换后 | 后续 `OperationLog.OperatorName` 记新名字；`UndoRequireSameOperator` 也用它 |
| 名单为空 | 隐藏【换人】，用登录账号的 `DisplayName` |
| **审计红线** | `OperatorName` **只作标注，不得据此做权限判断**——权限看的是**登录会话的账号与角色** |

> **这个区分是刻意的**：登录解决"谁能用这块屏"，换人解决"这一手是谁做的"。前者必须可信（要密码），后者只需诚实（点一下）。

#### 13.11.10 账号创建：**按角色分组，表单随角色变**

> **不做一个"什么都能填"的通用表单**——不同角色的必填项与风险完全不同，混在一起会让店长填错（例如给传菜员配了 `Owner`）。

**创建入口按角色分两组**

| 组 | 角色 | 入口 | 数量级 |
|----|------|------|--------|
| **管理角色** | `Owner` / `Manager` / `Viewer` | 管理端 → 账号管理 → 【新建管理账号】 | 1~5 个 |
| **屏账号** | `Operator` | 管理端 → 终端配置 → **【为本屏创建账号】** 或 账号管理 → 【新建屏账号】 | 每屏 1 个 + 换人名单 N 个 |

**表单随角色变化的必填项**

| 字段 | Owner | Manager | Viewer | Operator |
|------|:-----:|:-------:|:------:|:--------:|
| 账号 `UserName` | ✅ | ✅ | ✅ | ✅（建议用工号） |
| 显示名 `DisplayName` | ✅ | ✅ | ✅ | ✅ |
| 密码 / PIN | ✅ ≥8 位 | ✅ ≥8 位 | ✅ ≥8 位 | ✅ **≥6 位或 4~6 位 PIN** |
| 手机（可选） | ⚪ | ⚪ | ⚪ | ❌ 不显示 |
| **岗位 `Position`** | ❌ | ❌ | ❌ | ⚪（切配/制作/传菜/打荷…） |
| **可登录的屏** | ❌ | ❌ | ❌ | ⚪ 默认"全部绑定终端" |
| 是否进换人名单 | ❌ | ❌ | ❌ | ✅ `IsRosterVisible` |

**两条必须的校验**

| 校验 | 说明 |
|------|------|
| **至少 1 个启用的 `Owner`** | 停用/删除最后一个 Owner 时**拒绝**并提示"至少保留一个店长账号" |
| **`Viewer` 不给任何写权限** | UI 上直接隐藏写操作按钮，不只是接口拒绝（避免"点了报错"） |

**创建屏账号的推荐动线**（解决"配完终端还要跳去建账号"的绕路）

```
管理端 → 终端配置 → 某终端行 → 【创建屏账号】
  → 预填：账号 = 终端编码小写（term-001）、显示名 = 终端名、可登录屏 = 本终端
  → 只填密码/PIN → 保存 → 提示"请到该屏登录一次以启用无感登录"
```

#### 13.11.11 从 POS 同步员工（**可选，只同步身份不同步密码**）

> **结论：可以同步，而且很该做——但只能同步"人"和"角色映射"，密码/PIN 必须 KDS 自己设。**

**为什么该做**

| 若 KDS 手工维护 | 后果 |
|------------------|------|
| POS 有员工管理，KDS 再建一遍 | **两处维护**，改名/离职不同步 |
| 离职员工在 POS 删了，KDS 还留着 | **离职的人还能划单**（安全洞） |
| 新员工入职要教两次 | 实施成本 |

**为什么不能同步密码（三条硬理由）**

| # | 理由 |
|:-:|------|
| 1 | POS 的密码哈希算法**未知且不可迁移**，KDS 无法复用 |
| 2 | 要 POS 传**明文密码**是严重安全问题（明文在网线上跑） |
| 3 | 若做"KDS 调 POS 验证"（SSO），就把 KDS 的可用性**绑在 POS 上**——POS 挂了后厨登不进屏，直接违背"POS 挂了 KDS 照样做菜"的设计目标 |

> **所以：POS 给"是谁、什么角色、是否在职"，KDS 自己管"怎么证明是他"。**
> 首次同步来的账号 `MustChangePassword = 1`，需设一次 PIN；之后无感登录。

**同步模型**

| 项 | 设计 |
|----|------|
| 方向 | **单向 POS → KDS**（POS 是员工主数据权威） |
| 触发 | ① 事件推送 `Staff.Sync`（增量，POS 变更时推）；② KDS 每日定时拉取一次（兜底，防推送丢失） |
| 匹配键 | `ExternalId`（POS 员工ID）或 `工号`；匹配不到则**新建** |
| **不物理删除** | POS 删人 → KDS `IsEnabled = 0` + **撤销该账号所有会话**（不删行，保审计） |
| 冲突处理 | **同步来的字段以 POS 为准**，KDS 专属字段（密码、`IsRosterVisible`）**不被覆盖** |
| 字段级归属 | 见下表 |

**字段级归属（谁说了算）**

| 字段 | 归属 | 说明 |
|------|------|------|
| `UserName` / `DisplayName` / `Position` | **POS** | KDS 只读，改了下次同步会被覆盖（UI 置灰） |
| `IsEnabled` | **POS** | POS 离职 → KDS 停用 |
| `Role` | **映射结果**（见下） | — |
| **`PasswordHash` / PIN** | **KDS** | 绝不从 POS 取 |
| `IsRosterVisible` | **KDS** | 门店自己决定谁出现在换人列表 |
| `AccountType` | **KDS**（按角色映射） | — |

**角色映射（必须可配，因为每家 POS 角色命名不同）**

```
StoreConfig.PosRoleMapJson =
{
  "服务員":   "Viewer",      // 或 Owner，看门店
  "收银员":   "Viewer",
  "值班经理": "Manager",
  "店长":     "Owner",
  "厨师":     "Operator",
  "打荷":     "Operator",
  "传菜员":   "Operator"
}
```

| 规则 | 说明 |
|------|------|
| 未映射的 POS 角色 | **默认映射为 `None` → 不同步**（宁缺勿错，避免把服务员变成 Owner） |
| 映射结果在管理端**可见可改** | 同步来的账号显示"角色来自 POS 映射：厨师 → Operator" |
| **手工提权允许但要标记** | 若把 POS 来的 `Operator` 手工改成 `Manager`，下次同步**不被覆盖**（记 `RoleOverriddenByAdmin = 1`），并在列表里标"已手工调整" |

**三种员工维护模式（`StaffSource`）**

| 模式 | 适用 | 行为 |
|------|------|------|
| **`Local`（默认）** | POS 不支持员工同步 / 小店 | 全部手工建，无同步 |
| **`Pos`** | POS 有员工接口 | 定时同步；KDS 侧只能改密码与名单可见性 |
| `PosWithLocalExtra` | POS 只有后厨员工，前厅不在 | 同步来的只读 + 允许新建 `Source = Local` 的额外账号 |

**同步的验收要点**

| # | 验收 | 通过标准 |
|:-:|------|----------|
| 1 | POS 改名 → 同步 | KDS 显示名更新，**密码不变、会话不断** |
| 2 | POS 离职 → 同步 | 账号 `IsEnabled = 0`，**会话立即失效**（离职的人立刻登不进屏） |
| 3 | POS 新增员工 → 同步 | KDS 出现账号，`MustChangePassword = 1` |
| 4 | POS 角色改名（不在映射表） | **不同步**，并在健康检查提示"有 N 个 POS 角色未映射" |
| 5 | 同步来的账号改密码 | 下次同步**不覆盖密码** |
| 6 | POS 不可达 | 同步失败**不影响营业**，用上次数据，健康检查报 Warn |

> **第 6 条很重要**：员工同步是"锦上添花"，**绝不能因为 POS 拿不到员工数据就让屏登不进去**。已有的账号与会话必须继续有效。

#### 13.11.12 账号与终端的对应关系：**不做限制**

> **决定（v6.77）**：**任何可登录的账号都能登录任意一块作业屏**，不做"这个师傅只能登切配屏"的绑定。

| 项 | 决定 |
|----|------|
| 账号 ↔ 终端 | **不限制**（`Operator` 可登任何屏） |
| 是否加 `AllowedTerminalIds` 字段 | ❌ **V1 不加**（避免建了不用） |
| 将来若要加 | 加一个逗号分隔的 `AllowedTerminalIds`（空 = 全部）即可，**不改表结构** |

**为什么不限制**

| 理由 | 说明 |
|------|------|
| 门店人少 | 一个档口常常就 1~2 人，互相帮工是常态 |
| 硬限制会添乱 | 忙时"我只想在这块屏划一下"却被告知无权 → 现场必然要求开权限 |
| **限制点不在这里** | 真正决定"能看什么、能做什么"的是**终端配置**，不是账号（见下） |

**关键区分：限制的是"这块屏能做什么"，不是"谁能登这块屏"**

| 层级 | 决定什么 | 配置在哪 |
|------|----------|----------|
| **终端级（屏幕权限）** | 这块屏**能看到哪些阶段/档口的菜**、能否划单 | `TerminalConfig.Role` / `StationIds` / `EnableOperate` |
| **账号级（操作权限）** | 能做什么**类型的操作**（划单 / 撤销 / 报损 / 改配置 / 看报表） | `UserAccount.AccountType` + `Role` |

**两者叠加的效果（天然形成约束）**

| 谁登录 | 在哪块屏 | 实际能做什么 |
|--------|----------|-------------|
| `Operator` 张师傅 | **切配屏**（`Role = Prep`） | 只能划切配阶段的品项 |
| `Operator` 张师傅 | **制作屏**（`Role = Cook`） | 只能划制作阶段的品项 |
| `Operator` 张师傅 | **只读综合屏**（`EnableOperate = 0`） | **什么都不能划** |
| `Operator` 张师傅 | 管理端 | **登不进去**（`Operator` 无管理端权限） |

> **所以"不限制登录"≠"没有约束"**：约束由**终端角色**天然施加。炒锅师傅登到切配屏，看到的只有切配阶段的菜，他划的也是切配的活——这本来就是他想帮的忙。

**审计仍然可追溯**

```
OperationLog = TerminalId + OperatorName + FromStage + ToStage + OccurredAt
```

即使同一账号在多块屏上操作，**"在哪块屏、哪个阶段、由谁标注"三件都留痕**，不因不限制登录而丢失。

**换人名单的尺度**

| 项 | 规则 |
|----|------|
| 显示范围 | **全部** `IsRosterVisible = 1` 的 `Operator`（不按屏过滤） |
| 人数多时 | 按 `Position`（岗位）**分组展示** + 支持输入过滤（如"张"）；**不做强制过滤** |
| 为什么不按屏过滤 | 与"不限制登录"同源：帮工是常态，名单过滤反而挡住人 |


### 13.12 首次初始化向导（**登录之前**）

> **定位**：系统**第一次启动**时，库还是空的、没有账号，所以**必须先配置后登录**。向导是唯一在"登录前"可访问的界面。
> **判断条件**：`connection.json` 缺失 **或** 目标库没有 `UserAccount` 记录 → 进入向导；全部完成后才显示登录页。

#### 13.12.2 各步的硬规则

| 步 | 规则 | 原因 |
|:--:|------|------|
| 1 | 时区**只读**（取本机） | 时区配错会导致所有时间戳错位，且极难发现 |
| 2 | 门店编码**创建后不可改**（终端编码前缀依赖它） | 改了要重绑所有终端 |
| 2 | 业态只影响**默认值预设**（超时/餐段），后续都可改 | 降低首配门槛，不是锁定 |
| 3 | **SQLite 分支必查磁盘空间**（< 2GB 警告） | 库涨起来会把盘写满 |
| 3 | SQL Server 分支必须跑完 §13.10.3 的 12 项检测 | 见该节 |
| 4 | **营业日边界小时**必填且提示"夜宵店请改" | 这是最常见的配置错误，错了所有报表口径全错 |
| 4 | 餐段可为空（只按营业日统计） | 小店可能不分餐段 |
| 5 | 密码强度校验 + **禁止默认弱口令** | `admin/123456` 是最大风险 |
| 5 | 账号名唯一、**不区分大小写** | 避免 `Admin`/`admin` 两个账号 |

#### 13.12.3 中断与重入

| 情况 | 行为 |
|------|------|
| 第 3 步完成前退出 | 什么都不落盘（不建库），下次启动**从第 1 步重来** |
| 第 3 步完成后退出 | `connection.json` 已写 → 下次启动**跳过第 3 步**，从第 1 步继续 |
| 第 5 步失败（如账号已存在） | 停留在第 5 步，提示具体原因；**不回退已建好的库** |
| **全部完成** | 写 `StoreConfig` + `UserAccount` + 初始化标记；此后**向导永不再出现** |
| 想重跑向导 | 必须删 `connection.json` 或清空库（**均需 `Kds.DbSetup.exe`**，防止误操作） |
