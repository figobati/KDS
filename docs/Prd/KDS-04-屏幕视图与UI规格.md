# 第三部分：屏幕视图与 UI 规格

## 3. 屏幕视图（配置页二选一 + 屏幕三视图实时切换）

> **两个层次必须分清**：**① 配置页（管理端）**：**基础分组模式二选一** = 桌台模式 / 订单模式。这是一次性的业务场景选择，后厨不能改。
> **② 屏幕（运行时）**：**三个视图 Tab 实时切换** = 【基础分组视图（桌台 或 订单）】【合菜视图】【单菜视图】。师傅随手切，即时生效。
>
> 即：选中的基础分组模式，与合菜、单菜一起，在屏上**共同参与三选一筛选**。

### 3.0 两个层次：配置页定分组，屏幕切视图

#### 3.0.1 配置页：基础分组模式二选一

`TerminalConfig.BaseGroupMode`（**只在管理端配置，屏幕端不可改**）：

| 枚举值 | 名称 | 版本 | **分组键** | 布局 | 是否合并 |
|--------|------|------|------------|------|----------|
| `TableMode` | **桌台模式** | V1（默认） | **`OrderDetail.TableId`（订单-桌台关联 UID）** | 卡片网格（**一条关联 = 一卡**） | 卡内按 `OrderDetail` **逐条展示，不做合并** |
| `OrderMode` | **订单模式** | **V2 预留** | **`OrderDetail.OrderId`（订单 UID）** | 订单卡片 | V1 不启用 UI，仅保留枚举与配置字段 |

- **桌台模式**：按**订单-桌台关联**分组——一单多桌（联台）自然拆成多卡，一桌多单（拼桌）自然是多卡（§3.1）；
- **订单模式**：按**订单 UID** 分组，服务宴会 / 团队餐（一单多桌、每桌菜单一致）——V2 实现；
- **V1 只能选桌台模式**，订单模式在配置页灰显不可选；
- 切换此项**属于配置变更**：需保存 → 递增 `ConfigVersion` → 推送 `ConfigChanged` → 终端重载。**不允许在屏幕上直接切**。

> **为什么分组键是业务键 `(OrderId, TableId)`，而不是桌台 UID 或订单 UID**：
>
> | 分组键 | 联台（一单多桌） | 拼桌（一桌多单） | 问题 |
> |--------|------------------|------------------|------|
> | 桌号字符串 | 需拆分 | 会**混卡** | 改号即裂卡 |
> | `DiningTable.Uid` | 需按桌拆 | **混卡**（两单的菜并一起，整桌划/退菜边界乱） | 无法区分同桌不同单 |
> | `OrderId` | 并成一卡（要合并才有意义） | 天然分开 | 联台默认看不到"哪道菜去哪桌" |
> | **`(OrderId, TableId)`** | **天然多卡**（每桌一卡，各带该桌的菜） | **天然多卡**（每单一张，标题区分） | 无——这正是"订单在某张桌上的那一份" |
>
> 一句话：**卡片 = 订单在某张桌上的一份**。联台与拼桌都不需要额外规则，分组键天然正确。订单视图按 `OrderId` 分组（`PosOrderNo` 是业务单号，会换号、会重号，不能用作键）。

#### 3.0.2 屏幕：三视图实时切换（Tab）

屏幕上固定三个 Tab，**实时切换、无需请求、无需管理员**：

| Tab | 视图 | 内容来源 | 说明 |
|-----|------|----------|------|
| **① 基础分组视图** | 桌台视图 或 订单视图 | `BaseGroupMode` 决定 | 「桌台」被配置时显示"桌台"，配置为订单时显示"订单"（V2）；**Tab 文案随配置变** |
| **② 合菜视图** | 合菜 | 按聚合 Key 合并 | 跨桌/跨单同菜合并，显示总份数（§3.2） |
| **③ 单菜视图** | 单菜 | 不分组不合并 | 平铺明细清单，行内直接划单（§3.3） |

**切换规则：**

1. **即时生效**：切换只做本地重新分组与重绘，**不发请求、不刷新、不重新订阅**；
2. **不改变任何业务状态**：不影响流转、状态、推送、提交粒度（提交永远按最小 `OrderDetail`，§10.7）；
3. **随时可切**：营业中任意时刻都能切，包括严格只读的综合屏（`EnableOperate=false` 时仅浏览不划单，切换本身不受限）；
4. **三视图各自记忆排序**：`TableView_SortMode` / `ItemView_SortMode` / `SingleView_SortMode` 分别独立保存，切回来时恢复上次排序；
5. **记忆当前视图**：`LastActiveView` 本地持久化，屏幕重启后回到上次所在视图；首次启动用配置页的 `DefaultView`（默认 = 基础分组视图）；
6. **快捷键**：支持 `F1/F2/F3`（或 `1/2/3`）直接切三个 Tab，触屏为主时 Tab 常驻可点。

#### 3.0.3 数据供给口径（关键：一套数据、三种分组）

> 这是本轮修订最重要的实现约束。三个视图**共用同一份数据**，否则切换就要重新请求，做不到"实时"。

| 环节 | 约定 |
|------|------|
| **Master 下发** | 下发**明细行**（`OrderDetail` 必需字段）+ 每行预先算好的 **`MergeKey`** + **`TableId`** / `TableNo` + **`OrderId`** / `PosOrderNo`；**不下发"已聚合好的卡片"** |
| **聚合 Key** | 由 Master 按 §2.3.3 计算并随行下发；**终端只按 `MergeKey` 分组，绝不自行计算 Key**（保证同一道菜在任何屏卡片数一致） |
| **终端职责** | 纯渲染层分组：桌台视图按**业务键 `(OrderId, TableId)`** 分组、订单视图按 **`OrderId`** 分组、合菜视图按 `MergeKey` 分组、单菜视图不分组。分组是渲染动作，不是业务规则 |

**各视图分组键定义（实现口径）：**

```
桌台视图分组键（Merge_LinkedTable = false，默认）：
    "ZT:" + OrderId + ":" + TableId
        ↑ 一条关联 = 一卡。联台 → 多卡（每桌一张）；拼桌 → 多卡（每单一张）
        ↑ 两个 ID 都在明细行上，终端可自行拼出，无需 Master 额外下发标识

桌台视图分组键（Merge_LinkedTable = true，开启"联台合并"）：
    该订单有多条关联（联台）
        Merge_LinkedTable_CrossArea = false
            → "G:" + OrderId + "|" + AreaNameSnapshot   ← 跨区时按区域拆成多张组卡
        Merge_LinkedTable_CrossArea = true
            → "G:" + OrderId                            ← 整单一张组卡
    该订单只有一条关联（单桌 / 外卖）
        → "ZT:" + OrderId + ":" + TableId               ← 保持单卡，形态不变

订单视图分组键：
    "O:" + OrderId
合菜视图分组键：
    MergeKey（§2.3.3）
单菜视图分组键：
    无（不分组，按排序规则平铺）
```

> **联台组键用 `OrderId`**：联台业务本质是"一个订单覆盖多桌"，订单 UID 天然是组标识，无需 POS 新增 `TableGroupUid`。代价见 §3.1.4 的"加菜单"注意事项。

> **外卖不需要特例分支**：外卖单若不挂桌台，`TableId` 取固定哨兵 **`Guid.Empty`**（外卖不联台，一单最多一条，天然唯一）；若挂了桌台就填真实 `TableId`。两种情况都用同一个业务键分组，渲染层只多一个"标题显示外卖单号"的判断，不需要单独的分组分支。

| 环节 | 约定 |
|------|------|
| **增量同步** | 推送/轮询仍按 `DetailId` 下发增量（§2.10）；`MergeKey` / `TableId` 随行一起更新（合并条件变化或换桌时 Master 重算下发） |
| **切换成本** | 零网络开销；离线缓存状态下**依然可以切换视图**（三个视图都能展示已缓存数据） |
| **Revision** | 视图切换**不递增 Revision、不触发全量拉取**（它不是数据变化） |
| **`MergeKey` 是否落库** | **不落库**。它是下发 DTO 字段，由 Master 在组装响应/推送时按当前 `Merge_*` 配置与明细状态实时计算；配置或状态变化后重算并随增量下发 |

**为什么不在服务端下发三个视图的成品？**
三个视图的明细集完全相同，下发三份等于三倍带宽与三倍推送量；而"按服务端给的 Key 分组"是几十行渲染代码，远低于多传两份数据的代价。

**切换时的性能要求**：300 条明细在三视图间切换，**渲染完成 < 200ms**；若超过，说明实现里误加了服务端请求或全量重排，必须回退到纯本地分组。

#### 3.0.4 桌台视图为什么不合并

桌台卡片内的明细**逐条展示**，不做应用层合并，原因有三：

1. **同一订单内的相同菜品，POS 侧通常已合并为一行**（`Qty` 已含份数），KDS 再合并属于重复劳动；
2. **拼桌场景**一桌多订单，不同订单的菜合并会丢失"哪道菜属于哪单"的核对信息（退菜 / 结账要按单处理）；
3. **需要跨桌合并时切到合菜视图**——那是合菜视图存在的意义，两种视图分工清晰，避免"桌台视图里偷偷合并"造成认知混乱。

> 若门店强烈要求"桌台卡内同菜合并"，属于**待确认项（附录 B-8）**，当前版本不做。

#### 3.0.5 合并条件与视图的关系

- 7 项合并条件（§2.3.2）**决定 `MergeKey` 的生成**，只在**合菜视图**里体现效果；
- 合并条件是**屏幕配置**（管理端改），**不是运行时开关**——师傅切视图不会改变合并条件；
- 在桌台 / 单菜视图中，合并条件**不产生任何影响**（但配置保留，便于切回合菜视图时生效）；
- 合菜**只影响展示与计数**，不改变后端流转、状态、推送与提交粒度——提交永远按最小 `OrderDetail` 实例逐条校验（§2.3.4、§10.7）。

#### 3.0.6 三视图的选择建议

| 场景 | 推荐视图 | 理由 |
|------|----------|------|
| 传菜 / Expo、综合屏、正餐热菜 | **基础分组视图（桌台）** | 一桌一卡，整桌划单与上菜核对最直观；**联台频繁的门店建议在传菜屏开启联台组卡**（§3.1.4） |
| 切配 / 冷菜备料（同菜跨多桌批量出） | **合菜视图** | 同名菜合并，一次看清"这道菜一共要做几份" |
| 单份精细出餐、特殊定制、需按等待时长平铺 | **单菜视图** | 每份独立一行，不会因合并误划 |
| 宴会 / 团队餐（V2） | 基础分组视图（订单）+ 合菜 | 一单多桌统一备餐 |

**每一块终端屏幕（档口屏、综合屏）都拥有独立配置，屏幕之间互不干扰。**

### 3.1 桌台视图（基础分组视图，`BaseGroupMode = TableMode`）

> **采用桌台而非订单作为基础分组的核心原因：联台场景（一个订单对应多个桌台）。**
> 若按订单号分组，联台时一个订单的菜品被拆散到多个桌台，后厨无法定位每道菜该送去哪个桌台。桌台是后厨传菜、上菜、整桌划单的**物理单位**，按桌台聚合天然解决联台问题。

- **分组键**：**业务键 `(OrderId, TableId)`**——不是桌号、也不是桌台 UID 或关联行主键 `Uid`。桌号只做标题展示；
- **布局**：以卡片为单元，**一卡 = 一条 `OrderTableRel`（订单在某张桌上的一份）**；
- **联台处理**：一个订单跨多个桌台 → 明细行各自带不同 `TableId` → **默认天然多卡（每桌一张）**；可在该屏开启「联台组卡」按 `OrderId` 合并（§3.1.4，默认关闭）；
- **拼桌处理**（一桌多单）：同一 `TableId` 对应多个不同 `OrderId` → **天然多卡，卡片标题带桌号 + 订单尾号区分**；不合并（不同订单的退菜 / 结账 / 整桌划必须各自独立）；
- **外卖 / 无桌位**：`TableId = Guid.Empty`，标题显示外卖单号；若外卖单挂了桌台则正常显示桌号（外卖不联台，只会有一组）；
- **适用**：制作屏、传菜屏、综合屏——传菜、上菜、整桌核对都以桌台为准；
- **交互**：卡内展示该关联下所有待制作菜品；底部支持「整桌划(N) / 选中划(N)」——**此处"整桌划"= 划该卡（该订单在该桌）的菜，不是整桌所有订单**；可分页；
- **卡片内容**：桌号（`TableNo`）+（拼桌时）订单尾号、用餐人数、等待时长；**含套餐时增加套餐摘要行**（`套餐：双人商务餐×1、儿童餐×1`，§2.12.3）；卡内每行展示菜品名称（套餐子项带 `〔套餐名 2/4〕` 标注；**配菜在菜名后以小字列出**：`阳春面 +大肉 +虾`，§D18）、份数、当前流转阶段、等待时长。

**卡片标题的取值顺序（避免改号后标题错乱）**：

```
① 优先：DiningTable 主数据当前 TableCode（改名立即生效，分组键不变）
② 回退：OrderTableRel.TableCodeSnapshot（桌台停用 / 删除时）
③ 外卖 / 自提：无桌台时用外卖单号（`OrderHeader.PosOrderNo`）
④ 拼桌追加：同一 TableId 对应多条订单时，标题后追加订单尾号（如 `A05 · #3821`），否则两张 A05 无法区分
```

> **卡片永远按 `(OrderId, TableId)` 定位与排序，标题只是"显示层"**——改名不会让卡片换位置，也不会分裂。

**订单维度（辅助能力，不作为主分组）：**

- 桌台卡片内展示该桌台关联的订单号（联台时展示多个）；
- 提供订单维度辅助入口：按订单号查看、整单退菜 / 整单核对；
- **不改变主视图分组逻辑**。

#### 3.1.1 桌台视图排序策略

| 排序层级 | 规则 |
|----------|------|
| 一级排序（默认） | **`SortOrderSnapshot`（桌台排序号，来自 `DiningTable.SortOrder`）**，相同时按桌号字符串升序兜底 |
| 二级排序（默认） | 同卡内按**下单时间**升序（先点先做） |

> **为什么用排序号而不是桌号字符串**：字符串排序会出现 `ka10 < ka2`、`A05 < A5`（编码不一致时）等反直觉顺序。用 `DiningTable.SortOrder` 由门店在管理端配置（1F 从左到右、2F 从里到外），最符合后厨走动动线。

**切换按钮【按等待时长排序】**：

- 点击后改为**等待时长倒序**（超时最久的桌台置顶，优先处理）；
- 排序选择保存在 `TerminalConfig.TableView_SortMode`，**下次打开自动记忆**；切到其他视图再切回来也保持；
- 可叠加状态筛选（只看超时 / 只看催菜），见 §3.4。

#### 3.1.2 桌台视图卡片布局

```
┌─────────────────────────────────────────────────────┐
│ ka021    3人  1分57秒          │  ka041   1人  1分39秒 │
│ ─────────────────────         │  ───────────────────── │
│ 可乐        1份  2分           │  莴苣炒蛋    3份  2分    │
│ 可乐        1份  2分           │  ───────────────────── │
│ 鲜麻青椒牛油锅底附毛... 1份 2分 │  [整桌划(3)] [选中划(0)] │
│ ─────────────────────         │     1/1               │
│ [整桌划(3)] [选中划(0)]        │                        │
│     1/1                       │                        │
└─────────────────────────────────────────────────────┘
```

- 卡片 = 桌台，卡头显示桌台号、人数、当前桌台待制作总时长（超时标红）；
- 卡内列出该桌台所有待制作菜品：菜品名（**单行**，超长省略 + 悬浮看全；配菜小字跟在菜名后，§D18）、份数、等待时长、**当前流转阶段**（流转开启时）；
- 退菜 / 催菜 / 等叫 / 起菜 / 赠菜 / 加急菜品加标签标记；
- 底部操作：**整桌划**（一次性划该桌台全部待制作菜品）、**选中划**（勾选部分划单）；- 分页：大量桌台时分页展示。

#### 3.1.3 联台、拼桌与换桌边界

| 场景 | 处理 |
|------|------|
| **联台**（一订单多桌台） | 下单时生成多条 `OrderTableRel`（每桌一条），明细分别挂到对应关联 → **默认各桌独立卡片**；开启联台组卡后按 `OrderId` 合成一张（§3.1.4） |
| **拼桌**（一桌多订单） | 同一 `DiningTable` 挂多条 `OrderTableRel` → **多张卡**（同一桌号），卡片标题追加订单尾号区分（如 `A05 · #3821`）；退菜 / 结账 / 整桌划**按单独立**，不跨单影响 |
| **换桌 / 转台** | POS 推 `Order.Split`（或专项换桌事件）→ 更新受影响明细的 `TableId` + `TableNo` 快照 → 卡片按新关联迁移，**旧卡自动消失，不产生重复**（按桌号分组时会出现"两边都有"的幽灵卡片） |
| **改桌号** | POS 推 `DiningTable.Sync` → 更新 `DiningTable.TableCode` 与 `OrderTableRel.TableCodeSnapshot`，卡片标题刷新，**分组键 `(OrderId, TableId)` 不变、位置不变** |
| 整桌划 | 只划**本卡（本关联）**当前可见的待制作菜品；拼桌时不同订单的菜各在各卡，不会误划 |
| 部分结账 / 撤台 | 该桌台对应的 `OrderTableRel.Status = Closed`；其明细若已全终态则卡片消失，否则继续展示到终态 |
| 跨零点 / 跨营业日 | 归属按 `OrderHeader.BusinessDate`（下单时按营业日边界计算的**快照**），规则见 §2.13 |

#### 3.1.4 联台组卡（屏幕级可选，默认关闭）

> **适用诉求**：一桌 12 人坐 `A05 + A06`（联台），传菜员要对着两张卡来回核对"这桌还差几道"。开启后合并成**一张组卡**，一卡看全该联台组。

**开关（均在终端配置，屏幕级独立）：**

| 配置项 | 默认 | 说明 |
|--------|:----:|------|
| `TerminalConfig.Merge_LinkedTable` | **0（关）** | 是否把多桌订单合并成一张联台组卡。仅作用于**桌台视图**，不影响订单 / 合菜 / 单菜视图 |
| `TerminalConfig.Merge_LinkedTable_CrossArea` | **0（关）** | 跨区域联台（如 1F 的 `A05` + 2F 的 `B02`）是否合并。关闭时按 `OrderTableRel.AreaNameSnapshot` 各自成组卡；仅当上一开关为 1 时有效 |

**推荐配置**：**传菜屏 / Expo 屏、综合屏开启；制作屏保持关闭**（制作屏按菜做，不看桌号，合并后反而失去桌台视野）。

**分组规则**：

```
该订单的 Active OrderTableRel 数量 > 1（联台）+ Merge_LinkedTable = 1
        → 按 "G:" + OrderId 成组（跨区不合并时追加 |AreaNameSnapshot）
该订单只有 1 条关联（单桌 / 外卖）→ 仍按 "ZT:" + TableId（单卡形态不变）

即：只有"真正跨桌"的订单才变成组卡，单桌与外卖的卡片形态完全不变。
```

**组卡形态（每行必须带桌台标签，这是安全底线）**：

```
┌──────────────────────────────────┐
│ A05 + A06     7人     2分31秒     │   ← 标题：组内桌号按 SortOrderSnapshot 拼接
│ ───────────────────────────────  │
│ [A05] 宫保鸡丁        1份  2分    │   ← 行内桌台小标签，不可省略
│ [A05] 可乐            2份  1分    │
│ [A06] 莴苣炒蛋        3份  2分    │
│ [A06] 番茄牛腩        1份  3分    │
│ ───────────────────────────────  │
│ [整组划(5)]  [选中划(0)]          │
└──────────────────────────────────┘
```

| 要素 | 规则 |
|------|------|
| 标题 | 组内桌号按 `SortOrderSnapshot` 拼接（`A05 + A06`）；改号后标题即时刷新，**分组不变** |
| 人数 | 该订单 `GuestCount`（联台是一条订单，不求和） |
| 行内桌台标签 | **每行必带**（`[A05]` / `[A06]`），字号可小于菜名但**不可省略、不可只在悬浮里显示**——否则传菜员必然送错桌 |
| 等待时长 | 取组内**最久**那条明细（保守口径，宁报超时） |
| 超时标红 | 组内**任一**明细超时即整卡标红 |
| 排序定位 | 按组内**最小** `SortOrderSnapshot` 与单桌卡混排，不会整体沉底 |
| 展开 / 收起 | 默认合并显示；支持"按桌展开"查看各桌小计（展开状态不持久化） |
| 整组划 | 该组卡内所有待制作品项一次性划单；**仍按最小 `OrderDetail` 逐条提交**，失败项单独回退（§10.7） |

**收敛与边界：**

| 场景 | 处理 |
|------|------|
| 组内某桌先结账 / 撤台 | 对应 `OrderTableRel.Status = Closed`；该桌明细若已全终态则从卡片消失、标题去掉该桌号；**卡片保留**（其余桌还在吃） |
| 组内全部终态 | 卡片消失（与普通卡一致） |
| 跨区域联台且开关关闭 | 按 `AreaNameSnapshot` 拆成多张组卡（如 `A05` 一张、`B02` 一张），**不退回单桌卡**（保证每组仍是"该区域内的完整联台"） |
| 联台解散（POS 撤桌 / 拆台） | POS 推 `Order.Split` → 删除或重建受影响 `OrderTableRel`，明细改挂新关联 → 卡片按新分组键重建；单桌化后自动退回单卡 |
| **联台期间加菜**（原附录 B-9，v6.98 关闭） | **订单号不变**——**联台本身就是同一个订单**（一单多桌）。加菜走 `Order.Update` + **新 `LineNo`** → `OrderId` 不变、新增 `OrderDetail` 行、**天然不裂卡**；新行由 `DishLine.SourceTableId` 标注归属桌台，行内桌台标签（`[A05]` / `[A06]`）照常渲染。**加菜必须用新 `LineNo`**（同 `LineNo` 改数量属纠错，不加行，§4.6.1） |
| **假设性兜底：POS 违约另起新单** | 若某些 POS 对联台加菜**新建订单**（违反本口径），新单会生成**独立的一组 `OrderTableRel`** → 理论上出现第二张组卡。KDS **不猜测两单属同一桌组**（无依据）。实际对接以 `Order.Update` 复用原单为准，联调首轮须实测该路径 |
| 与订单视图的区别 | 联台组卡**只对多桌订单生效**；订单视图是"所有订单都按订单分组"，两者不是同一件事 |
| 与合菜视图的关系 | 互不影响：合菜视图本就跨桌合并，不区分联台组 |


### 3.2 合菜视图（`ActiveView = MergeMode`）

> **定位**：跨桌台 / 跨订单把**同一道菜**合并成一张卡，回答"这道菜一共要做几份"。适合切配、冷菜、传菜批量备菜。
> **进入方式**：屏幕 Tab 第 ② 个，随时可切。

**左右双栏布局：**

| 区域 | 功能 |
|------|------|
| **左侧主区：聚合菜品卡片** | 按聚合 Key 合并，同菜品合并成一张卡片；右上角标总份数；含规格 / 口味 / 做法标签。选中卡片，右侧明细自动筛选该菜品所有实例 |
| **右侧明细区：划单明细面板** | 展示该菜品下所有订单明细，支持两种明细策略（见 §3.2.2） |
| 顶部筛选栏 | 见 §3.4 |
| 底部快捷键栏 | 字母快捷筛选、搜索、分页、批量划单、划单打印 |

#### 3.2.1 左侧聚合菜品卡片：合并策略

**完整规则见 §2.3（合并条件 + Key 生成算法）。** 此处仅列合菜视图左侧卡片的落地要点：

- 左侧卡片 = 按 §2.3.3 算法生成的 Key 聚合；卡片显示名称 + 总待出份数 + 口味/规格分布（如"共 7 份（少辣 3 / 正常 4）"）+ 聚合标签（含外卖 / 含催菜 / 含超时 / 含等叫）；
- **卡片内品项名称两行显示**（`line-clamp: 2`，超出省略号截断），名称区固定占两行高度，见 §2.3 名称显示策略；规格 / 口味 / 做法标签在名称下方独立一行，不挤占名称空间；
- 聚合 Key 由 Master 计算并随明细行下推；**终端只按 `MergeKey` 分组渲染，不自行计算 Key**（§3.0.3）；
- **改名后历史卡片的判定**（§2.3.4）：POS 改名并推送后，**进行中**（未全部划单）的明细按新名称重新聚合；**已全部划单归档**的明细保留快照名称，聚类到旧名称卡片，且旧名称卡片进入"历史已划"视图（默认折叠，可查看）；
- 卡片上始终显示规格 / 口味 / 做法标签 —— **Key 只用于合并，标签用于让师傅确认**，不允许只显示"共 5 份"而不显示口味分布；
- 需要"逐份确认、绝不合并"的场景请改用**单菜视图**（§3.3），不要通过关闭全部合并条件来模拟。

#### 3.2.2 右侧明细面板：两种可配置策略（屏幕级）

配置项：`TerminalConfig.ItemView_DetailMode`，枚举 `SinglePortion` / `TableGroup`。**仅合菜视图生效**。

**模式 A：SinglePortion（最小单位 1 份）**

- **每个份格单独一行明细**，按桌台排序；份格数 = `Qty / QtyStep`（`Qty=3, Step=1` → 3 格）；
- 示例：ka041 莴苣炒蛋 3 份 → 右侧 3 行，每行 1 份、**独立划单按钮**（点第 2 格 → 只划 1 份），已划的格**置灰**；
- 同一 `DetailId` 的多格共享 `CompletedQty` 进度，划任意格即时刷新整组（`2/3`）；
- 适用：一份一份出餐，精确单份划单（**部分划单的主用场景**，§4.6）；
- **称重菜例外**：`SaleMode = ByWeight` 恒显示 1 行、整行划单，不分格（§4.5.1）。

**模式 B：TableGroup（按桌台聚合）**

- 同一桌台 + 同品项合并成一个分组条目，显示总份数（`共3份`，已完成时显示 `2/3`）；
- 示例：ka041 莴苣炒蛋 3 份 → 一行 `ka041 莴苣炒蛋 共3份`，可一次性划掉；
- 还可**划部分份数**：行内提供"划 1 份 / 划全部"或份数输入框（提交 `Qty` 参数，§4.6.2）；
- 适用：一桌同菜一次性全部做完（冷菜档口高频）。

> **底层约定**：无论前端如何分组展示，提交划单请求都会**定位到最小菜品实例**（`OrderDetail`）并带本次份数 `Qty`，Master 逐条乐观锁 / 版本号校验（见 §10.7）。

#### 3.2.3 右侧明细排序规则

**默认排序：桌台排序号一级排序 + 下单时间二级排序。**

| 排序层级 | 规则 |
|----------|------|
| 一级排序 | **`TableSortOrder`（桌台排序号）升序**，相同时按桌号字符串兜底；外卖单（无桌台）排在最后 |
| 二级排序 | 同桌台内按**下单时间**升序（先点先做）——已确认采用下单时间先后 |

> 排序依据是明细行上的 `TableSortOrder` 快照，**不是桌号字符串**（避免 `ka10 < ka2`），见 §9.4。

**切换按钮【按等待时长排序】**：

- 点击后改为**等待时长倒序**（超时最久排最上，优先处理）；
- 切换**只改变右侧明细排序**，不改变聚合、不改变左侧卡片；
- 两种排序可来回切换，默认保持桌台排序；屏幕记忆上次选择（`TerminalConfig.ItemView_SortMode`）。

#### 3.2.4 合菜视图交互与边界

- 选中左侧卡片 → 右侧明细自动筛选；清空选择 → 展示全部明细；
- 双击快速划单；勾选多行批量划单；
- 划单提交最终落到**最小品项实例行**，乐观锁逐条校验，**部分成功 / 失败分别提示**（返回结构见 §10.7）；
- 桌台聚合批量划单：前端拆分成多条实例依次提交；
- 明细行显示等待时长，超时标红预警；
- 同桌台同品项但口味 / 规格不同：**不合并**到同一桌台分组，拆开；
- 部分退菜：最小份模式退菜行标红禁用；桌台聚合模式分组标「含退菜 N 份」，批量划单**跳过退菜行**；
- 外卖订单：桌台号替换为外卖单号展示与排序；
- 网络断连：本地缓存维持当前视图，**只浏览不提交**（见 §13.2）。

#### 3.2.5 两栏的落地结构（**参考实机，v6.91 补齐**）

> **与桌台模式的关键差异**：**桌台模式"点整行即划、无勾选、无批量"；合菜模式"右侧明细可勾选 + 选中划 / 全部划 / 划单打印"。** 两者不冲突——桌台模式的动作对象是"这一桌的这道菜"，合菜模式的动作对象是"这道菜在多桌的若干份"，后者天然需要多选。

```
┌──────────────────────────────────────────────────────────────┬──────────────────────────┐
│ 全部 堂食 外卖 │ 全部(5) 催菜/加急(0) 超时(2) 等叫(0) 起菜(0) │ * 双击快速划菜    共2桌  │
│ 菜品 | 订单                                 [沽清][历史已划][已沽清] ├──────────────────────────┤
├──────────────────────────────────────────────────────────────┤ ka041 [制]        3份    │
│ 全部  饮料  热炒菜  奶茶                                      │ ○ 莴苣炒蛋   34分钟 [划菜]│
│ ┌─────────┐ ┌──────────────┐ ┌──────────────┐               ├──────────────────────────┤
│ │超    2份│ │         1份  │ │         4份  │               │ ka101 [制]        1份    │
│ │ 可乐    │ │ 鲜麻青椒牛油 │ │ 莴苣炒蛋  ✓  │               │ ○ 莴苣炒蛋   33分钟 [划菜]│

│                                                              │                        [▼]│
└──────────────────────────────────────────────────────────────┴──────────────────────────┘
```

**左栏（主区）**

| 元素 | 规格 |
|------|------|
| 顶部筛选 | 订单类型（全部/堂食/外卖）+ 状态（全部(N)/催菜加急(N)/超时(N)/等叫(N)/起菜(N)，**带计数**） |
| **`菜品 \| 订单` 切换** | 左栏聚合维度：`菜品` = 按 `MergeKey`（跨桌同菜）；`订单` = 按 `OrderId`。默认 `菜品` |
| 分类 Tab | 按 `DishType` 过滤（全部/饮料/热炒菜/奶茶…） |
| **菜品卡** | 菜名（**两行截断**）+ **右上角橙色份数角标** + **左上角状态角标**（`超`/`催`/`等`）+ 口味/规格标签 + **选中态右下角绿 ✓** |
| 卡底色 | 超时=红底、预警=黄橙底、正常=白底（**整卡状态用底色表达**，与桌台模式一致） |
| 动作 | **单击选中**（右栏联动筛选）；**双击 = 快速划单**（划该卡全部，见右栏标题提示） |

**右栏（明细 + 批量）**

| 元素 | 规格 |
|------|------|
| 栏宽 | **固定 380~420px**（不随窗口缩放，保证批量按钮够大） |
| 标题 | `* 双击快速划菜`（提示快捷键）+ 右侧 `共 N 桌` |
| 条目 | 桌号 + **阶段标记 `[制]`/`[切]`/`[传]`** + 份数角标 + **行首 ○ 勾选圈** + 菜名 + **等待时长** + **行尾【划菜】竖排按钮** |
| ○ 勾选 | **仅在本栏出现**（可多选）；勾选后底部【选中划】由灰转亮 |
| 行尾【划菜】 | 划掉**该行**（单条），不需要先勾选 |
| **底部操作条** | `[选中划]`（灰/亮）`[全部划]`（描边强调）`[划单打印]`（划完并出单） |
| **右侧 ▲▼** | 列表超出时出现，**72×72**，到顶/底置灰（§17.2） |
| 排序 | 默认桌台排序号；可切"按等待时长"（§3.2.3） |

**三个批量按钮的语义（必须分清）**

| 按钮 | 作用 | 边界 |
|------|------|------|
| **选中划** | 只划**勾选**的条目 | 未勾选时**置灰** |
| **全部划** | 划掉**当前右栏列出的全部**条目（即该菜品在所有桌的待做份数） | 需二次确认（数量大） |
| **划单打印** | 先划单，**再打印单据** | 受打印规则约束（§16）；无打印机时退化为"只划单" |

> **为什么桌台模式不需要勾选、合菜模式需要**：桌台模式的"批量"是**整卡**（一个按钮覆盖全卡，不需要选）；合菜模式的批量是**这道菜在多桌的若干份**，师傅常常"只划先做的 2 桌、留后面的"——**不勾选就无法表达这个意图**。

### 3.3 单菜视图（`ActiveView = SingleMode`）

> **定位**：**不分组、不合并**，把所有待制作菜品实例按时间平铺成一条清单，回答"现在该做哪一份"。
> **进入方式**：屏幕 Tab 第 ③ 个，随时可切。

**布局：单列平铺清单（每行 = 一条 `OrderDetail`）**

| 列 | 内容 | 说明 |
|----|------|------|
| ① 等待时长 | 全局等待时长 + 阶段等待时长（流转开启时） | 超时标红、预警标黄，按当前排序实时刷新 |
| ② 菜品名 | **两行显示**，超出省略号截断（`line-clamp: 2`） | 行高固定两行（如 40px），保证每行高度一致；规格 / 口味 / 做法标签在名称下方独立一行；**配菜小字跟在菜名后**（`阳春面 +大肉 +虾`，§D18）；悬浮显示完整名称（§2.3 名称显示策略） |
| ③ 桌台 / 外卖单号 | 桌台号或外卖单号 | 联台时显示实际桌台（明细行已按桌台拆分） |
| ④ 份数 | 该实例份数 | 单菜视图下列内份数通常为 1，若 POS 传多份则显示原值 |
| ⑤ 流转阶段 | 切配 / 制作 / 传菜 | 流转开启时显示 |
| ⑥ 状态标签 | 催菜 / 加急 / 等叫 / 起菜 / 退菜 / 赠菜 | 优先级见 §4.4.3 |
| ⑦ 操作 | 【划单】按钮 | 行内直接划单，无需先选卡片 |

**排序（屏幕级，`TerminalConfig.SingleView_SortMode`）：**

| 取值 | 排序规则 | 适用 |
|------|----------|------|
| `WaitDuration`（**默认**） | 等待时长倒序（最久置顶） | 单菜视图的核心诉求：先做最急的 |
| `TableOrder` | `TableSortOrder` 升序 + 下单时间升序 | 需要按桌顺序出品时 |

**交互与边界：**

- **行内直接划单**：单菜视图不设左侧卡片，划单入口就在明细行（双击行 = 划单，或点【划单】按钮）；
- **支持多选批量划单**：勾选多行后一次提交，仍按最小实例逐条校验，失败项单独回退并高亮（§10.7）；
- **不做聚合**：同名菜出现多少次就显示多少行，**永不合并**——这是与合菜视图的根本区别，用于"合并会做错"的场景（特殊定制、逐份摆盘、 allergy 菜品）；
- **退菜行**：标红删除线、禁止划单、可折叠隐藏（开关 `SingleView_HideCancelled`，默认显示）；
- **分页 / 虚拟滚动**：明细行数可达数百，采用虚拟滚动（不强制分页），保证滚动流畅；
- **与桌台视图的差异**：桌台视图是"按桌聚合看进度的卡片视图"，单菜视图是"不分组的待办清单"；两者**数据源完全相同**，只是分组维度不同（§3.0.3）。

### 3.4 顶部公共筛选栏（三视图共用）

> 吸取菜么么后厨大屏，三视图共用顶部导航：

| 区域 | 内容 |
|------|------|
| 分类 Tab | 全部 / 堂食 / 外卖 |
| 状态统计 | 全部(N) / 催菜加急(N) / 超时(N) / 等叫(N) / 起菜(N) |
| **视图切换 Tab** | **【桌台 或 订单】【合菜】【单菜】三个 Tab，实时切换**（§3.0.2）。第一个 Tab 的文案由 `BaseGroupMode` 决定（桌台 / 订单）；当前 Tab 高亮，切换即时生效、无请求 |
| 检索框 | 支持**桌台号、订单号、品项名称**多维度关键词检索，实时过滤当前展示数据；支持多条件组合 |
| 操作入口 | 当前配置方案、历史已划、已沽清、速查码输入、时间 / 超时预警 / 已超时标识 |

**筛选语义（必须明确，避免实现歧义）**：

- 筛选**仅作用于前端展示**，不改变后端业务与推送逻辑；
- **视图切换与筛选相互独立且可叠加**：先按视图分组，再叠加筛选条件（例：合菜视图 + 只看超时）；
- 切换视图时**保留当前筛选条件**（不重置），避免师傅每次切视图都要重新筛；
- 联动 / 不联动模式不影响筛选能力；
- 关键词匹配规则：**不区分大小写、去首尾空格、子串包含匹配**；
- 多条件为 **AND** 关系（如"桌台号含 ka0 且 品项名含 可乐"）；
- 状态统计数字为**点击可切换的筛选器**，多选时取 **OR**（如"催菜 + 超时"）；
- 筛选结果为空时展示空态（见 §3.6）。

### 3.5 综合屏专项配置规则（V1）

> **定位修正（v6.62）**：综合屏**不是只读大屏**，而是**一条独立的 `TerminalConfig`**——**可操作、可配置、能看到全部状态、拥有三视图**。默认 `EnableOperate = 0`（开箱只读），但**后台可开启划单**，开启后与档口屏享有完全相同的操作能力（含撤销）。

**① 与工序屏的差异（v6.97 定案）**

> 一句话：**工序屏是"我这一站"的干活界面；综合屏是"全店全工序"的总览界面。** 差异只在**可见范围**与**默认权限**，拿数机制与三视图能力完全相同。

| 维度 | 工序屏（切配 / 制作 / 传菜） | **综合屏（`TerminalType = Composite`）** |
|:---|:---|:---|
| `Role` | **必填**（`Prep` / `Cook` / `Expo`） | **可空**（跨角色） |
| **可见阶段** | 仅本角色那一站（自动模式下） | **全部阶段**：`Prep` / `Cook` / `Expo` 的品项**都能看到** |
| **三视图** | 桌台 / 合菜 / 单菜 | **同样全部支持**，`BaseGroupMode` 同样二选一 |
| 绑定档口 | **必须 ≥ 1** | 可绑多个（取并集）、**也可不绑** |
| `EnableOperate` | 默认 `1`（可划单） | 默认 `0`（**开箱只读**） |
| 撤销能力 | 有（自己的操作） | 只读态无；开 `EnableOperate=1` 后与工序屏**完全一致** |
| 典型位置 | 各档口灶台旁 | 传菜口 / 前厅 / 挂在墙上远处看 |
| 典型用途 | **干活**（划单） | **总览、查询、叫号**（可选），或纯展示 |

> **综合屏"能看到所有工序状态"与手动模式的"透明流水线"不是一回事**：综合屏是**另一种类型的屏**，它在 V1 自动模式下就跨全部阶段；手动模式讲的是**工序屏自己**也能看见上游未做完的菜（V2 实现，§2.7.1）。两者互不依赖。

**② 只读态（`EnableOperate = 0`）的准确定义（v6.97 定案）**

> **只读 ≠ 整屏锁死**。只读 = **隐藏所有会改动数据的入口**，让人能"看全景、能查、不能动"。
> 判据一句话：**凡是会写库或发事件的按钮，一律不渲染。**

| 区域 / 功能 | 只读态（`EnableOperate = 0`）表现 |
|:---|:---|
| 卡尾操作条 A-09（含【叫号】【划菜】） | **整条不渲染**（不是置灰），卡片变矮 |
| 桌台模式行点击划单 | **不响应**（整行不再是操作热区） |
| 合菜模式【选中划】【全部划】【划单打印】 | **不渲染** |
| 单菜模式行内划单 | **不渲染** |
| A-07【我的划单记录】抽屉 | 入口按钮**不显示**（无操作可看，抽屉无意义） |
| 撤销（含 `EnableManageUndo` 跨屏撤销） | **不渲染** |
| 补打 | `EnableReprint` 默认 `0`；只读态**强制不可用** |
| **叫号** | **不渲染**——叫号会写 `CallLog` 并发 TTS 广播，**属于操作**，不是查看 |
| **保留可用** | 全景查看、**三视图随时切换**（§3.0.2）、**检索查询**（桌号/单号/菜名）、筛选（催菜/超时/等叫/起菜）、分页滚动、语言切换、状态条、本机设置页中**不写库**的项 |

> ⚠️ **已知取舍**：V1 没有"只开叫号、不开划单"的中间态——`EnableOperate` 是**单一开关**，打开即同时获得划单与撤销能力。若门店只要叫号不要划单，V1 的处理是**建议当班传菜员用传菜屏叫号**，综合屏保持只读。若现场强诉求，可作为 V1.1 拆出 `EnableCall` 独立的权限开关。

**③ 与「前厅进度查询」的关系（原附录 B-5，v6.97 关闭）**

> 前厅服务员查进度**不需要独立端、不需要新页面**：**把一块综合屏设成只读态，挂在前厅 / 传菜口即可。**

| 项 | 结论 |
|:---|:---|
| 是否做独立前厅端 | ❌ **不做**（V1 边界，§1.3） |
| 是否新增只读 REST | ❌ **不需要**——复用 `/api/Terminal/{terminalId}/ActiveItems`（服务端按终端预筛选） |
| 是否新增账号 / 权限模型 | ❌ **不需要**——综合屏本身就是一条 `TerminalConfig`，走既有终端鉴权（`ScreenLogin` / `DeviceKey`） |
| 前厅能看到什么 | 全部未完成品项（跨工序）、当前阶段、等待时长、是否超时/催菜、已出/未出 |
| 前厅不能做什么 | 划单、撤销、退菜、改数量、叫号、补打、改配置 |
| 隐私边界 | 只读态**不显示"我的划单记录"**，也不显示操作人，避免前厅看到后厨人员操作明细 |

**④ 综合屏与「是否启用工序流转」解耦（v6.97 定案）**

> **关掉工序流转 ≠ 关掉综合屏。** 综合屏**不依赖** `StoreConfig.EnableWorkflowState`，两种配置下**都能用**、**功能都完整**。唯一变化是**品项不再显示"当前工序"**。

| 能力 | `EnableWorkflowState = true`（启用工序） | `EnableWorkflowState = false`（关闭工序） |
|:---|:---|:---|
| 屏幕是否可用 | ✅ 可用 | ✅ **照常可用，不降级、不禁用** |
| 桌台 / 合菜 / 单菜三视图 | ✅ 全部支持 | ✅ **同样全部支持** |
| 检索（桌号 / 单号 / 菜名） | ✅ | ✅ |
| 筛选（催菜 / 超时 / 等叫 / 起菜） | ✅ | ✅ 同样可用（**超时 = 全局超时**，不再有"本阶段超时"） |
| 卡尾操作条 / 划单 / 叫号 / 撤销 | ✅ 按 `EnableOperate` 决定 | ✅ **同样按 `EnableOperate` 决定，能力不变** |
| **品项「当前工序」显示** | ✅ 显示阶段名（切配/制作/传菜）+ C9 徽标 + **本阶段**等待时长 | ❌ **隐藏**：阶段名、阶段标识（C9 徽标）、阶段等待时长**全部不渲染** |
| **等待时长** | 本阶段时长（可另显全局时长） | ✅ **只显示全局等待时长**（从下单起算） |
| **品项状态语义** | 8 态 + 4 阶段态 | **简化为 2 态：待出 / 已划单**（§4.1） |
| 划单后行为 | 推进到下一工序 | **直接完成**（`已划单`），不再有下一站 |
| 卡片高度 | 含阶段行 | **变矮**（少一行，同只读态的处理方式：不占位、不留白） |

> **口径提醒**：关闭工序流转后，综合屏从"**工序大盘**"变成"**出品大盘**"——它的价值是**全店所有未出菜品的一览**（哪桌还差什么、等了多久、有没有催），**这个价值与工序无关**，所以不能因为关掉工序就把屏也停掉。很多门店第一年只用"待出/已划单"这套最简流程，综合屏正是它们最需要的那块屏。

**⑤ 与其他屏的关系（一句话定位）**

| 屏 | 关掉工序流转时 |
|:---|:---|
| 切配 / 制作 / 传菜工序屏 | ⚠️ **失去意义**——没有工序就没有"我这一站"，工程上建议不部署或少部署（不是禁止，屏仍能显示全部待出菜品，等于退化成一块小综合屏） |
| **综合屏** | ✅ **依然成立，且是关闭工序场景下的主力屏** |

1. **本质是一条独立 `TerminalConfig` 终端记录**，**首次启动默认进入基础分组视图（桌台）**，复用和档口屏同一套数据引擎、推送通道与三视图切换能力；
2. **顶部检索框**支持多维度检索：桌台号 / 订单号 / 品项名称，关键词实时过滤（同 §3.4）；
3. **桌台卡片内**，每一行菜品展示：当前流转阶段、等待时长；
4. **划单权限可配**：`EnableOperate` 默认 `0`（开箱只读），**后台终端配置可开启**；开启后**划单交互与档口屏完全一致**（§3.5.1），并**自动获得撤销能力**（综合屏有划单就有"自己的操作"可撤，§2.19.11）。

**综合屏展示细节：**

1. **开启流转时**：桌台卡片内每行菜品显示当前所处阶段（切配 / 制作 / 传菜）+ 本阶段等待时长；
2. **关闭流转时**（`EnableWorkflowState = false`）：综合屏**照常可用**，但隐藏阶段名称、阶段标识（C9 徽标）与阶段等待时长，只显示**全局等待时长**（从下单开始计时），不区分工序；品项状态退化为**待出 / 已划单**两态（§4.1），划单即直接完成。卡片因少一行而变矮（同只读态的处理方式，不占位不留白）；
3. **三视图完整可用**：桌台 / 合菜 / 单菜三视图**全部支持**（同档口屏，§3.0.2），`BaseGroupMode` 同样二选一；
4. **能看到所有状态**：综合屏 `Role` 为空 → **跨角色可见**，能看到 `Prep` / `Cook` / `Expo` 全部阶段的品项（不限于某一角色）；
5. 综合屏通常绑定**多个档口**（跨档口总览）：绑定多档口时按 §2.2 规则取并集，同一品项若命中多个已绑定档口，**每个档口各推一条**（Master 推送按"档口 × 屏幕"维度），终端按 `OrderDetail.DetailId` 去重展示，避免同菜重复显示；
6. 与档口屏共用同一套广播推送，**不做任何特殊分配逻辑**（见 §2.9）。

#### 3.5.1 划单交互规范（**所有屏幕统一，含综合屏**）

> **一句话**：**点一下就划，不弹确认、不弹提示、不要求长按。** 后厨是高频重复动作，任何确认框都会变成"闭眼点确定"，反而失去意义。

| 交互 | 规范 |
|------|------|
| **划单方式** | **鼠标单击 / 手指触摸单击即划单**（`click` / `touchend`） |
| ❌ 不做 | 二次确认框、长按确认、滑动确认、Toast 成功提示 |
| 反馈 | 行**立即置灰并淡出**（视觉反馈代替文字提示），乐观锁失败时该行**闪红回到原位** |
| 触发区域 | **整行可点**（不只是按钮），减少误触与瞄准成本 |
| 防连点 | 300ms 内同一点击忽略（防手抖/双击产生两次提交） |
| 批量划单 | **仅合菜模式**：勾选多行 → 【选中划】/【全部划】一次提交（逐条乐观锁，失败项单独标红，§10.7）。**桌台模式无批量**（用卡尾【划菜】整卡） |
| **搜索索引划单** | `SearchBumpWholeTable = 1` 时**必须两步确认**：回车只【定位并选中】该桌卡，**再回车或点【划菜】才执行**（§17.6）。**一次输入绝不直接改数据** |
| **撤销** | 走 §2.19 的【我的划单记录】，**不在划单瞬间提供"撤销"悬浮按钮**（避免误点） |

#### 3.5.2 桌台模式的卡片结构（**叫号 + 划菜 固定在卡片底部**）

> **两次修正记录**
> **v6.88**：原设计"页面右下角固定悬浮 + 需先选中卡" → 改为**每张卡自己的底部操作条**。
> **v6.90**：① **取消行首圆圈（○）**——它长得像单选/多选控件，会**诱导用户去点选**，而本系统**点击品项即划单、不支持多选批量划单**，所以不放任何选择控件；② **卡尾操作条必须固定在卡片底部**（`margin-top:auto` / sticky bottom），内容不满时空白留在**内容区**，不是留在卡尾之后。

```
┌──────────────────────────────┐
│ 共 3 道  👥4  🍽堂      A05  │  ← 卡头：明细数 + 人数 + 餐别 + 桌号（右对齐超大）
├──────────────────────────────┤
│ 宫保鸡丁    2  [催][超时]     │  ← 无圆圈、无勾选框；整行可点 = 划单
│ 微辣                          │
├──────────────────────────────┤
│ 米饭                    2    │
├──────────────────────────────┤
│ 例汤                 2  [赠]  │
├──────────────────────────────┤   ← 内容不足时，空白在这里（内容区）
│ 🕐1小时20分   [叫号] [划菜]  │  ← 卡尾：**固定在卡片底部**
└──────────────────────────────┘
```

| 元素 | 规格 |
|------|------|
| **行首选择控件** | ❌ **本模式不做**。不放圆圈、不放勾选框——**桌台模式**是"点整行即划单"，有选择控件就会让人以为要"先勾选再批量划" |
| **批量划单** | ❌ **桌台模式不支持**（整卡用卡尾【划菜】）。**合菜模式支持**——右侧明细面板有勾选 + 【选中划】【全部划】【划单打印】（§3.2.5） |
| 行的可点区域 | **整行**（≥64px 高），点即划；划后该行置灰淡出并加删除线 |
| **卡尾位置** | **固定在卡片底部**（flex 布局 `margin-top:auto`）。**内容不满时空白留在内容区，卡尾永远贴底** |
| 按钮顺序 | **左【叫号】、右【划菜】**——主操作在最右（拇指/指针自然落点） |
| 叫号 | 次级样式（白底描边）；**作用于本卡桌台**，无需先选中卡；详见 §3.5.3 |
| **划菜** | **主按钮**（品牌蓝填充）；一次性划掉本卡（本订单 × 本桌台关联）当前可见的全部待制作菜品 |
| 按钮计数 | **不显示 `(N)` 计数**——卡头已有"共 N 道" |
| 禁用态 | 划菜**置灰**当：① 本卡无可划明细 ② `EnableOperate = 0` ③ 离线/数据滞后未刷新成功 |
| 只读屏 | 卡尾**整条不显示**（不是置灰），卡片变矮 |
| 时长位置 | **卡尾左下**（不在卡头）——与"整桌完成情况"同处，语义更近 |
| 桌号 | **右对齐、超大（2.75rem / 44px）**——远距离一眼找到桌 |
| 卡头底色 | 随卡状态（超时=浅红底、预警=浅黄底、跨日=更深红）；**状态不只靠底色**，卡头另有徽标 |

> **为什么改成卡内**：页面固定悬浮需要"先选中卡"这一步，忙时**容易选错卡划错桌**（最严重的误操作）；卡内按钮**动作对象自明**。
> **为什么不要圆圈**：一个空心圆在触摸屏上就是"可勾选"的视觉承诺。用户会去点它，结果什么也没发生（或误划了整行）——**控件外观要和行为一致**。行本身可点，就不需要额外的选择指示。
> **为什么卡尾必须贴底**：卡片会被同行拉成等高，若卡尾跟着内容走，会在底部留出空白，用户会以为"卡片没加载完"或"下面还有内容"。贴底后视觉上卡片是"完整的"。

#### 3.5.3 叫号与 TTS（**预留接口，V1 可只做视觉提示**）

> **叫号是什么**：传菜口/综合屏发现某桌菜齐了或某道菜好了，**语音播报通知前厅/客人取餐或上菜**。它不是 KDS 的核心流程，但能显著减少传菜员来回跑。

**交互链路**

```
点本卡卡尾【叫号】
  ├─ 屏幕立即显示"已叫号 A05"（视觉反馈，必有）
  ├─ 记录 CallLog（桌号、时间、操作屏、播报内容）
  └─ 调用 TTS Provider 播报（若已配置，见下）
```

**TTS 抽象接口（预留，V1 定义契约即可）**

```csharp
public interface ITtsProvider
{
    string Name { get; }                       // Local / Baidu / Azure / Custom
    Task<bool> SpeakAsync(TtsRequest req, CancellationToken ct);
}

public class TtsRequest
{
    public string Text { get; set; }           // 已按模板渲染好的播报文本
    public string Lang { get; set; }           // BCP-47，取屏幕 CurrentLang（§11.1）
    public int Volume { get; set; } = 100;     // 0~100
    public int Rate { get; set; } = 0;         // -10~10
    public string OutputDevice { get; set; }   // 可选：指定输出设备
}
```

| 实现 | 说明 | V1 |
|------|------|:--:|
| `ConsoleTtsProvider` | 仅写日志/控制台（无声音） | ✅ **默认**，保证功能可跑通 |
| `LocalSapiTtsProvider` | Windows SAPI（离线可用，中文需装语音包） | ✅ 可选 |
| `HttpTtsProvider` | 调云端 TTS（百度/讯飞/Azure），需网络与密钥 | 🔶 预留 |
| 门店自建 | 通过 HTTP 回调门店广播系统 | 🔶 预留 |

**播报内容模板（可配，支持变量）**

```json
// StoreConfig.CallTemplate
{ "zh-CN": "{TableNo}桌，菜品已好", "en-US": "Table {TableNo}, your dishes are ready" }
```

变量：`{TableNo}` / `{TableNos}`（联台）/ `{DishNames}`（本次涉及的菜名，可空）/ `{GuestCount}`。

| 规则 | 说明 |
|------|------|
| 多语言 | 播报语言取**该屏 `CurrentLang`**（§11.1），模板按语言取 |
| 防轰炸 | **同一桌 30 秒内重复叫号 → 忽略**（`CallCooldownSeconds`，默认 30），避免连点刷屏 |
| 静音时段 | 可配 `CallQuietHours`（如 14:00-17:00 歇市不播报），仍记 `CallLog` |
| 失败降级 | TTS 失败**不影响任何业务**，仅记 `Warning`，屏幕视觉反馈照常 |
| 记录 | `CallLog`：桌号 / 时间 / 操作屏 / 操作人 / 播报文本 / 是否成功 |

> **为什么 V1 只做到"预留"**：TTS 涉及语音包安装、音量、方言、门店广播系统对接，**很容易变成一个吞时间的坑**。把接口和模板定好，先用"视觉提示 + 日志"跑通流程，等门店确认要语音再实现具体 Provider。

#### 3.5.4 语音播报模板（**可编辑，管理端维护**）

> **原则**：播报文案**不写死在代码里**。不同门店的叫法差异很大（"请取餐"/"请上菜"/"XX 号桌好了"），必须由门店在管理端自己改。

**模板按场景 + 语言各一份**

| `TemplateKind` | 场景 | 默认文案（zh-CN） |
|----------------|------|-------------------|
| **`Call`** | 手动叫号（§3.5.2） | `{TableNo}桌，菜品已好` |
| **`AllDone`** | 整桌全部出餐（自动） | `{TableNo}桌，菜品已全部上齐` |
| **`Timeout`** | 超时提醒（§4.4.3） | `{TableNo}桌，{DishName}已超时` |
| **`Remind`** | 催菜播报 | `{TableNo}桌，请注意催菜` |
| **`SoldOut`** | 沽清提示（可选） | `{DishName}已售完` |

**可用变量白名单（保存时强校验）**

| 变量 | 含义 | 适用场景 |
|------|------|----------|
| `{TableNo}` | 桌号 | 全部 |
| `{TableNos}` | 联台桌号（`A05+A06`） | 全部 |
| `{TableName}` | 桌台名（优先于桌号） | 全部 |
| `{DishNames}` | 涉及的菜名（多道时逗号连接，**最多 3 个**，超出补"等 N 道"） | `Call` / `Timeout` / `Remind` |
| `{DishName}` | 单个菜名 | `Timeout` / `SoldOut` |
| `{DishCount}` | 涉及菜品数 | `Call` / `AllDone` |
| `{GuestCount}` | 就餐人数 | 全部 |
| `{StoreName}` | 门店名 | 全部 |

| 编辑规则 | 说明 |
|----------|------|
| **保存校验变量** | 解析 `{X}`，出现白名单外的变量 → **拒绝保存**并提示"可用变量：…"（防止 `{TableNumber}` 这类手误导致播报变成"大括号 TableNumber"） |
| **插入而非手打** | 编辑区提供变量按钮，点击在光标处插入 `{TableNo}` |
| **长度提示** | `> 60 字` 给**警告**（不阻止）：按 5 字/秒估算，60 字约 12 秒，播报太久会盖住下一条 |
| **多语言独立编辑** | 每个语言一份，语言包缺失时回退：`当前语言 → 默认语言 → zh-CN → 内置默认模板` |
| **试播** | 每个模板提供【预览】：用样例数据渲染出文本 + （若 TTS 可用）实际出声，**不写数据库** |
| **生效** | 保存即生效（服务端缓存 30 秒内刷新），**不需重启** |
| **审计** | 每次保存写 `OperationLog`（谁、改了什么场景、什么语言、改前改后），支持**回滚到上一版** |
| **空模板** | 允许留空 → 该场景**不播报**（但仍记 `CallLog`），不报错 |

**渲染示例**

```
模板（zh-CN）：{TableNo}桌，{DishNames}已好，请取餐
样例数据：TableNo=A05，DishNames=[宫保鸡丁, 米饭]
渲染结果：A05桌，宫保鸡丁、米饭已好，请取餐

模板（en-US）：Table {TableNo}, {DishNames} ready
渲染结果：Table A05, Kung Pao Chicken, Rice ready
```

> **变量值也要按当前屏幕语言解析**：`{DishNames}` 取的是该屏 `CurrentLang` 下的菜名（§11.2），所以**中文模板 + 中文菜名、英文模板 + 英文菜名**自然一致，不会出现"英文模板里夹中文菜名"。

#### 3.5.5 模板编辑页规格（降低门店配置错误率）

> **问题**：只给一排变量按钮，店长**不知道 `{DishNames}` 和 `{DishName}` 的区别**，很容易配出"宫保鸡丁、米饭已超时"这类不通顺的播报。

**页面布局**

```
┌─ 语音播报模板 ────────────────────────────────────────────┐
```

**三条降低错误率的设计**

| 设计 | 作用 |
|------|------|
| **① 变量说明折叠区** | 每个变量的**含义 + 会变成什么 + 真实例子**；默认折叠（不占空间），点开可查。**这是最有效的一条**——比文档、比培训都直接 |
| **② 实时预览** | 输入时下方**边打边渲染**出最终播报文本，配错立刻看见（如漏了句号、变量拼错） |
| **③ 字数 + 预计秒数** | `字数 22 / 预计播报 4.4 秒`（5 字/秒），超 60 字转黄 |

**其他编辑器规则**

| 规则 | 说明 |
|------|------|
| 场景 / 语言切换 | 切换时**自动保存已改内容**（缓存草稿），避免切走丢失 |
| 保存校验 | 变量白名单 + 场景匹配 + 花括号配对（§3.5.4）；**不通过则定位到错误位置并高亮** |
| 恢复内置默认 | 清空本场景本语言的自定义内容，回退内置模板；需二次确认 |
| 回滚到上一版 | 显示 `Version` 与最近修改人/时间，一键回滚 |
| 空内容 | 保存空串 = 该场景不播报，**给一次提示确认**（"该场景将不播报，确定？"） |
| 未配语言标记 | 场景 × 语言列表中标出"未配置"（走回退）与"已自定义" |


### 3.6 界面通用状态规格

| 状态 | 触发条件 | 展示要求 |
|------|----------|----------|
| 空态 | 无待制作菜品 | 展示"暂无待制作菜品"+ 当前筛选条件摘要 + 清除筛选入口 |
| 离线态 | WebSocket 断开 **或连续 3 次轮询失败** | 顶部常驻提示条"网络已断开，仅可浏览"；所有操作按钮禁用；恢复后自动**全量替换** |
| 数据滞后态 | `Now - LastSyncAt > DataStaleSeconds`（默认 90s） | 顶部常驻黄条"数据可能滞后，正在恢复"；**允许浏览但划单前必须先刷新成功**（避免基于旧状态误操作） |
| 同步中态 | 全量拉取 / 大增量应用中 | 骨架屏或局部遮罩，禁止操作 |
| 错误态 | 接口失败（非离线） | 顶部提示 + 重试按钮，保留上次成功数据 |
| 大单预警态 | 单桌待制作项 > 阈值（门店可配，默认 30） | 卡片头部加"大单"标记；**大单明细仍计入超时统计**，不受该标记影响 |

### 3.7 分屏多作业面（`PaneLayout`，**V1.1 预留，V1 不实现**）

> **需求**：一台显示器水平均分成 2~3 栏，**每栏独立关联一组档口**，各栏只显示自己档口的品项，用来替代 2~3 台物理小屏（省设备、省墙面）。
> **V1 状态**：仅保留 `TerminalConfig.PaneLayout` 枚举与 `TerminalPane` 表设计，**V1 一律 `Single`、不创建该表、不开放配置入口**。

#### 3.7.1 硬约束

| 约束 | 规则 |
|------|------|
| **只支持单菜视图** | `PaneLayout != Single` 时**锁定 `ActiveView = SingleMode`**，视图 Tab 隐藏（不是禁用）。理由：桌台/合菜视图在 1/2~1/3 宽度下不可用（§3.7.2） |
| **仍是一条 `TerminalConfig`** | 分屏是**屏内分区**，不是多个终端。否则设备密钥、`EnableOperate`、打印执行终端、在线判定全部错乱 |
| **固定均分** | V1.1 只做等宽均分（2 栏 50/50、3 栏 33.3/33.3/33.3），**不支持拖拽调宽**；`WidthWeight` 字段预留不启用 |
| **每栏独立筛选** | 每栏有自己的分类 Tab / 状态筛选 / 搜索框，**互不影响**；顶部只保留全局信息（时间、连接状态、告警条） |
| **一个 Pane 可绑多个档口** | 允许（如"热菜档 + 汤档"合成一栏），按并集过滤 |

#### 3.7.2 为什么只支持单菜视图

| 视图 | 1/2 宽（约 900px） | 1/3 宽（约 600px） |
|------|--------------------|--------------------|
| **单菜视图** | ✅ 平铺清单，天然适配 | ✅ 行变窄，菜名两行折行即可 |
| 桌台视图 | ⚠️ 卡片约 200px，菜名挤成一行 | ❌ 卡片碎成条形 |
| 合菜视图 | ❌ 本身是左右双栏，再横切变 6 栏 | ❌ 不可用 |

#### 3.7.3 数据模型（`TerminalPane`，V1.1 建表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `Uid` | Guid | 主键 |
| `TerminalId` | Guid | 所属终端 |
| `PaneIndex` | int | 0/1/2，显示顺序 |
| `StationIds` | nvarchar(MAX) | **本栏关联的档口**（GUID 逗号分隔，允许 1~N 个） |
| `PaneTitle` | nvarchar(64) | 栏标题（默认取档口名，可自定义） |
| `SortMode` | Enum | 本栏排序：`WaitDuration`（默认）/ `TableOrder` |
| `WidthWeight` | decimal(5,2) | 宽度权重（**V1.1 固定 1.0，不启用**） |
| `DefaultFilter` | nvarchar(MAX) | 本栏默认筛选（JSON，可空；运行时筛选状态另存终端本地） |
| `CreatedAt` / `UpdatedAt` / `IsDeleted` | — | 审计字段 |

`TerminalConfig` 增加 `PaneLayout`：`Single`（V1 唯一可选）/ `Split2` / `Split3`。

#### 3.7.4 分发逻辑（关键实现点）

`OrderDetail.CurrentStationId` 是**单值**（当前阶段主档口，§2.2.1），但一条明细可能同时命中多个档口。分屏要判断"该进哪一栏"，必须知道**命中集合**：

```
Master 下发时额外带 DTO 字段 MatchedStationIds（不落库，组装时计算）

明细进入第 i 栏 ⟺ Pane[i].StationIds ∩ 明细.MatchedStationIds ≠ ∅
```

| 情况 | 行为 |
|------|------|
| 命中集合与某栏档口有交集 | 该栏显示此明细 |
| **同时命中两栏的档口** | **两栏都显示**（与广播语义一致），并触发配置告警 `MULTI_STATION_SAME_STAGE`（重复出品风险，§2.11.2） |
| 某栏档口无任何明细命中 | 该栏显示空态，**不隐藏该栏**（避免栏宽跳变） |
| 推送量 | **不变**：Master 仍按终端 `StationIds` 并集推送一次，分栏是本地渲染分发，无额外网络开销 |

#### 3.7.5 配置校验（与 §5.1 合并执行）

| 校验 | 规则 | 违反后果 |
|------|------|----------|
| `PANE_STATION_SUBSET` | 每栏 `StationIds` ⊆ 终端 `StationIds` | 越界看到未绑定的档口品项 |
| **`PANE_STATION_OVERLAP`** | 任意两栏的档口**不得重叠** | 同一道菜在两栏重复显示，师傅做两遍 |
| **`PANE_COVERAGE_GAP`** | 所有栏的档口并集 = 终端 `StationIds` | 有档口配了但没有任何栏显示 → **静默漏单** |
| `PANE_COUNT_MATCH` | `Split2` 需 ≥2 个档口、`Split3` 需 ≥3 个（允许留 1 栏空） | 空栏或配置无意义 |

#### 3.7.7 与其他能力的关系

| 能力 | 影响 |
|------|------|
| 综合屏 | 分屏是它的进阶形态：综合屏 = 多档口**混合**一栏；分屏 = 多档口**各占一栏**。综合屏继续保留（只读大屏） |

| 心跳 / 在线 | 一个终端一个心跳，不变 |
| 性能 | 单屏仍 ≤300 明细；分栏后按栏渲染，虚拟滚动要求不变 |
