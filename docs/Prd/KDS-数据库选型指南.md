# KDS 数据库选型指南（SQLite / SQL Server）

> 版本：v6.68　对应章节：§8.2 / §8.3
> 读者：售前、实施、客户 IT、架构评审
> 一句话：**门店默认 SQLite；需要 SQL Server 时，优先独立实例，兼容"与 POS 同实例"但必须隔离，拒绝"与 POS 同库同名的表"。**

---

## 1. 结论先行

| 场景 | 推荐 | 理由 |
|------|------|------|
| **单店 / 小店（< 15 屏）** | **SQLite**（默认） | 零安装、零运维、不占客户服务器、**POS 挂了 KDS 照跑** |
| 大店 / 多档口（15~30 屏） | SQLite 仍可用；若已有 DBA 与服务器 → 独立 SQL Server 实例 | 单店数据量 90 天约 0.5~1GB，SQLite 完全够 |
| **连锁多店 + 总部汇总** | 门店 **SQLite**，总部 **SQL Server**（独立实例） | 门店不产生运维负担；总部做跨店分析 |
| 客户要求"库放我们服务器" | **同实例、不同 database**（次选）；独立实例（首选） | 见 §4 |
| 客户要求"放 POS 同一个库里" | ⚠️ **拒绝**（可退让到"同实例不同库"或"同库不同 schema"） | 见 §4.3 |
| 云托管 / SaaS | SQL Server（Azure SQL / 云数据库）或 服务端 SQLite（单机） | 与部署形态匹配 |

---

## 2. 两种引擎的能力对比

| 维度 | SQLite | SQL Server |
|------|--------|-----------|
| 部署形态 | **嵌入式**，随 Master 进程运行，单文件 | 独立服务，需安装与运维 |
| 安装成本 | **0**（程序自带） | 需装服务器、配账号、开端口 |
| 运维成本 | **≈0**（自动维护窗口） | 需 DBA 或客户 IT：备份、索引、磁盘、升级 |
| 并发模型 | **单写者**（多读并行，WAL） | 多写并行、行锁、读写不互斥（开 RCSI） |
| 写入吞吐 | 单店完全够（划单是低频小事务） | 高并发强项 |
| 数据量 | 几十 GB 可用（单库） | TB 级 |
| 跨库/跨表高级能力 | 弱（无存储过程、无跨库） | 强（但本设计**不依赖**） |
| 备份 | **复制文件**（须在 checkpoint 后/停写时） | 原生备份 + 日志链 + 时间点恢复 |
| 高可用 | 无（单文件） | AlwaysOn / 镜像 / 日志传送 |
| 故障影响面 | **仅影响本机** | 实例级故障影响所有库 |
| 与 POS 的耦合 | **零耦合** | 可能被迫同实例（风险，见 §4） |
| 授权费 | **免费** | 按核收费（Express 版免费但有上限） |
| 适合的恢复目标 | RPO：分钟级（靠文件备份频率） | RPO：秒级（日志备份） |

### 2.1 SQLite 的关键短板与对策

| 短板 | 影响 | 本设计的对策 |
|------|------|--------------|
| **单写者** | 并发写排队 | 进程内 `SemaphoreSlim(1)` 串行 + 写事务短（见性能设计 §3.3） |
| 无高可用 | 磁盘坏 = 数据丢 | **每日自动备份 + 云端上报统计**（§14）；明细可重建靠归档卷 |
| 备份需停写 | 备份期间不能写 | 用 `VACUUM INTO`（在线快照，不阻塞写） |
| 无网络访问 | 只能本机 | 屏幕全部经 Master 访问，**本来就不直连库** |
| 大表改列类型=重建表 | 变更风险 | V1 冻结字段类型；变更走维护窗口 |

> **`VACUUM INTO 'backup.db'`** 是 SQLite 的原生在线快照，**不阻塞写**——这条解决了"备份要不要停机"的疑虑。

### 2.2 SQL Server 的关键代价

| 代价 | 说明 |
|------|------|
| 运维负担 | 客户得有 IT 能管：磁盘满、备份失败、索引碎片、补丁 |
| 授权成本 | Standard 按核计费；Express 免费但有限制 |
| **版本被环境绑架** | 若与 POS 同实例，版本由 POS 决定（§4.2） |
| **故障域扩大** | 实例挂 = 所有库挂（§4.4） |

## 3. 场景选择矩阵（细化版）

| # | 场景 | 屏幕数 | 数据量/90天 | 推荐 | 备注 |
|:-:|------|:------:|------------:|------|------|
| 1 | 快餐 / 单档口小店 | 1~3 | < 200MB | **SQLite** | 极端简单，客户可能没有服务器 |
| 2 | 中型正餐单店 | 5~15 | 500MB~1GB | **SQLite** | 默认形态 |
| 3 | 大型正餐多档口 | 15~30 | 1~2GB | SQLite 或独立 SQL Server | 看客户是否有服务器/DBA |
| 4 | 宴会厅 / 团餐（一单多桌） | 10~20 | 1~2GB | 独立 SQL Server | 报表与联台统计压力大 |
| 5 | 连锁门店（每家单店） | 每店 3~10 | 每店 < 1GB | **门店 SQLite + 总部 SQL Server** | 门店不占客户 IT 资源 |
| 6 | 中央厨房 / 配送中心 | — | 大 | SQL Server | 与 POS/ERP 集成多 |
| 7 | 客户统一 IT 管控（要求入集中库） | 任意 | 任意 | 同实例不同库 / 独立实例 | 见 §4 |
| 8 | 云托管（SaaS） | 任意 | 任意 | 云 SQL Server / 云托管 SQLite 卷 | 按平台能力 |
| 9 | 客户只有 SQL Server 2008 | 任意 | 任意 | **SQLite**（首选）；或单独装 Express 2019/2022 | 见 §5 |

## 4. 专项：**与 POS 共用同一个 SQL Server 实例**

> 这是客户最常见的诉求（"我们已经有 SQL Server 了，别再装一个"）。必须分四种情况讨论，**结论完全不同**。

### 4.1 四种共存方式

| 方式 | 隔离度 | 结论 | 说明 |
|------|:------:|:----:|------|
| **A. 独立实例 / 独立服务器** | 最高 | ✅ **首选** | 故障域、版本、备份、权限全独立 |
| **B. 同实例、不同 database** | 中 | ⚠️ **可用（次选）** | 必须按 §4.5 清单配置 |
| **C. 同库、不同 schema**（`kds.OrderDetail`） | 低 | ⚠️ 退让方案 | 备份/升级/故障域仍耦合，且要 POS 厂商同意改库 |
| **D. 同库、同名表 / 共用表** | **无** | ❌ **坚决拒绝** | 见 §4.3 |

### 4.2 同实例的八个风险（逐条给出对策）

| # | 风险 | 具体表现 | 对策 |
|:-:|------|----------|------|
| 1 | **版本被绑架** | 实例是 SQL 2008 → KDS 最低要求 2012 达不到 | 见 §5 决策树；**不要为它降 EF Core**（§8.3.3） |
| 2 | **资源争抢** | POS 午市结账 + KDS 出餐高峰完全重叠，CPU/IO 抢不到 | 独立文件组 + 独立磁盘；SQL 2016 企业版可用 Resource Governor 限 POS 报表 |
| 3 | **故障域合并** ⚠️ | 实例挂 = POS 与 KDS 同时挂 | 见 §4.4，**这是最需要客户书面确认的一条** |
| 4 | 备份互相影响 | POS 大库全备时 IO 打满，KDS 划单变慢 | **KDS 库独立备份计划**，避开 POS 全备时段 |
| 5 | 恢复互相影响 | 恢复 POS 库可能拖住实例 | KDS 库独立恢复演练；不接受"整实例还原" |
| 6 | 权限混乱 | 用一个高权限账号图省事 | 独立登录 + **仅限 KDS 库的 `db_owner`**，禁止 `sysadmin` |
| 7 | 排序规则冲突 | POS 库用 `Chinese_PRC_CI_AS`，KDS 若要不同 | KDS 库**单独指定 collation**（CREATE DATABASE 时定），不继承实例默认 |
| 8 | 升级耦合 | 升 SQL Server 要两家一起排停业窗口 | 合同写明升级协调责任；或选独立实例避免 |

### 4.3 为什么坚决拒绝"同库同名表 / 共用表"

| 原因 | 说明 |
|------|------|
| **命名必然冲突** | 几乎所有餐饮 POS 都有叫 `Order` / `OrderDetail` / `Table` 的表。KDS 的 26 张表要挤进去必然改名 → 破坏 §1.5 命名统一 |
| **权限无法隔离** | 同库内无法只给 KDS 部分表权限而不影响 POS；一旦给宽，KDS 的 bug 可写坏 POS 账单 |
| **备份粒度太粗** | 无法只备份/恢复 KDS 数据 |
| **升级死锁** | 任一方改表都要协调停机 |
| **数据责任不清** | 出账目问题无法界定是哪方写坏的 |
| **契约被破坏** | 本设计核心是"**KDS 与 POS 只走接口，不共享库**"（§9.0 解耦原则）——同库直接违反 |

> **如果客户坚持"一个库"**：可退让到 **C 方式（同库不同 schema）**，且必须同时满足：① POS 厂商书面同意建 schema；② KDS 账号对该 schema 之外无任何权限；③ 明确"升级需双方协调"。**A/B 仍优先。**

### 4.4 故障域：这一条必须让客户签字

本设计的核心韧性之一：**POS 挂了，厨房还能继续做已下单的菜**（明细已在 KDS 库，屏幕走推送，不依赖 POS 在线）。

| 部署方式 | POS 服务挂 | **SQL Server 实例挂** | KDS 还能做菜吗 |
|----------|:----------:|:---------------------:|:--------------:|
| KDS 用 SQLite | ✅ 不受影响 | — | ✅ **能** |
| 独立实例 | ✅ 不受影响 | KDS 库也不可用 | ✅ 能（**实例没挂就行**） |
| **同实例** | ⚠️ 视 POS 是否同实例 | **两个都挂** | ❌ **不能** |

> → **同实例会牺牲"数据库层面的故障隔离"**。若客户接受，请在实施确认单写明：*"KDS 与 POS 共用同一 SQL Server 实例，实例故障将同时影响收银与后厨，该风险由甲方知悉并接受。"*

### 4.5 同实例部署的强制配置清单

| # | 项 | 要求 |
|:-:|----|------|
| 1 | **独立 database** | 名称建议 `Kds_<StoreCode>`，`CREATE DATABASE` 时指定 `COLLATE` |
| 2 | **独立登录** | 专用 SQL 登录或域账号，**只授予该库 `db_owner`**；禁止 `sysadmin` / `securityadmin` |
| 3 | **独立文件组与磁盘** | 数据 `.mdf` 与日志 `.ldf` 分盘；与 POS 库不同物理盘 |
| 4 | **独立备份计划** | KDS 库每日全备 + 每小时日志备；**不与 POS 备份窗口重叠** |
| 5 | **RCSI** | `ALTER DATABASE Kds_xxx SET READ_COMMITTED_SNAPSHOT ON` |
| 6 | **兼容级别** | 与实例一致；**实例版本必须 ≥ 2012**（推荐 2016+） |
| 7 | **不建跨库查询** | KDS 与 POS 之间**禁止**跨库 JOIN / 同义词；只走 HTTP 接口 |
| 8 | **资源限制（可选）** | 企业版 2016+ 可用 Resource Governor 给 KDS 池设 CPU/内存上限，防 POS 报表拖垮 |
| 9 | **监控独立** | KDS 自己监控库大小、慢查询、备份结果；不依赖客户 DBA |

## 5. SQL Server 2008 决策树

> 背景：客户实例是 2008 时，**KDS 最低要求 2012**（EF Core 3.0+ 固定生成 `OFFSET…FETCH`，见 §8.3.1）。

```
客户实例是 2008 / 2008 R2，且要求"放我们库里"
│
├─ ① 能否升级实例到 2012+？
│    └─ 能 → ✅ 升级（最干净，一次性投入）→ 走 §4.5 同实例配置
│
├─ ② 能否让 KDS 用自己的库（不占实例）？
│    └─ 能 → ✅ **KDS 用 SQLite**（本设计默认形态）
│             优点：零依赖、不受实例版本影响、POS 挂了 KDS 照跑
│             这是**最推荐的答案**
│
├─ ③ 能否给 KDS 单独装一个免费的 Express？
│    └─ 能 → ✅ 装 **SQL Server Express 2019 / 2022**（独立实例，不动 POS）
│             限制：**单库 10GB / 内存 1GB / 4 核**（够单店，见下方容量核算）
│             注意：Express **没有 Agent**，定时任务由 KDS Master 自身调度
│
└─ ④ 以上都不行
     └─ ⚠️ 只能为该项目单独实现 `Kds.Infrastructure.Legacy`（纯 Dapper，分页改 ROW_NUMBER）
         成本 +40%，且仅在该客户运行，测试覆盖易空
         ❌ **不采用"降 EF Core 到 2.x"**（理由见 §8.3.3）
```

### 5.1 Express 够不够用（单店核算）

| 项 | 估算 | 结论 |
|----|------|------|
| 90 天明细 + 日志 | 约 **0.5 ~ 1GB** | 远低于 10GB |
| 统计表（永久） | 每年 < 50MB | 无压力 |
| 内存需求 | 1GB buffer pool 足够（SQLite 只配 32MB 缓存） | 够 |
| CPU | 单店划单极低频，4 核上限绰绰有余 | 够 |
| **要盯的** | `EventLog` / `OperationLog` 保留期 + 日志文件增长 | 若超 10GB，先归档/清理日志 |

> **Express 的 10GB 是"单库上限"，不是总量**。归档卷是独立 SQLite 文件，不占 Express 空间。

## 6. 在两种引擎之间迁移

### 6.1 SQLite → SQL Server（升配 / 客户要求入集中库）

| 步 | 操作 | 注意 |
|:-:|------|------|
| 1 | 停 KDS Master（或进入维护模式） | 必须先停写 |
| 2 | 用**同一套 EF Core Migration** 在目标 SQL Server 建库 | 模型一致，无需改代码 |
| 3 | 按表顺序导出/导入（父表先）：`StoreConfig` → `TerminalConfig` → 主数据 → `OrderHeader` → `OrderTableRel` → `OrderDetail` → 其余 | 外键约束顺序 |
| 4 | 校验行数（逐表对比 `COUNT(*)`）与抽样校验 | 必须全表行数一致 |
| 5 | 切换连接串 → 启动 → **全量重同步各屏** | 屏幕缓存需重建 |
| 6 | 单店跑一天再切回生产 | 演练 |

> 迁移工具建议：自写小工具（用 EF Core 双上下文读/写），**不要用第三方通用迁移器**——Json/`datetimeoffset` 字段易出错。

### 6.2 SQL Server → SQLite（降配 / 简化运维）

同理，反向执行；注意：SQLite **单写者**，切换后若并发变高需确认写串行化已生效。

### 6.3 切换的配置影响

| 配置 | 影响 |
|------|------|
| `ArchiveVolume.Engine` | 归档卷引擎随之变更（本地卷默认 SQLite，可保持） |
| 备份策略 | SQLite → 文件级 + `VACUUM INTO`；SQL Server → 原生备份 |
| 维护任务 | SQLite 需 `VACUUM`/`ANALYZE`；SQL Server 需索引维护 + 统计更新 |
| 监控 | 改为监控对应引擎的指标（性能设计 §9） |

## 7. 成本对比（定性）

| 项 | SQLite | SQL Server Express | SQL Server Standard |
|----|--------|-------------------|---------------------|
| 授权费 | **0** | **0** | 按核收费（需询价） |
| 服务器 | 不需要（随 Master） | 需一台/一实例 | 需一台/一实例 |
| 运维人力 | **≈0** | 低 | 中（需 DBA 或客户 IT） |
| 单库上限 | 无硬限（受文件系统） | **10GB** | 无 |
| 内存上限 | 系统内存 | **1GB buffer pool** | 系统内存 |
| 客户依赖 | **无** | 需装实例 | 需装实例 + 授权 |
| **总拥有成本** | **最低** | 低 | 中~高 |

## 8. 一句话总结

| 问题 | 答案 |
|------|------|
| 门店用什么？ | **SQLite**（默认，零运维，POS 挂了也能做菜） |
| 什么时候用 SQL Server？ | 连锁总部汇总 / 客户统一 IT 管控 / 宴会大店报表压力大 |
| 能不能和 POS 同一个实例？ | **能，但必须"同实例不同库" + §4.5 九条配置**；故障域风险要客户签字 |
| 能不能和 POS 同一个库？ | **坚决拒绝**（退让极限：同库不同 schema，且需 POS 厂商书面同意） |
| 客户是 SQL 2008 怎么办？ | ①升级 ②KDS 用 SQLite（首选）③单独装 Express 2019/2022 ④纯 Dapper 改造（不做） |
| 要不要为 2008 降 EF Core？ | **不要**——换来的只是一个分页开关，付出整套现代能力与安全基线（§8.3.3） |
