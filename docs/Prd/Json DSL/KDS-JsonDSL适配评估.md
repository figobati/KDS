# KDS 与 JSON DSL —— 适配性评估

> **输入基线**：`../KDS-完整PRD与设计文档-v6.md`（v6.59，6057 行）
> **参照物**：`PricePolicyDSL.md`（DSL v1 规格）+ `PricePolicy.md`（为什么生成 JSON 不是 C#、表达力边界、三条纪律）
> **本文只回答一个问题**：KDS 的设计里，**哪些地方适合用 JSON DSL 表达，哪些地方不适合**。
> 本文不产出具体 DSL 规格——A 级项各自另立 spec（照 `PricePolicyDSL.md` 的结构：结构总览 / 字段语义 / 求值 / 校验 / 回译 / 验收）。

---

## 0. 一句话结论

**KDS 里已经有 4 处"看不见的 DSL"，它们今天就在干 DSL 的活，却一项 DSL 能力都没有。**

| 隐形 DSL | 今天长什么样 | 它在干的 DSL 的事 |
|---|---|---|
| 档口反选（§2.2 / §9.10） | 3 个逗号分隔 GUID 字符串 + 硬编码四象限公式 | 路由谓词 = 条件 + 结论 + 冲突解决 |
| 品项工序路径（§2.4 / §9.11） | `"Prep,Cook,Expo"` 和 `"Prep>Cook,Cook>Expo"` | 流程图 = 节点 + 边 |
| 合菜归集（§2.3.2 / §2.3.3） | 7 个 `Merge_*` 开关 + 一段"条件加锁"伪代码 | 归集键生成策略 |
| 打印路由（§9.18 / §16.2–16.4） | `PrintRule`(阶段×档口→模板+触发+打印机) + 三步去重 | 规则表 + 优先级解析 |

所以真正的问题不是"要不要引入 DSL"，而是 **把已经隐性存在的东西显性化**；同时必须明确划出 **6 类不该 DSL 化的东西**，否则会滑向 `PricePolicy.md` §4.4 说的"内部平台效应"。

**第二个收益可能比第一个更快兑现**：文档里现存的 **12 处口径自相矛盾**（§8），全部属于"一份 schema + 一个校验器跑一遍就会报错"的类型。也就是说，把这些规则变成机器可读的**第一步不是获得新能力，而是让作者自己的矛盾当场暴露**。

## 1. 判定尺子

### 1.1 五条正向判据（全中才值得做）

| # | 判据 | 判断问法 |
|---|---|---|
| **P1 纯判定** | 输入快照 → 输出结论，零 I/O、零历史、无副作用 | "求值时要不要查库 / 看今天的记录？" 要 → 出局 |
| **P2 词表封闭** | 条件维度可枚举（≤10）、结果型可枚举（≤5） | "条件能不能列成一张字段表？" 不能 → 出局 |
| **P3 组合爆炸** | 今天的实现是"平铺字段 + if 链"，加一个维度是**乘法** | "再加一个维度要改几处代码 / 几张表？" 只改 1 处 → 不值得 |
| **P4 必须回译** | 配错了后果是**漏单 / 重复出品 / 送错桌**，店长要在保存前看见结论 | "店长能不能读懂当前配置到底命中什么？" 能（如两个排序枚举）→ 不值得 |
| **P5 冲突必须显式** | 多条规则可能同时命中，必须回答"谁赢" | "两条都命中时会怎样？" 文档答不上来 → 必须做 |

### 1.2 六条反向判据（命中任一就不做）

| # | 不做 | 理由 |
|---|---|---|
| **N1** | 状态机（§2.6.4 转移表、§2.15 全量枚举） | 转移表是**代码契约**。DSL 化等于允许门店在后台改状态机；且失去静态可达性分析与终态保证 |
| **N2** | 依赖时间推进 / 历史 / 计数（计时、等叫清零、限次） | 纯函数边界不成立——`PricePolicy.md` §4.3 已把同类需求判为"不是设计不够好，是它本来就不是纯函数" |
| **N3** | 算法 / 归一化 / 排版（`MergeKey` 归一化、打印折行、金额摊分） | **不可配置是安全属性**。允许门店配归一化规则 = 允许把"牛肉面"和"牛肉面（加辣）"配成同一张卡 = 做错菜 |
| **N4** | 需要 I/O 才能算（报表、节假日日历） | 归装配器。规则若需要上下文之外的数据，**那它不是规则，是流程**（`PricePolicy.md` §3 硬约束 3） |
| **N5** | 已经是正确的简单形态（§4.4.2 两层超时阈值） | 文档自己写了"只有两层，不要复杂化"。DSL 化是净损失 |
| **N6** | 容错策略（降级 / 默认值 / 跳过规则） | 把降级规则做成可配 = 允许门店把系统配崩。**容错写在引擎里 + 单测矩阵，不进 schema** |

### 1.3 与价格场景的四处本质差异（照抄 PricePolicyDSL 会错）

| 维度 | PricePolicy | KDS |
|---|---|---|
| **输出形态** | 标量（一个价）+ `appliedRuleIds` | **集合**（一组档口 / 一组 PrintJob）**+ 诊断**（`warnings[]`，且诊断本身就是产品功能 §2.11.2） |
| **冲突语义** | 同组互斥 + **跨组链式施加**（×0.8×0.89） | **互斥选取**（防重复出品）或 **并集收集**（广播需一对多）——没有"链式"这个概念 |
| **求值规模** | 单笔点单 < 1ms | 单条 < 10µs，但 `Menu.Sync` 后可触发 **2000 品项 × 50 档口 = 10 万次**批量判定，须 < 1s |
| **无兜底** | 无规则命中 → 返回原价（安全兜底） | **不能有兜底**。路由兜底到"随便一个档口"= 送错桌。必须显式 `onNoMatch: skipStage / warn / reject` |
| **输入维度** | 商品 × 时间 | 商品 × **阶段** × 时间 × 餐段 × 订单类型（同一品项在不同阶段落不同档口，价格没有"阶段"） |

## 2. 现状盘点：4 处隐形 DSL + 4 处半 JSON

### 2.1 四个隐形 DSL（它们是 DSL 的退化形态）

| # | 位置 | 现状形态 | 已有能力 | 缺失能力 |
|---|---|---|---|---|
| 1 | §2.2 / §9.10 档口反选 | `IncludeTypeIds` / `ExcludeItemIds` / `IncludeItemIds` 三个 `nvarchar(MAX)`，格式 `,g1,g2,` | 有语义（D1 四象限）、有真值表、有 SQL、有内存投影 | 无 schema、无版本、无可扩展维度、**不可回译** |
| 2 | §2.4 / §9.11 工序路径 | `StagePath = "Prep,Cook,Expo"`；`AutoFlowStages = "Prep>Cook,Cook>Expo"` | 有优先级（品项 > 品类 > 默认）、有 6 条降级规则 | **用了自造 `>` 微语法**却无 schema；降级规则是 6 个 `if` 无测试矩阵 |
| 3 | §2.3.2 / §2.3.3 归集 | 7 个 `Merge_*` bit + "`(Merge_DiffFlavor ? '' : #Taste)`"式条件加锁伪代码 | 有 5 条硬边界、有默认全开的商业理由 | 「哪些维度参与 key」被写法而不是数据；硬边界（规格恒参与、称重不合并）**只写在文档里，没进 schema** |
| 4 | §9.18 / §16.3–16.4 打印路由 | `PrintRule`(阶段×档口) + 三步去重 + 「聚合粒度是模板属性」 | 有去重顺序、有拆单算法 | 无冲突表达（同阶段同档口两条规则同时命中怎么办）、无 `priority` |

> **一个必须点出来的判断**：逗号字符串是**最差的中间态**——它有 DSL 的复杂度，没有字段的类型安全，也没有 schema 的校验能力。三个字段 `IncludeTypeIds`/`ExcludeItemIds`/`IncludeItemIds` 恰好把"条件"和"动作"混在同一层，导致 §2.2 那条 `(T ∧ ¬E) ∨ (¬T ∧ W)` 的隐式优先级（黑名单优先）**只能靠文档里一段"⚠️ 边界说明"来传达**。

### 2.2 四处"半 JSON"（已有 JSON 外壳，无 schema）

| 位置 | 现状 | 缺什么 |
|---|---|---|
| `StoreConfig.MealPeriods`（L3066 / §2.13.3） | `[{"Code":"Breakfast","Start":"06:00","End":"10:30"},…]` | 无 schema；"必须首尾相接覆盖整个营业日"是**可校验的区间分区不变量**，现在只是 prose |
| `Workflow.StageStandardSeconds`（L3458） | "阶段标准工时 JSON" | **文档没说结构**——这正是 §0.1 使用约定里明令禁止的"结构同前" |
| `LocalizedText`（§9.16） | `{"zh-CN":"…","en-US":"…"}` | 有回退链约定，无 schema；`{0}` / `{name}` 占位符集合是**可机器比对**的（§11.7 已给出正则） |
| 分组键协议（§3.0.3 / §3.1.4） | `"ZT:"+OrderId+":"+TableId`、`"G:"+OrderId+"\|"+Area`、`"O:"+OrderId` | 字符串拼接当结构化键用：改一个分隔符全体换 key，且**不可校验**（终端只会照拼） |

## 3. 分级结论总表

| 级别 | 对象 | 现状形态 | 命中判据 | 建议形态 |
|:--:|---|---|---|---|
| **A1** | **档口路由策略** | 3 个逗号字符串 + 硬编码四象限 | P1 P2 P3 P4 P5 | **`RoutePolicy` DSL**（条件树 + `group`/`mode` + `priority`） |
| **A2** | **打印路由** | `PrintRule` 表 + 三步去重 | P1 P2 P3 P4 P5 | **`PrintPolicy` DSL** |
| **B1** | 事件契约 | prose + 散落 JSON 片段 | 结构而非规则 | **JSON Schema**（判别联合 + 错误码 enum + 不变量断言） |
| **B2** | 工序路径 / 自动流转边 | `"Prep,Cook,Expo"` / `"Prep>Cook,…"` | P2 P3（P1 部分） | **`stageGraph`**（`stages[]` + `edges[]`，非规则引擎） |
| **B3** | 报表口径 | 20+ 条口径散在 prose，出现两套公式 | P2 P4 | **`ReportSpec`**（编译到 SQL，**不进纯函数引擎**） |
| **C1** | 终端视图配置 | `TerminalConfig` **约 45 个平铺列**，含 9 个 `Merge_*`（7 合并 + 2 联台） | 无 P5 | **`ViewProfile`** 版本化 JSON 子对象（收敛，不做 DSL） |
| **C2** | 合并条件 | 7 开关 + 条件加锁伪代码 | 无 P5；N3 拦住了主体 | **`keyFacets: [{field, normalize}]` 有序数组**（归一化仍不可配） |
| **C3** | 语言包 / 占位符 | JSON 已有，9 项自检已有 | 无 P5 | **JSON Schema + 插值 spec** |
| **C4** | 自检项（路由 10 + 打印 7 + 多语言 9） | prose 表格 | 每条检查是一段代码 | **统一 `CheckResult` 注册表**（`Code/Level/Category` 三件套已定，§11.7.5） |
| **D** | 状态机 / 计时 / 归一化 / 排版 / 归档 MOVE / 保留策略引擎 | — | N1 N2 N3 N6 | **不做**（见 §7） |

## 4. 草案一：`RoutePolicy`（A1，最高价值）

### 4.1 为什么是它

1. **责任最大**：配错的后果是**漏单**（`STATION_NO_SCREEN`，致命）与**重复出品**（`MULTI_STATION_SAME_STAGE`，高）。这是 KDS 唯一"配置写错就当场损失营业"的地方。
2. **表达力已经撞到天花板**：三个字段只能表达"类型白名单 ± 单品黑白名单"。而这些**真实门店需求今天根本写不出来**：
   - 早餐档口只在 06:00–10:30 收单（§2.13.3 已经有 `MealPeriod` 枚举，路由用不上）；
   - 外卖单不经过堂食传菜档口（`OrderType` 已有，路由用不上）；
   - 沽清品项不再进某档口（`SoldOut` 已有，路由用不上）。
   → 现状只能靠**人肉在开业/闭市时改配置**。
3. **文档自己已经造了一个"人肉回译器"**：§2.11.1 可见性追溯、§2.11.2 自检、§2.11.4 路由总表（`● ◐ ○ ●!` 四态）。一个系统需要专门做三张表来解释"我的配置到底命中了什么"，说明**它缺的不是展示，是可回译的源**（`PricePolicy.md` §4.4 纪律 2）。
4. **冲突无法结构性消灭**：现在"多个档口同时命中"只能在运行期报警。而价格场景已经给了解法——**同组互斥 + priority**——能把"重复出品"从"运行期告警"变成"配置期不可能"。

### 4.2 上下文与输出

```json
// RouteContext —— 值对象，纯输入，零 I/O（装配器负责取数）
{
  "storeId": "…",
  "itemUid": "…",
  "typeUid": "…",
  "tags": ["酒水"],
  "orderType": "DineIn",        // DineIn | Takeout
  "mealPeriod": "Lunch",        // 由装配器按 §2.13.3 算出
  "now": "2026-10-21T12:30:00", // 门店本地墙钟
  "isSoldOut": false
}

// RouteResult —— 集合 + 诊断（诊断是产品功能，不是副产品）
{
  "itemUid": "…",
  "stage": "Cook",
  "stations": [
    { "stationId": "…", "role": "Cook", "matchedRuleId": "R-HOT-COOK", "matchedBy": "TypeInclude" }
  ],
  "appliedRuleIds": ["R-HOT-COOK"],
  "warnings": []                // MULTI_STATION_SAME_STAGE / STAGE_NO_STATION 由引擎直接产出
}
```

> 注意：`stage` 是**求值维度**而非输入常量——同一品项在 `Prep` 与 `Cook` 两次调用，结果不同。这是与价格 DSL 最大的结构差异。

### 4.3 规则形状

```json
{
  "schemaVersion": 1,
  "storeId": "…",
  "revision": 12,
  "onNoMatch": "skipStage",
  "rules": [
    {
      "id": "R-HOT-PREP", "label": "热菜切配档口", "stage": "Prep",
      "group": "prep", "priority": 100,
      "when": { "types": ["<热菜typeUid>"], "not": { "tags": ["酒水"] } },
      "then": { "type": "routeTo", "stationId": "<热菜切配1>" }
    },
    {
      "id": "R-BREAKFAST-COOK", "label": "早点档口只在早餐时段收单", "stage": "Cook",
      "group": "cook", "priority": 300,
      "when": { "mealPeriods": ["Breakfast"], "types": ["<早点typeUid>"] },
      "then": { "type": "routeTo", "stationId": "<早点档口>" }
    },
    {
      "id": "R-DINEIN-EXPO", "label": "堂食才进总传菜", "stage": "Expo",
      "group": "expo", "priority": 100,
      "when": { "orderTypes": ["DineIn"] },
      "then": { "type": "routeTo", "stationId": "<总传菜>" }
    },
    {
      "id": "R-BANQUET-COOK", "label": "宴席菜同时落两个炒锅档口（显式允许一对多）", "stage": "Cook",
      "group": "cook-multi", "mode": "collect", "priority": 200,
      "when": { "tags": ["宴席"] },
      "then": { "type": "routeTo", "stationIds": ["<炒锅1>", "<炒锅2>"] }
    }
  ]
}
```

### 4.4 三个关键设计决定

**① `group` + `mode: exclusive | collect`**

- `exclusive`（默认）：同组内只取 `priority` 最大的**一条** → **`MULTI_STATION_SAME_STAGE` 从"运行期告警"变成"配置期不可能"**。这是 §2.11.2 想做但做不到的事。
- `collect`：同组并集 → 显式表达"这道菜确实要两个档口同时看"（广播模式需要）。**"想一对多"必须是作者的显式选择**，否则一律互斥——与 `PricePolicyDSL` §6.2 同一条哲学。

**② `not` 取代 D1 的隐式"黑名单优先"**

D1：`(TypeIncluded ∧ ¬ItemExcluded) ∨ (¬TypeIncluded ∧ ItemIncluded)`

新写法：`{ "types":[...], "not": { "items":[...] } }` —— 可读、可回译、能表达任意组合。但 **"白名单仅在类型未命中时生效" 这条隐式规则会消失**（那是文档 §2.2 专门加来防"三重矛盾"的）。所以：

> **DSL 化的第一件事不是加能力，是出等价性报告**——把每店现有三字段翻译成规则，然后对 2000 品项 × 50 档口逐格比对新旧结果（照 `PricePolicyDSL` A13 "与旧 `ApplyPriceRule` 逐值一致"的做法）。差异格必须人工确认，不许默认放行。

**③ `onNoMatch` 必须显式三选**

现在 §2.5 写死"未命中任何档口 → 跳过该阶段 + `Warning`"。这是一个**歧义点**被写成了默认行为：跳过意味着该工序形同不存在（§2.11.2 `STAGE_NO_STATION` 列为"高"严重度）。DSL 里它必须是作者的显式选择：`skipStage` / `warn` / `reject`。

### 4.5 回译：把 §2.11.4 的路由总表变成引擎输出

```
R-HOT-PREP   热菜切配档口                                   [组 prep · 优先级 100]
  当：品项类型属于「热菜」且不带「酒水」标签
  则：路由到「热菜切配1」

R-BREAKFAST-COOK   早点档口只在早餐时段收单                  [组 cook · 优先级 300]
  当：餐段属于「早餐」且品项类型属于「早点」
  则：路由到「早点档口」

—— 生效结果（宫保鸡丁 · Cook 阶段）——
  ● 热菜制作1（R-HOT-COOK）   ● 热菜制作2（R-HOT-COOK）
  ⚠ 同阶段命中 2 个档口 = 重复出品（exclusive 组下不可能发生，collect 组下为设计意图）
```

四态（`● ◐ ○ ●!`）**不再需要另写一套解析器**（§2.11.4 明确要求"与自检共用同一个路由解析器，禁止各写一套"）——它直接就是引擎的输出渲染。

### 4.6 校验（生成期 + 加载期都跑）

| # | 检查 | 例子 |
|---|---|---|
| 1 | 字段闭集（`types/items/tags/mealPeriods/orderTypes/not/all/any`） | `"categories"` → 拒绝（应为 `types`） |
| 2 | `group` 必填；同组同 `priority` = 错误 | 两条 `cook/100` |
| 3 | `exclusive` 组内跨档口指向必须同 role | `cook` 组里出现 `Expo` 档口 → 拒绝 |
| 4 | `stationId` 必须属于本店且启用（现在是"运行时跳过不存在项"） | 已删档口残留 |
| 5 | 能力核对：装配器填不出来的字段出现在规则里 → 拒载整份策略 | 类比 `PricePolicyDSL` §8-8 与 P7 |
| 6 | 覆盖率检查：每个角色阶段至少有一条可达规则 | 否则整阶段静默跳过 |

**校验失败保留上一版策略**（`PricePolicyDSL` §8 同款）——新版本进草稿态等人工确认，绝不顶掉能跑的好配置。

### 4.7 性能与缓存

- 编译一次 → 内存 `HashSet` 索引（沿用 §9.10 已有的 `StationIndex` 投影思路，只是把"硬编码四象限"换成"编译后的规则树"）；
- 缓存 key = `(storeId, ConfigVersion)`——`TerminalConfig.ConfigVersion` / 门店配置版本已经存在（L3145），**不需要新造版本机制**；
- 预算：单条 < 10µs；10 万次批量 < 1s；**禁止在请求路径上解析 JSON**（`PricePolicy.md` §3 硬约束 2）；
- 配置变更 → 后台重建 → 原子换引用（§9.10 已有"配置变更时重建 StationIndex"的约定）。

### 4.8 迁移与验收

| # | 用例 | 判据 |
|---|---|---|
| R1 | 旧三字段 → 新规则等价性 | 2000 品项 × 50 档口逐格一致（差异 0 或全部人工确认） |
| R2 | 黑名单优先 | 类型命中 + 在黑名单 + 也在白名单 → 排除（D1 原语义） |
| R3 | `exclusive` 防重复出品 | 两条同组规则同时命中 → 只落 priority 最大者，`warnings` 为空 |
| R4 | `collect` 一对多 | 两条同组 `collect` → 落 2 个档口，且矩阵视图显示两个 `●` |
| R5 | 阶段维度 | 同一品项 `Prep` 落 A、`Cook` 落 B，互不干扰 |
| R6 | `onNoMatch` 三态 | `skipStage` 写 `Warning`；`reject` 拒载文档 |
| R7 | 回译 | JSON → 中文与 `label` 一致；不一致进人工确认 |
| R8 | 自检不变 | §2.11.2 十项判定结果与改造前逐项一致 |
| R9 | 性能 | 10 万次批量 < 1s；单条 < 10µs |
| R10 | 版本切换 | 改配置 → `ConfigVersion` 递增 → 缓存立即生效 |

## 5. 草案二：`PrintPolicy`（A2）

### 5.1 为什么

- `PrintRule` 是 `(阶段 × 档口) → 模板 + 触发 + 打印机`，**已经是规则表的形状**，缺的只有 `priority` 与冲突语义；
- 后果同样是"漏单/重复出单"：§16.3 明确「若打印机绑屏，同一道菜会被每块屏各打一张 → 重复出单，而后厨无法分辨这是第二份菜还是重复单据」；
- §16.4 的「聚合粒度是模板属性，不是触发点属性」+ 拆单算法（`ItemSlip` 按条 / `OrderSummary` 按 `OrderId` / `ItemSummary` 按 `MergeKey`）**必须有明确的归属规则**，否则"整桌划出几张单"永远说不清；
- 店长必须能回答"这个档口这个阶段到底出哪几张单"——**这是最容易出错、最难自查的配置**。

### 5.2 形状

```json
{
  "id": "P-STIRFRY-SLIP", "label": "炒锅档口划单完成出跟盘单",
  "group": "stirfry-print", "priority": 100,
  "when": {
    "stage": "Cook",
    "stations": ["<炒锅>"],
    "triggers": ["OnStageComplete"],
    "orderTypes": ["DineIn"]
  },
  "then": {
    "type": "print",
    "templateId": "<ItemSlip.zh-CN>",
    "target": "auto",      // auto | masterDirect | terminalDirect
    "copies": 1
  }
}
```

### 5.3 边界（必须写清，否则会越界）

| 留在代码里 | 理由 |
|---|---|
| 拆单算法（按 `OrderId` / `MergeKey` / 明细分组） | 是算法不是规则（N3） |
| 执行通道选择与三步去重（MasterDirect → TerminalDirect → Pending） | 是实现细节 + 兜底，属容错策略（N6） |
| 渲染（`EscPos` / `Image`）、折行、列宽 | 排版是算法；**但版式语义（`TasteLayout`、不截断、数量右对齐）可以做 schema**——见 §7「打印排版」的取舍 |
| 重试 / 死信 | 是队列语义 |

### 5.4 回译

```
P-STIRFRY-SLIP  炒锅档口划单完成出跟盘单                  [组 stirfry-print · 优先级 100]
  当：阶段是「制作」且档口是「炒锅」且触发时机是「本阶段划单完成」且订单类型是「堂食」
  则：用模板「划菜单（跟盘单）·简体中文」打印 1 份，执行通道自动选择
```

## 6. 草案三：`stageGraph`（B2，不是规则引擎）

### 6.1 现状

```
Workflow.StagePath      = "Prep,Cook,Expo"          ← 逗号序列
Workflow.AutoFlowStages = "Prep>Cook,Cook>Expo"     ← 自造 `>` 箭头微语法
```

`>` 语法说明作者**已经意识到这是图**，只是没给它 schema。加上 §2.4 那 6 条降级规则（未知阶段丢弃 / 顺序重排 / 去重 / 全非法降级 `[Expo]` / 无档口跳过）**全是 if，没有测试矩阵**。

### 6.2 形状

```json
{
  "schemaVersion": 1,
  "stages": ["Prep", "Cook", "Expo"],
  "edges": [
    { "from": "Prep", "to": "Cook", "auto": true },
    { "from": "Cook", "to": "Expo", "auto": false }
  ]
}
```

### 6.3 关键取舍：**降级规则不可配**

`stages` / `edges` 是数据（可配、可回译、可校验）；**降级与容错策略不进 schema**（N6）：

| 异常输入 | 处理 | 谁负责 |
|---|---|---|
| 未知阶段名 | 丢弃 + `Warning` | 引擎（硬编码） |
| 顺序颠倒 | 按系统序重排 | 引擎（硬编码） |
| 重复 | 保留首次 | 引擎（硬编码） |
| 全非法 → 空 | 降级 `[Expo]` + `Error` | 引擎（硬编码） |

理由很直接：**允许门店配"出错时怎么办"，等于允许门店把系统配崩**。这四条要的是**单测矩阵**，不是配置项。

### 6.4 图校验（`stageGraph` 真正的收益）

- 无环、可达（每个 `stage` 至少被一条 `edge` 或作为入口可达）；
- `auto: true` 的边必须两端都有档口承接（否则自动流转会卡住）；
- `stage` 集合 ⊆ `Prep/Cook/Expo`（角色闭集）且与档口 `Role` 一致；
- 终态必须有定义（§2.15 L1358 已经明确要求「**是否终态必须集中定义为一个常量集合**」——把它落到一份数据里）。

## 7. 明确不该 DSL 化的六件事

| # | 对象 | 命中判据 | 硬做的后果 |
|---|---|---|---|
| 1 | **状态机**（§2.6.4 转移表 / §2.15 全量枚举） | N1 | 门店能改状态机 → 终态失去保证；且转移表本身是"3 主 + 4 辅助"的代码契约。**该做的是把转移表变成数据驱动测试矩阵，不是引擎** |
| 2 | **计时**（§4.4.1 / §2.16.3 起算点、等叫清零） | N2 | "等叫清零重算"依赖状态历史 + 当前时刻。DSL 求值必带「当前秒」，缓存即失效（`PricePolicy.md` §3 硬约束 1 直接破防） |
| 3 | **归集归一化**（§2.3.3 `Normalize`） | N3 | 允许配归一化 = 允许把「牛肉面」与「牛肉面（加辣）」配成同卡 = **做错菜**。只有"哪些维度参与 key"可配（C2），**怎么归一化不可配** |
| 4 | **打印排版语言**（§16.4.2 折行 / 列宽 / `TasteLayout`） | N3 | 再造一门排版语言 = 重新实现一个 CSS 子集。正确做法是**受限 HTML 子集 + 语义块标注**，让 `EscPos` 从语义块映射，而不是让门店写排版 DSL |
| 5 | **归档 MOVE 流程**（§13.6.4 七步 + 补偿模型） | N2 N6 | "先写卷、后删主库"的顺序是**安全属性**（L4794）。可配置 = 可以把顺序配反 = 丢数据 |
| 6 | **保留策略的"流程"部分** | N6 | 保留天数、允许删什么**可以**是配置（政策）；但"校验行数 → 后删主库 → 水位续跑"这套补偿顺序不可配 |

## 8. 顺带收益：schema 会当场抓出文档里 12 处自相矛盾

这是引入 schema/DSL **最便宜的第一个收益**——不需要新能力，只需要把已有规则写成机器可读，然后跑一遍。以下每一条都是"闭集校验 / 单一来源 / 引用完整性 / 阈值区间"任一种就能拦下的：

| # | 位置 | 矛盾 | 哪一类校验能拦 |
|---|---|---|---|
| 1 | L1419 vs L1507 | 超时判定 `≥ TotalTimeoutSeconds` 与 `⟺ ProducedSeconds > TotalTimeoutSeconds` **一个用 ≥ 一个用 >**；更严重的是**分子不同**——L1414 定义"总出品时长 = `Now/ProducedAt − OrderCreateTime − 等叫累计`"，L1508 定义 `ProducedSeconds = ProducedAt − LastFireAt` | 同一指标只能有一个表达式（单一来源） |

| 5 | L3393 + L4190 vs §4.4.2 | `Station.StageTimeoutSeconds` 承诺"档口级阶段超时阈值，优先级见 §4.4.2"，**§10.5 终端配置里还有 `StageTimeoutSeconds: {Prep:300,…}`（L4190）**，而 §4.4.2 已定「**阶段超时不显示、不判定**」 | 悬空引用 + 死字段（同一死字段出现在两处） |
| 6 | L3061 / L3062 | `WarnRatio` **在同一张表里出现两行**，类型分别是 `decimal(5,2)` 与 `decimal(3,2)` | 字段唯一性 |
| 7 | L2392 vs L3060 | 计时起点：§4.4.1 是"**起菜** `LastFireAt`"，§9.1 字段说明是"**从点菜时间**到制作完成" | 口径单一来源 |

## 9. 落地顺序与门禁

| 阶段 | 交付物 | 验收方式 |
|---|---|---|
| **P0-1** | `RoutePolicy` DSL 规格 + 校验器 + 回译器 + 旧三字段等价性报告 | §4.8 的 R1–R10；等价性差异为 0 或全部人工签收 |
| **P0-2** | 事件契约 JSON Schema（14 入站 + 6 出站 + 22 错误码 enum + 不变量断言） | §9.0 契约测试用例集可全事件回放；§11.7.6 G1 构建门禁接入 |
| **P1-3** | `PrintPolicy` DSL + 版式语义 schema（只做语义层，不碰排版算法） | "整桌划出几张单"可回译；重复出单用例为 0 |
| **P1-4** | `stageGraph` 替换两个逗号微语法 + 降级单测矩阵 | 6 条降级规则各 ≥1 用例；图校验拦非法配置 |
| **P2-5** | `ReportSpec`（编译到 SQL，双引擎） | 20+ 条口径可回译；两套对比公式不可混用可被校验拦下 |
| **P2-6** | `ViewProfile` 收敛 + `keyFacets` | 新增一个视图维度只改一处（数据），不改 DTO |

**进主干的四个前置（缺一不许合）**：

1. **校验器**（生成期 + 加载期，闭集 fail-closed）
2. **回译器**（确定性中文，与 `label` 交叉校验）
3. **黄金数据集**（联台 / 拼桌 / 换桌 / 称重 / 套餐 / 跨营业日 / 沽空）
4. **旧实现等价性报告**（逐单元比对，不是抽检）

## 10. 五条纪律（KDS 版，前三条照 `PricePolicy.md` §4.4）

1. **词表冻结**：新增一个条件维度需 ≥3 个真实门店需求支撑。
2. **回译必须全量**：渲染不出来的规则不许进 DSL。**KDS 加严一条**——每条规则必须能回答"**落到哪块屏、出哪张单**"，答不上来就不是规则，是缺字段。
3. **"表达不了"必须可观测**：统计"想配但配不出来"的比例，低于 20% 说明词表够用。
4. **容错策略不进 DSL**：降级、默认值、跳过、兜底一律硬编码 + 单测矩阵。
5. **同一事实只允许一个 DSL 表达**：不许"反选三字段"与"路由规则"两套真值并存（也正因如此，P0-1 必须先出等价性报告再切换）。
