> **输入**：`KDS-JsonDSL适配评估.md`（按 v6.59 基线撰写）
> **输出**：对 10 项建议的**逐项决定**（采纳 / 收缩 / 延后 / 不采纳）+ **可执行改动计划**
> **文档现状**：v6.78（29 表 / 72 索引，已拆为 14 章 + 5 份配套）
> **本文与评估文档的两个差异**：① 评估里的"12 处矛盾"**已全部修完**（见 §1），不再构成引入 DSL 的紧迫理由；② 评估**漏了一个落地前提**——店长不会手写 JSON，**必须配可视化编辑器**（见 §2.3），否则 DSL 只服务实施人员。

## 2. 逐项决定

### 2.1 决定总表

| 级别 | 对象 | 评估建议 | **我的决定** | 关键调整 |
|:--:|---|---|---|---|
| **A1** | 档口路由策略 | P0-1 上 DSL | ✅ **采纳，但拆两步** | Step1 只做"结构化 + 校验 + 回译"，**不加新维度**；Step2 才扩维度 |
| **A2** | 打印路由 | P1-3 | ✅ **采纳（收缩）** | 只做 `group` + `priority` + 回译；**不做执行通道/去重/排版** |
| **B1** | 事件契约 JSON Schema | P0-2 | ✅ **采纳，且提到第一位** | 成本最低、收益立现、可接 G1 门禁 |
| **B2** | `stageGraph` | P1-4 | ✅ **采纳（收缩）** | 先做 `stages`/`edges` schema + 降级单测；**`auto` 边延后**（依赖附录 B-2 未定） |
| **B3** | `ReportSpec` 编译到 SQL | P2-5 | ⚠️ **收缩为"指标口径登记表"** | **不做 SQL 编译**，只做机器可读的指标定义 + 一致性校验 |
| **C1** | `ViewProfile` 收敛 | P2-6 | ⚠️ **改为 DTO 层收敛** | **不改表结构**（45 列改 JSON 会破坏 EF 迁移与索引，收益不足） |
| **C2** | `keyFacets` | P2-6 | ⏸️ **延后** | 7 个 bit 已正常工作；替换收益中等、回归成本高，放在 A1 之后评估 |
| **C3** | 语言包 schema | P3-7 | ✅ **采纳** | 已有 9 项自检，补 schema 即可 |
| **C4** | 统一 `CheckResult` 注册表 | P3-7 | ✅ **采纳** | §11.7.5 已定 `Code/Level/Category/Detail`，只是没统一实现 |
| **D** | 状态机 / 计时 / 归一化 / 排版 / 归档 MOVE / 保留流程 | 不做 | ✅ **完全赞同** | 六条反向判据（N1–N6）判断准确，尤其 **N3"不可配置是安全属性"** |

### 2.2 三个"收缩"的理由（这是本文与评估文档的主要分歧）

**B3 不做 SQL 编译**

| 评估设想 | 问题 |
|---|---|
| `ReportSpec` 编译到查询计划，双引擎通用 | ① SQLite 与 SQL Server 的 `P90`、`窗口函数`、`日期函数`语义差异大，一份 spec 编两套 SQL 等价于写两遍；② 20+ 条口径里真正的分歧只有 **2 条公式**（#1 和 #11），**用登记表 + 单测就能锁住**，不值得为它建编译器 |

**采用**：`ReportSpec` = **机器可读的指标登记表**（指标名 / 公式 / 分子分母定义 / 依赖表 / 允许的维度），配套**一致性单测**（同一指标只有一个公式，出现第二版即测试失败）。

**C1 不改表结构**

| 评估设想 | 问题 |
|---|---|
| `TerminalConfig` 45 列收敛为 `ViewProfile` JSON 子对象 | ① EF Core 对 JSON 列的索引支持有限，`Merge_*` 这些要参与查询的字段进 JSON 会退化；② 双引擎 JSON 查询语法不同（SQLite `json_extract` vs SQL Server `JSON_VALUE`）；③ 迁移与回滚成本高，收益只是"列少一点" |

**采用**：表结构不动，**在应用层加 `TerminalViewProfile` DTO**，把 45 列按语义分组（视图/合并/操作/语音），**UI 与接口按 DTO 组织**。列还在库里，但开发者看到的是分组对象。

**C2 延后**

7 个 `Merge_*` bit 已经工作，且**合并条件是门店最不敢动的配置**（动错就并错菜）。把它换成 `keyFacets` 有序数组，**收益是"加维度更容易"**，但代价是**全量回归 + 门店重新理解**。建议**等 A1 的编辑器跑顺、店长适应了结构化配置之后再做**。

### 2.3 评估文档漏掉的一个落地前提：**可视化编辑器**

> 评估文档有"**回译**"（DSL → 中文），但没有回答"**店长怎么改**"。
> 如果只能手写 JSON，这套 DSL 就**只服务实施人员**——门店想改个档口还得打电话找我们，那还不如现在的三勾选框。

**所以 A1/A2 必须成对交付两样东西**

| 交付物 | 作用 | 不做会怎样 |
|--------|------|------------|
| **回译器**（DSL → 中文） | 店长看懂"现在到底命中什么" | 配错了看不出来 |
| **可视化编辑器**（中文 → DSL） | 店长自己改，不经手 JSON | **DSL 退化为实施专用工具** |

**编辑器形态（V1 最小）**

```
┌─ 档口路由 ─────────────────────────────────────────────┐
│ [制作] 阶段    [+ 新增规则]        [查看生效结果]        │
│                                                        │
│ ① 热菜制作档口          组:制作 · 优先级 100    [编辑][删]│
│    当 品项类型 ∈ {热菜}  且  标签 ∉ {酒水}              │
│    则 路由到  热菜制作1、热菜制作2                       │
│    ⚠ 同组命中 2 个档口（本组为"并集"模式，属设计意图）    │
│                                                        │
│ ┌─ 编辑规则 ────────────────────────────────────────┐  │
│  │ 规则名  [热菜制作档口            ]                │  │
│  │ 条件    品项类型 [选择…]  ▾                       │  │
│  │        [+ 加条件]  组合方式 ● 全部满足 ○ 任一满足  │  │
│  │ 动作    路由到 [热菜制作1 ▾] [+ 再加一个档口]      │  │
│  │ 组      [制作 ▾]    优先级 [100]                  │  │
│  │                        [取消]  [保存]             │  │
│  └───────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘
```

**关键：条件维度用下拉，不让店长打字段名**。JSON 只是存储格式，**不是用户界面**。

**预置模板**（降门槛的关键）：新建门店时给一组"典型规则模板"（热菜/凉菜/酒水各一档），店长只需选档口，不用从零搭条件。

## 3. 改动计划

### 3.1 阶段划分与工作量

| 阶段 | 交付物 | 依赖 | 估算 | 验收 |
|:----:|--------|------|:----:|------|
| **P0-A** | **事件契约 JSON Schema**（14 入站 + 6 出站 + 错误码 enum + 不变量断言）+ G1 门禁接入 | 无 | **3~4 人日** | 契约测试用例集可全事件回放；非法报文在 schema 层被拒 |
| **P0-B** | **`RoutePolicy` Step1**：结构化（`when`/`then`/`group`/`priority`）+ 校验器 + **回译器** + **旧三字段等价性报告** | 无 | **8~10 人日** | R1 等价性差异为 0 或全部人工签收；R8 自检十项逐项一致 |
| **P0-C** | **`RoutePolicy` 可视化编辑器** + 预置模板 | P0-B | **6~8 人日** | 店长能在无实施人员协助下改规则并看到"生效结果" |
| **P1-A** | **`RoutePolicy` Step2**：扩维度（`mealPeriod` / `orderType` / `isSoldOut`）+ `mode: collect` | P0-B、P0-C | **4~5 人日** | 三张真实门店需求（早餐档口/外卖不走传菜/沽清联动）能配出来 |
| **P1-B** | **`PrintPolicy`**：`group` + `priority` + 回译（不碰执行通道/去重/排版） | P0-B（复用校验器） | **4~5 人日** | "整桌划出几张单"可回译；重复出单用例为 0 |
| **P1-C** | **`stageGraph`**：`stages`/`edges` schema + 6 条降级单测矩阵 | 无（`auto` 边另计） | **3~4 人日** | 6 条降级各 ≥1 用例；图校验能拦非法配置 |
| **P2-A** | **`ReportSpec` 指标登记表** + 一致性单测 | 无 | **3~4 人日** | 同一指标出现第二版公式即测试失败 |
| **P2-B** | **语言包 schema** + **统一 `CheckResult` 注册表** | 无 | **2~3 人日** | 三类自检（路由/打印/语言）共用同一出口与同一结果模型 |
| **P2-C** | `TerminalViewProfile` DTO 层收敛 | 无 | **2 人日** | 接口字段按语义分组；**表结构不变** |
| **P3** | `keyFacets` 评估（做不做另议） | P1-A | 评估 1 人日 | 给出"加维度省多少处改动"的量化对比 |

**合计（P0+P1）约 33~40 人日**；P2/P3 约 8~10 人日。

> **建议排期原则**：**P0-A 先做**（成本最低、能立刻接门禁）；**P0-B 与 P0-C 必须成对验收**（只有回译没有编辑器，等于没解决门店自主配置）。

### 3.3 进主干的四个前置（沿用评估文档，全部同意）

| # | 前置 | 为什么不能省 |
|:-:|------|-------------|
| 1 | **校验器**（生成期 + 加载期，闭集 fail-closed） | 没有它，DSL 只是"格式更花的逗号字符串" |
| 2 | **回译器**（确定性中文，与 `label` 交叉校验） | 没有它，店长看不懂自己的配置 |
| 3 | **黄金数据集**（联台 / 拼桌 / 换桌 / 称重 / 套餐 / 跨营业日 / 沽空） | 没有它，等价性报告不可信 |
| 4 | **旧实现等价性报告**（逐单元比对，不是抽检） | 路由改错的代价是**漏单**，抽检等于赌博 |

### 3.4 我会加为第五个前置：**回滚开关**

| 项 | 说明 |
|----|------|
| 内容 | `StoreConfig.RoutePolicyMode = Legacy` / `Dsl`（默认 `Legacy`，试点门店切 `Dsl`） |
| 作用 | 上线后若发现漏单，**一个开关切回旧实现**，不用回滚版本 |
| 配合 | DSL 为唯一真值 + 三字段作为**生成产物**双写一版（评估文档 §11-1 的建议，同意） |
| 期限 | 试点 2 周无差异后，下个大版本删旧实现与开关 |

## 4. 风险与对策

| 风险 | 后果 | 对策 |
|------|------|------|
| **等价性验证不彻底** | 漏单（致命） | R1 必须逐格比对 2000 品项 × 50 档口；差异**全部人工签收**，不许默认放行 |
| **门店学不会** | DSL 只有实施用 | P0-C 编辑器 + 预置模板；**编辑器不验收，DLS 不算交付** |
| **两套真值并存** | 三字段与规则打架 | 双写一版 + `RoutePolicyMode` 开关 + 明确"DSL 为唯一真值，三字段是产物" |
| **词表膨胀** | 变成"内部平台" | 纪律：新增一个条件维度需 **≥3 个真实门店需求**支撑（评估文档 §10-1，同意） |
| **回译与实现不一致** | 店长看到的中文与实际行为不同 | 回译器的输出**直接来自编译后的规则树**，不另写一套解析（这条评估文档 §4.5 讲得很好） |

## 5. 一句话决定

| 问题 | 答案 |
|------|------|
| 值不值得改？ | **值得**，但优先级不是评估文档给的顺序 |
| 先做什么？ | **① 12 处矛盾（已做完）② 事件契约 Schema ③ RoutePolicy Step1 + 编辑器** |
| 最大的坑是什么？ | **不是技术，是"店长改不了"** —— 没有可视化编辑器，DSL 就是给实施用的高级配置 |
| 哪些坚决不做？ | 状态机 / 计时 / 归一化 / 排版语言 / 归档流程 / 保留流程（六条反向判据成立） |
| 什么时候能看出收益？ | **P0-A 完成就能接 G1 门禁**（约 3~4 人日）；**P0-B+P0-C 完成后门店能自助改路由**（约 15~18 人日） |
