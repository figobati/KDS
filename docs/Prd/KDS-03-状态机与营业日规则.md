### 2.11 路由自检与品项可见性追溯

> **背景（非抢单模式下的必要性评估）**：系统采用 Broadcast（无抢单、无分派），品项一进档口就推给该档口**所有**同角色屏。这带来两个必须区分的问题：
>
> | 现象 | 是否异常 | 说明 |
> |------|:--------:|------|
> | 同一品项出现在**同档口的多块屏**上 | **正常** | 这正是广播模式的设计意图（谁有空谁做，划单后实时移除）。**不能作为告警项**，否则天天误报 |
> | 同一品项在同一阶段被**多个不同档口**接收 | **异常** | 两个档口各做一遍 → **重复出品**，而且在广播模式下没有"锁定"能挡住它 |
>
> 结论：**该做的是"路由闭环自检"，不是"多屏重复检查"。**

#### 2.11.1 品项可见性追溯（"这道菜会显示在哪几块屏上"）

**用途**：配置反选规则后验证、新品上线确认路由、现场投诉"这道菜没出现"时定位、多阶段流转落点核对。

**输入**：`ItemCode`（或 `DishItem.Uid`）+ 可选 `StoreId`。
**输出**（按阶段展开）：

```json
{
  "ItemCode": "FOOD001",
  "DishName": "宫保鸡丁",
  "DishTypeId": "guid-type-hot",
  "StagePath": ["Prep", "Cook", "Expo"],
  "Stages": [
    {
      "Stage": "Prep",
      "MatchedStations": [
        { "StationId": "guid-st-1", "StationName": "热菜切配1", "MatchedBy": "TypeInclude" }
      ],
      "ReceivingScreens": [
        { "TerminalId": "guid-t-01", "TerminalName": "切配屏1", "Role": "Prep", "Online": true, "EnableOperate": true }
      ],
      "Warnings": []
    },
    {
      "Stage": "Cook",
      "MatchedStations": [
        { "StationId": "guid-st-2", "StationName": "热菜制作1", "MatchedBy": "TypeInclude" },
        { "StationId": "guid-st-3", "StationName": "热菜制作2", "MatchedBy": "ItemInclude" }
      ],
      "ReceivingScreens": [
        { "TerminalId": "guid-t-02", "TerminalName": "制作屏1" },
        { "TerminalId": "guid-t-03", "TerminalName": "制作屏2" }
      ],
      "Warnings": ["MULTI_STATION_SAME_STAGE"]
    }
  ]
}
```

> 关键：**"多屏"正常展示，`MatchedBy` 说明命中的是哪条规则**（`TypeInclude` / `ItemInclude`），`Warnings` 只报真问题。

#### 2.11.2 路由自检（全量扫描，输出问题清单）

| 检查项 | 判定 | 严重度 | 后果 |
|--------|------|:------:|------|
| `STATION_NO_SCREEN` | 某启用档口没有被任何启用终端绑定 | **致命** | 该档口品项**无人接单**（漏单） |
| `STAGE_NO_STATION` | 某品项的 StagePath 阶段在本店无任何档口承接 | 高 | 该阶段被静默跳过，工序形同不存在 |
| `ROLE_NO_SCREEN` | 某档口 `Role = X`，但门店没有启用中的 `Role = X` 屏绑定它 | 高 | 同上（角色维度） |
| **`MULTI_STATION_SAME_STAGE`** | 同一品项在同一阶段命中 **>1 个档口**（综合屏除外） | **高** | **重复出品**（两档口各做一次），广播模式无法拦截 |
| `ROLE_MISMATCH` | 终端 `Role` 与其绑定档口 `Role` 不一致 | 高 | 屏幕收到错误阶段的品项 |
| `SCREEN_NO_STATION` | 非综合屏未绑定任何档口 | 中 | 该屏永远无数据 |
| `SCREEN_DISABLED_BUT_BOUND` | 终端已停用但仍绑定档口，且该档口无其他屏 | 中 | 等价于 `STATION_NO_SCREEN` |
| `AUTO_CREATED_TABLE` | 存在 `DiningTable.IsAutoCreated = 1` | 低 | 桌台资料不全，需补录 |
| `PANE_STATION_OVERLAP`（V1.1） | 分屏时任意两栏绑定同一档口 | 高 | 同一道菜在两栏重复显示，师傅做两遍 |
| `PANE_COVERAGE_GAP`（V1.1） | 分屏时某终端档口未被任何栏覆盖 | **致命** | 该档口品项在本屏无栏显示 → 静默漏单 |

**执行时机**：

1. **保存配置后自动跑一次**（档口 / 屏幕 / 档口反选 / 品项 StagePath 任一变更）→ 有致命或高危项则**阻止保存**或强提示；
2. **每日定时跑一次** → 结果进管理端"健康检查"页；
3. **手动触发**（管理端按钮）。

#### 2.11.3 非抢单模式下的取舍结论

| 需求 | 是否有必要 | 理由 |
|------|:----------:|------|
| 查"某道菜显示在哪几块屏" | **有必要（V1 做）** | 路由是隐式推导（反选规则 × 档口 × 屏幕绑定），不给人看就只能靠猜；漏单时这是第一诊断工具 |
| 自检"某菜绑到同角色多块屏" | **没必要作为告警** | 广播模式下这是**正常态**；只看"多屏"会天天误报，反而淹没真问题 |
| 自检"同阶段命中多个档口" | **必须做（V1）** | 这才是广播模式真正的重复出品风险，且无法靠乐观锁发现（两条明细各自独立） |
| 自检"档口无屏 / 阶段无档口 / 角色不匹配" | **必须做（V1）** | 静态配置错误 → 静默漏单，上线才发现代价极高 |

> **与抢单模式的对比（说明为什么这里更依赖自检）**：抢单/分派模式在运行期有"锁定屏"兜底，重复制作会被互斥挡住；**广播模式没有运行期互斥**，只能靠"配置期把路由查干净" + "运行期实时移除"两道防线。所以自检在广播模式下**更重要**，而不是更没必要。

#### 2.11.4 全品项路由总表（Route Matrix）

> §2.11.1 是"查单个品项"，§2.11.2 是"只看问题清单"。本节是**全量视图**：所有品项 × 所有档口的对应关系一张表看完，用于开业前核对、换菜单后复核、门店自查。

**两种视图（同一份数据，切换不重算）**

**A. 列表视图（默认）** —— 行 = 品项，命中档口以标签展示，横向不怕档口多：

| 品项 | 类型 | StagePath | 命中的档口（按角色分组） | 异常 |
|------|------|-----------|--------------------------|------|
| 宫保鸡丁 | 热菜 | Prep→Cook→Expo | **切配**：热菜切配1 ｜ **制作**：热菜制作1、热菜制作2 ｜ **传菜**：总传菜 | ⚠ 制作阶段命中 2 个档口（重复出品） |
| 可乐 | 饮品 | Cook→Expo | **制作**：吧台 ｜ **传菜**：总传菜 | — |
| 预包装小食 | 小食 | Expo | **传菜**：总传菜 | — |
| 例汤 | 汤品 | Prep→Cook→Expo | **切配**：汤档 ｜ **制作**：—（无档口） | ⚠ 制作阶段无档口承接（阶段将被跳过） |

**B. 矩阵视图** —— 行 = 品项，列 = 档口（列头按角色分组），单元格三态：

| 品项 | 切配·热菜切配1 | 制作·热菜制作1 | 制作·热菜制作2 | 传菜·总传菜 |
|------|:---:|:---:|:---:|:---:|
| 宫保鸡丁 | ● | ● | ● | ● |
| 可乐 | ○ | ● | ○ | ● |
| 预包装小食 | ○ | ○ | ○ | ● |
| 凉拌黄瓜 | ● | ○ | ○ | ● |

图例：

| 符号 | 含义 | 说明 |
|:--:|------|------|
| **●** | **命中且生效** | 该档口会收到该品项（且该阶段在 StagePath 内） |
| **◐** | **命中但阶段被跳过** | 反选规则命中了，但该品项 StagePath 不含这个角色 → **实际不会收到**。最常见于凉菜配了制作档口 |
| **○** | 未命中 | 该档口与该品项无关 |
| **●!** | 命中且生效，但**该档口当前没有可用屏** | 等价于漏单（§2.11.2 `STATION_NO_SCREEN`） |

> **为什么必须有 ◐ 这一态**：命中和生效是两件事。配置界面上"勾选了热菜"看起来是命中，但若该品项的 StagePath 是 `Prep,Expo`（跳过制作），制作档口永远不会收到它。只显示"命中/未命中"会让门店反复检查一个其实没错的配置，或误以为配置没生效。

**判定口径（三态算法，与自检共用同一引擎）**

```
对每个 (品项 i, 档口 s)：
    Hit   = §2.2 反选判定(i, s)
    Stage = s.Role                                  // 档口角色
    InPath = Stage ∈ StagePath(i)                   // 该阶段是否在品项路径里
    HasScreen = 存在启用终端绑定 s（同角色）

    Hit 且 InPath 且 HasScreen  → ●
    Hit 且 InPath 且 !HasScreen → ●!（漏单风险）
    Hit 且 !InPath              → ◐
    !Hit                        → ○
```

**筛选与排序**

| 维度 | 说明 |
|------|------|
| 关键词 | 品项名称 / 品项编码（模糊匹配） |
| 类型（品类） | 多选 `DishType` |
| 档口 / 角色 | 只看某档口或某角色的命中情况（矩阵视图下自动只显示相关列） |
| 异常筛选 | 只看：无任何档口 / 同阶段多档口 / 命中但档口无屏 / 命中但阶段跳过 / 沽清品项 |
| 排序 | 默认 **异常严重度 → 类型 → 品项名**；可切按编码 |

**交互与边界**

| 项 | 规则 |
|----|------|
| 编辑 | **本页只读**，不提供直接修改档口配置；每行提供"跳转编辑"（跳到该品项的 StagePath 或相关档口的反选配置），避免在总表上误改 |
| 导出 | 支持导出 **CSV**（含三态、异常说明），供门店打印核对 |
| 数据量 | 单店品项 ≤ 2000、档口 ≤ 50；**矩阵视图分页**（默认每页 50 行），并采用虚拟滚动 |
| 计算时机 | Master 启动后、以及档口 / 屏幕 / 反选 / StagePath / 菜单变更时**重算一次并缓存**；页面查询只读缓存，不做实时全量计算 |
| 与自检的关系 | 同一份路由计算结果：`SelfCheck` 输出**问题列表**，`Matrix` 输出**全量表格**；两者口径必须一致（共用同一个路由解析器，禁止各写一套） |

**为什么值得做（价值判断）**

| 场景 | 没有总表 | 有总表 |
|------|----------|--------|
| 开业前配置核对 | 逐个品项点开看，2000 个品项要几天 | 一张表筛"仅看异常"，半小时核完 |
| 换季换菜单 | 不敢动反选规则，只能全量重配 | 改完看一眼矩阵，立即知道哪些品项漏了或重了 |
| 门店投诉"某菜从没出现" | 现场猜、翻日志 | 搜菜名 → 看它命中哪个档口 → 是否无屏 / 阶段被跳过 |
| 交接与培训 | 路由规则只存在老员工脑子里 | 表格即文档，新人可自查 |

### 2.12 套餐显示规则

> **核心决策**：**套餐由 POS 展开为子项明细，KDS 不显示"套餐本体"**；子项在屏上**扁平显示 + 套餐标注**，不引入第三层嵌套。

#### 2.12.1 契约要求（KDS 定标准，POS 必须遵守）

| # | 要求 | 违反后果 |
|---|------|----------|
| 1 | **套餐必须展开成子项明细**，每个子项一个独立 `LineNo` | 出现一个不可划单的"套餐A ×2"行长期挂在屏上 |
| 2 | **子项 `Qty` 必须已乘套餐份数**（点 2 份套餐 → 每个子项 `Qty = 2`） | 数量翻倍或减半——**套餐实现最典型的事故** |
| 3 | 同一套餐的子项**共享同一个 `ComboNo`**，并带 `ComboName` / `ComboSeq` / `ComboItemTotal` | 无法标注、无法聚类、打印缺"2/4" |
| 4 | **不推送"套餐本体行"**（不产生制作动作的行） | KDS 忽略该行并记 `Warning: COMBO_HEADER_IGNORED` |
| 5 | 退套餐由 POS **拆成各子项退** | KDS 不推断"退一个子项 = 退整套"（会误退） |

> 契约测试必须覆盖：单套餐、多套餐、同菜既在套餐内又单点、套餐改数量、整套餐退、单子项退。

#### 2.12.2 屏幕显示（V1：扁平 + 标注）

**每个子项独立一行**，与普通菜行同构，仅在**菜名后追加套餐标注**：

```
A05  ┌──────────────────────────────────┐
     │ 宫保鸡丁 〔双人商务餐 2/4〕   2份  │  ← 子项，标注套餐名 + 套内序号
     │ 米饭     〔双人商务餐 3/4〕   2份  │
     │ 可乐     〔双人商务餐 4/4〕   2份  │
     │ 鱼香肉丝                      1份  │  ← 普通菜，无标注
     └──────────────────────────────────┘
```

| 规则 | 说明 |
|------|------|
| 标注格式 | `〔{ComboName} {ComboSeq}/{ComboItemTotal}〕`；**同一订单只有 1 个套餐时**简化为 `〔套餐 {ComboSeq}/{ComboItemTotal}〕`（省宽度） |
| 颜色/样式 | 标注用小号灰色字，**不用彩色标签**（避免与"退/赠/催/急"标签抢注意力，§4.4.3 已定优先级） |
| 卡内排序 | **同一 `ComboNo` 的子项必须相邻**，按 `ComboSeq` 升序；套餐组之间按组内最小等待时长排序 |
| 合菜视图 | 开启 `Merge_ComboAndNormal` → 与单点同菜合并成一张卡，卡片必须显示 **"含套餐 2 份"** 聚合标签；关闭 → 套餐子项单独成卡，卡片标题带套餐名 |
| 单菜视图 | 同桌台视图，逐行标注 |
| 桌台/订单视图卡头 | **显示套餐摘要**（见 2.12.3） |

#### 2.12.3 卡片头部的套餐摘要

```
┌────────────────────────────────────────┐
│ A05  4人  ⏱12分                        │
│ 套餐：双人商务餐×1、儿童餐×1            │  ← 新增摘要行（仅在含套餐时显示）
├────────────────────────────────────────┤
│ 宫保鸡丁 〔双人商务餐 1/4〕        2份   │
```

| 规则 | 说明 |
|------|------|
| 显示条件 | 该卡片（该订单/桌台）**存在 `IsComboItem = 1` 的明细**才显示 |
| 格式 | `套餐：{ComboName}×{份数}`，多个套餐用 `、` 分隔；份数取该 `ComboNo` 的子项 `Qty`（同一套餐各子项 `Qty` 相同） |
| 位置 | 桌台号行下方，**单行显示**，超宽用 `…` 截断（摘要不承载关键信息，可截断；菜名不可截断） |
| 作用 | 让师傅/传菜**一眼看出这桌有几个套餐**，不必去数子项 |

#### 2.12.4 为什么不做"套餐分组卡"（三层嵌套）

| 原因 | 说明 |
|------|------|
| 空间不可用 | 桌台卡内已是"卡片→菜行"两层，再加"套餐组"变成三层；1/2 分屏栏与 58mm 打印单放不下 |
| 对单档口无决策价值 | 广播模式下各档口只看到自己那份子项（切配只看切配菜），"整套是否齐"不是单个档口的决策依据 |
| 齐套是传菜问题 | 真正的需求是"整套齐了才能上桌"，属于**传菜核对**场景，应做独立面板而不是塞进卡片 |

#### 2.12.5 齐套核对（V2）

独立页面（不并入主视图）：按 `ComboNo` 聚合，显示每套的 `已出 N / 共 M` 子项，全部完成时高亮；供传菜口判断"这套可以上了"。

#### 2.12.6 打印

| 模板 | 规则 |
|------|------|
| `ItemSlip`（跟盘单） | **必打套餐标注** `{{ComboLabel}}`（如 `双人商务餐 2/4`），否则传菜员不知道这张单属于套餐 |
| `OrderSummary` / `ItemSummary` | 菜名后括注套餐名（`宫保鸡丁(双人商务餐)`），便于核对 |
| 空值 | `ComboNo` 为空 → 不输出该行/该标注，不留空白 |

#### 2.12.7 套餐与路由 / 合并的关系

| 项 | 规则 |
|----|------|
| 档口路由 | **套餐不改变路由**：子项各自按 §2.2 反选规则落到自己的档口 |
| 多档口命中 | 同一子项命中多个档口 → 正常触发 `MULTI_STATION_SAME_STAGE` 告警（§2.11.2） |
| 合并条件④ | `Merge_ComboAndNormal` 只影响**合菜视图**的卡片归并，不影响明细行数与打印张数 |
| 部分划单/退菜 | 子项按 §4.6 / §4.7 独立处理，与是否套餐无关 |

### 2.13 营业日与餐段（时间口径，**全系统的日期基准**）

> **核心问题**：餐饮的"一天"不是 00:00–23:59。典型门店 **06:00 开早市**，营业到**次日 05:59**。若统计、归档、报表都用自然日，会出现三种事故：① 凌晨的单被算进"第二天"，日报数字对不上；② 归档卷把同一营业日的数据劈到两个自然月；③ 定时清理在**营业中**执行，锁库卡住出餐。
> **所以：全系统统一用「营业日 `BusinessDate`」，自然日只在日志时间戳里出现。**

#### 2.13.1 营业日定义

```
BusinessDayStartHour（门店配置，默认 06，取值 0~23）
BusinessDate(ts) = ts 在门店时区下的日期，若 time(ts) < BusinessDayStartHour 则减 1 天
```

**示例（门店配置 `BusinessDayStartHour = 6`）**

| 下单时间 | 营业日 | 说明 |
|----------|--------|------|
| 2026-10-21 06:00:00 | **2026-10-21** | 早市第一单（**含边界**） |
| 2026-10-21 18:30:00 | 2026-10-21 | 晚市 |
| 2026-10-21 23:59:59 | 2026-10-21 | 仍是 21 日 |
| 2026-10-22 **03:00:00** | **2026-10-21** | **夜宵/收尾，仍算 21 日的营业日** |
| 2026-10-22 05:59:59 | 2026-10-21 | 21 日营业日结束 |
| 2026-10-22 06:00:00 | 2026-10-22 | 新营业日开始 |

> **边界包含规则**：`ts == 起点` 属于**新**营业日（左闭右开区间 `[D 06:00, D+1 06:00)`）。必须写死，否则跨零点那 1 秒会出现"两天的单都算/都不算"。

#### 2.13.1a 营业月与营业日序列（**统计口径只认这两个**）

**营业月（`BusinessMonth`）**

```
BusinessMonth = 营业日所属的年月
营业月 2026-10 的时间范围 = [2026-10-01 06:00, 2026-11-01 06:00)
```

| 关键点 | 说明 |
|--------|------|
| **11-01 凌晨 00:00~05:59 属于 10 月营业月** | 因为它属于营业日 10-31。这不是"跨月错误"，而是营业日口径的**正确结果** |
| 月度报表 / 归档卷归属 / 日期筛选上限 | **一律用营业月**，不用自然月 |
| 与 POS 自然月账单的差异 | 差异只出现在月末 6 小时内；对账时需说明"KDS 按营业月，POS 若按自然月，月末 6 小时会归到不同月份" |

**营业日序列（用于"前 N 天""上周期"等相对区间）**

```
营业日序列 = 按 BusinessDate 升序排列的营业日
取"前 7 个营业日" = 从当前营业日往前数 7 个营业日（跳过闭店日）
```

| 规则 | 说明 |
|------|------|
| **闭店日不计入序列** | 每周固定闭店的门店，"前 7 天"= 前 7 个**有营业**的日，而不是前 7 个自然日（否则闭店日会把均值拉低） |
| 判定依据 | 该营业日存在 `DailyStoreStat` 记录（无营业则无记录） |
| 与"近 30 天"的关系 | `[近30天]` = **最近 30 个营业日**，允许跨营业月（见 §13.6.8 ①） |

> **为什么必须区分"自然日序列"与"营业日序列"**：门店周一闭店，若按自然日取前 7 天，会包含 1 个零数据日，日均被压低 14%，导致每天都显示"上升"。用营业日序列可自动排除闭店日。


#### 2.13.2 三条硬规则

| # | 规则 | 原因 |
|---|------|------|
| 1 | **按「下单时间」归属，不按「完成时间」** | 23:50 下单、00:30 完成的单属于前一天；按完成时间会把一单拆到两天，导致"前一天少了单、后一天多了单" |
| 2 | **`BusinessDate` 在入库时计算并落库为快照（`OrderHeader.BusinessDate`），之后永不重算** | 若门店事后改 `BusinessDayStartHour`，历史数据不能跟着变，否则昨天的日报今天就被改写 |
| 3 | **所有统计/归档/报表/"今日"口径一律用 `BusinessDate`** | 自然日只在技术日志（`CreatedAt`）里使用；`StatDate` 字段语义 = 营业日（§9.22/§9.23） |

#### 2.13.3 餐段（`MealPeriod`）

餐段是**营业日内的时段划分**，可跨零点：

| 餐段 | 示例区间 | 说明 |
|------|----------|------|
| `Breakfast` 早餐 | 06:00–10:30 | |
| `Lunch` 午餐 | 10:30–14:00 | 含午市高峰 |
| `Dinner` 晚餐 | 17:00–21:30 | 正餐主力 |
| `LateNight` 夜宵 | 21:30–**次日 06:00** | **跨零点**，仍属同一营业日 |

| 规则 | 说明 |
|------|------|
| 配置 | 每餐段起止时间存在 `StoreConfig`（`MealPeriods` JSON），**必须构成营业日的完整分区**（可机器校验的不变量）：① 相邻区间**首尾相接**、② **无重叠**、③ **无缝隙**、④ 并集 = `[D 06:00, D+1 06:00)`（营业日边界，§2.13.1）。非营业时段用 `Closed` 段**显式占位**，不允许留空 |
| 归属 | 按**下单时间**落 `MealPeriod`，与 `BusinessDate` 同源同快照 |
| 边界 | 左闭右开，与营业日一致 |
| 非营业时段 | 若某时段不营业（如 14:00–17:00 歇市），归属为 `Closed`，**不计入任何餐段报表**但在门店日报里单独列出（避免"总数对不上"） |

> **为什么必须在营业日框架内定义餐段**：夜宵 21:30–06:00 跨自然日，如果按自然日切，夜宵会被劈成两段，报表里永远看不到完整的夜宵数据。

#### 2.13.4 定时任务必须相对营业日边界（**原来的时间表是错的**）

> ⚠️ 原设计把聚合（03:00）、清理（04:00）定在固定钟点，**若门店营业到次日 05:59，这些任务全在营业中执行**——批量删除会锁库，直接卡住出餐。

| 任务 | 触发时机（相对营业日） | 原设计（错误） |
|------|------------------------|----------------|
| T+1 预聚合（`DailyStoreStat` / `DailyDimStat`） | **营业日结束后 + 30 分钟**（如 06:30），聚合上一个营业日 | ~~03:00~~ |
| 归档 MOVE（主库 → 历史卷） | **营业日结束后 + 60 分钟**，且不晚于下一营业日开始前 60 分钟 | ~~04:00~~ |
| 清理（日志 / Outbox / PrintJob） | 同归档窗口 | ~~04:00~~ |
| 封卷（月末） | 月末营业日结束后的归档窗口 | — |
| 归档卷上传 | 封卷后紧接执行 | ~~04:30~~ |
| `VACUUM` / `incremental_vacuum` | 每周/每季，**同一窗口**；窗口不足则跳过并顺延 | — |

```
营业日 D 的时间轴（BusinessDayStartHour = 6）：
  10-21 06:00 ═══════ 营业中（严禁任何维护任务）═══════ 10-22 05:59:59
  10-22 06:00  营业日结束
  10-22 06:30  ▶ 聚合营业日 10-21
  10-22 07:00  ▶ 归档/清理窗口（07:00 前必须结束）
```

**窗口不足的处理**：任务**只做能做完的批数**，剩余顺延到下一窗口，**绝不跨进营业时段**。宁可多天清完，也不能卡出餐。

#### 2.13.5 对查询与报表的影响

| 场景 | 口径 |
|------|------|
| "今日 / 昨日" | 当前营业日 / 上一营业日，**不是自然日** |
| 日报 / 月报 | 按 `BusinessDate` 汇总；月度 = 营业日属于该自然月的集合（**首末两天的营业日可能跨自然月**） |
| 归档卷月份归属 | 按 `BusinessDate` 的月份，**不按 `CompletedAt` 的自然月** |
| 日期区间查询 | 用户选"10-01 ~ 10-31"= 营业日区间；底层自动换算成时间戳范围 `[10-01 06:00, 11-01 06:00)` |
| 报表上显示 | 明确标注"营业日"，避免与自然日混淆；跨月营业日在两端各标注归属 |

#### 2.13.6 边界用例（必须进测试集）

| # | 用例 | 期望 |
|---|------|------|
| 1 | 05:59:59 下单 | 归前一营业日 |
| 2 | 06:00:00 下单 | 归新营业日 |
| 3 | 23:50 下单、次日 00:30 完成 | 归前一营业日（按下单） |
| 4 | 门店把 `BusinessDayStartHour` 从 6 改为 4 | **历史 `BusinessDate` 不变**；新单按新边界 |
| 5 | 月末营业日跨自然月（如 10-31 06:00 ~ 11-01 05:59） | 整段归 10 月卷 |
| 6 | 夜宵时段（21:30–次日 06:00） | 归属同一营业日、`MealPeriod = LateNight` |
| 7 | 维护任务启动时仍在营业 | **拒绝执行**，顺延到下一窗口 |

### 2.14 跨营业日未完成的处理（标记 / 清理）

> **问题**：手动流转模式下，菜可能一路没人管，营业日结束（如 06:00）时还挂在切配屏上。次日开门它还在，且 `BusinessDate` 已是昨天——**它会污染今日的"待制作数"、卡住"整桌划"、并让超时统计失真**。
> **处理原则**：**先提示、再按门店策略处理；默认只标记不清理**（不擅自替门店决定"这道菜还要不要做"）。

#### 2.14.1 判定与标记

**判定时机**：营业日切换后（维护窗口内，§2.13.4），Master 扫描一次。

```
跨营业日未完成 = BusinessDate < 当前营业日
              AND WorkflowStage ∉ { Done, Cancelled, Void, Closed }
```

| 字段 | 写入规则 |
|------|----------|
| `IsCrossDay = 1` | 命中上述条件 |
| `CrossDayDays` | `当前营业日 - BusinessDate`（挂 1 天显示"跨日 1 天"，挂 3 天显示"跨日 3 天"） |
| 恢复 | 该菜被正常划单完成或退菜后，`IsCrossDay = 0`、`CrossDayDays = 0` |

#### 2.14.2 三种处理策略（`StoreConfig.CrossDayHandleMode`）

| 模式 | 行为 | 适用 |
|------|------|------|
| **`MarkOnly`（默认）** | **只标记，不清理**。屏幕显示"跨日 N 天"红标并**置顶**；营业日切换时弹一次提示 | 绝大多数门店：昨天没做完的菜今天可能还要做（如慢炖、预订菜） |
| **`AutoClose`** | 跨日达到 `CrossDayAutoCloseDays`（默认 1）时**自动置 `Closed`** | 快餐 / 夜宵店：收市即清，不留隔夜单 |
| **`Prompt`** | 只生成"待处理清单"进管理端待办，由店长逐条决定 **清理 / 继续** | 需要人工把关的门店 |

> **为什么默认 `MarkOnly` 而不是自动清**：清理等于替门店宣布"这道菜不做了"，而它可能是客人还在等的、或次日要继续的预订菜。**替门店做决定的风险远大于多留几个标记。**

#### 2.14.3 `Closed` 状态（已清理）语义

| 项 | 规则 |
|----|------|
| 定义 | `WorkflowStage = Closed`：该菜跨营业日未完成，被**主动关闭**，不再进入任何作业流程 |
| 可见性 | **不出现在任何屏幕的待制作列表**；在管理端"跨日未完成 / 已清理"清单里可查 |
| 统计 | **不计入**待制作数、超时数、产量；单独计入 `CrossDayOpenCount`（日终仍挂着）/ `CrossDayClosedCount`（被清理） |
| 记录 | `ClosedAt` + `ClosedReason`（`CrossDayAutoClose` / 店长手动） |
| **可恢复** | 管理端可**【恢复】**：`WorkflowStage` 回到原阶段、`StageStatus = Waiting`、`IsCrossDay = 0`（误清时兜底，**不允许物理删除**） |
| 后续事件 | 已 `Closed` 的明细再收到 `StageComplete` / `Item.Remove` → 拒绝并返回 `DETAIL_CLOSED`（与 `DETAIL_CANCELLED` 区分） |
| POS 回执 | 清理时发 **`Item.Cancelled`**（`Reason = 跨日未完成自动清理`，`IsFullCancel = true`），**不新增事件类型**。POS 侧按退菜处理即可，避免再多一套契约 |

#### 2.14.4 提示与交互（用户要的"提示下"）

| 位置 | 表现 |
|------|------|
| **营业日切换时** | 管理端弹一次汇总提示：`上一营业日有 N 道菜未完成（点此查看）` |
| **作业屏** | 跨日菜加红标 `跨日 N 天`，并**置顶**（排在正常菜前面）；`MarkOnly` 模式下卡片可正常划单 |
| **屏幕顶部常驻** | 存在跨日菜时显示提示条：`跨日未完成 N 道`，点击筛选 |
| **管理端清单页** | "跨日未完成"页：按挂的天数排序，支持**单条清理 / 批量清理 / 恢复**；`AutoClose` 模式下列表只读（已被自动清理的进"已清理"页） |
| **日报** | 日报末尾列出"日终未完成：N 道 / 已清理：M 道" |

#### 2.14.5 与"整桌划 / 待制作数"的关系

| 场景 | 规则 |
|------|------|
| 整桌划是否包含跨日菜 | **包含**（否则桌上的菜永远划不掉）；但在确认弹窗里提示"其中含跨日菜 N 道" |
| 待制作数统计 | 跨日菜**计入**（它确实还没做）；`Closed` 的**不计入** |
| 超时判定 | 跨日菜超时严重（挂 N 天），**按最严重级别显示**，不做额外惩罚计算 |
| 卡片排序 | `IsCrossDay` 优先置顶，其次按等待时长 |

#### 2.14.6 配置项

| 字段 | 默认 | 说明 |
|------|------|------|
| `CrossDayHandleMode` | `MarkOnly` | `MarkOnly` / `AutoClose` / `Prompt` |
| `CrossDayAutoCloseDays` | 1 | `AutoClose` 模式下跨几日关闭（0 = 不自动关） |
| `CrossDayPromptOnSwitch` | 1 | 营业日切换时是否弹提示 |

### 2.15 品项流转状态总表（全量枚举，实现以此为准）

> 品项（`DishItem` 的一个实例 = `OrderDetail`）身上有 **3 个正交的状态维度**，外加若干标记位。**不要把它们混成一个字段**。

#### 2.15.1 主状态：`WorkflowStage`（8 态，三态流转模式）

> **V1 / V2 边界（v6.96）**：下表与 §2.15 后续各节中凡标注"**手动模式**"的**可见性**（下游屏能看上游）与**越级完成路径**，均为 **V2 实现**；**V1 恒为自动模式（`FlowMode = Auto`）**，每屏只看自己那一站，只能逐级推进（§2.7.1）。`SkippedStages` / `DirectDone` / `SkipDoneCount` 等越级审计字段**保留建表**，V1 恒为空或 0。

| # | 枚举 | 中文 | 终态 | 进入条件 | 未完成？ | 作业屏可见 | 默认排序 |
|:-:|------|------|:----:|----------|:--------:|:----------:|----------|
| 1 | `Pending` | 待分配 | ✗ | 刚下单，引擎尚未进入首阶段（毫秒级瞬时态） | ✓ | 否 | — |
| 2 | `Prep` | **待切配** | ✗ | 进入切配阶段（StagePath 含 `Prep`） | ✓ | **切配屏**（手动模式下制作屏/传菜屏也能看到） | 正常 |
| 3 | `Cook` | **待制作** | ✗ | 进入制作阶段 | ✓ | **制作屏**（手动模式下传菜屏也能看到） | 正常 |
| 4 | `Expo` | **待传菜** | ✗ | 进入传菜阶段 | ✓ | **传菜屏** | 正常 |
| 5 | `Done` | **已完成** | **✓** | 传菜完成 / 越级完成（§2.7.1） | ✗ | 否（立即移除） | — |
| 6 | `Cancelled` | **已退菜** | **✓** | 全部份数被退（`CancelledQty = Qty`），**只针对未出品份** | ✗ | **仍显示**（标红 + 删除线，禁止划单，§4.3） | 置底 |
| 7 | `Void` | **已报损** | **✓** | **已出品后作废**（`VoidQty > 0`）：做错 / 客人不满意 / 超时太久 / 打翻。**出品后退菜一律走这里**，不退回到消费成功 | ✗ | 否（进报损报表与损耗统计） | — |
| 8 | `Closed` | **已清理** | **✓** | 跨营业日未完成被关闭（§2.14） | ✗ | 否（管理端清单可见，可恢复） | — |

> **终态共 4 个**：`Done` / `Cancelled` / `Void` / `Closed`。（`Pending` 不是终态）
> **实现纪律**：**"是否终态"必须集中定义为一个常量集合**（如 `static readonly HashSet<Stage> TerminalStages = { Done, Cancelled, Void, Closed }`），禁止在各处散写 `!= Done && != Cancelled`——后续加状态必然漏改。

#### 2.15.2 阶段状态：`StageStatus`（4 态，与主状态正交）

| 枚举 | 中文 | 含义 | 计时 |
|------|------|------|------|
| `Waiting` | 待处理 | 已进入该阶段，师傅尚未动手 | 阶段计时**未开始**（`StageBeginTime` 为空） |
| `Doing` | 处理中 | 师傅已开始（打开/勾选/首次操作） | 计时中 |
| `Completed` | 已完成 | 该阶段份数全部完成或退完 | 计时停止，`StageElapsedSeconds` 定稿 |
| `Skipped` | 已跳过 | 该阶段不在 StagePath 内，引擎直接跨过 | 无时长（**记 `null` 不是 0**） |

**两者组合示例**

| `WorkflowStage` | `StageStatus` | 实际含义 |
|:---------------:|:-------------:|----------|
| `Cook` | `Waiting` | 已交制作，师傅还没开始做（手动模式下"待开始"） |
| `Cook` | `Doing` | 正在做 |
| `Cook` | `Completed` | 制作完成，即将推进到 `Expo` |
| `Expo` | `Skipped` | 该品项不需要传菜（StagePath 无 Expo），直接 `Done` |
| `Done` | `Completed` | 全流程结束 |

#### 2.15.3 二态降级：`EnableWorkflowState = 0` 时的状态

| 枚举 | 中文 | 说明 |
|------|------|------|
| `Pending` | **待出** | 未划单 |
| `Done` | **已划单** | 已划单 |
| `Cancelled` / `Void` / `Closed` | 保留 | 终态语义不变 |

> 关闭三态后：所有屏幕隐藏阶段标签（§4.1）、`StageStatus` 不再参与展示、`Closed` 与 `Cancelled` 仍生效。

#### 2.15.4 数量维度（与主状态正交，不是状态）

| 派生态 | 条件 | 展示 |
|--------|------|------|
| 未做 | `CompletedQty = 0` 且 `CancelledQty = 0` | 正常待制作 |
| **部分完成** | `0 < CompletedQty` 且 `RemainingQty > 0` | 进度 `2/3` |
| **含退份** | `0 < CancelledQty` 且 `RemainingQty > 0` | 标"含退 N 份"，其余继续做 |
| 混合（出一部分 + 退一部分） | 两者都 > 0 且 `RemainingQty = 0` | 行结束 |
| 整行退 | `CancelledQty = Qty` | 红删除线，`WorkflowStage = Cancelled` |

#### 2.15.5 标记位（布尔，不是状态机）

| 字段 | 中文 | 影响 |
|------|------|------|
| `IsGift` | 赠菜 | 展示"赠"标签，不影响流转 |
| `IsRush` | 加急 | 展示优先级高（§4.4.3） |
| `IsRemind` + `RemindCount` | 催菜 | 展示 + 统计，不影响流转 |
| `IsHold` / `IsFire` | 等叫 / 起菜 | **等叫期间计时暂停**；起菜后恢复 |
| `IsCancel` | 整行退（派生） | 仅用于红删除线与查询，**部分退看 `CancelledQty`** |
| `IsCrossDay` + `CrossDayDays` | 跨营业日 | 红标 + 置顶（§2.14） |
| `IsComboItem` + `ComboNo` | 套餐子项 | 标注套餐名与序号（§2.12） |
| `SkippedStages` | 越级跳过阶段 | `A→C` 记 `B`，统计不虚增产量（§2.7.1） |

#### 2.15.6 派生展示态（不存储，由上述字段算出）

> **时长口径统一（唯一公式）**：下表所有"时长"都是**总出品时长** = **`ProducedAt`（或 `Now`）− `LastFireAt`**（§4.4.1 / §2.16.3）。
> 等叫期间已用时长归 0，**不是**"点菜时间减去等叫累计"——那个公式（v6.55 曾用）已在 v6.56 废弃。

| 展示态 | 计算方式 |
|--------|----------|
| **预警（黄）** | 已用总时长 **≥** `TotalTimeoutSeconds` × `WarnRatio`（0.8） |
| **超时（红）** | 已用总时长 **>** `TotalTimeoutSeconds`；或用 `IsTimeout`（制作完成后定格） |
| **已出餐（定格林）** | `ProducedAt` 非空：显示定格时长 + 是否超时，时长不再增长 |
| **大单** | 该桌待制作明细数 > 门店阈值（默认 30） |
| **待开始** | `StageStatus = Waiting` 且已进入该阶段（手动模式） |
| **停滞** | `Now - StatusUpdatedAt > 阈值`（用于发现"没人管的菜"） |

#### 2.15.7 状态流转图（三态模式，完整）

```
                     ┌─────────────────────────────────────────┐
 下单 ──► Pending ──►│ Prep ──► Cook ──► Expo ──► Done         │
                     │  │        │        │                   │
                     │  └────────┴────────┴──► Cancelled（全退）│
                     │  └────────┴────────┴──► Void（报损）     │
                     │  └────────┴────────┴──► Closed（跨日清理）│
                     └─────────────────────────────────────────┘

越级路径（手动模式，§2.7.1）：
  Prep ──(制作屏操作)──► Expo        SkippedStages = Cook
  Prep ──(传菜屏操作)──► Done        SkippedStages = Cook
  Cook ──(传菜屏操作)──► Done        SkippedStages = 空
  Expo ──(传菜屏操作)──► Done        正常
```

### 2.16 通知单状态（`NotifyState`）：**KDS 定义序号，POS 填序号**

> **为什么必须由 KDS 定义，而不是解析 POS 的文本**
> ① **多语言**：POS 可能推 "等叫" / "Hold" / "保留"，文本不可比；序号唯一。
> ② **解耦**：不同 POS 的措辞、粒度不同，KDS 若认文本，每接一个 POS 就要改代码。
> ③ **稳定**：序号一经发布不改语义，**只增不改**；新增状态用预留区间，不打乱既有值。
> **契约方向（同 §9.0）**：**KDS 出标准号段，POS / 适配器负责把自己的状态翻译成 KDS 序号。KDS 不反向适配任何 POS 的文本。**

#### 2.16.1 状态号段（**10 间隔预留，只增不改**）

| 序号 | 枚举 | 中文（语言包 key） | 含义 | 计时动作 |
|:----:|------|-------------------|------|----------|
| **0** | `Unknown` | 未知 | 未收到 POS 状态（默认） | 不计时 |
| **10** | `Placed` | **已下单（待叫起）** | 已下单但尚未叫起（预订单、需人工催起） | **不计时** |
| **20** | `Fired` | **已起菜** | 厨房开始制作 | **开始 / 重新开始计时**（`LastFireAt = 发生时刻`） |
| **30** | `Held` | **等叫** | 暂停制作（客人还没到 / 要晚点上） | **停止计时并清零累计** |
| **40** | `Produced` | **已出品** | 制作完成 / 已划单 | **定格**（`ProducedAt` = 发生时刻） |
| **50** | `Cancelled` | **已退菜** | 整行退菜 | 终止 |
| **60** | `Voided` | **已报损** | 已出品后报废 | 终止 |
| **70** | `Closed` | **已清理** | 跨营业日清理（§2.14） | 终止 |
| 11/12… | *预留* | — | 未来插入 `Placed` 的细分（如"预订"、"叫起中"） | — |
| 21/22… | *预留* | — | 未来插入 `Fired` 的细分（如"加急起菜"） | — |
| 31/32… | *预留* | — | 未来插入 `Held` 的细分（如"客人未到"、"延迟上菜"） | — |

> **为什么用 10 而不是 1**：号段之间留 9 个空位，将来加状态**不必重排序号**。序号一旦发给 POS 就永久固定——重排会让已对接的 POS 全部错位。

#### 2.16.2 标记（`NotifyFlags`，位组合，与状态正交）

| 位值 | 枚举 | 中文 | 说明 |
|:----:|------|------|------|
| 1 | `Remind` | 催菜 | 可多次（`RemindCount` 累加） |
| 2 | `Rush` | 加急 | 展示优先级提升 |
| 4 | `Gift` | 赠菜 | 展示"赠"标签 |
| 8 | `Booked` | 预订 | 预订单标记（通常配合 `Placed`） |

> **状态与标记分开的理由**：一道菜可以"已起菜 **且** 催菜 **且** 赠菜"，如果全塞进一个序号会产生组合爆炸（8 状态 × 4 标记 = 32 个号）。分开后 POS 只需填两个字段。

#### 2.16.3 计时规则（**起菜起算，等叫清零**）

```
字段：
  FirstFireAt       首次起菜时刻（只写一次，用于分析）
  LastFireAt        最近一次起菜时刻（等叫后重新起菜会更新）
  HoldCount         等叫次数
  HoldAccumSeconds  等叫累计时长（仅分析，不计入超时）
  ProducedAt        制作完成时刻

当前已用时长：
  NotifyState = Held     → 冻结为 0（显示"等叫中"）
  ProducedAt 非空        → ProducedSeconds = ProducedAt - LastFireAt（定格）
  其他（Fired 中）        → Now - LastFireAt（每秒自增）
```

**三条硬规则**

| # | 规则 | 说明 |
|:-:|------|------|
| 1 | **计时起点是"最近一次起菜"，不是点菜时间** | 等叫 2 小时后再起菜，只从起菜算起——厨房不为等叫买单 |
| 2 | **等叫 = 清零重算，不是暂停累计** | 产品明确："中间换成等叫，就得等下次叫起菜重新算"。所以 `Held` 时已用时长归 0，而不是冻结在旧值 |
| 3 | **未收到起菜的兜底** | 若 POS 从未推 `Fired`，按 `StoreConfig.TreatPlacedAsFired`（默认 **1**）视为**下单即起菜**：`LastFireAt = OrderCreateTime`。否则菜品永远不计时、永不算超时 |

**超时判定**（与 §4.4.2 联动，口径修正）

```
超时 ⟺ ProducedSeconds > TotalTimeoutSeconds
ProducedSeconds = ProducedAt - LastFireAt      ← 只算最后一次起菜之后
```

#### 2.16.4 与内部状态机的映射

| `NotifyState` | → `WorkflowStage` | 副作用 |
|---------------|-------------------|--------|
| `Placed` | 保持 `Pending`（不进阶段） | 屏幕不显示（等叫起前不进作业队列） |
| `Fired` | 若 `Pending` → 进入首阶段 `Waiting` | 写 `FirstFireAt`（首次）/ `LastFireAt`（每次） |
| `Held` | 不变 | `HoldCount++`、累加 `HoldAccumSeconds`、停止计时 |
| `Produced` | 进入 `Expo` 或 `Done`（按操作屏语义，§2.7.1） | 写 `ProducedAt`、定格 `ProducedSeconds`、判 `IsTimeout` |
| `Cancelled` | `Cancelled` | 同退菜 |
| `Voided` | `Void` | 同报损 |
| `Closed` | `Closed` | 同跨日清理 |

> **双来源幂等**：`Produced` 可能来自 **POS 推送**，也可能来自 **KDS 屏幕划单**。以**先到者为准**，后到者幂等忽略（`Version` 乐观锁 + `NotifyState` 单调性校验：**状态序号只能增大，不允许回退**）。
> **唯一例外**：`Fired` 可在 `Held(30)` 之后再次到达（`30 → 20`），这是**允许的"回退"**，因为它表达的是"又起菜了"，不是状态倒退。

#### 2.16.5 多语言处理（序号 ↔ 文案）

| 层 | 用什么 |
|----|--------|
| POS → KDS 传输 | **只传序号**（`NotifyState: 30`），不传文本 |
| KDS 内部状态 | 序号（数据库存 `int`，不存字符串） |
| 屏幕 / 报表展示 | 按当前屏幕语言查语言包：`notify.state.30` → "等叫" / "Hold" / "保留" |
| 与 POS 界面对账 | 双方各自翻译各自语言，**只要序号一致就对得上** |

语言包 key 规范：

```json
{
  "notify.state.0":  "未知",
  "notify.state.10": "待叫起",
  "notify.state.20": "已起菜",
  "notify.state.30": "等叫",
  "notify.state.40": "已出品",
  "notify.state.50": "已退菜",
  "notify.state.60": "已报损",
  "notify.state.70": "已清理",
  "notify.flag.1":   "催菜",
  "notify.flag.2":   "加急",
  "notify.flag.4":   "赠菜",
  "notify.flag.8":   "预订"
}
```

> **语言包缺失时不显示序号本身**（§11.1 回退链保证）；但**数据库与接口永远只出现序号**，不出现任何语言文本。这是多语言与解耦同时满足的前提。

#### 2.16.6 前向兼容（POS 推了 KDS 不认识的序号）

| 情况 | KDS 行为 |
|------|----------|
| 序号在预留区间（如 11、35） | **忽略但记录** `Warning: UNKNOWN_NOTIFY_STATE`，不改变当前状态（**不崩、不回退**） |
| 序号超出范围（如 999） | 同上，并进健康检查清单，提示"POS 契约版本可能高于 KDS" |
| `NotifyFlags` 有未知位 | 忽略未知位，保留已知位（位运算天然幂等） |

> **"不认识就忽略"是解耦的关键**：POS 升级先于 KDS 时，KDS 只是少了一个新状态的展示，不影响出餐。

#### 2.16.7 POS 契约（POS 必须实现）
```json
// 事件：Item.Notify（POS → KDS）
{
  "PosOrderNo": "T20261021001",
  "LineNo": 2,
  "NotifyState": 30,            // ★ KDS 定义的序号，必填
  "NotifyFlags": 1,             // 位组合，可选，默认 0
  "OccurredAt": "2026-10-21T11:20:00+08:00",   // ★ POS 侧发生时刻（计时基准）
  "Remark": "客人未到"           // 可选，仅日志用，KDS 不解析
}
```

| 字段 | 必填 | 说明 |
|------|:----:|------|
| `NotifyState` | ✓ | **必须是 KDS 号段中的值**；未知值忽略 + 告警 |
| `NotifyFlags` | ✗ | 位组合；未知位忽略 |
| `OccurredAt` | ✓ | **计时以此为准**；若与 Master 时间偏差 > 5 分钟 → 用 Master 接收时间并记 `Warning: POS_CLOCK_SKEW` |
| `Remark` | ✗ | 仅落日志，**不参与任何逻辑**（避免文本依赖） |

> **对接验收**：契约测试必须覆盖 `10→20→30→20→40` 这条"起菜→等叫→再起菜→出品"的完整链路，验证**计时在第二次起菜时归零重算**。

### 2.17 报损原因（`VoidReasonCode`）：**出品后退菜的唯一出口**

> **规则（与 §4.7 一致）**：**退菜只能作用于未出品的份**；**已出品后要作废，一律走报损**，不允许把 `Done` 改回 `Cancelled`。
> 所以「出品后退菜」这个业务场景**在数据上是报损**，必须能被报表统计到——本节定义报损原因与统计口径，避免这笔成本"消失"。

#### 2.17.1 报损原因序号（KDS 定义，10 间隔，多语言）

| 序号 | 枚举 | 中文（语言包 key `void.reason.*`） | 典型场景 |
|:----:|------|-----------------------------------|----------|
| **0** | `Unspecified` | 未指定 | 操作人没选原因（允许，但报表会标"未归类"） |
| **10** | `WrongDish` | **做错菜** | 做成了别的菜、口味做反 |
| **20** | `CustomerReject` | **客人不满意** | 上桌后客人说不要了 / 说难吃 |
| **30** | `TooLate` | **超时太久** | 上来已经太晚，客人不要了 |
| **40** | `Dropped` | **打翻掉落** | 传菜途中翻洒 |
| **50** | `QualityIssue` | **质量问题** | 变质、有异物、不新鲜 |
| **60** | `GuestLeft` | **客人已离开** | 未结账走人 / 取消了整桌 |
| **70** | `OperatorError` | **操作失误** | 误点出餐、误划单 |
| **99** | `Other` | **其他** | 兜底，需配 `VoidRemark` 说明 |

> **与 `NotifyState = 60 (Voided)` 的分工**：`NotifyState` 说明"这行已报损"（**状态**），`VoidReasonCode` 说明"为什么"（**归因**）。前者必填，后者可空。

#### 2.17.2 归因与责任（经营价值）

| 原因 | 责任方 | 可改进项 |
|------|--------|----------|
| `WrongDish` / `OperatorError` | 厨房 / 收银 | 培训、复核流程 |
| `CustomerReject` / `QualityIssue` | 出品质量 | 菜品标准、食材验收 |
| `TooLate` | 节奏 / 产能 | 排产、档口负荷 |
| `Dropped` | 传菜 | 传菜路线、托盘 |
| `GuestLeft` | 前厅 | 结账流程 |

> **报表必须能按 `VoidReasonCode` 分组**，否则"报损 12 份"只是一个数字，无法指导改进。

#### 2.17.3 统计与报表（**补上"统计不到"的洞**）

**新增统计指标**（`DailyStoreStat` / `DailyDimStat`）

| 字段 | 含义 |
|------|------|
| `VoidCount` | 报损明细行数 |
| `VoidQty` | 报损份数合计 |
| `VoidAmount` | 报损金额合计（依赖 POS 推 `Amount`） |

**KPI 与报表调整**

| 位置 | 调整 |
|------|------|
| 报表首页 KPI | 在"退单数/催单数/超时数/出品数"之外**新增「报损数」**（`VoidQty`） |
| **损耗总览** | 新增合并口径：`损耗份数 = CancelledQty + VoidQty`、`损耗金额 = CancelledAmount + VoidAmount` |
| 明细报表 | **新增第 5 张：报损明细表**（`type=Void`），列：单号 / 台号 / 服务员 / 菜品 / 数量 / 单价 / 小计 / 出品时间 / **报损时间 / 时长 / 报损原因 / 报损人** |
| 排行 | 可选"易报损菜品"榜（按 `VoidQty` 排序），与"退单菜品"分开 |

**退菜 vs 报损的口径对照（必须在报表上有区分）**

| 维度 | 退菜 `Cancelled` | 报损 `Void` |
|------|------------------|-------------|
| 发生时机 | **出品前** | **出品后** |
| 损失内容 | 备料 + 少量工时 | **食材 + 工时 + 已占用产能** |
| 成本口径 | 低（可能还能回收食材） | **高（已上桌/已装盘）** |
| 报表 | 退菜明细表 | **报损明细表（新增）** |
| KPI | `CancelledQty` | `VoidQty` |

> **为什么必须分开而不是合并成一个"损失"**：退菜多说明**点单与沟通**有问题；报损多说明**出品质量与节奏**有问题。合并后这两个诊断信号就丢了。

#### 2.17.4 POS 契约（报损）

```json
// Item.Void（POS → KDS，或 KDS → POS）
{
  "PosOrderNo": "T20261021001",
  "LineNo": 2,
  "VoidQty": 1,
  "VoidReasonCode": 20,          // ★ KDS 号段；v6.99 定案：原因由 KDS 侧填，POS 可不填
  "VoidRemark": "客人说太咸",
  "OccurredAt": "2026-10-21T12:30:00+08:00"
}
```

| 规则 | 说明 |
|------|------|
| `VoidQty` 上限 | `≤ CompletedQty - 已报损份数`（**只能报损已出品的份**） |
| 原因必填？ | **可空**（`0 未指定`），但报表会把未归类单独列出，倒逼门店填写 |
| 多语言 | 同 §2.16.5：**只传序号**，展示走语言包 |
| 未知序号 | 忽略并归为 `99 其他` + 记 `Warning`（不丢数据） |
| 双向发生 | POS 可发起（客人退），KDS 管理端也可发起（做错/打翻），两条路径写同一组字段 |
| **谁填原因（v6.99 定案）** | **由 KDS 填**。报损原因是**内部成本归因**，只有厨房 / 管理端知道真实原因（做错、打翻、变质）；POS 侧只掌握"客人退了"这一层，硬要它按 KDS 号段填只会被填成 `99 其他`。因此：**POS 发 `Item.Void` 时 `VoidReasonCode` 可缺省**（schema 本就是可选），KDS 收到后由**发起报损的操作人**在屏上 / 管理端选原因；若 POS 顺手填了合法序号，KDS 直接采用、不覆盖 |

### 2.18 沽清（`SoldOut`）：停止未来售卖，**绝不隐式退菜**

> **先把三个动作的边界划线**——它们最容易被混成一个"这个菜不做了"的按钮，一旦混了账就乱：
>
> | 动作 | 作用对象 | 是否改账单 | 谁发起 |
> |------|----------|:----------:|--------|
> | **沽清 `SoldOut`** | **未来的点单** | ❌ 否 | KDS 申请 / POS 生效 |
> | **退菜 `Cancel`** | **已点但未做的份** | ✅ 是 | **仅 POS**（§4.7.2） |
> | **报损 `Void`** | **已做出来的份** | 视策略 | POS 或 KDS（§2.17） |

#### 2.18.1 沽清是什么、不是什么

| 是 | 不是 |
|----|------|
| "这道菜**从现在起不再接新单**" | ❌ 不是"已点的单作废"（那是退菜） |
| 影响 POS 菜单可点状态 | ❌ 不是"这道菜要取消制作"（那是厨房的活） |
| 可定时 / 限量自动恢复 | ❌ 不是报损（没做出来的东西谈不上报损） |

#### 2.18.2 沽清粒度

| 粒度 | 是否支持 | 说明 |
|------|:--------:|------|
| **品项级**（`DishItem`） | ✅ **V1 主用法** | "宫保鸡丁卖完了" |
| **批量品项**（管理端多选） | ✅ | 一次勾 10 个菜一起沽清 |
| 品类级（`DishType`） | ✅ 可选 | "海鲜全停"（少见，一般用批量品项替代） |
| 原料级（`Ingredient`） | ❌ **V1 不做** | KDS 没有原料/BOM 模型；用"批量品项"绕开。若后续接原料库存再评估 |
| 门店级（全店停售） | ❌ | 那是歇业，不是沽清 |

#### 2.18.3 两段式生效（**KDS 只能申请，POS 决定生效**）

```
① 厨房发现没食材
   ↓ 屏上点【沽清】→ 选品项 / 原因 / 时效（UntilManual / UntilTime / LimitedQty）
② KDS 发申请：Item.SoldOutRequest（出站，菜单动作非订单动作，PosOrderNo 可空）
   ↓
③ POS 收到 → 服务员/店长确认 → 菜单置为不可点
   ↓ 回执
④ POS 推 Item.SoldOut（入站，Status = Active）→ KDS 更新沽清状态、屏幕标记
```

> **涉及两个事件**：出站 `Item.SoldOutRequest`（申请）、入站 `Item.SoldOut`（POS 的生效 / 拒绝 / 恢复结果）。
> 事件字段定义见 `schema/`（P0-A 待补），业务规则见本节。

| 模式（`SoldOutMode`） | 行为 | 适用 |
|-----------------------|------|------|
| **`PosConfirm`（默认）** | KDS 申请 → POS 确认 → 生效；**KDS 侧处于"申请中"状态**（屏幕显示黄色"沽清申请中"） | 有服务员的门店 |
| `KdsDirect` | KDS 点沽清**立即生效**（本地标记），同时推 POS 通知；POS 应按通知更新菜单 | 快餐 / 无人确认 / POS 能力弱 |
| `PosOnly` | KDS 无沽清按钮，只能 POS 发起 → 推 KDS | POS 是唯一菜单权威的门店 |

> **为什么默认 `PosConfirm`**：菜单可点状态是**售卖决策**，影响客人点单与营收。厨房只能提供"没食材"的事实，不该单方面关掉一个菜——尤其是连锁门店，某个档口说没了，可能只是这个档口没了，别的档口还有。

#### 2.18.4 沽清的三种时效（`SoldOutType`）

| 类型 | 行为 | 典型场景 |
|------|------|----------|
| **`UntilManual`（默认）** | 一直沽清，直到人工恢复 | 食材售罄，明天进货 |
| **`UntilTime`** | 到指定时刻**自动恢复** | "午市后恢复"（备货下午到） |
| **`LimitedQty`** | **限量 N 份**，卖出 N 份后自动沽清 | "今天只剩 5 只龙虾" |

`LimitedQty` 的计数口径：**按已下单份数扣减**（不是已出品），因为下单即占库存；扣到 0 自动转沽清并推 POS。

#### 2.18.5 沽清对 KDS 屏幕的影响

| 场景 | 处理 |
|------|------|
| 屏幕品项列表 | 已沽清品项**不再出现在新增**（因为不会有新单），但作业屏本来也不展示菜单 |
| **已有订单里的该菜品** | **照常显示、照常制作**——沽清不影响已点的单 |
| 屏幕提示 | 档口屏顶部显示"本档口已沽清 N 项"，可展开查看（让师傅知道"这道菜暂时不用做了"） |
| **新单推来已沽清的菜** | **接受但标警告**：`Warning: ITEM_SOLDOUT`，屏幕该行标黄"已沽清"。**绝不静默拒单**——POS 会以为订单丢了 |
| 沽清申请中 | 标黄"沽清申请中"，师傅知道已提交、等 POS 确认 |

#### 2.18.6 沽清原因（**这里用枚举，与退菜不同**）

| 序号 | 枚举 | 中文 |
|:----:|------|------|
| 0 | `Unspecified` | 未指定 |
| **10** | `OutOfStock` | **食材售罄** |
| **20** | `EquipmentDown` | **设备故障** |
| **30** | `PrepCapacity` | **产能不足 / 做不过来** |
| **40** | `QualityHold` | **食材质量不合格** |
| **50** | `ManualStop` | **临时停售**（活动/盘点） |
| 99 | `Other` | 其他 |

> **为什么沽清可以枚举而退菜不行**：沽清是**KDS 自己发起**的动作，KDS 有权规定填什么；退菜是 **POS 发起**的外部事件，KDS 无权规定（§4.7.2）。这不是不一致，而是**发起方不同**。

#### 2.18.7 恢复

| 方式 | 触发 | 实现要点 |
|------|------|----------|
| 手动恢复 | 管理端 / POS 操作 → 推 KDS | 入站 `Item.SoldOut`（`Status = Ended`、`EndReason = Manual`） |
| 定时恢复 | `SoldOutEndAt` 到点 | **营业中即时生效**（用一个轻量定时器逐分钟扫 `IX_SoldOutLog_Status_End`），**不能等到维护窗口**——客人午市点不到、下午又能点，这才是对的 |
| 限量售完自动 | 份数扣到 0 | 下单即扣（§2.18.4）；到 0 转 `Active` 并推 POS |
| **营业日切换** | `UntilTime` 类型在跨营业日后**自动失效** | 昨天的"卖完了"不该管今天；`EndReason = CrossDay` |
| 手动恢复后 | — | `UntilManual` 同样可提前恢复（补货了） |

#### 2.18.8 沽清记录与报表

记录表 **`SoldOutLog`** —— 字段级定义见 **§9.15b**（本节不复述，避免两份口径漂移）。
状态机：`Requested`（申请中）→ `Active`（生效中）→ `Ended`（已结束）；`Requested` 被 POS 否决则 → `Rejected`。

| 报表指标 | 用途 |
|----------|------|
| 沽清品项数（日/周） | 缺货严重程度 |
| 平均沽清时长 | 补货效率 |
| **沽清期间该菜品被点次数** | **销售信息未同步的直接证据**（菜单没关及时） |
| 按原因分布 | 缺货 / 设备 / 产能，对应不同改进 |
| **沽清申请被拒次数** | 厨房判断与售卖策略的分歧 |

> 最后一条特别有价值：如果"厨房说没了、POS 拒了"频繁发生，说明**档口与前台对库存的认知不一致**，这是流程问题。

#### 2.18.9 与 `AllowKitchenCancel` 的关系（**必须写死**）

| 问题 | 答案 |
|------|------|
| 开启"允许厨房退菜"后，点沽清会**顺带**把已点的单退掉吗？ | **绝对不会。** 沽清与退菜是**两个独立动作、两套字段、两条记录** |
| 那厨房想"停止售卖 + 取消这单"怎么办？ | 分两步：① 点【沽清】→ 只影响未来；② 若还要取消本单，再点【申请取消】（生成 `Item.UnableToCook` 或 `AllowKitchenCancel=1` 时生成 `Item.Cancelled`） |
| 为了省事能不能做成一个按钮"沽清并退单"？ | **不能合成一个事件**。UI 可以提供"同时执行"的便捷操作，但**必须发出两条独立事件**，各自记账、各自可追溯 |
| 为什么这么严 | 沽清**不改账单**、退菜**改账单**。合成一条事件后，POS 无法区分"该退钱"还是"只是关菜单"，必然出错账 |

> **一句话**：**沽清管"以后"，退菜管"这一单"。** 两者永远不隐式联动。

### 2.19 操作历史与撤销（**只能回退一格，不能跳状态**）

> **需求**：每块角色屏能看**自己的历史操作**，并能撤销；但撤销有硬边界——**只能撤销"我这一手划出来的那一格"**，如果这道菜已经被推到更后面，就撤不回来了。

#### 2.19.1 可撤销性的精确判定（**四条全满足才行**）

| # | 条件 | 说明 | 不满足时 |
|:-:|------|------|----------|
| 1 | **在撤销时间窗内** | `UndoWindowSeconds`（默认 **120 秒 = 2 分钟**，门店可配 30~1800）；从操作时刻起算 | `UNDO_WINDOW_EXPIRED` |
| 2 | **明细当前状态 == 本操作的 `ToStage`** | 即"我推到的那一格还没被越过"。例：切配屏 `A→B`，现在必须仍是 `B`；若已变成 `C` → **不可撤销** | `UNDO_STATE_ADVANCED` |
| 3 | **该操作记录未被撤销过** | 一条操作只能撤一次（防来回跳） | `UNDO_ALREADY_REVERTED` |
| 4 | **`Version` 未变** | 期间没有其他屏 / 其他人改过这条明细 | `UNDO_CONFLICT` |

**"不能跳状态撤销"的场景对照（核心边界）**

| 操作 | 当前状态 | 能否撤销 | 原因 |
|------|:--------:|:--------:|------|
| 切配屏 `A→B` | `B` | ✅ **可** | 我推的那一格还在 |
| 切配屏 `A→B` | `C`（已被制作屏推进） | ❌ **不可** | **状态已被越过**，撤销会造成"跳过制作回退" |
| 切配屏 `A→B` | `Done` | ❌ 不可 | 已交付 |
| 制作屏 `B→C` | `C` | ✅ 可 | 我推的那一格还在 |
| 制作屏 `A→C`（越级） | `C` | ✅ 可，**回退到 `A`**（不是 B） | 回退目标是本操作的 `FromStage` |
| 传菜屏 `C→Done` | `Done` | ✅ 可，回退到 `C` | 但**已打印的跟盘单不能追回**（见 2.19.5） |
| 任意 | `Cancelled` / `Void` / `Closed` | ❌ 不可 | 终态且已定性，走对应流程处理 |

> **一句话规则**：**撤销 = 把我最后推的那一格推回去；只要那一格已经不在原位，就撤不了。**

#### 2.19.2 撤销的目标：回到本操作的 `FromStage`（不是"上一格"）

```
撤销目标 = OperationLog.FromStage（本操作发生前的状态）
```

| 操作 | FromStage | ToStage | 撤销后 |
|------|-----------|---------|--------|
| 切配屏正常划单 | `A` | `B` | → `A` |
| 制作屏正常划单 | `B` | `C` | → `B` |
| **制作屏越级代办** | `A` | `C` | **→ `A`**（跳过 `B` 的越级，回退也跳过） |
| 传菜屏越级完成 | `B` | `Done` | → `B` |

> **为什么必须记录 `FromStage`**：没有它就只能"退一格"，越级操作会退错（`A→C` 退成 `B`，而 `B` 从未发生过）。所以 `OperationLog` **必须落 `FromStage` / `ToStage`**。

#### 2.19.3 撤销时必须一并回滚的数据（漏一项就出错账）

| 数据 | 处理 |
|------|------|
| `WorkflowStage` | 回退到 `FromStage` |
| `StageStatus` | 置 `Waiting`（该阶段重新待处理） |
| `StageCompleteTime` / `StageElapsedSeconds` | **清空**（该阶段从未完成） |
| `OrderDetailStageLog` 对应行 | `ExitAt` 置空、`ElapsedSeconds` 置空、标 `Reverted`，或删除该行（推荐标记，保留审计） |
| **`ProducedAt` / `ProducedSeconds` / `IsTimeout` / `TimeoutSeconds`** | 若撤销的是"制作完成"，**全部清空**——否则超时统计会留一条幽灵记录 |
| `CompletedQty` | 若操作是划单完成份数，**回扣**（`CompletedQty -= 本次份数`） |
| `SkippedStages` | 若撤销越级操作，清空对应记录 |
| `NotifyState` / `NotifyFlags` | 回退到操作前的值（如 `40 已出品` → `20 已起菜`） |
| `SiblingCart`（屏幕缓存） | 推 `LineReverted` 让所有屏恢复显示该行 |
| **POS 回执** | 若已完成回执 → 发 **`Item.Undo`**（新出站事件，见 2.19.6） |
| 打印任务 | **不回滚已打印的单据**，但记一条"该单已撤销"（见 2.19.5） |

#### 2.19.4 操作历史（屏幕级）

**数据来源**：`OperationLog`（已有表），按 `TerminalId` / `OperatorName` 过滤，**每块屏只看自己的**。

**屏幕 UI**：底部/侧边【我的操作】抽屉

```
┌─ 我的划单记录 ──── 营业日 2026-10-21 ── 共 47 条 ─┐
│ 时间      桌号 菜品        当前状态          撤销 │
│ 12:03:15  A05  宫保鸡丁    待制作             ⤺  │
│ 12:02:40  A08  拍黄瓜      待制作             ⤺  │
│ 12:01:05  C1   佛跳墙      待制作（已被推进）  —  │
│ 11:58:33  A05  米饭        待传菜             —  │
│ 11:40:12  B07  干炒牛河    已完成             —  │
│ 11:20:08  A03  清蒸鲈鱼    已退菜             —  │
└──────────────────────────────────────────────────┘
```

| 元素 | 说明 |
|------|------|
| **时间范围** | **当日（当前营业日）**，按 §2.13 营业日边界（如 06:00~次日 05:59），**不是自然日** |
| 显示内容 | 时间、桌号、菜名、**当前状态**、撤销按钮 |
| **当前状态列** | 显示该明细**此刻**的真实状态（§2.15.1 的 8 态中文名），并标注是否已被推进："待制作（已被推进）" |
| 可撤销标识 | 实时计算四条条件：**可撤销显示 ⤺**，不可撤销显示 `—` + 悬浮原因（已推进 / 超时 / 已撤销 / 已终态） |
| 每行独立判断 | **不是"只能撤最后一条"**——连划 5 道菜想撤第 3 道，只要那一格还在就能撤 |
| 排序 | 默认**时间倒序**；可切"仅看可撤销" |
| 刷新 | 操作后即时刷新；撤销后该行置灰标"已撤销" |
| 统计 | 抽屉头部显示当日划单总数 / 可撤销数 / 已撤销数 |
| 数据保留 | 当日记录常驻；**跨营业日后归档为只读历史**（仍可查，不再可撤） |

**`OperationLog` 必须补充的字段**

| 字段 | 说明 |
|------|------|
| `FromStage` / `ToStage` | 操作前后阶段（**撤销的判定依据**） |
| `FromStatus` / `ToStatus` | 操作前后阶段状态 |
| `Qty` | 本次操作份数（部分划单回扣用） |
| `IsUndoable` | 是否可撤销（写入时预判，**读取时仍须实时复核**） |
| `RevertedAt` / `RevertedBy` | 被撤销的时间与操作人（非空 = 已被撤销，不可再撤） |
| `VersionAt` | 操作时该明细的 `Version`（用于比对是否被他人改过） |
| `BusinessDate` | **营业日**（按当日查询的索引键） |

#### 2.19.5 已打印单据怎么处理（不能装作没发生）

| 场景 | 处理 |
|------|------|
| 划单时已打印跟盘单，随后撤销 | **单据已出纸无法追回**。系统记录"该打印任务已撤销"（`PrintJob.Status = Cancelled`），并提供**【补打撤销单】**（可选功能）：打一张小票标注"作废/撤销 桌号 菜名"。否则传菜员手里的纸与实际不符 |
| 未打印（打印失败或未配打印） | 直接作废打印任务 |

> **这是撤销功能最容易被忽略的副作用**：厨师划单 → 单子出纸跟着菜走了 → 发现划错 → 撤销。厨房系统里干净了，但**纸上那张单还在**。如果门店有打印，必须给"作废单"能力，否则现场会拿错单。

#### 2.19.6 POS 回执：撤销要单独发事件

| 事件 | 触发 | Payload |
|------|------|---------|
| **`Item.Undo`**（新增） | 撤销一个已完成回执的划单 | `PosOrderNo` / `LineNo` / `UndoStage`（被撤销的阶段）/ `RestoredStage`（回退到的阶段）/ `Qty` / `OccurredAt` |
| 幂等 | 按 `IdempotencyKey = DetailId + UndoStage + OccurredAt` 去重 |

| 规则 | 说明 |
|------|------|
| POS 必须处理 | 收到 `Item.Undo` 要把该菜品的出餐状态**退回一格**；若不支持，需在对接文档写明降级策略（忽略并记日志），**不允许静默丢弃** |
| 与越级的关系 | 越级完成撤销时，`UndoStage` 记 `ToStage`，`RestoredStage` 记 `FromStage`（中间被跳过的阶段**不发事件**，因为从未发生过） |

#### 2.19.7 配置项

| 字段 | 默认 | 说明 |
|------|------|------|
| `EnableUndo` | 1 | **撤销总开关**（关闭则历史仍可看，但不可撤销） |
| `UndoWindowSeconds` | **120** | 撤销时间窗（秒）；门店可调（**30~1800**） |
| `UndoScope` | `PerDetail` | `PerDetail`（每条明细独立判断，**推荐**）/ `LastActionOnly`（仅本屏最后一次操作可撤） |
| `UndoRequireSameOperator` | 1 | 是否要求同一操作人才能撤销（0 = 同屏任意人可撤，适合共用屏） |
| `UndoPrintVoidSlip` | 0 | 撤销时是否补打"作废单"（有打印的门店置 1） |

> **`UndoScope` 默认 `PerDetail` 的原因**：师傅连续划 5 道菜，第 2 道发现划错，若只能撤最后一条，他得把后面 3 道也撤了再重划——这是**制造更多错误**。

#### 2.19.8 明文禁止的行为

| ❌ 禁止 | 原因 |
|--------|------|
| 跳状态撤销（`A→B` 后菜已到 `C`，从切配屏撤销回 `A`） | 会**覆盖制作屏已完成的动作**，等于抹掉别人的工作记录 |
| 撤销已 `Cancelled` / `Void` / `Closed` 的明细 | 终态已定性，应走恢复/重开流程 |
| 同一操作撤销两次 | 会导致状态抖动（`A→B→A→B`） |
| 撤销后不清理 `ProducedAt` / 超时字段 | 报表会留下"幽灵完成记录" |
| 撤销时不检查 `Version` | 并发下会覆盖他人的操作 |

#### 2.19.9 撤销二次确认（**仅在有打印时确认**）

| 场景 | 是否弹确认 |
|------|:----------:|
| 无打印配置（`UndoPrintVoidSlip = 0` 或无打印机） | **不弹**，点了就撤——纠错不该再加阻力 |
| 有打印且该单**已成功打印** | **弹确认**："该单已打印，撤销将补打作废单，确认？" |
| 有打印但该单**打印失败/未打印** | 不弹 |

> **原则**：撤销本身是纠错动作，**默认不该被二次确认打断**；只有会产生"纸质后果"（补打作废单）时才确认。

#### 2.19.10 撤销率指标（用数据发现问题，不做硬限制）

**统计字段**（`DailyStoreStat` / `DailyDimStat`）

| 字段 | 含义 |
|------|------|
| `UndoCount` | 撤销次数 |
| `UndoRate` | **撤销率** = `UndoCount / StageCompleteCount` |

| 阈值 | 含义与建议动作 |
|------|----------------|
| < 3% | 正常，属偶发误操作 |
| **3% ~ 10%** | **关注**：可能是按钮太小 / 无二次确认 / 菜品排列密集导致误点 |
| > 10% | **异常**：说明划单动作设计有问题，或师傅在"先划后做"（虚假划单） |

> **为什么要这个指标而不是限制次数**：撤销率高**不是用户手滑，是界面或流程问题**。硬限制次数只会让人划错了也修不了，反而更糟。
> **另一个隐蔽用途**：如果某档口撤销率显著高于其他档口，可能是该档口的**操作节奏**或**人员熟练度**问题，比单纯看产量更有诊断价值。

#### 2.19.11 综合屏（`TerminalType = Composite`）的撤销处理

> **修正（v6.62）**：综合屏**可以划单**（`EnableOperate` 可配，默认 0 只是开箱只读）。**只要它划过单，就有"自己的操作"，就能撤销自己的操作**——规则与其他角色屏**完全一致**，没有任何特殊化。

| 综合屏状态 | 能否撤销 | 说明 |
|------------|:--------:|------|
| `EnableOperate = 0`（默认只读） | ❌ | 它没划过单 → 【我的划单记录】为空 → 无操作可撤 |
| **`EnableOperate = 1`（已开划单）** | ✅ **可撤自己的操作** | 四条条件（§2.19.1）**完全相同**，时间窗/一格/未撤销/Version 一个不少 |

**综合屏独有的两点差异（都不影响撤销规则）**

| 差异 | 说明 |
|------|------|
| **可见范围更大** | `Role` 为空 → 跨角色可见全部阶段。所以综合屏的【我的划单记录】里可能同时出现切配/制作/传菜三种阶段的菜品——**但撤销仍按各自明细独立判定** |
| **可能跨档口操作** | 综合屏绑多档口。撤销时同样只校验**该明细当前状态是否还是我推的那一格**，与"哪个档口"无关 |

**关于"跨屏撤销别人操作"（仍不提供，V1.1 可选）**

| 场景 | 处理 |
|------|------|
| 综合屏想撤销**其他屏**划的单 | ❌ **V1 不支持**——撤销的对象是"我的操作"（§2.19 定位）。别人划错的，让他自己撤，或走管理端 |
| V1.1 可选 | `EnableManageUndo = 1` + 管理端口令解锁 → 综合屏"管理模式"可撤任意屏操作；`OperationLog` 记 `Source = ManageUndo`，报表单列 |

> **一句话**：**综合屏划了单就能撤自己的，撤不到别人的。** 权限模型不因屏的类型而变，只因"这块屏是否真的做过这个操作"而变。
