## 阶段 2　数据库配置

> **现实情况**：实施通常是**用 KDS 自带 SQLite**，或**用客户已有 SQL Server 实例、但建独立库**。
> **绝不与 POS 同库**（同库会出现 `Order`/`OrderDetail`/`Table` 等表名冲突，且权限无法隔离）。

### 2.A　选 SQLite（默认，推荐）

| # | 检查项 | 通过标准 | ✔ |
|:-:|--------|----------|:-:|
| A1 | 数据库文件位置 | 放在**数据盘**，不要放系统盘或网络盘 | ☐ |
| A2 | 🔴 目录权限 | 运行账号对数据目录有读写权限 | ☐ |
| A3 | 🔴 首次启动 | 自动建库成功，`StoreConfig` 有 1 行 | ☐ |
| A4 | ⚪ WAL 生效 | 启动后目录出现 `.db` / `.db-wal` 文件 | ☐ |
| A5 | ⚪ 备份策略 | 每日 `VACUUM INTO` 备份（在线快照，不阻塞写） | ☐ |

### 2.B　选 SQL Server（**同实例、不同库** — 常见诉求）

> 前提：实例版本 **≥ SQL Server 2012**（推荐 2016+）。若是 2008，见 §2.C。
> **建库与初始化请用 `Kds.DbSetup.exe` 图形向导**（§13.10），**不要手敲 SQL**——建库时它会自动设 `SIMPLE` / `MAXSIZE` / `FILEGROWTH` / `RCSI`，手敲最容易漏这几项。
> 下表的检查项用于**向导完成后逐项复核**。

| # | 检查项 | 通过标准 | 验证方式 | ✔ |
|:-:|--------|----------|----------|:-:|
| B1 | 🔴 实例版本 | ≥ 2012 | `SELECT SERVERPROPERTY('ProductVersion')` | ☐ |
| **B0** | 🔴 **用图形向导建库** | 已跑 `Kds.DbSetup.exe`，12 项检测全绿（§13.10.3） | 检测页截图 | ☐ |
| B2 | 🔴 **独立 database** | 名为 `Kds_<门店编码>`，**不与 POS 同库** | `SELECT name FROM sys.databases WHERE name LIKE 'Kds%'` | ☐ |
| B3 | 🔴 **独立登录** | 专用账号，**仅该库 `db_owner`**，**不是 `sysadmin`** | `SELECT IS_SRVROLEMEMBER('sysadmin','账号名')` → 应为 0 | ☐ |
| B4 | 🔴 排序规则 | 库级 collation 明确（如 `Chinese_PRC_CI_AS`），不依赖实例默认 | `SELECT collation_name FROM sys.databases WHERE name='Kds_xxx'` | ☐ |
| B5 | 🔴 **RCSI 开启** | 读写不互斥，报表不阻塞划单 | `SELECT is_read_committed_snapshot_on` → 应为 1 | ☐ |
| B6 | 🔴 **数据/日志分盘** | `.mdf` 与 `.ldf` 在不同物理盘（或至少不同分区） | `SELECT physical_name FROM sys.master_files` | ☐ |
| B7 | 🔴 **独立备份计划** | 每日全备 + 定时日志备；**不与 POS 备份窗口重叠** | 查看 SQL Agent 作业 | ☐ |
| B8 | 🔴 **禁止跨库耦合** | KDS 库**不得**建到 POS 库的 JOIN / 同义词 / 触发器 | 查 `sys.synonyms` / 视图 | ☐ |
| B9 | ⚪ 资源限制 | 企业版 2016+ 可用 Resource Governor 给 KDS 限 CPU/内存 | 可选 | ☐ |
| B10 | ⚪ 连接串 | 用 SQL 登录时，密码复杂度符合客户策略 | — | ☐ |
| **B11** | 🔴 **建完库立刻验证恢复模式** | `SIMPLE`（且日志 `MAXSIZE` 已设） | 见下方验证脚本 | ☐ |
| **B12** | 🔴 **确认无「FULL 模式 + 无日志备份」组合** | 该组合会让 LDF 无限增长直至拖垮实例 | 见下方判定 | ☐ |

**B11 / B12 验证脚本（建库后立即执行，结果截图存档）**

```sql
-- ① 恢复模式与日志截断阻塞原因
SELECT
    name                    AS DbName,
    recovery_model_desc     AS RecoveryModel,   -- 期望：SIMPLE
    log_reuse_wait_desc     AS LogReuseWait,    -- 期望：NOTHING / CHECKPOINT
    log_reuse_wait          AS LogReuseWaitCode
FROM sys.databases
WHERE name LIKE 'Kds%';

-- ② 日志文件的 MAXSIZE 与 FILEGROWTH 是否已设
SELECT
    DB_NAME(database_id) AS DbName,
    name                 AS LogicalName,
    physical_name        AS FilePath,
    CAST(size AS decimal(18,2)) * 8 / 1024 AS SizeMB,
    CASE max_size WHEN -1 THEN 'UNLIMITED(!!)'         -- 期望不是 UNLIMITED
                  ELSE CAST(CAST(max_size AS decimal(18,2)) * 8 / 1024 AS varchar(20)) + ' MB'
    END                  AS MaxSize,
    CASE is_percent_growth WHEN 1 THEN CAST(growth AS varchar(10)) + '%'
                           ELSE CAST(CAST(growth AS decimal(18,2)) * 8 / 1024 AS varchar(20)) + ' MB'
    END                  AS Growth
FROM sys.master_files
WHERE database_id IN (SELECT database_id FROM sys.databases WHERE name LIKE 'Kds%')
  AND type_desc = 'LOG';                        -- 只看日志文件

-- ③ 若恢复模式是 FULL，必须有日志备份作业
--    有 Agent 的版本：
SELECT  j.name AS JobName, j.enabled, s.step_name, s.command
FROM    msdb.dbo.sysjobs j
JOIN    msdb.dbo.sysjobsteps s ON s.job_id = j.job_id
WHERE   s.command LIKE '%BACKUP LOG%Kds%';
--    期望：若 RecoveryModel = FULL，此处至少有一行且 enabled = 1
```

| 判定 | 处置 |
|------|------|
| `RecoveryModel = SIMPLE` + 日志 `MaxSize` 为具体值（非 `UNLIMITED`） | ✅ 通过 |
| `RecoveryModel = SIMPLE` 但 `MaxSize = UNLIMITED` | ⚠️ **补设** `MAXSIZE`（§13.9.2），否则单日暴涨会涨满整块盘 |
| `RecoveryModel = FULL` **且** 有启用的日志备份作业 | ⚠️ 可接受，但需在实施单上记录"已配日志备份"，并**告知客户该作业不可停** |
| **`RecoveryModel = FULL` 且无日志备份作业** | 🔴 **必须立即改回 `SIMPLE` 或补建备份作业**——这是"定时炸弹"：LDF 会一直涨到磁盘满，连带 POS 一起挂 |

> **为什么这事儿不能只查一次**：客户的 DBA 或 POS 厂商有可能**事后把恢复模式改成 `FULL`**（做备份策略时很常见），而 KDS 不会收到任何通知。
> 因此 KDS 侧还有两道兜底：
> 1. **每日维护窗口自动核对**恢复模式，与 `StoreConfig.SqlServerRecoveryMode` 不一致 → 健康检查报 `DB_RECOVERY_MODE_CHANGED`（Warn）；
> 2. **LDF 大小每日检查**，超 `DbLogWarnMb`（默认 2048MB）→ 健康检查报 `DB_LOG_GROWING`（Warn），并附 `log_reuse_wait_desc` 的翻译建议。

**B 组必须让客户签字的条款**

> *"KDS 与 POS 共用同一 SQL Server 实例，实例故障将同时影响收银与后厨。该风险由甲方知悉并接受。"*
> 　甲方签字：____________　日期：__________

## 阶段 9　应急预案（贴在 Master 机器旁）

| 故障 | 现场处置 |
|------|----------|
| **Master 不启动** | 检查服务状态 → 端口占用 → 日志 `%ProgramData%\Kds\logs` → 数据目录权限 |
| **所有屏不刷新** | 检查 Master 是否活着 → ping → 防火墙 → 各屏网络 → 重启终端浏览器 |
| **某档口漏单** | 管理端跑**路由自检** → 看该档口是否绑屏 → 看品项反选规则 |
| **打出乱码** | 检查 `Encoding`（应 `GB18030`）/ `RenderMode`（建议 `Image`）；打测试页 |
| **数据库文件过大** | 检查归档是否在跑；手动触发清理；**不要直接删数据** |
| **磁盘满** | 先清 `logs` 与归档卷之外的临时文件；**不要删数据库** |
| **突然断电后异常** | 用最近备份恢复；WAL 通常能自愈，先尝试正常启动 |
| **POS 全挂** | ✅ **KDS 仍可继续做已下单的菜**（这是 SQLite 部署的价值）；新单无法进入 |
