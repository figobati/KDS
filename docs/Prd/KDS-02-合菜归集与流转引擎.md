# 第二部分：核心业务模型与工作流引擎

## 2. 菜品流转模型（工作流引擎）

### 2.1 角色分屏

后厨屏幕固定为三种角色，不管门店有多少档口，屏幕视图只有三套：

| 角色屏 | 英文 | 枚举值 | 职责 |
|--------|------|--------|------|
| 切配屏 | Prep | `Prep` | 洗菜、切配、备料 |
| 制作屏 | Cook | `Cook` | 烹饪、调制 |
| 传菜屏 / Expo | Expo | `Expo` | 摆盘核对、出餐确认 |

- 顺序固定 `Prep → Cook → Expo`，**不可逆**；
- 可以跳过中间阶段（由品项 StagePath 决定，见 §2.4）；
- 每个屏幕可配置绑定档口 + 例外品项（见 §2.2）；
- 档口不强制物理划分：多台同角色屏幕可绑定同一个档口或不同档口；
  - 一台切配屏可绑定【热菜档口 1】，另一台切配屏绑定【热菜档口 2】——两台屏做同角色的活，分档口显示；
  - 档口是逻辑概念，不一定对应独立房间。一个档口可由**多块屏共享**（广播），每块屏都完整显示该档口的品项；
  - 品项路由到档口，档口绑定角色屏，屏幕按规则拉取属于自己的品项。

### 2.2 品项-档口关联规则（反选逻辑）

档口通过 `Station` 表内的三个字段配置与品项的关联（见 §9.10）。**字段本身即代表种类，无需额外判别列**：

| 字段 | 类型 | 语义 | 对应角色 |
|------|------|------|----------|
| `IncludeTypeIds` | nvarchar(MAX) | 类型纳入集合（**白名单-类型**） | 品类批量纳入 |
| `ExcludeItemIds` | nvarchar(MAX) | 单品剔除集合（**黑名单-单品**） | 从已纳入的品类里剔除个别单品 |
| `IncludeItemIds` | nvarchar(MAX) | 单品追加集合（**白名单-单品**） | 跨类型单独追加个别单品 |

> 三者均为 GUID 逗号分隔字符串，规范格式 `,g1,g2,`（存储与性能约定见 §9.10）。

**判定顺序（必须按此顺序执行）**：

1. **先匹配品项类型 ID**；
2. 如果该品项属于该类型，**再看品项 ID 黑名单**：存在该品项 ID 则**排除**；
3. 命中规则：`(类型匹配 AND 品项不在黑名单)` **OR** `(类型未匹配 AND 品项在白名单)` → 该品项归属此档口。

**等价判定式**（实现口径，对应 §1.6-D1）：

```
设：
  TypeIncluded = 品项所属类型 ID 在档口「类型纳入」集合中
  ItemExcluded = 品项自身 ID 在档口「单品剔除」集合中   ← 黑名单
  ItemIncluded = 品项自身 ID 在档口「单品追加」集合中   ← 白名单

品项属于本档口 ⟺
  (TypeIncluded AND NOT ItemExcluded)
  OR
  (NOT TypeIncluded AND ItemIncluded)
```

**四种情况：**

| 类型在纳入集合 | 单品在黑名单 | 单品在白名单 | 结果 | 业务含义 |
|:-:|:-:|:-:|:-:|---|
| ✅ | ❌ | — | ✅ 包含 | 类型批量纳入，单品正常 |
| ✅ | ✅ | — | ❌ 排除 | 类型纳入但剔除该单品 |
| ❌ | — | ✅ | ✅ 包含 | 跨类型单独追加该单品 |
| ❌ | ❌ | ❌ | ❌ 不包含 | 无关 |

> ⚠️ **边界说明（对应 §1.6-D1）**：白名单（单品追加）**仅在类型未命中时生效**，不是无条件白名单。即：一个品项即使被加入白名单，若其类型同时命中且它又在黑名单中，**结果仍为排除**（黑名单优先于白名单）。此规则用于避免"某单品既被类型批量纳入、又被人工剔除、又被误加入白名单"的三重矛盾。

### 2.2.1 `StationId` 的语义辨析（**五个不同的 StationId，禁止混用**）

> **`Station`（档口）是逻辑作业分组，不是物理位置**：品项靠 §2.2 反选规则落到档口，档口再绑定角色与屏幕。全文出现 5 处 `StationId(s)`，语义各不相同：

| 字段 | 所在实体 | 含义 | 谁维护 | 一句话 |
|------|----------|------|--------|--------|
| `TerminalConfig.StationIds` | 终端 | **这块屏绑定哪些档口** | 管理员 | "这块屏负责哪些作业组" |
| `OrderDetail.CurrentStationId` | 明细 | **这条明细当前阶段被路由到的主档口**（反选推导结果） | Master（落库） | "这道菜现在该谁做" |
| `MatchedStationIds`（DTO 字段，不落库） | 下发报文 | **当前阶段的命中集合**（可能多个） | Master（组装时算） | "这道菜同时被哪些作业组命中" |
| `PrintRule.StationId` | 打印规则 | 该打印规则作用的档口 | 管理员 | "哪个档口的单从哪台机出" |
| `PrinterConfig.OwnerStationId` | 打印机 | 打印机归属档口 | 管理员 | 同样服务于打印路由 |
| `TerminalPane.StationIds`（V1.1） | 分屏栏 | 该栏显示的档口集合 | 管理员 | "这一栏看哪些作业组" |

**三个必须记住的推论**：

1. **档口不决定"哪块屏"**：档口 → 屏幕是**一对多**（同一档口可挂多块屏，广播模式全部接收，§2.1）。要定位屏幕必须查 `TerminalConfig.StationIds` 的绑定关系，不能只看明细的档口。
2. **`CurrentStationId` 是"当前阶段"的，会变**：品项 StagePath 可能是 `Prep→Cook→Expo`，切配阶段的档口与制作阶段的档口不同 → **每次阶段推进必须重算并更新**（§2.6.4）。它不是"这道菜一辈子属于哪个档口"。
3. **单值 + 集合并存**：
   - `CurrentStationId`（单值）用于**打印路由 / 档口级超时阈值 / 回执 POS / 统计主口径**，取命中集合中**排序第一**的档口（`Station.SortOrder`），保证结果稳定可复现；
   - `MatchedStationIds`（集合）用于**分屏分发（§3.7）与多档口命中告警（§2.11.2 `MULTI_STATION_SAME_STAGE`）**；
   - **禁止**用单值去判断"是否命中多个档口"——那永远看不出问题。


**业务价值：**

- 档口绑定类型后，该类型下新增品项**自动关联**，不用维护档口配置；
- 类型下个别特殊品项不需要进本档口 → 加入黑名单剔除；
- 个别跨类型品项需要进本档口 → 加入白名单单独追加。

**查询实现**：门店品项数据量小（通常几百到一两千），字符串 LIKE 筛选即可满足性能。**但该 SQL 只用于低频场景**（管理端匹配预览、`Menu.Sync` 后批量重算归属），**运行期推屏一律走 §9.10 的内存投影 + 哈希查表**。

```sql
-- 查某档口可见的所有品项（SQLite 语法，门店本地库执行；仅用于校验/批量重算）
SELECT i.* FROM DishItem i
WHERE i.StoreId = @StoreId
  AND (
    -- 情况 1：类型纳入，且单品不在黑名单
    (',' || @IncludeTypeIds || ',' LIKE '%,' || i.DishTypeId || ',%'
     AND ',' || @ExcludeItemIds || ',' NOT LIKE '%,' || i.Uid || ',%')
    OR
    -- 情况 2：类型未纳入，但单品在白名单
    (',' || @IncludeTypeIds || ',' NOT LIKE '%,' || i.DishTypeId || ',%'
     AND ',' || @IncludeItemIds || ',' LIKE '%,' || i.Uid || ',%')
  );
```

> ⚠️ `||` 为 SQLite 字符串拼接语法；若在 SQL Server 上执行需改用 `+` 或 `CONCAT`。本查询**仅在门店本地 SQLite 库执行**，总部汇总侧不做该匹配（总部只收终态订单）。
> 拼接时必须**统一补前后逗号**（`,a,b,c,`），否则会出现 `uid=12` 命中 `uid=123` 的子串误匹配。

### 2.3 菜品归集规则（合菜 / 单菜视图）与合并条件

> 合菜 / 单菜是**屏幕上的两个实时视图**（§3.0.2）。本章描述这两种视图下的**归集规则**（决定 `MergeKey` 怎么算）；桌台 / 订单视图的归集见 §3.1（按 `TableId` / `OrderId` 分组、卡内逐条）。

#### 2.3.1 两种归集方式

| 视图 | 枚举值 | 归类方式 | 适用 |
|------|--------|----------|------|
| **合菜视图** | `ActiveView = MergeMode` | 按**合并条件**动态生成聚合 Key（`MergeKey`），相同 Key 合并为一张卡片，卡上显示总份数 | 切配、冷菜、传菜批量备菜（一锅出、一次备多份） |
| **单菜视图** | `ActiveView = SingleMode` | 每个 `OrderDetail` 实例独立一行，**不做任何合并**（Key = `DetailId`） | 出餐精细、必须逐份确认的档口（正餐热菜、特殊定制菜） |

> **合菜视图是"效率优先"，单菜视图是"防错优先"。** 合并会牺牲一部分精细度（例如不同口味的菜被并到一张卡），所以让师傅**随时切换**，而不是替他做决定——这正是三视图实时切换（§3.0.2）的价值。
>
> **单菜视图 ≠ 关闭全部合并条件的合菜视图**：前者没有左侧聚合区、行内直接划单、默认按等待时长倒序（§3.3）；后者仍是双栏结构，只是每张卡只含一份。二者在 UI 与交互上不同。

#### 2.3.2 合并条件（决定 `MergeKey`，默认全部开启）

| # | 开关（`TerminalConfig.Merge_*`） | 默认 | 关闭时的行为 |
|---|--------------------------------|:----:|--------------|
| 1 | `Merge_DiffOrder` 不同订单合并 | ✅ 开 | 卡片按**订单**分开；同一订单内的同菜仍可合并 |
| 2 | `Merge_DiffFlavor` 不同口味 / 做法合并 | ✅ 开 | 口味 / 做法不同则**拆卡**（即原 C3 行为） |
| 3 | `Merge_DineInTakeaway` 堂食外卖合并 | ✅ 开 | 堂食与外卖**分开**成两张卡 |
| 4 | `Merge_ComboAndNormal` 套餐品项与普通菜合并 | ✅ 开 | 套餐内品项与单点同菜**分开**成两张卡 |
| 5 | `Merge_Timeout` 超时菜与未超时菜合并 | ✅ 开 | 已超时的菜**单独成卡**，不与正常菜混合 |
| 6 | `Merge_Rush` 催菜 / 加急与正常菜合并 | ✅ 开 | 催菜 / 加急菜**单独成卡**，突出紧急 |
| 7 | `Merge_Hold` 等叫菜与正常菜合并 | ✅ 开 | 等叫菜**单独成卡**，不与正在做的混排 |

> **默认全开的商业理由**：门店最怕的是"同一道菜散成十几张小卡"，切配师傅无法一次备料。默认全开等于给一个"能直接用"的开箱体验；需要精细化的门店再逐项关闭（例如正餐店关掉"不同口味做法合并"）。

#### 2.3.3 聚合 Key 生成算法（实现口径，必须严格照做）

```
Key 分段（按开关决定是否参与 key）：

  key = Normalize(MergeBaseName)               ← 恒参与，名字是归类的根（**必须语言无关**，见下方注 5）
      + #Spec                                  ← 恒参与（同名的不同规格永远不是同一道菜）
      + (Merge_DiffFlavor ? '' : #Taste)        ← 关闭"不同口味做法合并"时，口味参与 key
      + (Merge_DiffFlavor ? '' : #Method)
      + (Merge_DiffOrder      ? '' : #OrderId)
      + (Merge_DineInTakeaway ? '' : #OrderType)
      + (Merge_ComboAndNormal ? '' : #IsComboItem)
      + (Merge_Timeout        ? '' : #IsTimeout)   ← 超时是"随时间变化"的维度，见下方注意
      + (Merge_Rush           ? '' : #IsRushOrRemind)
      + (Merge_Hold           ? '' : #IsHold)

Normalize(x) = Trim(x).ToLowerInvariant()      ← 只做这两步，禁止简繁转换 / 去标点 / 同义词
空值统一按 "" 参与拼接（禁止 null 拼入，否则变 "null" 产生幽灵卡片）

MergeBaseName = LocalizedText 中 StoreConfig.MainLang（默认 zh-CN）的值
                缺失时取 JSON 里按 key 字典序第一个非空值
                ⚠️ 与屏幕 CurrentLang 无关（绝不能用"当前语言解析结果"做 key）
```

**五个必须注意的实现细节：**

1. **不依赖 `DishItemId`**：临时菜在 POS 端改名后 UID 不变但名字变了，按 UID 聚合会出现"旧名卡 + 新名卡"并存。**名字才是厨房认知的根**（客户已确认按名字聚合，不按 UID）。
2. **`#Spec` 恒参与**：规格差异（大杯 / 中杯）物理上是不同容器，**即使客户打开全部合并开关也不合并**——这是唯一硬性不可配维度。
3. **超时是可变的 key 维度**：若关闭了"超时菜与未超时菜合并"，某个菜品超时的瞬间它的 Key 会变化 → 卡片会**重新拆分并跳到另一张卡**。为避免闪烁：**Key 只在卡片刷新周期（默认 3 秒）重新计算一次**，且卡片发生变化时带**淡入淡出过渡**，不做逐帧重排。
4. **`MergeKey` 由 Master 计算并随明细行下推**（终端只按键分组，不自行计算）：否则同一道菜在不同屏会因算法差异或数据到达顺序不同而卡片数 / 份数不一致；同时这是"三个视图零请求切换"的前提（§3.0.3）。
5. **`MergeKey` 必须用语言无关的主名（`MergeBaseName`），不能用当前屏幕语言解析结果**：否则① 切换语言时整屏卡片会重排；② 同一道菜若某行缺英文、另一行有英文，英文屏上一行解析为英文、一行回退中文 → **卡片分裂、份数变少**。归集是"业务身份"，翻译是"展示语言"，两者必须解耦（§11.4）。

**另一个硬性排除：称重菜恒不参与合并**

```
若 DishItem.SaleMode = ByWeight（称重菜）：
    MergeKey = "DETAIL:" + DetailId      ← 强制唯一，一张明细一张卡，任何开关都无法合并
```

理由见 §4.5：称重菜每一行都是**一个独立的物理标的**（这条 1.2 斤鲈鱼 vs 那条 0.8 斤鲈鱼），按名称/规格合并会把两个不同实物加总成"2.0 斤"，后厨既不知道这份量对应哪条鱼，也无法把成品对回桌台。

#### 2.3.4 合菜视图卡片与明细的展示规则

- 卡片显示：**菜品名 + 总待出份数**；若卡内口味 / 规格 / 做法存在差异，**卡片必须列出各值分布**（如"共 7 份（少辣 3 / 正常 4）"），不允许只显示总数；
- 卡片标签：当合并了跨堂食外卖 / 催菜 / 超时 / 等叫的实例时，卡片显示对应**聚合标签**（如"含外卖 2""含催菜 1"），便于师傅判断；
- 右侧明细：**永远按实例逐条展示**（合菜不改变明细粒度），每条独立显示所属订单号 / 桌台号 / 口味 / 状态标签；
- **批量划单必须按"最小实例"拆分提交**：合菜只是"展示合并"，提交时仍逐条 `DetailId` 提交并逐条校验（§10.7），**失败项单独回退**并高亮；
- 退菜实例不参与份数统计，卡片仍显示但标红删除线，明细对应条目标"退菜"且不可划单；
- 点击卡片 → 右侧明细自动筛选；**V1 不支持多选多张卡片**；
- 外卖订单无桌台号时，以**外卖单号**替代桌台号展示与排序。

#### 2.3.5 三视图与典型场景对照

| 场景 | 推荐模式 | 关键点 |
|------|----------|--------|
| 切配 / 冷菜批量备料 | **合菜视图** | 合并条件全开（尤其"不同口味做法合并"+"等叫菜合并"） |
| 传菜屏核对出餐 | **合菜视图** | 关"不同口味做法合并"（必须逐份核对口味）；或直接用桌台模式 |
| 正餐热菜制作 | **单菜视图** | 逐份确认，绝不合并 |
| 快餐 / 奶茶 / 吧台 | **合菜视图** | 全开，追求一次备多份 |
| 传菜 / Expo / 综合屏 | **桌台模式** | 一桌一卡，整桌划单与上菜核对 |
| 宴会（V2 订单模式） | 订单模式 + 合菜思路 | V2 实现，一单多桌统一备餐 |

**已确认的硬性边界（§1.6-D3，必须严格遵守）：**

| # | 边界 | 违反后果 |
|---|------|----------|
| 1 | 归一化只做 `Trim` + 大小写不敏感，禁止简繁转换 / 去标点 / 同义词替换 | "牛肉面"与"牛肉面（加辣）"被错并，厨房做错菜 |
| 2 | 空值一律按 `""` 参与拼接，禁止 `null` 拼入 | 产生 `可乐|null|…` 幽灵 Key，凭空多出重复卡片 |
| 3 | 聚合由 Master 计算并随卡片下推，各屏不自算 | 同一道菜在不同屏卡片数 / 份数不一致，无法排查 |
| 4 | `#Spec` 恒参与 Key（规格不可配合并） | 大杯与中杯被合并，装错杯 |
| 5 | 合菜只合并"展示"，提交必须按最小实例拆条 | 一次批量提交导致部分成功无法回滚定位 |

**临时菜改名规则：**

- 临时菜改名由**收银 POS 端**操作，KDS **不追溯**历史；
- KDS 聚合统一按**当前最新品项名称**归类；POS 改名后推送基础资料同步事件，KDS 刷新 `DishItem` 主数据，后续下单及聚合按新名称；
- 已在制作 / 已划单的历史记录（`OrderDetail` 快照字段）保持原名展示，不影响进行中工序，不额外做改名历史追溯。

**品项名称显示策略（长菜名）：**

> **合菜 / 单菜视图的卡片内，品项名称固定两行显示**，超出两行以省略号截断。

| 位置 | 名称显示规则 |
|------|--------------|
| **合菜视图左侧聚合卡片** | **两行**（`line-clamp: 2`），超出以省略号截断 |
| **单菜视图明细卡片 / 行** | **两行**，超出以省略号截断 |
| **合菜视图右侧明细区** | 两行（与左侧卡片一致），超出省略 |
| 桌台视图卡内明细行 | **仍为单行**（行式布局，见 §3.1.2），超出省略——该视图为保证一屏容纳更多桌台，不做两行 |
| 顶部检索结果 / 历史已划列表 | 单行 |

**两行显示的实现要求（必须照做，否则卡片会跳动）：**

1. **高度预留两行**：卡片名称区高度固定 = `2 × lineHeight`（如 lineHeight 20px → 固定 40px）。**即使名称只有一行也占满两行高度**，保证网格中卡片高度一致、不因菜名长短错位；
2. **CSS 方案**（WebView2 / Chromium 支持）：
   ```css
   .dish-name {
     display: -webkit-box;
     -webkit-line-clamp: 2;      /* 两行 */
     -webkit-box-orient: vertical;
     overflow: hidden;
     line-height: 20px;
     height: 40px;               /* 2 × line-height，占满两行 */
     word-break: break-all;      /* 中文/长英文串都能断行 */
   }
   ```
3. **省略号由浏览器渲染**，不要在服务端截字符串（避免中英文宽度不同导致截多/截少）；
4. **名称与规格 / 口味 / 做法标签分两区**：名称两行独立占位，标签在名称下方另起一行，**不挤占名称的两行空间**；
5. 卡片支持 hover / 长按悬浮，弹出**完整品名**（含规格 / 口味 / 做法完整拼接）；
6. **划单日志与打印输出完整名称，绝不截断**（截断只发生在屏幕展示层，不进入数据与回执）。

### 2.4 品项自定义流转路径（StagePath）

每个品项在菜单主数据里配置它经过哪些角色阶段（存于 `Workflow` 表，实体定义见 §9.11；档口反选字段定义见 §9.10）：

| 品项示例 | StagePath | 说明 |
|----------|-----------|------|
| 宫保鸡丁（热菜） | `[Prep, Cook, Expo]` | 全流程 |
| 凉拌黄瓜（冷菜） | `[Prep, Expo]` | 跳过制作，切配完直接传菜 |
| 可乐（饮品） | `[Cook, Expo]` | 跳过切配，吧台直接制作 |
| 预包装小吃 | `[Expo]` | 直接出餐 |

**默认值**：未配置的品项走全流程 `[Prep, Cook, Expo]`。

**批量配置**：后台支持按品类批量设置 StagePath；新增品项自动继承所属品类的默认 StagePath（品项级配置覆盖品类默认）。

**配置层级（对应附录待确认项 6 的结论）**：

```
优先级：品项级 StagePath  >  品类默认 StagePath  >  系统默认 [Prep, Cook, Expo]
```

**非法配置的降级规则（必须实现，避免引擎崩溃）**：

| 异常输入 | 降级行为 |
|----------|----------|
| 空字符串 / null | 视为系统默认 `[Prep, Cook, Expo]` |
| 含未知阶段名 | 丢弃该阶段并记 `Warning` 日志，其余阶段按序保留 |
| 顺序颠倒（如 `Cook,Prep`） | **强制按系统序重排**为 `Prep,Cook,Expo` 的子序 |
| 重复阶段（如 `Prep,Prep,Cook`） | 去重，保留首次出现 |
| 全部非法（结果为空） | 降级为 `[Expo]`，并记 `Error` 日志 |
| 品项的 StagePath 阶段在本店**没有对应档口/屏幕** | 该阶段自动跳过（不阻塞流转），并在管理端告警"存在无屏幕承接的阶段" |

### 2.5 档口流转与阶段归属

- 品项按 StagePath 逐步推进，每个阶段对应一个角色（`Prep` / `Cook` / `Expo`）；
- 每个阶段需要落到**具体档口**才有屏幕承接：品项在某阶段命中的档口集合由 §2.2 的反选规则 + 该档口 `Role` 决定；
- 若品项在某阶段**命中多个档口**：每个命中档口的所有同角色屏都可见（广播，V1 唯一分配模式），见 §2.9；
- 若品项在某阶段**未命中任何档口**：该阶段**跳过**（视为该阶段无人工序），继续下一阶段，并记 `Warning` 日志。

### 2.6 品项行状态机

#### 2.6.1 状态枚举

`OrderDetail.WorkflowStage`（阶段位置）+ `OrderDetail.StageStatus`（阶段状态）两个字段联合表达：

| 字段 | 枚举值 | 说明 |
|------|--------|------|
| `WorkflowStage` | `Pending` | 尚未进入任何阶段（订单刚创建，等待引擎进入首个阶段） |
| | `Prep` | 当前处于切配阶段 |
| | `Cook` | 当前处于制作阶段 |
| | `Expo` | 当前处于传菜 / 出餐阶段 |
| | `Done` | 全流程完成（已出餐） |
| | `Cancelled` | 已退菜（非终态退菜进入此态；已归档退菜仅标记） |
| | `Void` | 报损 |
| `StageStatus` | `Waiting` | 已进入本阶段，尚未开始动手 |
| | `Doing` | 制作中（唯一活动态；无接单步骤，§1.6-D5） |
| | `Completed` | 本阶段已完成（等待流转下一阶段或已终态） |
| | `Skipped` | 本阶段被跳过（无档口承接 / StagePath 不含） |

#### 2.6.2 三态状态机（`EnableWorkflowState = true`）

```
                    ┌──────────┐
     订单创建 ─────► │ Pending  │
                    └────┬─────┘
                         │ 按 StagePath 找第一个阶段
                         ▼
              ┌──────────────────────┐
              │ 进入第一阶段          │
              │ StageStatus=Waiting  │
              └──────┬───────────────┘
                     │
        ┌────────────┴────────────┐
        │ 广播：推给本档口所有屏    │
        └────────────┬────────────┘
                     ▼
        所有同角色屏可见
        （无锁，谁先划谁生效）
                     │
                     │ （V1 无接单步骤，师傅直接操作）
                     ▼
              StageStatus=Doing
                    │
                    │ 当前阶段划单（Bump）
                    ▼
            StageStatus=Completed
                    │
       ┌────────────┴────────────┐
       │ 还有下一阶段？            │
       └────────────┬────────────┘
          是 │              │ 否
             ▼              ▼
    联动/自动流转？        WorkflowStage=Done
       │        │          （整单可出餐）
   开启│        │关闭
       ▼        ▼
 自动进入下一  进入下一阶段 Waiting
 阶段(Waiting) （等师傅操作）
                    │
任意非终态 ─────────┴──► Cancelled（退菜）
任意状态   ────────────► Void（报损）
```

> **状态机口径（§1.6-D5 / D6）**：`StageStatus` 不设 `Accepted`；品项一律广播到本档口所有同角色屏，不存在"分派给某一块屏"。防重复依靠"划单后广播 `LineCompleted` 使其他屏该行自动移除"+"乐观锁兜底"。

#### 2.6.3 二态降级状态机（`EnableWorkflowState = false`）

关闭流转时**不区分工序**，仅保留两个业务状态（对应 §1.6-D4）：

| 显示状态 | 判定 | 可执行操作 |
|----------|------|-----------|
| 待出 | `WorkflowStage ≠ Done` 且未退菜 | 划单（直接置 `Done`） |
| 已划单 | `WorkflowStage = Done` | 撤销（在时间窗内） |

- 不写 `Prep` / `Cook` / `Expo` 中间态；`StageStatus` 固定为 `Waiting` → `Completed`；
- 品项自定义流转配置（`Workflow`）**失效**（数据保留，不删除，便于重新开启流转）；
- 屏幕上隐藏阶段标签与阶段等待时长，仅显示**全局等待时长**（从下单开始计时）；
- `FlowMode`（流转模式）置灰不可编辑；
- **屏侧影响（v6.97）**：**综合屏在该模式下照常可用**——三视图、检索、筛选、划单、叫号、撤销全部不变，只是品项不再显示当前工序（§3.5 ④）；**失去意义的只是工序屏**（无工序即无"我这一站"）。

#### 2.6.4 状态转移表（实现口径）

| 当前 `WorkflowStage` | 当前 `StageStatus` | 事件 | 守卫条件 | 结果 | 副作用 |
|----------------------|--------------------|------|----------|------|--------|
| `Pending` | `Waiting` | `Order.Create`（引擎进入首阶段） | StagePath 非空 | 进入第一有效阶段，`StageStatus=Waiting`，`StageBeginTime=now`，**重算 `CurrentStationId`** | 落库、广播推送（命中档口的所有同角色屏）、`OperationLog` |
| 任意阶段 | `Waiting` | 师傅首次操作（打开 / 勾选 / 双击划单） | — | `StageStatus=Doing` | 无推送 |
| 任意阶段 | `Waiting`/`Doing` | `StageComplete`（本次划 `Q < RemainingQty`） | `EnableOperate=true` 且 `Q` 符合步长 | `CompletedQty += Q`；**状态仍为 `Doing`，不推进阶段** | 回执 POS（`Item.Complete` 带 `IsFullComplete=false`）、打印（数量=本次份数）、`OperationLog` |
| 任意阶段 | `Waiting`/`Doing` | `StageComplete`（本次划完 `RemainingQty`） | `EnableOperate=true` | `CompletedQty = Qty`；`StageStatus=Completed`，记录完成时间与耗时 | 回执 POS（`IsFullComplete=true`）、广播 `LineCompleted`、**异步生成打印任务（§16）**、`OperationLog` |
| 任意阶段 | `Waiting`/`Doing` | `StageComplete`（并发，已被他人完成） | `Version` 不匹配 | **拒绝**，返回 `VERSION_CONFLICT`（该行已划单则返回 `DETAIL_ALREADY_COMPLETED`） | 强制刷新该行 |
| 任意阶段 | `Completed` | 引擎推进 | 还有下一阶段 | **推进 `WorkflowStage` 到下一阶段**：`StageStatus=Waiting`、`StageBeginTime=now`；**必须按新阶段重算 `CurrentStationId`（§2.2.1）** | 推下一阶段屏；**上游屏移除该行**（§2.7.1） |
| 任意阶段（含下游代办） | 非 `Done` | `StageComplete`（**越级完成**，**仅手动模式，V2 实现**） | 操作屏为下游阶段 | **目标状态由操作屏决定**（§2.7.1 ②）：切配屏→`B`、制作屏→`C`、传菜屏→`Done`；记 `SkippedStages`，**不产生产量/时长给中间阶段** | 回执 POS（**只发当前阶段完成，不补发前态**）、按目标状态推屏 / 完成时三屏移除、`OperationLog` 标 `DirectDone` |
| 任意阶段 | `Completed` | 引擎推进 | 无下一阶段 | `WorkflowStage=Done` | 回执 POS（`Order.Done`）、推屏 |
| 任意非终态 | 任意 | `Item.Remove`（退菜） | 品项**未划单归档** | `WorkflowStage=Cancelled` | 推所有屏标红删除线、`OperationLog` |
| 任意非终态 | 任意 | `Item.Remove`（退菜） | 品项**已划单归档** | 状态不变，仅标记 | **仅日志记录**（不回退状态），见 §4.3 |
| `Completed`（本阶段） | — | `StageUndo`（撤销） | **四项全部满足**（§2.19.2）：① 在撤销时间窗内；② **该明细当前状态 == 本操作的 `ToStage`**（未被推进）；③ 该操作记录未被撤销过；④ `Version` 未变（无他人操作） | **回退一格**到本操作的 `FromStage` + `StageStatus=Waiting`；清空该阶段完成时间/耗时；若撤销的是制作完成则**清空 `ProducedAt`/`ProducedSeconds`/`IsTimeout`**；`StageLog` 该行标 `Reverted` | 回执 POS `Item.Undo`（若已报完成）；推屏恢复；`OperationLog` 记 `Reverted` |
| 任意非终态 | 任意 | `Item.Void`（报损） | 有权限（管理端） | `WorkflowStage=Void` | 推所有屏移除、`OperationLog` |

**非法转移统一处理**：一律**拒绝并返回错误码**，不静默成功、不部分落库，错误码见 §10.6。

### 2.7 阶段联动与自动流转

阶段之间是否**自动联动推进**，由 **§1.6-D2 的两层模型**（总开关 + 流转模式）决定：

> **注意区分两个"开关"**：本节讲的是**工序之间的联动**（完成一站 → 推到下一站），它由 `FlowMode` 决定表现；`EnableWorkflowState` 是更上层的**"要不要区分工序"**总开关，关闭后根本不存在工序，也就谈不上联动（§4.1）。

| 流转模式 | `Prep → Cook` | `Cook → Expo` |
|----------|---------------|---------------|
| **`Auto`（自动模式，V1 实现）** | 切配屏划单完成 → 品项**自动推到制作屏**（下发 `StageAdvanced` 推送 + 轮询兜底） | 制作屏划单完成 → **自动推到传菜屏** |
| **`Manual`（手动模式，V2 实现）** | 切配完停在"已切配"，制作屏**也能看见它**并可越级代办（§2.7.1） | 制作完停在"已制作"，传菜屏**也能看见**并可一次结掉 |

**两层配置模型（权威口径，v6.96 由三层收敛为两层）**：

| 层级 | 配置项 | 位置 | 作用 |
|------|--------|------|------|
| 第 1 层：总开关 | `StoreConfig.EnableWorkflowState` | 门店 | **是否启用工序流转**。关闭则整层失效，退化为"待出 / 已划单"二态（§2.6.3） |
| 第 2 层：流转模式 | `StoreConfig.FlowMode`（`Auto` / `Manual`） | 门店 | **仅在总开关开启时可编辑**。`Auto` = **自动模式（V1 唯一的实现口径）**；`Manual` = 手动模式（**设计保留，V2 实现**） |

> **V1 默认值与实现边界（v6.96 定案）**：`EnableWorkflowState = true`、`FlowMode = Auto`。
> **`Manual` 在 V1 只留设计与数据结构，不实现交互**：管理端下拉框只呈现 `Auto`（`Manual` 标灰并注明"V2"）；若因导入配置 / 手工改库出现 `FlowMode = Manual`，**引擎按 `Auto` 运行并记 `Warning` 日志**，不得因未知模式中断出餐。
>
> **废止字段（v6.96）**：原第 3 层 `Workflow.AutoFlowStages` / `DishItem.AutoFlowStages`（`Prep>Cook,Cook>Expo` 这类"逐边自动推进白名单"）**已整体删除**——流转触发条件恒为"屏上划单"，不存在"某条边无需人划"，该字段无任何语义。两份 DDL 与 §9.11 / §9.5 均已去列。

#### 2.7.1 两种流转模式的**显示范围与操作语义**（按产品口径）

> **V1 / V2 实现边界（v6.96）**：**V1 只实现「自动模式」**（下表上方"核心差别"与 ① 显示范围中自动列、② 操作语义逐级推进部分）。**「手动模式」（透明流水线 / 越级代办 / `SkippedStages`）为设计保留，V2 实现**——本节保留完整口径，是为了 V2 开写时不必重新推导，**不代表 V1 要做**。

> **核心差别只有一条**：**自动模式每屏只看自己那一站；手动模式每屏还要看得见上游没做完的菜，并且可以直接代办。**
> 两种模式的**数据定稿规则完全一致**：某阶段一旦完成，该阶段的份数、完成时刻、耗时、产量立即定稿，永不被后续操作改写。

**① 显示范围对比（首阶段 = `StagePath` 第一道工序；默认全流程时 A=待切配 → B=待制作 → C=待传菜）**

| 屏幕 | 自动模式显示 | 手动模式显示 |
|------|--------------|--------------|
| **切配屏 A** | 仅 `A` | `A`（无上游） |
| **制作屏 B** | 仅 `B` | **`A` + `B`** |
| **传菜屏 C** | 仅 `C` | **`A` + `B` + `C`** |

> **手动模式是"透明流水线"**：下游能看见上游压了多少活（便于预判与催办），也能直接上手处理。上游屏则**不会**看到下游的菜（单向可见）。

**② 操作语义：目标状态由「操作屏」决定，与来源状态无关**

> 这是整套模型里最简洁的一条规则：**哪块屏点的完成，菜就到达"那块屏的下一站"**，不看在哪个状态被点的。

| 操作屏 | 目标状态 | 说明 |
|--------|:--------:|------|
| **切配屏 A** | **→ B** | 切配完成，交制作 |
| **制作屏 B** | **→ C** | 制作完成，交传菜 |
| **传菜屏 C** | **→ Done** | 交付完成，三屏全部移除 |

**完整真值表（来源状态 × 操作屏 → 结果）**

| 菜当前状态 | 切配屏操作 | 制作屏操作 | 传菜屏操作 |
|:----------:|:----------:|:----------:|:----------:|
| `A` 待切配 | → `B`（正常） | **→ `C`**（切配忘标记，制作代办）<br>`SkippedStages = B` | **→ `Done`**<br>`SkippedStages = B` |
| `B` 待制作 | 不可见 | → `C`（正常） | **→ `Done`**（制作忘标记，传菜代办）<br>`SkippedStages = 空`（C 由操作者完成） |
| `C` 待传菜 | 不可见 | 不可见 | → `Done`（正常） |

> **"制作屏操作 A 状态的菜 → C" 的业务解释（产品已明确）**：菜实际已经做完了，只是切配员忘了点完成。制作员点完成后**直接进入待传菜**，此时**只有传菜屏能看到它**（切配屏、制作屏都不再显示）。
> **不是 `B`、也不是 `Done`**——因为制作这个动作**真实发生过**，不能假装它没做（推到 B 会让菜回到一个它已经越过的站），也不能跳过交付（推 Done 会让传菜漏掉）。

**③ 产品已明确的场景（逐字落地）**

```
某菜处于 A（待切配）
  ├─ 自动模式：只有切配屏能看到；必须 A→B→C 逐级推进，传菜屏才能看到它
  └─ 手动模式：传菜屏也能看到（上游范围内）
              传菜员直接操作 → 该菜变为 Done → 三块屏同时消失
```

| 这条规则意味着什么 | 说明 |
|--------------------|------|
| **手动模式允许"越级完成"** | 最后交付的人可以直接把整道菜结掉，不必等前两站逐级确认 |
| **前态数据不受影响** | 越级完成时，未发生过的阶段（B/C）**不产生**完成记录与时长，更不会反向修改 A 阶段已定稿的数据 |
| **并发安全** | 多屏可操作同一菜 → 乐观锁 `Version`；后提交者收到 `DETAIL_ALREADY_COMPLETED`，前端提示"已被 XX 屏完成"并自动移除该行 |
| **可见性单向** | 下游能看上游，**上游永远看不到下游**（产品已确认：切配屏不需要看到 B/C） |

**④ 两种模式的数据影响（结论一致，逐项对照）**

| 数据 | 阶段完成时 | 手动模式越级完成时 |
|------|-----------|--------------------|
| `CompletedQty` / `StageCompleteTime` / `StageElapsedSeconds`（已完成阶段） | **定稿，不再变** | **定稿，不再变** |
| 已完成阶段的档口产量 / 超时统计 / 打印记录 | **定稿** | **定稿** |
| 未发生阶段（被跳过的 B / C） | — | **不产生产量、不产生时长**，记 `SkippedStage`（见 ⑤） |
| `WorkflowStage` | 推进到下一阶段 / `Done` | 直接 `Done`（越级） |
| `CurrentStationId` | **必须随阶段重算**（§2.2.1） | 置空或保留最后阶段档口（见 ⑤） |
| 屏幕可见性 | 本阶段移除、下阶段接住 | **全部移除**（Done） |

**⑤ 越级完成必须补记的审计信息（否则统计会失真）**

| 项 | 规则 |
|----|------|
| **跳过标记** | `OrderDetail.SkippedStages` = 「来源状态」到「操作屏阶段」之间的中间阶段。`A→C` 记 `B`；`B→C` 记空；`A→Done` 记 `B`（`C` 由操作者完成）；`C→Done` 记空 |
| 操作归属 | `OperationLog` 记录**操作屏阶段与档口**（`Stage` + `StationId`）+ `DirectDone`（是否越级） |
| **产量归属** | **计入操作屏的阶段**（制作屏代办 → 产量归 B，与实际生产一致） |
| 时长归属 | 只有实际发生的阶段有时长；**被跳过阶段的时长记 `null` 而非 `0`**（0 会把档口均值拉低，看起来效率提升，实际没做） |
| 报表口径 | 新增 **「越级完成率」** 指标（`SkipDoneCount / DoneCount`），并入 `DailyStoreStat` / `DailyDimStat`；超过 20~30% 说明前段积压或分工失效 |

> **产量归属的已知局限（如实记录）**：若传菜员代办一个 `B` 状态的菜，产量会记到 `C`（传菜）而不是 `B`（制作）。这种情况本身属异常操作，**不追求精确归因**，由「越级完成率」指标暴露数据质量问题——比强行推算一个错误的归属更诚实。

**⑥ 与"前态数据是否受影响"的最终回答**

> **不需要、也不允许影响前一阶段已定稿的数据。**
> 手动模式改变的只是**"能看到什么"**与**"谁能一次结掉"**，不是"改写历史"。前一阶段完成的份数/时刻/耗时一旦落库即不可变；越级完成只是"后面的阶段不发生"，而不是"前面的阶段作废"。

**⑦ 越级完成的 POS 回执（已定：不补发前态）**

| 项 | 规则 |
|----|------|
| 回执内容 | 越级完成时**只发 `Item.Complete`（`Stage = 操作屏阶段`）或 `Order.Done`**，**不补发**被跳过阶段的完成事件 |
| POS 侧语义 | **收到"后续状态完成"即意味前态已完成**——这是契约里必须写明的推断规则（§10.4），POS 不需要 KDS 补发前态回执 |
| 为什么不补发 | 补发会让 POS 收到"实际未发生的阶段完成"，与 KDS 记录冲突；且 POS 的状态判断只需"最新阶段"，补发是冗余 |
| 文档要求 | 在对接文档中明确：**KDS 存在越级完成，POS 必须以最高已完成阶段推断前态完成**，不得依赖逐级事件 |

**⑧ 已定口径（原 3 项待确认全部关闭）**

| # | 结论 |
|---|------|
| 1 | 制作屏操作 `A` 状态菜 → **`C`**（不是 `B`、不是 `Done`），`SkippedStages = B`，此时只有传菜屏可见 |
| 2 | 切配屏**不显示下游**（单向可见），上游永远看不到 B/C |
| 3 | 越级完成**不补发前态回执**，只发当前状态完成；POS 以"最高已完成阶段"推断前态完成 |

**与视图模式的独立性**：

| 维度 | 联动 / 不联动 | 视图模式 |
|------|--------------|----------|
| 层级 | 门店级，POS 数据同步与工序推进策略 | **单屏幕终端级**，前端展示视图 |
| 作用 | 控制工序是否自动推进、退菜 / 赠菜 / 改单是否自动推送 KDS | 控制菜品怎么分组展示 |
| 生效范围 | 全局数据流转 | 仅当前屏幕 UI |
| 组合 | 4 种组合全部支持 | 联动 + 桌台 / 联动 + 品项 / 不联动 + 桌台 / 不联动 + 品项 |

### 2.8 划单操作模式

**操作链路（唯一链路，无接单步骤）：**

```
品项进入本档口 → 屏幕显示"待制作"（StageStatus=Waiting）
→ 师傅直接操作（打开 / 勾选 / 双击）
→ 点"完成"划单（StageStatus=Completed）
→ 流转下一阶段 / 整单完成
```

`StageStatus` 不设"已接单"状态：品项到达屏幕即可操作，不做人工锁定。

**多屏协作下如何避免重复制作：**

| 手段 | 说明 |
|------|------|
| **广播 + 实时移除** | 所有同档口同角色屏可见；任一屏划单成功，Master 广播 `LineCompleted`，其他屏**该行立即移除**（通常 < 1 秒），师傅看到时已经没有这一行 |
| **乐观锁兜底** | 极端并发（几乎同时点击）时以 `OrderDetail.Version` 判定，先提交者成功，后到者返回 `VERSION_CONFLICT` 并强制刷新该行，提示"已被其他屏划单" |
| **视觉反馈** | 同一菜品被他人划掉时，屏幕给出短暂提示（"XX 屏已划单"），避免师傅困惑 |

**相关配置项：**

| 配置 | 位置 | 说明 |
|------|------|------|
| `EnableOperate` | 终端 | 该屏是否允许划单（综合屏默认 false） |
| `BaseGroupMode` | 终端 | 配置页二选一：桌台 / 订单（V2）（§3.0.1） |
| `ActiveView` | 终端（运行时） | 屏幕三视图实时切换：基础分组 / 合菜 / 单菜（§3.0.2） |
| `Merge_*` | 终端 | 合菜视图的 7 项合并条件（决定 `MergeKey` 生成，§2.3） |

### 2.9 同档口多屏协作：广播模式

同档口多块屏（如 2 台热菜制作屏）时，**所有屏看到完全相同的品项集合**：

| 项 | 规则 |
|----|------|
| 可见性 | 品项**推送给该档口所有同角色在线屏**，每块屏都完整显示 |
| 划单 | 任一屏划单成功后，Master 广播 `LineCompleted`，**其他屏该行自动移除** |
| 并发划单 | 两屏同时点同一行 → 乐观锁 `OrderDetail.Version` 判定，**先提交者成功**，后到者返回 `VERSION_CONFLICT` 并强制刷新该行 |
| 屏幕数量 | 无限制；新增 / 替换屏幕只需绑定档口，**无需任何策略配置** |
| 综合屏 | 同样是广播，天然满足 |
| 容错 | 任一屏故障 / 关闭，其他屏持有完整数据，业务不中断 |

**广播模式的最大风险在传输侧，不在业务侧**：一道菜要同步到 N 块屏，任何一块屏漏收一条推送，师傅就可能以为"这道菜已经做完"或"还没下单"。因此广播必须配**推送 + 本机轮询**双通道兜底，完整策略见 §2.10。

> **关于"抢单 / 指派"模式的场景说明（本产品不提供，不列入版本规划）**
> 有的连锁门店实行"菜要指派到人到屏"的流水线分工（例如每块屏对应一位师傅，菜只能由被指派的屏完成，其余屏不可见）。该模式适合分工极明确、且屏幕与人员稳定一一对应的档口；其代价是屏故障或师傅离岗时菜品无人承接，需要额外的改派机制兜底。
> 本产品的定位是**后厨自主认领**：菜在档口内公开可见、谁有空谁做、做完即同步移除。因此不提供指派/抢单能力，也不在 V1 / V2 规划中。

### 2.10 分屏数据刷新与防漏单策略（推送 + 本机轮询）

> 广播模式下"一道菜在 N 块屏上都可见"是容错优势，但前提是**每块屏的数据必须完整**。一旦某块屏漏收一条推送，师傅就会以为"这道菜没人做"或"这道菜已经做完了"——**漏单不是丢一条消息，是丢一道菜**。所以推送必须配本机轮询兜底。

#### 2.10.1 三层刷新机制

| 层 | 机制 | 触发 | 作用 |
|----|------|------|------|
| ① 主通道 | **WebSocket 推送增量** | 状态变化即时推送 | 正常路径，延迟最低（P95 < 1s） |
| ② 本机轮询（轻量） | **每 `PollingIntervalSeconds`（默认 15s，±20% 随机抖动）比对 `Revision`** | 定时器 | 兜住"推送丢了 / 客户端处理异常"——**这是防漏单的核心** |
| ③ 恢复全量 | **全量拉取** | 启动 / 重连 / Revision 差异过大 / 用户手动刷新 | 兜住"断网期间的变更"与"脏状态" |

#### 2.10.2 本机轮询的完整算法（客户端实现口径）

```
客户端本地状态（内存，重启时从 localStore 恢复到 AppliedRevision）：
    AppliedRevision : int      // 已应用到界面的最新 Revision
    LastPushAt      : DateTime // 最近一次收到推送的时间
    LastSyncAt      : DateTime // 最近一次"权威数据"到达时间（推送或轮询任一）

定时器（默认 15s ± 20% 抖动）：

1) 若 连接已断开（WebSocket 状态 ≠ Connected）
     → 跳步骤 4（全量）先重连

2) 【推送静默看门狗】若 Now - LastPushAt > PushSilenceSeconds（默认 30s）
     → 即使连接显示正常，也判定"推送通道异常"，立即执行步骤 3
     （这是最容易漏的场景：WS 不断线但推送被吞）

3) 【轻量轮询】
   GET /api/Terminal/{terminalId}/Poll?sinceRevision={AppliedRevision}
   Server 返回三选一：
     a. RevChanged = false（服务端 Revision == AppliedRevision）
          → 无变化，仅本地刷新等待时长文本；结束
     b. RevChanged = true 且 (ServerRevision - AppliedRevision) <= DeltaWindow(默认 300)
          → 返回增量变更集 { Cards: [...], Details: [...], Deleted: [...], Revision }
          → 客户端按 DetailId 应用增量、更新 AppliedRevision、LastSyncAt = Now
     c. 差异过大 / 本地 Revision 缺失 / 返回 RequiredFullSync = true
          → 执行步骤 4（全量）

4) 【全量拉取】
   GET /api/Terminal/{terminalId}/ActiveItems
   → 用服务端权威快照**整体替换**本地视图（不做增量合并，避免脏状态累积）
   → 同时更新 AppliedRevision / LastPushAt / LastSyncAt = Now

异常处理：
   - 轮询失败（超时 / 5xx）→ 指数退避重试（1s / 2s / 4s … 上限 30s），不阻塞下一次定时
   - 连续 3 次失败 → 界面切"离线态"（禁提交，保留浏览），并持续重试
   - 超过 DataStaleSeconds（默认 90s）没有任何权威数据到达 → 顶部显示**"数据可能滞后，正在恢复"**常驻提示条
```

#### 2.10.3 为什么不能只靠"推送"或只靠"全量轮询"

| 只靠推送 | 只靠全量轮询 |
|----------|--------------|
| WS 断线重连期间、服务端推送队列溢出、客户端反序列化异常、浏览器后台标签页节流 —— 任一发生就**静默漏单**，且无任何自我修复 | 每 15s 拉一次全量，300 条明细 × 20 块屏 = 高频重查询，SQLite 与 Kestrel 都会被拖慢，且延迟最差 15s |

**本方案的关键是用 `Revision` 把轮询压成"一次整数比较"**：绝大多数轮询只返回 `RevChanged=false`（几十字节），只有真有变化时才传增量。这样既省资源，又能把漏单窗口压到 15 秒以内。

#### 2.10.4 Master 侧配套要求（必须实现，否则轮询无效）

1. **门店级单调递增 `Revision`**：任何影响屏幕展示的变更（订单增删改、阶段推进、退菜、催菜、等叫、超时标记、配置变更）**都必须递增 Revision**，且与业务落库在**同一事务**内（否则会出现"数据已变、Revision 没变"，轮询永远发现不了）。
2. **Revision 历史环缓冲**：内存保留最近 300 个 Revision 对应的变更集（约 10 分钟）；`sinceRevision` 落在窗口内 → 返回增量；落在窗口外 → 返回 `RequiredFullSync = true`。
3. **`Poll` 接口必须廉价**：无变化时只返回 `{ RevChanged: false, ServerRevision, ServerNow }`，禁止顺手做重查询。
4. **主动通知落后终端**：Master 发现某屏上报的 `AppliedRevision` 落后超过 300 时，主动推 `RevisionGap`，让终端立即全量，不用等它轮询。
5. **随机抖动**：`PollIntervalSeconds` 由服务端下发，客户端实际间隔 = 配置值 × (0.8 ~ 1.2 随机)，避免 20 块屏同时打同一毫秒。
6. **幂等应用**：终端按 `DetailId` upsert，重复收到同一变更不产生重复行（推送与轮询可能同时到达）。

#### 2.10.5 与广播模式的关系（回应"防漏单"）

| 漏单场景 | 广播模式下的后果 | 本策略如何兜住 |
|----------|------------------|----------------|
| 推送丢失（A 屏没收到新菜） | A 屏师傅看不到这道菜，若其他屏也没注意 → **漏单** | 15s 内轮询发现 `Revision` 不一致 → 增量补齐 |
| 推送丢失（A 屏没收到"已被 B 屏划单"） | A 屏仍显示该菜 → **重复制作** | 同上；且 A 屏点划单时乐观锁返回 `VERSION_CONFLICT` 强制刷新 |
| 断网期间新单 + 其他屏已做完 | A 屏恢复后看到一堆过期菜品 | 重连 → 全量替换（不合并） |
| 客户端反序列化失败 / 前端异常 | 界面卡在旧状态 | 静默看门狗 + 轮询 +（连续失败 3 次）切离线态 |
| 屏幕重启（浏览器崩溃 / 断电） | 从空白恢复 | 启动即全量；若 `localStore` 有 `AppliedRevision` 且在窗口内，走增量快速恢复 |

> **一句话**：推送负责"快"，轮询负责"准"，全量负责"对"。三者缺一，广播模式的容错优势都会变成漏单风险。

**Master 侧筛选逻辑（不下放前端）**：

终端请求 / 订阅时带上 `TerminalId`，Master 根据终端配置（绑定档口 + 角色 + `EnableOperate` + `BaseGroupMode` + `Merge_*`）、品项当前阶段、品项 StagePath、档口反选规则，**在服务端预筛选**，并给每条明细**预先算好 `MergeKey`**，只返回该屏应看的明细行。前端按 Key 分组渲染，不重新计算业务规则。

**增量推送的顺序保证**：每次变更携带单调递增的 `Revision`（门店级全局序号），终端丢弃 `Revision` 小于本地已应用值的消息，防止乱序覆盖。
