# 第四部分：业务规则

## 4. 门店全局流转开关（StoreConfig）

流转开关属于**门店全局配置**，门店所有屏幕（档口屏、综合屏）统一生效，**不能单屏单独控制流转**。

> **理由**：工序流转是门店后厨业务规则，不能 A 屏有工序、B 屏看不到工序，会造成状态不一致。

### 4.1 EnableWorkflowState（是否启用三态流转）

| 取值 | 行为 |
|------|------|
| `True` | **开启**。启用切配 / 制作 / 传菜三阶段流转；所有屏幕展示流转阶段标签、阶段等待时长；菜品按自定义工序流转 |
| `False` | **关闭**。菜品仅保留 2 个状态：**待出 / 已划单**；**所有屏幕（含综合屏）隐藏流转阶段标签，不再区分工序**；`FlowMode` 置灰不可编辑；品项自定义流转流程配置**失效**（数据保留不删除）；业务简化为只保留基础划单 |

> **关闭流转 ≠ 关闭屏幕（v6.97 明确）**：`EnableWorkflowState = false` 时**综合屏照常可用**，三视图、检索、筛选、划单、叫号、撤销能力**全部不变**，只是**品项不再显示当前工序**、等待时长改为全局计时、状态退化为"待出 / 已划单"两态、划单即直接完成。**失去意义的只是工序屏**（没有工序就没有"我这一站"），综合屏反而成为该场景下的主力屏（§3.5 ④⑤）。

### 4.2 FlowMode（流转模式：自动 / 手动）

> **本字段是 v6.96 对原 `AutoFlowEnable`（bit）的重构**：原字段名为"是否自动流转"，但真实语义是"用哪一种流转模式"，布尔量容易误读，故改为枚举。

| 取值 | 行为 |
|------|------|
| 不可编辑 | 仅当 `EnableWorkflowState = true` 时可编辑；总开关关闭则置灰（§4.1） |
| **`Auto`（自动模式，默认）** | **V1 唯一的实现口径**。品项按 `StagePath` 逐级推进；**每屏只看自己那一站**；师傅在屏上**划单即完成本阶段**，Master 立即广播 `StageAdvanced` 把品项推到下一工序屏，另有 `Revision` 轮询兜底（§2.10） |
| **`Manual`（手动模式）** | **设计保留，V2 实现**。透明流水线：下游屏能看见上游未完成的菜，并可直接越级代办（§2.7.1）。V1 管理端下拉**只呈现 `Auto`**，`Manual` 标灰注明"V2" |

> **V1 引擎兜底**：若配置中出现 `FlowMode = Manual`（导入配置 / 手工改库 / 未来版本数据回滚），**V1 引擎按 `Auto` 运行并记 `Warning` 日志**，不得抛异常或停止出餐。
>
> **流转触发条件（原附录 B-2，v6.96 关闭）**：**只有"屏上划单"一个触发条件**，不存在"等待 N 秒自动推进"或"按标准工时定时推进"。`StageStandardSeconds` / `TotalTimeoutSeconds` **只用于超时预警与瓶颈分析，不参与流转判定**。
>
> **已废止**：`Workflow.AutoFlowStages` / `DishItem.AutoFlowStages`（逐边自动推进白名单）已删除——划单是唯一触发，无"免划边"存在。

### 4.3 退菜、赠菜跨流程业务规则

支持 POS **联动 / 不联动**两套模式，对退菜、赠菜校正业务流程。

| 场景 | 规则 |
|------|------|
| **退菜（按份）** | **V1 支持退部分份数**（§4.7）：`Item.Remove` 带 `Qty`（本次退份数）→ `CancelledQty += Qty`，**所有屏幕同步**；剩余份数为 0 时该行终止。**不能"整行一刀切"**——3 份只退 1 份时，另 2 份仍要做 |
| **已划单部分的退菜** | 已出餐的份**不可退**（不是退菜，是报损）→ 走 `Item.Void`；退菜只能作用于 `RemainingQty` 范围内的份 |
| **赠菜** | 正常进入后厨流转流程，仅标记赠菜标识 `IsGift = true`（展示"赠"标签，不影响流转与统计口径中的营收类字段） |
| **改单（数量 / 规格变更）** | 未划单：按最新值更新明细；已划单：生成新明细行（新 `DetailId`），旧行保留归档 |
| **删菜（整行删除）** | 等价于"退全部剩余份数"（`CancelledQty = Qty`），保留审计痕迹，不物理删除；已划单部分仍按报损处理 |
| **催菜 / 加急** | POS 推送标记，实时同步所有终端（展示优先级见 §4.4） |
| **不联动模式** | POS 端自行校正退菜 / 赠菜结果后**以新事件覆盖**推送 KDS；KDS 不做反向推导，仅按事件语义落库 |

> **数据一致性要求**：退菜 / 赠菜事件必须携带原 `DetailId`（或可唯一定位明细的 `PosOrderNo + LineNo`）与 `EventId`；无法定位到明细的退菜事件**拒绝处理**并返回 `DETAIL_NOT_FOUND`，记 `Error` 日志。

### 4.4 超时预警、催菜、加急规则

> 本章节为 V1 实现范围，细化如下。

#### 4.4.1 计时起点与时长定义（**界面只有一个时长：总出品时长**）

> **产品口径已明确**：界面上的超时**不是每阶段的超时**，而是**从"起菜"到"制作完成（待传菜）"的总时长**有没有超。
> 即：**`起菜`（POS 推 `NotifyState = 20` 的时刻，`LastFireAt`）→ `制作完成`（进入待传菜那一刻，`ProducedAt`）**，这一段与门店/菜品配的总超时比较。
> ⚠️ **注意不是"从点菜时间"**：v6.55 曾从点菜算起，v6.56 起改为起菜起算（等叫期间清零重算，§2.16.3）。

| 时长 | 起点 | 终点 | 用途 |
|------|------|------|------|
| **总出品时长（界面唯一口径）** | **`LastFireAt`（最近一次起菜时刻）** | **`ProducedAt`（制作完成、进入待传菜那一刻）** | **超时判定、卡片时长显示、报表时长指标** |
| 阶段时长（**只记录，不判定**） | `StageLog.EnterAt` | `StageLog.ExitAt` | 仅用于**瓶颈分析**（哪个阶段慢），不触发红黄 |

**三条必须写死的规则**

| # | 规则 | 说明 |
|---|------|------|
| 1 | **起点是"起菜"时刻（`Fired`），不是点菜时间** | 等叫 2 小时后再起菜，只从起菜算起——厨房不为等叫买单（§2.16.3） |
| 2 | **等叫（`Held`）清零重算，不是暂停冻结** | 产品口径："中间换成等叫，就得等下次叫起菜重新算"；`Held` 时已用时长归 0，再次 `Fired` 从 0 开始 |
| 3 | **终点是"制作完成"（进入待传菜），不是"传菜完成"** | 制作完成即定格，之后传菜耗时不再累加；责任到制作结束 |

**计时的校准（**注意：等叫不是"暂停"，是清零重算**）**

> ⚠️ 早期版本曾用 `HoldPauseCounting` 做"暂停累计"，**v6.56 起已废弃**：产品口径是"等叫后重新起菜从 0 算"。字段保留仅为兼容旧库，**不再参与任何计算**。

1. **等叫（`Held`）清零重算**：`Held` 期间已用时长归 0（不是冻结旧值）；再次 `Fired` 时 `LastFireAt = 起菜时刻`，从 0 开始累计；`HoldAccumSeconds` 只作分析，**不进 `ProducedSeconds`**；
2. **Master 时钟为准**：`OccurredAt` 来自 POS，需与 Master 校时；**若 POS 时间比 Master 超前 > 5 分钟，记 `Warning`**（防止 POS 时钟错乱导致全部超时红屏）；
3. **Master 重启 / 终端重连**：总时长按墙钟继续累计，**不重置**；
4. **前端自增**：屏幕每秒本地自增（基于 `ServerNow` 与 `LastFireAt` 差值校准），**不依赖服务端每秒推送**；
5. **停表时点**：`ProducedAt` 一旦写入，前端不再自增，改为显示定格时长。

#### 4.4.2 超时阈值（**门店总超时 + 菜品特例**）

> **只有两层，不要复杂化**：门店配一个默认总超时，个别菜品单独配。

```
① 菜品特例  DishItem.TotalTimeoutSeconds      （可空，配了就用它）
② 门店默认  StoreConfig.DefaultTotalTimeoutSeconds  （必填，默认 1200 秒 = 20 分钟）
```

**取值与判定**

| 项 | 规则 |
|----|------|
| 取值 | 菜品配了用菜品，否则用门店默认；**下单时快照**到 `OrderDetail.TotalTimeoutSeconds` |
| 判定时点 | **制作完成（`ProducedAt`）时定格判定**：`总出品时长 > 阈值` → `IsTimeout = 1` |
| 进行中如何显示 | 未完成时也显示"已用时长 / 阈值"，**超过阈值即刻转红**（表示"已经超了还没做完"），并在完成时定格 |
| 预警（黄） | 已用时长 **≥** 阈值 × `WarnRatio`（默认 0.8） |
| 超时（红） | 已用时长 **>** 阈值（**严格大于**，与 `IsTimeout` 判定同符号） |
| 阶段超时 | **界面不显示、不判定**；`StageLog` 的阶段时长仅供管理端瓶颈分析 |
| 传菜阶段 | **不计时**（终点已在制作完成定格），传菜阶段显示定格时长与超时标记 |

> **为什么不需要阶段超时判定**：门店关心的是"客人等多久能上菜"，这是一个**总账**。阶段超时是**管理诊断**需求（哪个环节拖了），放在报表里看比放在作业屏上更有价值——屏上出现"切配超时 2 分钟"这类提示，师傅只会困惑。

**为什么默认 20 分钟**：中餐正餐热菜从点菜到出品通常 15~25 分钟，20 分钟作默认值误报率最低；快餐/饮品店应下调（如 300~600 秒）。

**配置字段与快照**

| 项 | 规则 |
|----|------|
| 门店主配置 | `StoreConfig.DefaultTotalTimeoutSeconds`（int，默认 1200s = 20 分钟），**必填**，保证任何菜品都有兜底 |
| 菜品特例 | `DishItem.TotalTimeoutSeconds`（int，可空）；配了就覆盖门店值 |
| 生效时点 | **下单时快照**到 `OrderDetail.TotalTimeoutSeconds`，之后改配置**不影响进行中订单** |
| 预警阈值 | 预警 = 超时 × `WarnRatio`（默认 0.8），**不单独配时间**，避免两套数字打架 |
| 改配置边界 | 改门店默认 → **只影响新单**；历史单已快照 |

> **为什么必须"下单快照"**：门店中途把超时从 20 分钟改成 15 分钟，正在做的菜不能突然全部变红——那会让师傅以为系统坏了。快照保证"一单一个标准"。


#### 4.4.3 视觉与语音优先级

超标标签同时存在时，**展示优先级从高到低**：

```
退菜（红删除线） > 超时（红） > 催菜/加急（橙，闪烁） > 等叫（灰） > 起菜（蓝） > 赠菜（紫标签） > 正常
```

**语音播报规则（防轰屏，必须实现）**：

1. 同一品项的超时语音**只播报一次**（以 `DetailId + Stage` 为去重键），不重复播报；
2. 同一秒内多条超时 → **合并播报**（如"3 道菜品超时"），单条播报队列上限 3 条，超出的合并；
3. 催菜 / 加急播报优先级高于普通超时；退菜**不播报**；
4. 语音内容按当前屏幕语言包生成（见 §11.1），支持门店开关与音量配置；
5. 综合屏（只读）**默认关闭语音**，可配置开启。

#### 4.4.4 与排序 / 统计的关系

- 「超时(N)」「催菜加急(N)」「等叫(N)」「起菜(N)」统计数 = 当前**筛选范围内**的明细条数（非卡片数）；
- **已划单 / 退菜明细不计入**超时与催菜统计；
- 按等待时长排序时，使用**全局等待时长**（保证桌台卡片头部与排序口径一致）；
- 阶段级超时**不改变排序位次**（排序仍按桌台或全局等待时长），仅改变颜色与统计。

### 4.5 称重菜与数量步长（"份"的粒度口径）

> **本章解决两个容易混淆的问题**：① 称重菜能不能合并 / 拆分；② 0.5 份起点的品项要不要按 0.5 拆。
> **一句话：KDS 不拆 Qty。** "拆"只发生在 POS 建模（一行几份）与展示层（分几行显示），**不改变一行明细的份数**。

#### 4.5.1 品项售卖模式（`DishItem.SaleMode`）

| 取值 | 含义 | 数量单位 | 典型 |
|------|------|----------|------|
| `ByPiece`（默认） | 按份数卖 | 份 / 例 / 只 | 绝大多数菜品 |
| `ByWeight` | **按重量卖** | 斤 / 公斤 / 克 | 海鲜、现切肉、散称卤味 |

**称重菜的三条硬规则**

| 规则 | 说明 | 理由 |
|------|------|------|
| **① 不参与合并** | `MergeKey = "DETAIL:" + DetailId`，任何 `Merge_*` 开关都无效（§2.3.3） | 每行是**独立物理标的**：1.2 斤鲈鱼与 0.8 斤鲈鱼合成为"2.0 斤"后，后厨不知道做哪条、也无法对回桌台；且称重菜通常还要现场挑货 |
| **② 不做展示拆分** | 即使屏幕配置 `ItemView_DetailMode = SinglePortion`，称重菜也**恒显示为 1 行**（不虚拟拆成多行） | `SinglePortion` 的"每份一行"语义对小数/重量无意义（1.2 斤拆成 1.2 行？） |
| **③ 退菜只能整行退** | 不支持"退 0.5 斤" | 实物已按整份称出，退部分无法对应 |

**显示与打印**：数量显示为 `{Qty}{Unit}`，如 `1.20斤`（重量保留 2 位小数，`.00` 不显示）；**不显示"份"**。

**多做法称重菜**（一条鱼两吃：一半清蒸一半红烧）：由 **POS 拆成两行**（各自 `Qty` + 不同 `做法`），KDS 按两行独立处理——不是 KDS 拆。

#### 4.5.2 数量步长（`DishItem.QtyStep`）

| 取值 | 含义 | 用途 |
|------|------|------|
| `1`（默认） | 起订与递增都是 1 份 | 绝大多数菜品 |
| `0.5` | **0.5 份起订、按 0.5 递增** | 半份菜、按半只卖、小份/大份 |
| `0.1` | 按 0.1 递增 | 称重/散装（与 `ByWeight` 搭配） |

**KDS 侧如何使用 `QtyStep`（只做校验与展示，不做拆分）**

| 环节 | 行为 |
|------|------|
| 入站校验 | `Qty` 必须是 `QtyStep` 的整数倍（存在浮点误差，按 `QtyStep × N` 判定，容差 1e-6），否则返回 `VALIDATION_FAILED` |
| 展示 | `Qty` 原样显示（`0.5`、`1.5`、`1.20斤`），**不四舍五入、不凑整** |
| 合计 | 合菜卡总份数按 `Qty` 求和后按 `QtyStep` 精度格式化（0.5 步长 → `共 1.5 份`） |
| **不拆分** | **绝不允许**把 `Qty = 1` 的一行拆成 `0.5 + 0.5` 两条任务/两张卡 |

#### 4.5.3 为什么"0.5 份"不该用拆分实现

**关键区分**：

| 场景 | 正确做法 | 错误做法 |
|------|----------|----------|
| 客人点"半份宫保鸡丁" | POS 下一条明细 `Qty = 0.5`（`QtyStep = 0.5`）→ KDS 显示"0.5 份" | — |
| 客人点"1 份"，但厨房要分两次做 | **POS 拆两行**（0.5 + 0.5），或师傅一次做完 | KDS 把 `Qty=1` 的明细拆成两个 0.5 的任务 |
| 3 份同菜分批出餐 | **POS 拆三行**（1+1+1） | KDS 按份虚拟拆行后"单份划单" |

**为什么不让 KDS 拆**：

1. **`Qty` 是 POS 的账务口径**。KDS 拆行后，回执给 POS 的 `Item.Complete` 就对不上原始行号，结账/退款会错账；
2. **状态复杂度爆炸**：拆行意味着一条明细要维护"已完成 N 份 / 剩余 M 份"，乐观锁、部分回执、部分退菜、打印次数全部要改（见 §4.5.4）；
3. **POS 本来就能拆**：拆行是下单时的一次性动作，放 POS 侧成本最低，且符合"KDS 定契约、POS 适配"（§9.0）。

#### 4.5.4 相关口径澄清（消除原设计歧义）

原 §3.2.2 的 `ItemView_DetailMode = SinglePortion`（"每 1 份单独一行"）容易被理解为"可单份划单"，实际口径为：

| 项 | 口径 |
|----|------|
| `SinglePortion` 的"每份一行" | 展示层按"份槽位"展开，**每格可单独划单**（配合 §4.6 部分划单） |
| `Qty > 1` 时 | 显示 `Qty` 个份格（或"进度 2/3 + 划 N 份"控件），**已完成的格置灰** |
| 称重菜 | 恒 1 行、**不可分份划单**（`ByWeight` 优先于 `SinglePortion`） |
| 划单粒度 | `DetailId + 本次份数`（见 §4.6），不是"整行全有或全无" |

### 4.6 部分划单（V1 必须支持）

> **业务场景**：一条明细 `Qty = 3`，师傅先出 2 份、后出 1 份；或客人点了 3 份、后追加 1 份要求分开跟单。

#### 4.6.1 `OrderDetail` 的行粒度：**一行 = 一个 POS 下单行（`LineNo`）**

**回答"先点 3 份 A，后来追加 1 份 A，对应几行"：**

```
首单：LineNo=1  A  Qty=3   CreateTime=10:30   → 1 行
加菜：LineNo=2  A  Qty=1   CreateTime=10:45   → 另 1 行
                                              合计 2 行（不是 1 行 4 份，也不是 4 行）
```

**为什么必须是 2 行而不是合并成 4 份：**

| 维度 | 合并成 1 行 4 份的后果 |
|------|------------------------|
| **等待时长** | 加菜那份应从现在开始计时（后厨要优先补），合并后 4 份共用一个起点，先点的 3 份会"拖累"新加的 1 份 |
| **做法 / 备注** | 加菜常带不同做法（"再加一份，不要香菜"），合并会覆盖原行备注 |
| **部分划单** | 若已划 2 份再合并成 4 份，剩余 2 份里哪 1 份是"刚加的"完全无法区分 |
| **打印** | 跟盘单要印"第 N 次加菜"，合并后无法体现 |
| **退菜** | 客人退掉刚加的 1 份，合并后只能退"其中 1 份"，与原始行号对不上 |

**契约规定（写进 §10.3）**：

| 场景 | POS 行为 | KDS 结果 |
|------|----------|----------|
| 新下单 / **加菜** | **必须使用新的 `LineNo`** | 新增一行 `OrderDetail` |
| 同一行改数量（点错了、纠错） | 同 `LineNo` 推 `Order.Update`，覆盖 `Qty` | 更新原行 `Qty`（**不新增行**） |
| 同 `LineNo` 且 `Qty` 增大 | 视为"改数量"，**允许**但记 `Warning`（疑似加菜未换行） | 更新原行，**不区分批次**（降级） |
| **联台期间加菜** | 同上（新 `LineNo`），**`PosOrderNo` 不变**（联台即同一订单），并带 `SourceTableId` 指明归属桌台 | 在**同一 `OrderId`** 下新增一行，挂到对应桌台关联；联台组卡**不裂**（§3.1.4 / D11） |

> **不合并是硬规则**：`LineNo` 是明细行的稳定业务标识，KDS **不主动合并同品项的多个 `LineNo`**。合菜视图的"合并"只发生在**展示层卡片**（按 `MergeKey`），右侧明细永远按 `LineNo` 逐条列出。

#### 4.6.2 部分划单的数据与状态

`OrderDetail` 增加：

| 字段 | 类型 | 说明 |
|------|------|------|
| `CompletedQty` | decimal(18,3) | **已划单份数**（默认 0）。`RemainingQty = Qty - CompletedQty` |
| `QtyStepSnapshot` | decimal(18,3) | 下单时的数量步长快照（1 / 0.5 / 0.1），用于分份校验与 UI 分格 |

**派生状态（不新增字段，按 `CompletedQty` 与 `Qty` 比较得出）**：

| 派生状态 | 条件 | 屏幕显示 |
|----------|------|----------|
| 未做 | `CompletedQty = 0` | 正常待制作 |
| **部分完成** | `0 < CompletedQty < Qty` | **进度 `2/3`**，剩余份数高亮，仍计入待制作与超时 |
| 本阶段完成 | `CompletedQty = Qty` | 进入 `StageStatus = Completed`，后续按 §2.6.4 推进 |

**划单请求（`ReportAction` / `POST Action`）**

```json
{
  "Action": "StageComplete",
  "DetailId": "guid-detail",
  "Stage": "Cook",
  "Qty": 2,                 // 本次划单份数（默认 = RemainingQty）
  "Version": 3,
  "ClientEventId": "guid-client"
}
```

| 校验 | 规则 | 错误码 |
|------|------|--------|
| `Qty > 0` | 必填正整数或步长倍数 | `VALIDATION_FAILED` |
| `Qty ≤ RemainingQty` | 不能超划 | `QTY_EXCEEDS_REMAINING` |
| `Qty % QtyStepSnapshot = 0`（容差 1e-6） | 必须符合步长 | `QTY_STEP_MISMATCH` |
| 称重菜 | `Qty` 必须等于 `RemainingQty`（**不可分份**） | `WEIGHED_ITEM_NOT_SPLITTABLE` |

**幂等**：以 `ClientEventId` 去重；同一事件重复到达不得重复加 `CompletedQty`。

#### 4.6.3 部分划单的连带影响（必须一并实现，否则会出错账）

| 环节 | 处理 |
|------|------|
| **乐观锁** | 仍用 `OrderDetail.Version`；部分划单也 `Version + 1` |
| **回执 POS** | `Item.Complete` **必须带 `CompletedQty`(本次) / `Qty`(整行) / `IsFullComplete`**（§4.7.3）；`IsFullComplete = false` 时 POS 不得将该行标记为出餐完毕 |
| **打印** | 触发时数量取**本次划单份数**（不是整行 `Qty`）；`ItemSlip` 模板需能区分"本次 2 份 / 共 3 份" |
| **待制作数统计** | 按 `RemainingQty` 求和，不按 `Qty` |
| **超时判定** | 只要 `RemainingQty > 0` 就继续计时（不因部分完成而清零） |
| **阶段推进** | 仅当 `RemainingQty = 0`（即 `CompletedQty + CancelledQty = Qty`）才推进；部分完成**不推进** |
| **退菜** | **支持按份退**（§4.7），`CancelledQty` 累加；退掉的份不再参与划单与统计 |
| **合菜卡总份数** | `Σ RemainingQty`（已完成 / 已退的不计入"待出"） |
| **端上交互** | `SinglePortion` 显示份格，已完成置灰；其他视图显示 `2/3` 进度徽标 + "划 1 份 / 划全部"快捷动作 |
| **操作日志** | `OperationLog` 记录 `Qty`（本次份数）与操作后 `CompletedQty` / `CancelledQty`，便于事后核对"谁划了几份、谁退了几份" |

### 4.7 部分退菜（V1 必须支持）

> **业务现实**：客人点了 3 份，厨房出了 1 份，剩下 2 份不要了。如果只能"整行退"，那已出的 1 份账就对不上、已做的活也被一笔抹掉。**退菜必须按份。**

#### 4.7.1 三个数量字段与派生关系

`OrderDetail` 用三个量描述一行菜的生命周期：

```
Qty           整行份数（POS 下单量，不可变，除"改数量"事件）
CancelledQty  已退份数（累计）
CompletedQty  已划单（已出品）份数（累计）

恒等式（必须始终成立）：
    0 ≤ CompletedQty + CancelledQty ≤ Qty
RemainingQty = Qty - CancelledQty - CompletedQty     ← 待制作份数
```

| 派生状态 | 条件 | 含义 |
|----------|------|------|
| 待制作 | `RemainingQty = Qty` | 一份都没动 |
| **部分完成** | `CompletedQty > 0` 且 `RemainingQty > 0` | 出了若干份，还要继续做 |
| **含退份** | `CancelledQty > 0` 且 `RemainingQty > 0` | 退了若干份，其余继续做 |
| 混合 | `CompletedQty > 0` 且 `CancelledQty > 0` 且 `RemainingQty = 0` | 出一部分、退一部分，本行结束 |
| 整行退 | `CancelledQty = Qty`（`CompletedQty = 0`） | 全退 |
| 本阶段完成 | `RemainingQty = 0` 且 `CompletedQty > 0` | 该行在此阶段结束，可推进下一阶段 |

> `IsCancel` 保留为**派生冗余字段**（`IsCancel = (CancelledQty = Qty)`），仅用于"整行退"的快速查询与红删除线展示；**一切计算以 `CancelledQty` 为准**，禁止用 `IsCancel` 判断部分退。

#### 4.7.2 退菜接口与校验（**发起权归 POS，KDS 不接受终端直接退菜**）

> **一句话**：**退菜会改账单，账务权威在 POS，所以只能 POS 发起；KDS 只执行与展示。**
> KDS 侧允许厨房发起的只有两个动作：**报损（已出品作废）** 与 **沽清申请（做不了，请 POS 处理）**——都不能直接改消费。

| 动作 | 谁能发起 | 是否改账单 | KDS 行为 |
|------|:--------:|:----------:|----------|
| **退菜 `Cancel`** | **仅 POS**（`Item.Remove`） | ✅ 是 | 接收 → `CancelledQty += Qty` → 三屏同步标红 / 移除 |
| **报损 `Void`** | **POS 或 KDS 管理端** | 视 POS 策略 | 记 `VoidQty` + 原因（§2.17）→ 回执 POS |
| **沽清申请 `UnableToCook`** | **KDS 屏 / 管理端** | ❌ 否 | 推 POS 事件 `Item.UnableToCook`，**由服务员在 POS 决定是否退**（详见 §2.18） |

**退菜原因用「文本」，不用枚举（**有意的不对称**）**

| 动作 | 原因形态 | 为什么 |
|------|----------|--------|
| **退菜** | **自由文本**（`CancelReason`，nvarchar 200） | 退菜是**POS 侧发起的外部事件**，原因是服务员在现场的一句话（"客人说太咸""小朋友不要了"）。**KDS 无权规定 POS 该填什么枚举**，强加枚举只会让 POS 侧填"其他" |
| **报损** | **序号枚举** + 备注（§2.17.1） | 报损是**KDS 管理端自己发起**的动作，能规范填写；且报损金额大，必须能分组归因 |

> **代价与取舍（如实记录）**：退菜原因用文本 → **报表只能按文本原样列出，无法做"原因分布"分组统计**。若门店日后需要这块分析，可在管理端做"人工归类"（把历史文本归到几个桶里），而不是改契约逼 POS 加字段。


**为什么禁止 KDS 屏直接退菜（三条硬理由）**

| # | 理由 | 后果 |
|:-:|------|------|
| 1 | **账务一致性** | KDS 退了但 POS 账单没退 → **客人少付/多付**，收银对不上 |
| 2 | **责任链** | "这菜不做了"是客人+服务员的决定，**不是厨房单方面能定的** |
| 3 | **防滥用** | 屏上能一键退菜 → 忙时随手退掉 → **漏单且无人知晓**，事后查不到是谁 |

**POS 推退菜（唯一入口）**

```json
{ "EventType": "Item.Remove", "Payload": { "PosOrderNo": "...", "LineNo": 2, "Qty": 2, "Reason": "客人不要了" } }
```

**KDS 侧两个合法动作**

| 动作 | 接口 | 说明 |
|------|------|------|
| 报损 | `Action = ItemVoid`（带 `VoidQty` / `VoidReasonCode`） | 已出品作废，§2.17 |
| 沽清申请 | `Action = ItemUnableToCook`（带 `Reason`） | 厨房做不了（食材没有/沽清），**推 POS 待处理**；KDS 不自行改数量 |

> **`Action = ItemCancel` 已从终端 Action 枚举中移除**：若门店确需厨房帮退，只能通过"沽清申请 + POS 确认"两步完成，不允许一步到位。

| 校验 | 规则 | 错误码 |
|------|------|--------|
| 定位明细 | `DetailId` 或 `PosOrderNo + LineNo` 必须能唯一定位 | `DETAIL_NOT_FOUND` |
| `Qty > 0` 且符合 `QtyStepSnapshot` | 必须合法份数 | `VALIDATION_FAILED` / `QTY_STEP_MISMATCH` |
| **`Qty ≤ RemainingQty`** | **只能退未出品的份**；已出品部分不可退（应走报损 `Item.Void`） | `CANCEL_EXCEEDS_REMAINING` |
| 称重菜 | `Qty` 必须等于 `RemainingQty`（不可部分退） | `WEIGHED_ITEM_NOT_SPLITTABLE` |
| 幂等 | 同 `EventId` 重复到达不重复累加 | `DUPLICATE_EVENT` |

**退菜后该行是否终结**：`RemainingQty = 0` → 行在本阶段结束；`WorkflowStage` 置 `Done`（若 `CompletedQty > 0`）或 `Cancelled`（若 `CompletedQty = 0`）。

#### 4.7.3 回执 POS：**必须明确告知"部分"还是"全部"**

> 无论 POS 是否支持部分完成，**KDS 都必须把区分信息发出去**，由 POS 自己决定怎么处理。**禁止"含糊地只说完成"**。
>
> **v6.99 口径澄清（重要）**：**KDS 不存在"部分退"这个操作**。`Action = ItemCancel` 已从终端枚举移除（§4.7.2），退菜**只能由 POS 发起**（`Item.Remove` 带 `Qty`）。所以「退几份」是 **POS 说了算**，KDS 只执行 + 回执；KDS **从不主动发起部分退**。真正需要 POS 表态的只有**部分完成**（划单）一种。

| 出站事件 | 触发 | 必填字段 | 契约要求 |
|----------|------|----------|----------|
| `Item.Complete` | 划单（**含部分完成**） | `CompletedQty`（**本次份数**）、`Qty`（整行）、**`IsFullComplete`**、`RemainingQty` | `IsFullComplete = (RemainingQty = 0)`。**POS 必须接收**，不得因不认识而拒收事件；是否"按份记账"由 POS 能力声明决定（见下表） |
| **`Item.Cancelled`** | **仅 KDS 主动取消**（跨日清理 `IsFullCancel=true`）；**POS 发起的退菜不回执** | `CancelledQty`（本次退数）、`Qty`、**`IsFullCancel`**、`RemainingQty`、`Reason` | `IsFullCancel = (CancelledQty = Qty)`。**POS 发起退菜时不需要回执**——它是发起方，自己知道退了几份，KDS 再发一遍纯属噪声、且有双方重复扣减的风险；该事件只用于"KDS 替 POS 做了取消"的场景 |
| `Item.Void` | 报损（已出餐作废） | `VoidQty`、`Qty`、**`VoidReasonCode`**、`VoidRemark` | 与"退菜"语义分开：退菜=未做不要了（POS 独占发起），报损=已做报废（POS 或 KDS 均可发起，§2.17） |
| **`Item.UnableToCook`** | **沽清申请**（KDS → POS） | `PosOrderNo` / `LineNo` / `Reason` / `RequestedBy` | 厨房做不了（食材没有/沽清）；**POS 收到后由服务员决定是否退菜**，KDS 不自行改数量（§4.7.2） |
| **`Item.Undo`** | **撤销划单**（KDS → POS，§2.19.6） | `PosOrderNo` / `LineNo` / **`UndoStage`**（被撤销的阶段）/ **`RestoredStage`**（回退到的阶段）/ `Qty` / `OccurredAt` | POS 须把该菜品出餐状态**退回一格**；越级撤销时中间跳过阶段**不发事件** |

**与 POS 支持能力的关系（写进对接验收）**

**部分完成：POS 选择性接受（v6.99 定案）**

KDS **始终发送** `IsFullComplete`，POS 在对接时**必须二选一并在对接文档写明**：

| POS 选择 | 含义 | POS 侧动作 | KDS 侧 |
|:---|:---|:---|:---|
| **A. 接受** | 按份记账，出餐状态随每次划单变化 | 收到 `IsFullComplete=false` 时**立即**把该行记为"部分出餐 2/3"，并参与账单 / 出餐率统计 | 不做额外处理 |
| **B. 不接受** | 只在整行完成时改出餐状态 | 收到 `IsFullComplete=false` 时**自行累计份数**，直到 `IsFullComplete=true` 才标"已出餐" | 不做额外处理（**仍照常发 false**，供 POS 累计） |

> **两条硬底线**：
> 1. **不允许静默丢弃事件**——`IsFullComplete=false` 可以"不立即改状态"，但必须累计；否则整行永远等不到 `true`（KDS 不会补发）。
> 2. **选择必须在对接文档登记**——否则联调时无法判断"POS 显示部分出餐"是功能还是 bug。

**退菜：不存在"部分退"这个操作（v6.99 定案）**

| 事实 | 后果 |
|:---|:---|
| 退菜**只能 POS 发起**（`Item.Remove`），KDS 无退菜按钮 | KDS **不会主动发起**部分退；`IsFullCancel=false` 只可能出现在"POS 退 1 份、KDS 回执"这条链上 |
| 既然退菜由 POS 发起，**POS 自己知道退了几份** | KDS **不再对 POS 发起的退菜回执 `Item.Cancelled`**（省一半流量，且避免双方重复扣账） |
| KDS 主动取消只有**跨日清理**一种（§2.14） | 该场景恒为整行（`IsFullCancel=true`），POS 收到后把账单该行作废即可 |

> 一句话：**KDS 负责"说清楚"，POS 负责"怎么办"**。这一条是接口验收的硬门槛，跑不通不允许上线。
