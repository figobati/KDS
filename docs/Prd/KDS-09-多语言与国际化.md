## 11. 多语言设计

设计原则：前端 UI 文本资源独立资源文件；支持简体中文、英文等；**切换以屏幕终端为单位，单屏独立语言设置**；菜品名称按 POS 推送原始文本展示。

### 11.0 设计思想（三层分离 + 服务端一次解析）

> **一句话**：**"系统词汇"和"业务数据"分开治理；翻译归 POS，解析归 Master，展示归屏幕。**

**第一层：两类文本，两套机制**

| 类别 | 例子 | 归属 | 机制 | 谁翻译 |
|------|------|------|------|--------|
| **UI 文本**（系统词汇） | "划单""催菜""版本冲突" | KDS | 语言包（内嵌 JSON + 门店可覆盖 `ScreenLangPack`） | KDS 自己维护 |
| **业务数据文本** | 菜名、做法、备注、桌台名、档口名 | POS | `LocalizedText` JSON（`{"zh-CN":"…","en-US":"…"}`） | **POS / 菜单维护方** |

> **为什么必须分开**：合在一起会出现"菜名改一次要发版"或"UI 词条被 POS 数据覆盖"两类事故。UI 文本是代码资产（随版本发布），业务文本是数据（随订单流动）。

**第二层：解析在 Master 做一次，屏幕只拿单字符串**

```
POS 推 LocalizedText {"zh-CN":"宫保鸡丁","en-US":"Kung Pao Chicken"}
        │
        ▼  Master 按该屏 CurrentLang 解析（§11.2 回退链）
屏幕 DTO 里只有 "Kung Pao Chicken" 一个字符串
```

| 收益 | 说明 |
|------|------|
| 前端零多语言逻辑 | 每行渲染不用查字典，虚拟滚动性能不受影响 |
| **分组/排序/合并一致** | 所有键基于同一份解析结果（但归集键本身语言无关，见 §11.4） |
| 打印模板简单 | 模板不需要处理多语言对象 |
| 解析规则唯一 | 规则只存在于 Master 一处，不会出现"两块屏回退策略不同" |

**代价**：切换语言需要重新拉取数据（不是纯前端换字体）。可接受——切语言是极低频动作，且必须递增 `ConfigVersion` 走配置变更流程（§11.3）。

**第三层：语言是"屏"的属性，不是"人"或"门店"的属性**

| 层级 | 配置 | 说明 |
|------|------|------|
| 门店默认 | `StoreConfig.DefaultLang` | 兜底语言 |
| **屏幕** | **`TerminalConfig.CurrentLang`** | **主配置**：一块屏一种语言 |
| 打印模板 | `PrintTemplate.Lang` | 每类模板每语言一份（排版宽度差异大） |

> **为什么按屏而不是按人**：后厨是混合语言环境——切配屏可能是中文老师傅，传菜屏可能是外籍员工，同一门店不同屏需要不同语言。按"人"要引入登录与个人偏好（KDS 后厨屏通常无人登录），按屏最贴合实际。这也与 §5.1「屏幕级配置在 Master、终端只读」一致。

**四条不可妥协的底线**

| 底线 | 理由 |
|------|------|
| **不做机器翻译** | 菜名翻错是业务事故（且责任无法界定），翻译责任归 POS/菜单维护方 |
| **绝不显示空白或 key 名** | 后厨屏空白 = 师傅不知道这盘菜是什么；显示 `zh-CN` 只是噪音 |
| **不回写 POS** | KDS 只读外部多语言数据，任何"KDS 里改菜名"的能力都不做（避免双向同步冲突） |
| **归集键语言无关** | 见 §11.4，否则切语言会重排卡片、缺翻译会拆卡 |

### 11.1 UI 语言包

| 项 | 约定 |
|----|------|
| 存储 | 程序内嵌资源文件（`Resources/Lang/{lang}.json`），可选门店级覆盖（`ScreenLangPack` 表，§9.15） |
| 语言代码 | 标准 BCP-47：`zh-CN`、`zh-TW`、`en-US`、`ja-JP`（**V1 交付 `zh-CN` + `en-US` + `zh-TW`**；`ja-JP` / `ko-KR` 为 V1.1 评估） |
| Key 命名 | 点分小驼峰：`scr.card.newOrder`、`common.action.complete`、`error.versionConflict.title`；**命名空间 13 个**（`common`/`status`/`view`/`scr`/`adm`/`cfg.store`/`cfg.terminal`/`error`/`void.reason`/`print`/`health`/`tts`/`wizard`），V1 冻结清单见 `docs/Design/2026-10-24-语言包key清单.md`（**761 条**，zh-CN 基准 100%） |
| 占位符 | **只用命名式** `{name}` / `{n}` / `{qty}` / `{duration}`；禁止位置式 `{0}`（§11.7 检查器仍兼容旧词条） |
| 复数 | **不做 ICU 复数变形**，用不变短单位（`{qty} pcs` / `{n} min`）；确需单复数时用 `.one` / `.other` 成对 key |
| 默认语言 | `StoreConfig.DefaultLang`（默认 `zh-CN`） |
| 回退链 | `屏幕语言 → 门店默认语言 → zh-CN → key 原文`（key 原文兜底便于发现漏翻） |
| 缺 key 处理 | 生产环境展示回退值并上报统计；开发环境界面标红提示 |
| **V1 三语交付状态（2026-10-24）** | `zh-CN` **verified**（761 条基准，SSOT）/ `en-US` **verified**（同 761 条，占位符 100% 对齐）/ `zh-TW` **draft**（机转初稿 + 术语校正，待繁体母语复核，流程见 §11.6）。三份文件在 `docs/Design/`，可直接作 `Resources/Lang/{lang}.json` 初稿 |

### 11.2 业务数据多语言

| 数据 | 处理 |
|------|------|
| 菜品名称 / 备注 / 档口名 | POS 以 `LocalizedText` JSON 推送（§9.16）；**Master 推屏时按屏幕 `CurrentLang` 解析为单字符串**（前端不处理多语言） |
| 合并归集键 | **不用解析结果**，用语言无关的 `MergeBaseName`（§2.3.3 / §11.4） |
| 未提供某种语言 | 按 §9.16 回退链处理，**KDS 不做机器翻译** |
| 屏幕显示 | 跟随 `CurrentLang`（切语言即变） |
| 打印 | 用任务生成时的**内容快照**（§16.6），并按当前屏语言选择**对应语言的模板** |
| 历史归档 | 保留下单时快照文本，不因语言切换或改名而变 |
| 回执 POS | 只回传 `PosOrderNo` / `LineNo`，**不带名称**（避免语言差异影响匹配） |

### 11.3 语言切换

- 屏级切换：终端配置页修改 `CurrentLang` → 递增 `ConfigVersion` → 推送 `ConfigChanged` → 终端重载语言包与全量数据；
- 语言切换**不影响业务状态与流转**，仅影响文案与名称解析。

### 11.4 与归集 / 打印 / 快照的关系（三个易错点）

**① 归集键必须语言无关（`MergeBaseName`）**

| 做法 | 结果 |
|------|------|
| ❌ 用当前屏幕语言解析后的名字做 `MergeKey` | 切语言 → 整屏卡片重排；某行缺译文 → 同菜被拆成两张卡、份数变少 |
| ✅ 用 `MergeBaseName`（`StoreConfig.MainLang` 主名，缺失时取 JSON 字典序第一个非空值） | 与语言无关，切语言只换显示文字，卡片不重排 |

> 这也解释了为什么"按名字归集"仍然成立：归集用的是**同一个语言的主名**（业务身份），显示用的是**当前语言的译文**（展示），两者是不同字段。

**② 展示层跟随语言，凭证层固定文本**

| 场景 | 用哪个文本 | 理由 |
|------|-----------|------|
| 屏幕显示 | 当前 `CurrentLang` 解析结果（**随切换变化**） | 切了语言屏幕还是旧语言会让人以为没生效 |
| **打印单据** | **任务生成时的内容快照**（`PrintJob.ContentSnapshot`） | 补打时必须与已跟盘的那张一致 |
| **历史归档 / 上报总部** | **下单时快照文本** | 事后对账不能因改名或切语言而变 |
| 回执 POS | 原样回传 `PosOrderNo` / `LineNo`，不带名称 | 避免语言差异导致匹配失败 |

**③ 打印与多语言的真实约束：字体，不是字符串**

| 语言 | ESC/POS 字库支持 | 结论 |
|------|------------------|------|
| 简体中文 | 部分机型支持（GB18030） | 可用，且必须 GB18030 |
| 英文 / 拉丁 | 普遍支持 | 可用 |
| 日文假名 / 泰文 / 阿拉伯文 | **绝大多数热敏机字库没有** | **只能走 `Image` 位图渲染**（§16.5） |

> 这是推荐 `Image` 模式作为默认的第一理由：不是"排版好看"，而是**多语言在硬件层就没有字库**。位图绕过字库问题，代价是传输量变大。

**④ 模板按语言各一份**

`PrintTemplate.Lang` 每语言一份，因为同一张单在中英文下**宽度占用不同**（英文更长、易折行），列宽与`TasteLayout`需分别调优；不能用一套模板硬套多语言。

### 11.5 UI 多语言适配规范（文本膨胀与布局弹性）

> **核心问题**：**布局按中文设计，一切到英文就会崩。** 中文"划单"两个字，英文是 `Complete`（8 字符，视觉宽度约为中文的 2 倍）。所以多语言不是"换字典"，而是**布局必须按最长语言设计**。
> 繁体（`zh-TW`）是另一个性质的问题：**字数几乎一样，但字形与用词不同**，见 §11.6。

#### 11.5.1 文本膨胀基线（布局设计依据）

| 目标语言 | 相对 zh-CN 的宽度膨胀 | 原因 | 典型翻车点 |
|----------|:--------------------:|------|-----------|
| **en-US** | **+30% ~ +50%**（短标签/按钮最严重） | 单词长、无空格断词 | 按钮文字溢出、状态标签撑破卡片 |
| **zh-TW** | **≈ 0%**（字数相同） | 字形不同、用词不同 | **不是宽度问题，是字体与术语问题**（§11.6） |
| ja-JP | +10% ~ +20% | 假名混排、助词多 | 菜单项换行 |
| de-DE / fr-FR（若扩展） | +35% / +20% | 复合词极长 | 表格列被顶开 |
| ru-RU / ar-SA（若扩展） | +20% / 视情况 | 西里尔字母 / RTL | 布局镜像 |

**设计基线（v6.99 实测修正，写死）**：

原口径「所有容器 × 1.5」**已证伪**——按 761 条实际词条实测（`docs/Design/2026-10-24-语言包key清单.md` §11），短标签区 125 条里有 **41 条（33%）超过 1.5 倍**，最坏 `多方案` → `Multiple profiles` 达 **2.83 倍**。改为**两档**：

```
档 A｜长文本（≥8 汉字：说明、hint、提示句）   按 ×1.5 预留      实测中位 1.25~1.50，够用
档 B｜短标签（≤4 汉字：按钮 / Tab / 筛选 chip）按 ×2.5 预留     实测中位 1.38，p95 2.25，须留 2.5
      或改用「图标 + 短词」（< 8 字符），不进入膨胀统计
禁止：为某一语言调好的固定像素宽度
验收：用 en-US 走查全部界面，任何溢出/截断/挤压都算缺陷
```

> **为什么短标签反而更危险**：中文 2 个字承载的信息，英文要 8~12 个字符。`换人`→`Switch User`、`全屏`→`Full Screen`、`重叫`→`Call Again` 全是 2.5~2.8 倍。**厨房屏恰恰以短标签为主**（§1.2 要求极简），所以档 B 是主战场，档 A 反而不易出事。

#### 11.5.2 布局硬规则（10 条，逐条可验收）

| # | 规则 | 反例（禁止） |
|---|------|-------------|
| 1 | 按钮 / 标签用 `min-width` + `padding`，**允许换行** | `width: 80px` 的"划单"按钮 |
| 2 | **按钮文字禁止截断**；宁可加宽或换行 | "Complete" 被截成 "Compl…" |
| 3 | 卡片标题最多 **2 行**，超出省略号；**菜名允许 2 行**（§1.6） | 标题固定 1 行单行截断 |
| 4 | 表格列宽用**比例（flex）+ 关键列 min-width**；列头允许换行 | 列宽固定 px，英文列头被压成两字 |
| 5 | **状态标签用图标或固定短词**（退/赠/催/急），不随语言变长 | "Cancelled" 撑破卡片角标 |
| 6 | 筛选 chips 用 `flex-wrap`，**允许换行，不许 overflow:hidden** | 筛选栏被裁掉一半 |
| 7 | 侧栏 / 工具栏用 `min-width` / `max-width`，不用固定宽 | 右侧操作区被挤出屏幕 |
| 8 | `line-height ≥ 1.4`，行高不写死（跟随字体） | 固定 `height: 24px` 导致英文被切头 |
| 9 | 截断处**必须有兜底**：Tooltip（鼠标）/ 长按（触屏）查看全文 | 截断后无法看到完整内容 |
| 10 | 禁止用文字撑开布局（用容器约束 + `min-width: 0` 防 flex 溢出） | flex 子项被长单词撑破父容器 |

#### 11.5.3 字体与字形（zh-TW / ja-JP 必读）

| 语言 | 推荐字体 | 关键点 |
|------|----------|--------|
| zh-CN | Noto Sans SC | 简体字形 |
| **zh-TW** | **Noto Sans TC** | **不可用 SC 字体渲染繁体文本**：`門/门`、`直`、`骨` 等字形不同，用错字体显示的是"简体字形的繁体文本"，本地员工一眼能看出问题 |
| en-US | 系统无衬线 | — |
| ja-JP | Noto Sans JP | 日文汉字与中文写法不同（`直`、`骨`、`海`），**不能用中文字体顶替** |

> **按语言按需加载字体子集**（unicode-range + 子集化），不要一次加载全部 CJK 字体（单字体包 5~10MB，会拖慢后厨老机器首屏）。

#### 11.5.4 数字 / 时间 / 日期（避免 locale 歧义）

| 项 | 规则 | 理由 |
|----|------|------|
| 时间 | **固定 `HH:mm:ss` 24 小时制**，不随 locale 变 12 小时制 | 后厨不认 AM/PM，且 `11:14:42 PM` 更长 |
| 日期 | **固定 `YYYY-MM-DD`** | `10/21/2026` 与 `21/10/2026` 在不同 locale 下是不同日期，必错 |
| 时长 | 走语言包：`common.duration.minutes` → `12分` / `12 min` | 不要拼字符串 |
| 数字 | 份数**不带千分位**；金额类才按 locale 加 | `1,000 份` 在后厨场景无意义 |
| 计时器 | 数字用**等宽字形**（`font-variant-numeric: tabular-nums`） | 否则每秒跳动时文字宽度变化，整行抖动 |

#### 11.5.5 测试方法（这三条是验收门槛）

| 方法 | 做法 | 抓什么问题 |
|------|------|-----------|
| **伪本地化（pseudo-loc）** | 把所有 zh-CN 文案替换为加宽 40% 的伪文本（`［Ŝćŕééń 划单 Ŝćŕééń］`），走查全部界面 | 溢出、截断、挤压、换行错位 |
| **语言包完整性检查** | CI 阶段比对各语言 key 集合，缺 key 直接失败 | 漏翻（生产环境会显示 key 或中文） |
| **视觉基线回归** | 每语言各存一套关键页面截图，改动后自动比对 | 某种语言下布局回归 |

> **管理端配置页同样要测**：配置页也有大量表格与表单，英文下同样会溢出；打印模板更要单独测（英文更长，折行位置不同，§16.4.2）。

### 11.6 繁体中文（zh-TW）的特别规定

> 繁体**不是**"简体换个字形"：它是**独立语言**，有独立的用词与术语。这一节专门写死，避免开发期用自动转换糊弄过去。

| 规则 | 说明 |
|------|------|
| **UI 语言包必须人工独立维护 zh-TW** | **禁止用简繁自动转换生成**。自动转换会产生"記憶體/內存""軟件/軟體"这类错误，餐饮术语更严重 |
| **业务数据（菜名）不做简繁转换** | 菜名的 zh-TW 由 **POS 提供**；KDS 只解析不转换（否则等于篡改菜名，且无法对账） |
| **字形依赖字体** | 必须加载 TC 字体，见 §11.5.3 |
| **术语对照表（示例，供翻译者参考）** | 划单→**劃單**；档口→**檔口**（部分门店用"工作站"）；打印→**列印**；打印时间→**列印時間**；外卖→**外送／外帶**（台湾不叫"外賣"）；退菜→**退菜／取消**；报损→**報廢**；桌台→**桌位／桌檯**；份数→**份數**；催菜→**催菜**（相同） |
| **长度** | 实测 761 条与简体差 **−2 ~ +3 字符**（≈0%），**不额外预留宽度**；标点与阿拉伯数字混排时略宽，仍按 §11.5.1 **档 A（×1.5）** 执行 |
| **zh-TW 同时服务 zh-HK（v6.99 拍板）** | **不单设 `zh-HK`**：港澳门店用 `zh-TW` + 门店覆盖表 `ScreenLangPack` 覆盖个别用词（如「檔口」↔「工作站」、「外送」↔「外賣」）。理由：港澳与台湾同用繁体，差异集中在少数词汇而非整套文案，单开一套等于 key 总量 ×1 却换不来多少准确度 |
| **初稿生成流程（不违反上一行"禁止自动转换"）** | 允许用「字符映射 + 本表术语校正」批量产出**初稿**，但：① 初稿状态标记 `draft`，**不得进生产包**；② 交付前必须由**繁体母语使用者逐条复核**（重点：术语表命中项、`ScreenLangPack` 覆盖点）；③ 复核签署后才可置 `verified`。**"禁止自动转换"禁的是"未经人审就上线"，不是禁机器起稿** |

> **为什么业务数据不能转换**：`zh-TW` 菜名若由 KDS 自动转换，"土豆→馬鈴薯""菠萝→鳳梨"这类差异会导致**打印单据与 POS 账单不一致**，客人核对时直接投诉。菜名文本是 POS 的资产，KDS 只读。

### 11.7 启动自检：语言包完整性核对

> **为什么必须在启动时做**：语言包是**随程序发布的静态资源**，漏翻的 key 不会报错，只会静默回退成中文或英文——门店装到英文屏上才发现"按钮变中文了"，此时已上线。所以要在**加载完成的那一刻**就把缺口暴露出来。

#### 11.7.1 检查时机

| 时机 | 执行者 | 说明 |
|------|--------|------|
| **启动加载语言包后** | 终端 + Master | 主检查点（本需求核心） |
| **每次 `ConfigChanged` 后** | 终端 | 语言切换 / `ScreenLangPack` 覆盖变更后重查 |
| Master 启动 | Master | 校验内嵌资源 + `ScreenLangPack` 覆盖记录的 key 是否有效 |
| **CI / 打包阶段** | 构建任务 | **严格模式：有缺口直接构建失败** |

```csharp
// 伪代码：启动自检
var basePack = LoadLang(StoreConfig.MainLang);          // 基准：zh-CN
var targets  = new[]{"zh-TW","en-US","ja-JP"};
foreach (var lang in targets) {
    var pack = LoadLang(lang);
    var report = I18nChecker.Compare(basePack, pack, lang);
    _i18nReports.Add(report);
    _logger.LogWarning(...);                             // 只告警，不阻塞启动
}
foreach (var ov in ScreenLangPackOverrides)              // 门店覆盖
    CheckOverrideKeyExists(ov, basePack);
```

#### 11.7.2 检查项与级别

| 检查项 | 判定 | 级别 | 运行时后果 |
|--------|------|:----:|-----------|
| **基准语言缺 key** | `basePack` 缺某 key（被其他语言引用） | **Error** | 该文案全语言都显示 key 原文 |
| **目标语言缺 key** | `targetPack` 缺 `basePack` 中的 key | **Warn** | 该文案回退到基准语言（中文出现在英文屏） |
| **多余 key** | `targetPack` 有、`basePack` 没有 | Warn | 疑似拼写错或废弃词条，白占体积 |
| **空值 / 纯空格** | 值为 `""` 或全空白 | Warn | 等于缺 key，但更隐蔽 |
| **占位符不匹配** | 两语言的 `{0}` / `{name}` 集合不一致 | **Error** | **运行时格式化抛异常或丢参数**（如 `共 {0} 份` 译成 `Total portions`） |
| **JSON 解析失败 / 重复键** | 文件损坏或有重复 key | **Error** | 整包加载失败或后者覆盖前者（隐蔽） |
| **语言码不在白名单** | 出现 `zh-Hans` 这类非约定码 | Warn | 配置可能写错，永远加载不到 |
| **`ScreenLangPack` 覆盖无效** | 覆盖的 key 在内嵌包中不存在 | Warn | 覆盖静默不生效 |
| **值过长** | 单条文案 > 200 字符 | Info | 疑似把整段说明贴进了按钮词条，会撑破布局（§11.5） |

> **占位符检查为什么定成 Error**：这是唯一会**在运行期抛异常**的一类。缺 key 只是退回中文（难看但能用），占位符错位会让 `.format()` 直接崩——而后厨屏崩一个按钮就可能挡住划单。

#### 11.7.3 自检结果的处理

| 场景 | 行为 |
|------|------|
| 生产环境启动 | **绝不阻塞启动**（后厨不能因为一个漏翻的词条开不了机），只记日志 + 进健康检查页 |
| 缺 key | 按 §11.1 回退链显示（目标语言 → 门店默认 → 基准 → key 原文） |
| **占位符不匹配** | 该 key **强制回退到基准语言**（不用错位的译文），并记 Error |
| 屏幕上 | **不显示警告**（不给师傅添噪音）；仅管理端可见 |
| **严格模式（CI / 开发）** | 有 Error 或 Warn 即失败退出码非 0，阻断构建 |
| 结果留存 | 内存保留最近一次报告 + 落 `OperationLog`（便于升级后对比） |

#### 11.7.4 统一健康检查（三类自检合并出口）

本自检与 §2.11.2（路由）、§16.7（打印）**共用同一个"健康检查"页与同一套结果模型**：

| 自检类别 | 检查数 | 详见 |
|----------|:------:|------|
| 路由自检 | 10 项 | §2.11.2 |
| 打印自检 | 7 项 | §16.7 |
| **语言包自检** | **9 项** | §11.7.2 |

```json
// GET /api/Admin/Health/SelfCheck 统一结果结构
{
  "CheckedAt": "2026-10-21T11:30:00+08:00",
  "Categories": [
    { "Category": "Routing",  "Errors": 0, "Warnings": 1, "Items": [ … ] },
    { "Category": "Printing", "Errors": 1, "Warnings": 0, "Items": [ … ] },
    { "Category": "I18n",     "Errors": 0, "Warnings": 12,
      "Items": [
        { "Code": "I18N_MISSING_KEY", "Level": "Warn", "Lang": "en-US",
          "Keys": ["screen.cook.newOrder", "common.reprint", "…共 12 条"] }
      ] }
  ]
}
```

> **结果模型必须统一**（`Code` / `Level` / `Category` / `Detail`），否则三套自检会长出三种页面。管理端只做一个列表，按类别分组展开。

#### 11.7.5 实现要点

1. **差集运算**：key 数量级 500~2000，纯内存字典比对 < 10ms，不影响启动时间；
2. **占位符解析**：正则 `\{(?<name>[A-Za-z0-9_]+|\d+)(:[^}]*)?\}` 提取后比较**集合**（忽略顺序）；
3. **报告截断**：缺失清单最多列 20 条 + 总数，避免一次刷屏几百行日志；
4. **失败不抛**：语言包加载异常按"该语言整体不可用"处理，回退到基准语言并记 Error（**绝不让语言包问题导致进程退出**）。

#### 11.7.6 发布门禁：三项自检统一执行（CI + 现场）

> **目标**：把"装到门店才发现"的问题，提前到**构建时**和**上线前**。三道门禁，越早越便宜。

**门禁分三档**

| 档位 | 何时跑 | 跑什么 | 数据来源 | 失败处理 |
|:----:|--------|--------|----------|----------|
| **G1 构建门禁** | 每次构建 / PR | ① **语言包自检**（严格）<br>② **打印模板渲染自检**（用内置样例数据渲染每个模板，校验无异常、列宽不溢出）<br>③ **契约用例集**（§9.0：幂等 / 乱序 / 必填 / 拼桌 / 联台 / 换桌 / 退菜 / 部分划单） | 仓库内资源 + 样例数据 | **构建失败，退出码非 0** |
| **G2 发布门禁** | 打发布包前 | ① 语言包 ② 打印模板<br>③ **路由自检**（用**参考门店快照**） | 仓库内 `ConfigSnapshot.reference.json` | **阻断发布** |
| **G3 现场门禁** | 上门安装完成、正式营业前 | **三项全跑 + 打印连通性 + 档口绑屏核对** | **该门店真实配置** | **Error 必须为 0**；Warn 需登记并签收 |

> **为什么路由自检不能只在 CI 跑**：CI 里没有真实门店的档口 / 屏幕 / 菜单，只能用"参考门店快照"验证**自检逻辑本身不出错**；真正能发现"这家门店热菜制作2档口没绑屏"的，只有**现场用真实配置跑 G3**。

**配置快照（让路由自检可离线执行）**

新增管理端能力：**导出 / 导入配置快照**（`ConfigSnapshot.json`）

| 内容 | 说明 |
|------|------|
| 包含 | `StoreConfig`、`Station`（含反选三字段）、`TerminalConfig`（**剔除 `DeviceKey`**）、`PrintRule`、`PrintTemplate`、`Workflow`、`DishType`、`DishItem` |
| 不包含 | 订单 / 明细 / 日志 / 设备密钥 |
| 用途 | ① CI 用参考快照跑路由自检；② **上线前存档基线**；③ 配置变更前后 diff（换菜单、改档口后对比路由差异） |
| 敏感处理 | `DeviceKey`、管理员口令一律不导出 |

```json
// ConfigSnapshot.json（结构示意）
{
  "SnapshotVersion": "1.0",
  "StoreId": "guid",
```

**G3 现场检查清单（装店 SOP，逐项签收）**

| # | 检查 | 通过标准 |
|---|------|----------|
| 1 | 路由自检（§2.11.2） | `STATION_NO_SCREEN` / `MULTI_STATION_SAME_STAGE` / `PANE_COVERAGE_GAP` **均为 0** |
| 2 | 打印自检（§16.7） | 连通性通过、无 `RULE_WITHOUT_PRINTER`、试打一张样张 |
| 3 | 语言包自检（§11.7.2） | 无 Error；Warn 明细登记 |
| 4 | 各语言实机走查 | 每块屏切到实际使用语言，确认无溢出/截断（§11.5） |
| 5 | **导出并签收自检报告** | 支持导出 CSV/PDF，附门店签字留档 |

> **签收报告为什么重要**：连锁部署时"这店配好了没有"是扯皮高发点。有一份带时间戳、带 Error/Warn 明细的报告，责任边界清楚。
