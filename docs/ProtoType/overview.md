# KDS 原型 v2 · 交付总览

## 做了什么

基于 v1 两套比稿方案，针对三条反馈做了**引擎级重做**（不是补丁式调整），产出 `prototype/v2/`：

| 反馈 | 根因 | 解法 | 验证 |
|---|---|---|---|
| 宽屏两端是空的 | v1 用固定 1920×1080 画布 + `transform:scale()` 等比缩放，16:9 锁死必然留白 | 流式网格 `#app{position:fixed;inset:0}` + `minmax(0,1fr)`；**自动密度**按目标卡宽 560px 反推列数 | 1280→3840 六档实测，单卡宽恒在 396–602px，两端零留白 |
| 多语言大量换行 | 德/俄文本长度 ×2.2–2.3，靠留空间永远不够 | 三层文本策略（固定段 nowrap / 弹性段 ellipsis / 折叠段 +N）+ **CSS 容器查询**让字号跟卡片尺寸走 + 溢出审计 + RTL | 5 语言 × 6 分辨率全部无换行，长词可切两行档 |
| 行列数、字号实时查看 | v1 无配置入口 | `⚙` 抽屉：列 2–6 / 行 2–4 / 字号 75–135% / 1-2 行菜名 / 强对比 / 自动密度 / 溢出审计，**读数区全为实测值** | 每次变更即时刷新，含 48px 触摸达标告警 |

## 关键决策

1. **宽屏加列不加宽**：屏幕越宽只增列数，单卡尺寸锁在可读区间，避免"卡片被拉成条"导致字号与卡宽脱节。
2. **字号跟卡片不跟屏幕**：`container-type:size` + `min(k-w*cqw, k-h*cqh)`，卡片变矮变窄字号同步降，任何密度都不撞行。
3. **菜名默认截断而非换行**：牺牲完整菜名换零换行；需完整可见时改两行档或下单端限制字数。
4. **48px 触摸下限硬锁**：`.cft{clamp(48px,21.5cqh,86px)}` + `.btn{clamp(48px,17.5cqh,58px);max-height:100%}`，宁可少显示一道菜也不压触点。文档原要求 56px，在 1280×720 下会吃掉 1/4 卡高，暂取 48px（若终端最低 1920×1080 可回调 56px）。

## 踩坑

**Chromium `calc()` 不接受「数字 × 数字 × 长度」三连乘**（如 `calc(5.0 * 1.72 * 1cqh)`），整条声明被静默丢弃、字号回退 16px，控制台无报错。解法：系数预乘为成对常量 `--k-*-w` / `--k-*-h`，由 JS `applyScale()` 在缩放变化时统一重算。

## 文件

- `prototype/v2/index.html` — A/B 并排比稿入口
- `prototype/v2/app.html` — 主原型（单文件、零依赖、可交互）
- `prototype/v2/README-v2-满铺自适应与多语言方案.md` — 完整设计说明
- `prototype/v2/final-*.png` — 各分辨率/语言验证截图
- `prototype/v2/compare.html` — 总对比页（v1 两套方案 + v2 两套主题，一键切换）

# v2.1 修复：配置面板看不清 + 夜航对比度不足

## 根因（一个 bug，不是三个）

`#panel` / `#fab` / `#scrim` 是 `#app` 的**兄弟节点**，而主题属性只写在 `#app` 上：

```html
<div id="app" data-theme="a"> … </div>
<aside id="panel">   <!-- 这里拿不到 --bg-surface -->
```

`#panel{background:var(--bg-surface)}` 中变量未定义 → 整条声明非法 → **浏览器丢弃 → 背景完全透明**，控制台不报错。于是面板里的中文/EN/DE/RU 按钮、滑块、读数全都直接叠在菜卡上，才有"看不清楚、没法配置"。

**三层修复**：① 主题挂 `<html>`（`document.documentElement.dataset.theme`）；② `:root` 补浅色兜底值；③ `#panel` 再写 `background:#fff; background:var(--bg-surface,#fff)`。

实测：`panel-bg=rgb(22,29,38) alpha_ok=true`（A）/ `rgb(255,255,255)`（B），已无不透明通道。

# v2.2：单菜改小卡片 + 三视图独立行列/字号配置

两条反馈：① 单菜模式改成小卡片形状；② 合菜和单菜也要能配置行列数和字体大小。

## ① 单菜：表格行 → 小卡片

原实现是 `.s-hd` 表头 + `.srow` 七列行（桌号/菜名/数量/做法/等待/标记/操作），横向被列宽切碎，德语/俄语必然换行。改为 `.single` 网格 + `.scard` 小卡：

```
┌─────────────────────┐
│ A03      [超时][加急]│   ← 桌号 + 状态徽标（右上角，不够就省略）
│ 宫保鸡丁             │   ← 菜名，-webkit-line-clamp:2
│ 少辣 · 不要花生       │   ← 做法，单行 ellipsis
├─────────────────────┤
│ 12:34           ×3份 │   ← 等待时长（左） + 大号数量（右，品牌色）
└─────────────────────┘
```

- **整卡即触点**：点一下划单（打勾 + 半透明 + 删除线），再点撤销。砍掉了原来偷走横向空间的独立「操作」按钮。
- **状态靠色不靠字**：超时/预警/暂挂用底色 tint + 左侧 3–7px 状态条；状态条用 `inset-inline-start`，RTL 下自动镜像，不用写第二套样式。
- **容器查询驱动字号**：`container-type:size` + `min(k-w*cqw, k-h*cqh)`，卡变窄变矮字号同步收，任何密度都不撞行。
- 单菜卡菜名**固定两行截断**（不进面板的"菜名显示"开关）—— 一行会切掉德语/俄语菜名。

实测 @1920×1080：**7 列 × 4 行 = 28 卡/页**，卡片 **253×178**，菜名 **25.9px**，数量 **21.3px**，触摸目标 **180px 达标**。

## ② 三视图独立行列 + 统一字号

原来只有桌台视图吃 `--cols/--rows`，合菜硬编码 `4×3`、单菜根本没有配置入口。现在三者共用同一套令牌：

| | 列数范围 | 行数范围 | 自动密度目标卡 | 默认 |
|---|---|---|---|---|
| 桌台 | 2–6 | 1–4 | 560×400 | 3×2 |
| 合菜 | 2–6 | 2–5 | 360×250 | 5×3 |
| 单菜 | 3–8 | 2–5 | 272×186 | 7×4 |

- `.mgrid` / `.single` 都改成 `repeat(var(--cols),minmax(0,1fr))`，面板调一次三处都跟。
- **`S.dens` 按视图存密度**：切 tab 时先存档当前视图的 `{cols,rows}`，再载入目标视图的，来回切不丢设置。
- `buildDensityOpts()` 按 `DENS[view]` 动态重建面板里的列/行按钮组，不会出现"单菜视图里有 2 列按钮"这种无效项。
- 字号滑块（75–135%）本来就是全局的，单菜卡的六个系数（`k-sno / k-sdish / k-sway / k-swait / k-sqty / k-sdone`）已并入 `K_BASE`，`applyScale()` 统一重算。
- 面板顶部新增 **配置对象（桌台/合菜/单菜）** 选择器，边看边调。

实测：合菜 @1920×1080 → **5×3 = 15 卡/页**，卡片 **274×224**，菜名 **19.3px**（旧 12.6px），触摸目标 **226px 达标**。

## 顺带修掉的三个问题

1. **合菜/单菜没有分页**：原来 `renderPager()` 在这两个视图里被隐藏，数据一多就溢出。现在三视图统一走 `itemsOf(S.view)` + `pageSlice()`，末页自动并排收缩行数不留半空格；计数口径按视图区分（桌 / 道 / 道待出）。
2. **读数区误报"触摸目标低于 48px"**：`updateReadout()` 量的是 `.cft .btn`（只有桌台卡有）。改为「桌台量按钮、合菜单菜量整卡」。
3. **合菜卡偏瘦高**：目标卡从 320×300 调到 360×250，`k-dish2` 系数 5.1/7.5 → 7.8/10.6。

# v2.3 修复：合菜/单菜「行数」设置不起作用

## 根因

`renderMerge()` / `renderSingle()`（以及 `renderTable()`）里都有一段「末页收行」逻辑：

```js
const rows = Math.max(1, Math.ceil(list.length / S.cols));
if(rows < S.rows) wrap.style.gridTemplateRows = `repeat(${rows},minmax(0,1fr))`;
```

而每页容量是 `pageSize() = cols × rows`，所以 `list.length ≤ cols × rows` 恒成立，
`ceil(len/cols)` 永远不会大于 `S.rows` —— **这段代码只会往下收，不会往上撑**。

结果：合菜 12 条 @5 列 → 无论设 3/4/5 行都渲染 3 行；单菜 24 条 @7 列 → 设 4/5 行都是 4 行。
只有**调小**行数（合菜设 2 行 → 每页 10 条 → 2 页）才看得出变化，调大则完全无反应。

## 决策：行数 = 密度（卡片尺寸），不是「把当前数据塞满屏幕」

真正的问题不是"没生效"，而是这条收行逻辑本身设计错了 —— 它让**卡片尺寸变成数据量的函数**：
第一页 28 张卡每张 178px 高，翻到末页只剩 4 张就变成每张 700px 高。厨房里手会形成肌肉记忆，
卡片忽大忽小比留白危险得多。

所以改成：

- **默认严格按 `S.rows` 渲染**，末页剩下几个格子就空几个格子，卡片尺寸恒定。
- 新增面板开关 **「末页铺满」**（`S.fill`，默认关）。想要"最后一页放大铺满"的人自己开。
- 三视图统一走 `applyGridRows(g, n)`，不再各写各的。
- 读数区如实显示 **「本页占用 X/Y 格」**；开了铺满则显示 **「实渲 N 行（末页铺满）」**。

## 实测（1920×1080，手动 5 列 / 7 列）

| 设置 | fill=0（默认） | fill=1 |
|---|---|---|
| 合菜 5×3 | 卡 274×224，菜名 19.3px | 同左（本来就满） |
| 合菜 5×4 | 卡 274×165，菜名 14.7px | 卡 274×224（收成 3 行） |
| 合菜 5×5 | 卡 274×129，菜名 11px | 卡 274×224（收成 3 行） |
| 单菜 7×3 | 卡 253×241，菜名 27.3px | 同左 |
| 单菜 7×4 | 卡 253×178，菜名 25.9px | 卡 253×178（本来就 4 行） |
| 单菜 7×5 | 卡 253×140，菜名 20.4px | 卡 253×178（收成 4 行） |

注意：合菜 5×5 时菜名降到 11px（clamp 下限）—— 这是 25 个格子装 12 道菜的真实代价，
提示使用者"行数不是越大越好"，要配合列数一起调。

# v2.4 修复：合菜/单菜卡内容改为顶部对齐

## 问题

单菜 `.sbody` 用了 `justify-content:center`，合菜 `.mname` 用了 `margin-block:auto` —— 都是垂直居中。
一排卡片里菜的叫法长短不一：有做法行的卡、菜名一行的卡、菜名两行的卡，整块内容高度不同，
居中之后**菜名的起始 y 各不相同**，横着扫一行眼睛要上下找，视觉上就是锯齿。

正确形态是：桌号/状态在顶 → 菜名紧跟 → 做法在菜名下 → 底栏（时长 + 数量）贴卡底。

## 改法

| 元素 | 原 | 现 |
|---|---|---|
| `.sbody`（单菜卡身） | `justify-content:center` | `justify-content:flex-start` |
| `.mname`（合菜菜名） | `margin-block:auto` | `margin-block:clamp(17px,14.5cqh,44px) 0` |
| `.srow1`（单菜首行） | 高度随内容 | `min-height:clamp(16px,5.6cqh,32px)`（与 `.badge` 同一套 clamp） |

两个细节值得记一下：

1. **合菜菜名要预留顶部一条**，因为状态角标（`.mcorner`）和数量角标（`.mqty`）是绝对定位压在卡顶的。
   以前靠垂直居中「躲开」它们，改成顶对齐就得显式让位。而且这条留白**所有卡都留** ——
   只在有角标的卡上加，那些卡又会被压下去，锯齿照样存在。
2. **单菜首行要等高**。实测 6×5 档还残留 2px 错位：有徽标的卡首行被撑到 16px，
   没徽标的卡只有 13px 文字行高。把 `.srow1` 的 `min-height` 写成和 `.badge` 完全相同的
   `clamp(16px,5.6cqh,32px)`，两者永远等高。

## 验证（headless 实测菜名相对卡顶的偏移）

| 视图 / 密度 | 菜名 top 偏移 | 离散度 | 压底栏 | 溢出 |
|---|---|---|---|---|
| 单菜 7×4 | 28.8px 全部一致 | **0** | 0 | 0 |
| 单菜 6×5 | 25.1px 全部一致 | **0** | 0 | 0 |
| 单菜 8×2 | 38.3px 全部一致 | **0** | 0 | 0 |
| 单菜 4×4 | 28.8px 全部一致 | **0** | 0 | 0 |
| 合菜 5×3 | 42.9px 全部一致 | **0** | 0 | 0 |

德语 / 俄语 / 阿拉伯语 × 1920 / 1440 / 1280 八组回归：溢出 0、角标压名 0、压底栏 0。

# v2.5：新增繁體中文（tag：zh-TW）

语言从 5 种变 6 种，面板语言项的第二个按钮。

> **v2.19 标签修订（2026-10-25）**：对外语言标签原本写 `yue-Hant-HK`（粤语），
> 与 `KDS-09 §11` 规定的 BCP-47 语言表（`zh-CN` / `zh-TW` / `en-US`）不一致，
> 现统一为 **`zh-TW`**。内部词典 key 仍沿用 `yue`（旧深链 `?lang=yue` 要继续能用），
> 深链同时接受 `?lang=zh-TW` / `zh-Hant` / `zh-HK`，三种写法指向同一份繁體詞典。
> 另：文本膨胀系数 1.15 → **1.05**（KDS-09 §11.5 记 zh-TW 相对 zh-CN 字数相同 ≈0%，
> 只为正体笔画略宽留 5% 余量）；字形栈改为 **TC 优先**并去掉简体 YaHei 兜底。

## 不是「把简体转繁体」

繁體词条整份重写，没有走简转繁。词汇层面差异非常大：

| key | 简体中文 | 繁體中文 |
|---|---|---|
| `d_rice` | 米饭 | 白飯 |
| `d_cucumber` | 拍黄瓜 | 拍青瓜 |
| `d_cauliflower` | 干锅花菜 | 乾鍋椰菜花 |
| `tabTable` | 桌台 | 檯 |
| `tabMerge` | 合菜 | 併菜 |
| `handover` | 换人 | 交更 |
| `shift` | 早班 | 早更 |
| `mergeSel` | 已选 {n} 道 | 已揀 {n} 道 |
| `todo` | 待制作 | 待整 |
| `mWarn` | 即将超时 | 就快超時 |
| `t_ice` | 冰 | 凍 |
| `b_gift` | 赠 | 送 |
| `loginBtn` | 登 录 | 登 入 |
| `empNo` | 工号 | 員工編號 |

只做简转繁会产出「米飯 / 桌台 / 換人 / 早班」——港台同事读得出来但别扭，是典型的机器翻译味。

> **待确认**：词条目前是**港式**用词（檯 / 走單 / 少冰 / 交更）。若门店定位在台湾，
> 需另过一遍台湾用词（桌 / 出菜 / 去冰 / 交班）—— KDS-09 §11.6 明确禁止用简繁自动转换糊弄。

## 字形：必须切字体栈，否则渲染成大陆字形

```css
html:lang(zh-TW) body, html:lang(zh-Hant) body, html:lang(zh-HK) body{
  font-family:"PingFang TC","Microsoft JhengHei","Noto Sans TC","PingFang HK","Noto Sans HK",sans-serif;
}
```

繁体不是「同一种字的不同写法」，港台字形有独立规范（如 骨 / 內 / 起 的笔形）。继续吃 `PingFang SC` / `Microsoft YaHei` 会渲染成大陆字形，一眼就看出不对。
**兜底也不能落回简体字体** —— 宁可退到系统 sans-serif。

对应 lang 标签必须是 **`zh-TW`**（KDS-09 §11）：不能写裸 `zh-Hant`（不含地区），也不能写 `yue`（只声明语种不含文字系统），浏览器都可能按简体回退。为此新增 `LANG_META` 表统一驱动：

| | tag | dir | 文本长度 | 备注 |
|---|---|---|---|---|
| zh | `zh-CN` | ltr | ×1.00 | 基准 |
| **yue**（对外 `zh-TW`） | `zh-TW` | ltr | **×1.05** | 字数与简体相同，正体笔画略宽留 5% |
| en | `en` | ltr | ×1.70 | |
| de | `de` | ltr | ×2.20 | 复合长词 |
| ru | `ru` | ltr | ×2.30 | 最长 |
| ar | `ar` | rtl | ×1.35 | 唯一 RTL |

`render()` 里改从 `langMeta()` 取 tag / dir，不再硬编码 `S.lang==='ar' ? 'rtl' : 'ltr'`。

## 顺带四处

# v2.6：字号缩放按视图独立

反馈：改一个视图的字号会影响另外两个。

## 为什么必须独立

原来的 `S.scale` 是全局单值，`applyScale()` 把所有 `--k-*` 乘上它统一写到 `<html>`。
问题是三种视图的卡片根本不是一个量级：

| 视图 | 卡片（1920×1080 默认密度） | 菜名基准字号 |
|---|---|---|
| 桌台 | 600×362 | 30.0px |
| 合菜 | 274×224 | 19.3px |
| 单菜 | 253×178 | 25.9px |

字号走容器查询 `min(k-w×cqw, k-h×cqh)`，卡片大一倍字就大一倍。所以「同一档缩放」
在三张卡上对应的实际 px 完全不同 —— 为了看清合菜把滑块拉到 130%，切到桌台字就大到溢出。
共用一根滑块的结果就是逼着用户在视图间来回重调。

## 改法

照抄已经验证过的 `S.dens` 模式：

```js
fonts:{ table:1, merge:1, single:1 }   // S.scale 始终代表「当前视图」
```

- `setView()`：离开时 `S.fonts[旧视图] = S.scale`，进入时 `S.scale = S.fonts[新视图]`。
  login 视图不参与存档，避免污染三视图。
- `syncFontUI()`：滑块位置 / 百分比 / 标签里的视图名永远跟着当前视图走，切视图自动同步。
- 滑块 `oninput` 只写 `S.fonts[S.view]`，另外两个不动。
- 新增 **「把当前值套用到全部视图」** 按钮（`.pn-btn`）：三视图各自独立，但总要留一个批量出口，
  否则想统一时得手动调三次。按下后按钮文案变成 `✓ 已套用到三个视图`（i18n key `fsApplied`，六语言齐备）。
- 面板标签改成 **「字号缩放 · 单菜 130%」**，一眼知道在调谁。
- 读数区：`字号缩放 130%（仅单菜）`。

**CSS 侧完全没动**。同一时刻只渲染一个视图，`render()` 里按当前 `S.scale` 重算 `--k-*` 就够了；
`--k-*` 只被卡片内部元素使用（21 处），顶栏 / 页脚 / 面板不吃这些系数，所以切视图时 chrome 字号不会跳。

## 验证（headless 程序化切视图）

```
起始 table   [scale=1.00 {t:1.00, m:1.00, s:1.00} 标签=100% 对象=桌台]
切 single    [scale=1.00 {t:1.00, m:1.00, s:1.00} 标签=100% 对象=单菜]
single 调130%[scale=1.30 {t:1.00, m:1.00, s:1.30} 标签=130% 对象=单菜]
切 table     [scale=1.00 {t:1.00, m:1.00, s:1.30} 标签=100% 对象=桌台]
切 merge     [scale=1.00 {t:1.00, m:1.00, s:1.30} 标签=100% 对象=合菜]
回 single    [scale=1.30 {t:1.00, m:1.00, s:1.30} 标签=130% 对象=单菜]
点套用全部   [scale=1.30 {t:1.30, m:1.30, s:1.30} 标签=130% 对象=单菜]
```

渲染层同步生效：单菜菜名 100% 时 25.9px → 130% 时 **33.7px**；同一时刻切到桌台，
桌号仍是 **39.6px**（桌台档位的 100%），没有被单菜的 130% 带跑。

深链隔离同样成立：`?view=single&scale=1.3` 只写 `single`；`?view=merge&scale=0.8` 只写 `merge`；
`?view=login&scale=1.2` 不污染任何视图存档。六语言下 `fsApplied` 齐备（缺 key 0），
阿语显示 `منفرد`、粤语显示 `單菜`。

## 补记：index.html 成为唯一入口（导航页 v2.8）

要求：在 `index.html` 加登录入口，以后其它页面也都从这里加入口。

### 做法：把入口做成数据清单，而不是再加一个按钮

原来入口是手写三行 `<button data-view>`。加登录若只是再拷一行，问题不在这次拷贝，
而在于**每加一个页面要改三处**：HTML 按钮、底部 footer 说明、全屏链接文案。
漏一处就不一致 —— 比如登录页进了，底部还在教人「按 ← → 翻页」，而登录页根本没有分页。

「全屏打开」链接 / URL 深链全部自动生成。**以后加页面只改这一个数组。**

```js
{ id:'login', label:'登录', sep:true, paged:false, tip:'登录态收起顶栏全部业务入口…' }
```

1. **登录不是「第四种视图」**：三个数据视图是同一工单集合的三种呈现，登录是流程起点。

   长度差异最大的一屏（「请输入工号与 PIN 码」德语长 80%），它比列表页更该做语言压测。
3. **删掉没行为的字段**：`ENTRIES` 里原本还有 `panel` 字段，只是声明、不驱动任何东西。
   留着会让后来改的人以为动它有效果 → 删掉，只保留真正驱动 UI 的 `paged`。

### 顺手加的比稿便利

- 数字键 `1`–`4` 直接切入口（越界键无副作用，带修饰键不拦）。
- 当前语言 + 入口写进 `#lang=zh-TW&view=login`，链接可直接发给同事；

也不用会前先在群里吵一轮。缺点是交付前要记得删掉（三个，很好认）。

### 2. 只读屏不是"变灰屏"，是"变矮屏"

清单第 2 点要求 `EnableOperate=0` 时卡尾整条不显示。这个动作有个附带好处我经常忽略：
**省下来的高度正好够多排一行数据**。

所以只读屏看起来不像"坏了的完整版"，而像"能多看一屏的精简版" —— 同样一屏面积下，
只读屏反而更装得下。这一点体现在卡高计算里：`gridRows(len) + (ro ? 1 : 0)`。

### 3. 管理端必须另开文件，不是为了省事

作业屏是站着戳的触控场景（≥44px 触摸目标、**禁止滚动**），管理端是坐着用鼠标的场景（可以更密、允许滚动）。

这是**两套密度标准**。塞进同一个文件会让两边都别扭，更要命的是会让"作业屏必须 ≥44px"
这条约束被管理端悄悄稀释 —— 真到了厨房里，吃亏的是那个手上有油、还赶着出菜的人。

所以开了 `admin.html`，管理端沿用 v2 的全部 Token，但另建 `--adm-*` 别名、全部 `.adm-` 类名前缀。

# 修正与定案（v2.13）

## 1. 导航页两个预览框全黑 —— 是 grid 轨道塌陷，不是 iframe 的问题

打开 `index.html` 只看到两片深色，页头文字悬在中间。量一下就知道：

```
stage0=753x0  iframe=0x0  tf=matrix(0,0,0,0,0,0)
```

`.stage` 里唯一的子元素 iframe 是 `position:absolute` —— 绝对定位不参与撑高，
而 `main` 又写着 `align-content:center`，行轨道退化成按内容定高，于是 `.stage` 高度 = 0，
缩放系数 = 0，什么都没了。

**修**：`grid-template-rows:minmax(0,1fr)`，窄屏给两条轨道。修完 `stage=753x647`、
iframe 按 0.523 缩放成 `753x471`（正好 1440×900 的 16:10）。

顺手把页头徽标从写死的「1920×1080 等比预览」改成跟入口走 —— 切到管理端时显示
「管理端 · 1440×900」，免得有人以为管理端字小是压缩压出来的。

## 2. 管理端：鼠标为主，触控必须可用

**这是这次最实质的决定。** 原方案把管理端当纯桌面（34px 控件），理由是"坐着用鼠标"。
但现实是：这台机器在店里就是一台触摸一体机 —— 店长要站那儿点开日报。

所以不是二选一，而是**同一个 URL 服务两拨人**：

| | 鼠标范式 | 触控范式 |
|---|---|---|
| 正文 | 14px | 15.5px |
| 控件高 | 34px | 46px |
| 表格行 | 36px | 48px |
| 侧栏宽 | 208px | 232px |
| 顶栏高 | 52px | 62px |

**做法是换令牌，不是换样式表。** 管理端的尺寸本来就全走 `--adm-*`，
只要在 `.adm.is-touch` 下重算这 6 个值，全端几十处引用自动跟随。
不写第二套 `admin-touch.css` —— 那种做法半年后必然两边分叉。

### 踩到的坑：`calc(基准 + var(--touch) * 增量)` 不生效

我第一版想用一个 `--touch` 管所有，结果字号纹丝不动。原因是自定义属性在 `:root` 上声明时，
里面的 `var()` **在 `:root` 那一层就替换完了**，后代继承到的是已经算死的
`calc(34px + 0 * 12px)`，再把 `--touch` 改成 1 也不重算。

探针抓得很清楚：`touchvar=1 | ctl=calc(34px + 0 * 12px) | fs=14px`。

最后改成两套字面值，只有 6 行，行为可预期。

### 触控不只是"放大"

尺寸到位还不够，下面每条都对应一个具体的手感问题：

- 44×44 命中区（WCAG 2.5.5）—— 垃圾桶图标原来 28×30，手指根本点不准；
- `touch-action:manipulation` —— 不写的话每次点按多 300ms 判断双击，慢半拍；
- 去掉 `tap-highlight` —— 否则点一下留一块灰蓝方块，像脏了指印；
- `:active` 按压态 —— 触控没有 hover，按下去没反馈就会连点两次；
- 滚动条常显 —— 手指只能拖条，隐形滚动条在触控下等于"看不出还有内容"；
- `.adm-switch` 也进 44px 名单 —— 酒水 TOP 开关是 158×22 的细条。

### 判定优先级

URL `?input=touch|mouse` → 顶栏虚线对照位 → `matchMedia('(pointer:coarse)')` → 兜底鼠标。

导航页会把自己的指针类型**透传**给管理端 iframe，免得在触摸一体机上打开比稿页时
看到一屏 28px 小按钮、误判"管理端没法摸"。

### 验证

4 屏 × 2 主题 × 4 语言 = **32 组合**，1440×900 与 1280×800 两档：

- 小于 44×44 的交互元素：**0 个**（两档都是）
- 横向溢出（文档 / 顶栏 / 内容区）：**0**
- JS 报错：**0**

## 3. 定案：统一用 v2 设计，不重建 v1

v1 那两套丢了。既然 v2 已经把主题、密度、多语言、无障碍收进一套令牌，
重建 v1 只会得到两份互相追不上的设计。

要看"两套方案并排"，直接用 `index.html` 的 A/B 双栏 + `theme=a/b` —— 那本来就是它的用途。

**v1 到此为止，后面所有页面只加在 `prototype/v2/`。**

# 登录屏重做（v2.14）

需求：卡与数字键盘**居中、不要占满整个屏**，**背景要占满屏**；顺手把三条小遗留一起修掉。

## 布局：控件居中、背景铺满

原来是两栏铺满（卡的边界就是屏的边界）。现在给它一组 vw/vh 尺寸（约 66vw × 68vh），四边留白。

1920×1080 实测：容器 1180×670，左右各 334、上下各 101 —— 两边数字相等，即居中。

背景用 `径向渐变 + 页面底色` 铺满整个可用区。

> 这一步不能省：控件一居中，四周就露出来了。露出来的地方如果不先铺一层**有意的**底，
> 看上去就像没画完 —— 「背景占满屏」说的是这个，不是加个色块就行。

## 又撞上同一个坑，但这次提前躲开了

`.login-card` 是 `container-type:size`，等于给元素加了 `contain:size` —— **尺寸不能由内容决定**。
改成居中的那一刻，它就面临「高度塌成 0」的风险，和 `index.html` 预览框全黑是同一个病。

所以定尺寸的责任放在 `.login-wrap`：`width/height` 用 `clamp(...vw/vh)` 写死，
行列 `minmax(0,1fr)` 把确定尺寸传下去。

## 三条遗留

1. **语言入口进登录屏**。6 语种本名自称（简体中文 / Deutsch / العربية），不给 CN/DE/AR 代码 ——
   未登录的人看不懂代码。理由不是"方便"，是避免死锁：语言藏在设置里，
   看不懂当前这屏的人根本走不到设置。
2. **PIN 真的能输了**。点数字键盘会填，点字段切换目标，⌫ 退格，PIN 掩码。
   校验失败时**只标没填好的那一项** —— 两个框一起标红，人反而不知道该改哪个。
   通过之后给一个成功态再切视图：点完直接跳，人会怀疑自己没按上。
3. **工号不再写死**。原来是死值 `10086`，看着像"这台机器只能这个人登"。改成空 + 占位提示。

## 一个刻意的实现选择：表单状态提到模块级

`S.login = { emp, pin, tgt, err }`。

必须这样。因为 `render()` 每次重建整屏，切语言也重建 —— 局部变量会当场清空，
人还没输完，点了下语言，工号就飞了。探针专门走了这条路径确认没丢。

## 验证

- 三档分辨率（1920 / 1440 / 1280）× 四语（zh/de/ru/ar）× 昼夜班：零横向溢出、零纵向裁切、零报错；
- 数字键最小边 **139 / 109 / 97 px**，都过 96 的触控下限；
- 输入流程全链路：填数字 → 掩码 → 退格 → 切语言内容保留 → 错误只标一项 → 成功态 → 进桌台视图。

## 顶栏搜索框触摸键盘 v2.15（2026-10-24）

后厨一体机上的系统输入法不可靠 → 搜索框自带键盘。三个决策点由用户拍板后落地：
**底部抽屉** + **数字优先 ⇄ 字母** + **⌨ 常驻**。

### 关键实现

- `#kb` 是 `#app` 的**直接子元素**，不在 `.body` 里 —— 放进内容区就只能走「挤压卡片」那条路，
  那就成了另一套方案；抽屉要的是浮在内容区之上、盖住分页条。
- 状态 `S.kb / S.kbPage / S.q` 挂在模块级：`render()` 每次重建卡片网格，
  搜索词与筛选必须能重放，否则「切个语言搜索就没了」。
- 一次输入三处同源同步：顶栏输入框 / 抽屉里的取景框 / 卡片网格高亮。不同步就会出现
  「抽屉里显示 A12、屏上却高亮 B03」这种说不清的鬼状态。
- 真键盘与虚拟键盘共用 `kbPress`：另写一套必然分叉。演示走查时打字比戳屏快得多。
- 拼音索引 `PY` 挂数据层、不进翻译词典：六语共用一份，也不污染 i18n 结构；
  值是「全拼 + 首字母」，输 `gb` 与 `gongbao` 都能命中宫保鸡丁。

### 踩到的两个坑

1. 数字页原本排 3×4，限宽 940 下每个键被拉成 **348×53** 的扁条。改 **4×3** 后，
   同样面板高度换出更高的键（240×66）。
2. 1366×768 这类矮屏，抽屉自身留白会把键高挤到 46px，破 48px 触摸线 →
   加 `@media (max-height:860px)` 先压抽屉 padding / 头部 / 命中条，实测回到 **51px**。

### 验证

14 组关键用例（4 视图 × 1920/1440/1366/1280 × 双主题 × zh/de/en/ru/ar 含 RTL）：
`docOvf=0x0`、JS 错误 0、抽屉 `bottomGap=0` 严格贴底、键最短边全部 ≥48px。

## 综合屏重定义 v2.16（2026-10-24）：模式 × 范围

用户澄清了综合屏的产品定义，据此重构。**这不是补充，是推翻了既有实现的两个点。**

### 新的产品定义

1. **进度看的是综合屏。只读 = 隐藏操作按钮，只留「全景查看」+「查询」。**
2. **综合屏与工序屏的区别只在数据范围**：综合屏看**所有工序**的品项；
   两类屏同样都有桌台 / 合菜 / 单菜三种模式。

### 结构：综合屏不再是第四种视图

顶栏从「4 个 Tab（桌台/合菜/单菜/综合）」改成**正交两维**：
**模式 Tab（3 个）× 范围开关（本工序 ⇄ 全工序＝综合屏）**。
组合数 3×2=6，用两组控件表达比六个 Tab 清楚。

`S.view`（模式）+ `S.scope`（范围）两个状态；`itemsOf(v)` 按范围挑数据源，
三种模式共用同一套渲染。**原来的决策点①（要不要为综合屏动 `ActiveView` 枚举）因此消失。**

### 修掉的两个错

1. **只读方向搞反了**。旧实现在只读态把 `.sft` 整条不渲染 ——
   而 `.sft` 装的是**等待时长 + 份数**，也就是"进度"本身。
   对一个拿来盯进度的屏，只读恰恰把最该看的东西抹掉了。现在卡尾无条件渲染。
2. **只读没真的只读**。只读态下 `c.onclick` 还挂着，点一下照样能划菜。
   现在操作控件（划单、✓、勾选框、催菜、叫号/清台、批量/清空）与划单手势一并收掉。

### 只读的边界线

- **隐藏（改状态）**：点卡划单、已划 ✓、合菜勾选框、催菜、叫号/清台、批量划菜/清空、我的划单入口
- **保留（看 + 查）**：桌号、菜名+做法、**等待时长、份数**、超时/催菜角标、档口标签、
  搜索 + 触摸键盘、筛选 chips、翻页

只读只禁"改"，不禁"找"。

### 顺带补的两处信息缺口

- 桌台菜行在全工序下加**档口胶囊** `.dst`（一桌常横跨 3–4 个档口，混在做法文字里扫不出来）。
- 全工序合菜卡补**「最长等待」** —— 聚合到一道菜上没有时间，就看不出哪道最拖。

### 实现要点

- 密度存档分两本（`S.dens` / `S.densAll`），卡片目标尺寸也分两组（`DENS` / `DENS_ALL`）：
  全工序一页要装下五倍数据，套用本工序的理想卡尺寸会溢出。
- 全工序外框（汇总条 + 评审对照条）抽成 `comboChrome()`，三种模式共用 —— 汇总条讲的是
  "全店还有多少活"，跟底下用哪种模式看无关。
- 兼容旧深链：`?view=combo` → `scope=all + view=single`。
- 入口页 `index.html` 新增 `e.view` / `e.qs` 字段：**id 是入口唯一键，view 才是模式名** ——
  两者必须分开，否则「全工序」与「单菜」会撞成同一个键，`scope=all` 传不下去。

### 验证

16 组组合（3 模式 × 2 范围 × 只读开关 × 1920/1440/1366/1280 × 双主题 × zh/de/en/ar 含 RTL）：
横向溢出 0、JS 报错 0；只读态操作控件节点数 **= 0** 且"我的划单"已收起，
等待时长/份数节点数 > 0；全工序档口标签节点数 > 0；顶栏恒为 3 Tab + 2 范围按钮。
分栏分支单独验：5 档口列 / 37 卡 / 3 列如实报 `+N` / 只读 op=0。

> **探针踩坑**：卡片菜行是 `requestAnimationFrame` 里补渲染的（`fillBody`），
> 单次 `setTimeout` 在 headless 下会抢在它前面，量出来是 0 行 —— 同一配置时好时坏。
> 改成**轮询等到菜行出现**再测，才拿到可信结果。

## v2.17 综合屏布局崩坏修复（2026-10-24）

### 现象

切到「全工序 · 综合屏」后版面整个散架：汇总条三个大数字被压成三根竖条立在左侧，
对照条飘在中间，卡片全挤到最右边一列。用户原话：「掉下来了」。

### 根因

`comboChrome()` 返回的是 **DocumentFragment**，`body.appendChild(fragment)` 会把
csum / cbar 展开成 `#body` 的**直接子元素**；而 `#body`（`.body`）是 `display:flex`、默认行方向。
于是「汇总条 · 对照条 · 卡片区」被当成三栏横着排：

- `.csum` 没有宽度约束 → 被挤成百来像素，三个 cell 竖着叠（这就是那三根竖条）
- `.cbar` 在中间被压扁
- 卡片区 `flex:1` 吃掉剩余宽度 → 只剩最右一列看着正常

外框的 `.combo`（flex 列容器）CSS 一直存在，但**从来没有被创建过** —— 重构时把包裹层弄丢了。
之前 16 组验收全过，是因为检查项只有「横向溢出 = 0」：横排本身不溢出，所以没报。

### 修复

1. `comboChrome()` 返回**一个** `.combo` 容器（汇总条 + 对照条装在里面），
   三个 render 函数改成 `const host = S.scope==='all' ? body.appendChild(comboChrome()) : body;`，
   卡片区追加到 `host`。追加顺序 = 汇总 → 对照条 → 卡片，永远是竖的。
2. `.combo` 去掉自带的 `padding` —— `.body` 已经给过内边距，再加一层会让综合屏的卡片区
   比本工序窄一圈，切个范围版面就跳。
3. 顺手补两条防回归：
   - `.ccols` 从 `grid-template-columns:repeat(5,...)` 改成 `grid-auto-flow:column` +
     `grid-auto-columns:minmax(0,1fr)`：列数跟着档口数走，第 6 个档口不会掉到第二行。
   - 删掉 `.ccard.ro .sft{display:none}`（综合屏还是第四视图时的死规则，口径与现在相反：
     只读**保留**卡尾的等待时长与份数）。

### 附带修掉的可读性问题（分栏）

分栏原先写死每列 8 条。1366×768 下列高只有 ~504px，8 条 = 每卡 50px，

## v2.20 桌台卡内品项展开：点一下就地放大看全部（2026-10-25）

### 起因

用户问：「桌台模式，卡片内品项过多，一页显示不全，有翻页效果吗」。

先说清楚**有两层**，容易混：

| 层 | 有没有翻页 | 机制 |
|---|---|---|
| 桌台 ↔ 桌台 | **有** | 底部 `#pager`，一页 `cols × rows` 张卡，「第 n / m 页 共 N 桌」 |
| 一张卡里的菜品行 | **没有**（现在改成展开） | 按卡身高度算能放几条，放不下的折叠成 `+{n} 道` |

而且 `+{n} 道` 之前是**死文字** —— 连 onclick 都没有，厨师点不了，剩下的菜是什么谁也看不到。

实测折叠有多普遍（`.tmp/tblprobe.html`）：

| 场景 | 卡高 | 卡身容量 | 被折叠 |
|---|---|---|---|
| 本工序 3×2（默认） | 424 | 5 条 | 0 张 |
| 全工序 4×3 | 224 | 3 条 | 4 张 |
| 全工序 1366 | 244 | 3 条 | 3 张 |
| 本工序 6×4 | 201 | 2 条 | **8 / 12 张** |

密度越高折叠越狠，6×4 时三分之二的卡看不全。

### 四个方案，选了「点卡就地展开」

| 方案 | 不选的理由 |
|---|---|
| **A 点卡就地展开**（采用） | — |
| B 卡内滚动 | 没有视觉提示，站两米外看不出这张卡下面还有菜；小区域触屏滚动容易误触 |
| C 卡内小翻页 | 翻走的信息等于消失的信息，后厨最容易漏单；箭头触点小，戴手套难点 |
| D 点卡弹全桌详情面板 | 会挡住整屏，看完要关掉；这一屏是挂墙远看为主，不该频繁出全屏面板 |

### 为什么不做「grid 内跨行 / 跨列」

那是就地放大最直觉的做法，但卡片一跨格，**其余卡片就要重排补位**。
这个项目里「卡片位置恒定」是硬原则（见 `gridRows()` 的注释：厨师靠肌肉记忆找卡，
卡片尺寸随数据量跳动比留白更糟）。所以走 `position:fixed` 浮层：
原卡留在流里纹丝不动，只在它上面长出一个放大版，其余压暗。

### 交互

- 触发：点 `+{n} 道`，或点卡身空白（菜品行自己 `stopPropagation` —— 点行是划单，不冲突）。
- 浮层从原卡矩形**长出来**（起始矩形 = 原卡，再过渡到目标矩形），不是凭空出现。
- 关闭：点遮罩 / Esc / 再点一次。
- 浮层里的操作**落回原卡**：划单清的是原卡，划一道菜原卡对应行同步打勾。
  不做这一步的话，「划单」只删掉浮层那张，遮罩还盖着 —— 界面直接卡死。

### 三个不好踩的坑

1. **不能估算尺寸**。菜名会不会换行、容器查询字号（`cqh`）随高度怎么变、padding 有多少，
   统统估不准 —— 实测每次差 5~30px，结果就是「点开了还得滚」，那还不如不展开。
   改成**迭代到自洽**：把卡片撑到 `hh` 高度量一次行高和，算出新高度，重复到不再变化
   （行高本身跟着 `cqh` 变，不迭代就收敛不了）。
2. **`cbd.scrollHeight` 量不出内容高度** —— 内容不溢出时它等于容器高度，
   量出来永远是「刚好填满」，卡片会一路撑到满屏。必须逐行累加 `offsetHeight`，
   且展开态的 `.drow` 要 `flex:none`（拉伸状态下量什么都是填满）。
3. **卡头/卡尾的 4px 边框**。卡片上下边框 2px + 卡头下边框 1px + 卡尾上边框 1px 漏算，
   展开完就正好差 4px 要滚一下。另外卡头/卡尾高度写的是 `cqh`，卡片一放大它们也跟着变高，
   所以展开态把它们**锁回原卡尺寸** —— 「展开」只是多露出几行，不该把卡头卡尾重新排版。

顺手修的旧 bug：`fillBody()` 用 `requestAnimationFrame` 等一帧，离屏 iframe /
后台标签页里 rAF 不触发，**整张卡的菜品行一片空白**（探针测出 `显示=0`）。
跟之前 `fitCols` 同一个坑，改成 `renderTable()` 在 `appendChild` 之后同步填充。

### 验收

展开专项 10 组（`.tmp/expprobe.html`，模拟点 `+N 道` 再点遮罩收起）：
1920 / 1366 / 1280 × 6×4 / 5×3 / 4×3，含德语 `lines=2`、阿语 RTL、繁體、只读。
断言：浮层行数 == 全部菜品数、展开态不再折叠、不出界、高度确实变大、
卡内不需要滚动、遮罩生效、收起后 DOM 清零 —— **全部 OK**。

|---|---|---|
| 本工序 6×4 @1366 | 210×142 | 320×233 |
| 本工序 6×4 @1920 | 295×201 | 427×263 |
| 全工序 4×3 @1920 | 453×224 | 657×314 |
| 全工序 阿语 RTL @1280 | 407×260 | 591×334 |

回归 12 组（3 模式 × 2 范围 × cols/grid × 只读 × 6 语言 × 双主题 × 4 屏宽）：
`#body` 直接子元素恒 1 个，横纵溢出全 0/0。

## v2.21 大单（二三十道菜）：展开态自动分列（2026-10-25）

### 起因

接着 v2.20 的问题往下追：「**如果一个卡片有二三十道菜怎么弄**」。

宴席 / 包厢一桌 30 道是常态，原型自带的 mock 最多 5 道，压根测不出来。
造了个 28 道的大单实测，v2.20 的展开直接露馅：

| 场景 | v2.20 展开后 | 卡内还要滚 |
|---|---|---|
| 28 道 @1920 | 浮层被夹到满屏高 1048px | **1315px**（26 行照样看不见） |
| 28 道 @1366 | 撑到 736px | 1355px |
| 40 道 @1920 | 撑到 1048px | 1973px |

点开了还得滚一屏半 —— 那跟没展开没区别。

### 改法：按需要自动分列

展开态的卡身从「单列竖铺」改成**多列网格**，列数由可用高度反推：

- 单列试起，装不下就 +1 列，上限 4 列；
- 每列固定 300px 宽（字号已改用 vw 驱动，不随列宽缩水）；
- **列优先填充**（`grid-auto-flow:column`）：第 1 列放前 R 道、第 2 列接下去。
  行优先会把「1 2 3」横着排，后厨按单子从上往下读的习惯就断了；
- 4 列用尽还装不下（如 120 道 @1280）才允许卡内滚 —— 这时给**底部渐变 + 下箭头**
  提示，滚到底自动撤掉。不给提示，厨师不知道下面还有菜，跟折叠成「+N 道」一样糟。

| 场景 | 列数 | 展开后 | 卡内滚动 |
|---|---|---|---|
| 28 道 @1920 | 2 | 657×878 | 0 |
| 28 道 @1366 | 3 | 920×581 | 0 |
| 40 道 @1920 | 3 | 920×878 | 0 |
| 40 道 @1366 | 4 | 1230×581 | 0 |
| 60 道 @1920 | 4 | 1230×934 | 0 |
| 120 道 @1280 | 4 | 1230×768 | 778px（可滚，有提示） |

### 最阴的一个坑：行高不能用 `cqh`

第一版分列做完，28 道菜被压成 **374px 高、每行 10px**。原因是原卡的行高写的是
容器查询高度单位（`max-height:clamp(72px,27cqh,132px)`、字号 `min(x*cqw, y*cqh)`）：

> 浮层越矮 → `cqh` 越小 → 字号越小、行越矮 → 越「装得下」→ 收敛在一个矮胖的不动点上。

这是个**自我实现的预言**：迭代算法和 CSS 互相喂养，最后收敛到「最挤」的解。
所以展开态的行高 / 字号必须**脱离浮层自身高度**，改用 `vw` / `vh` 驱动 ——
跟视口走，不跟自己走：

```css
.expcard .drow{flex:none;max-height:none;min-height:clamp(40px,4.4vh,56px)}
.expcard .rname{font-size:clamp(15px,1.25vw,26px)}
.expcard .rqty {font-size:clamp(15px,1.3vw,26px)}
```

### 另一个坑：`for` 循环变量溢出

列数循环用 `for(cols=1; cols<=maxCols; cols++)`，列数用尽时退出后 `cols` 已经 +1，
拿它去 `setExpCols()` 就会给出 `maxCols+1` 列 —— 列比 `wOf()` 算出来的宽度窄。
循环结束后必须 `cols = Math.min(cols, maxCols)` 夹回来。

### 顺带：headless 里 `scrollHeight` 也是动画中间值

之前只在 `getBoundingClientRect` 上踩过这个坑（浮层出界误报）。这次发现
`scrollHeight - clientHeight` 同样会停在过渡起始值上 —— 因为 `width/height` 的
transition 让**布局**也停在中间态。探针里先 `style.transition='none'` 强制一次布局，
才能读到真实终态。

### 验收

大单专项 10 组（`.tmp/expprobe.html?n=28`，直接喂一个 N 道菜的假 tb 给 `expandCard()`）：
1920 / 1366 / 1280 × 28 / 40 / 60 / 80 / 120 道，含阿语 RTL、繁體、只读、6×4 高密度。
断言：行数 == 全部菜品数、不出界、确实放大、装得下就不该滚、
标了可滚就必须真的滚、收起后 DOM 清零 —— **全部 OK**。

小单回归 10 组（点 `+N 道` 那条路径）：列数恒为 1、滚动 0，行为与 v2.20 一致。
跨模式回归 12 组：`#body` 直接子元素恒 1 个，横纵溢出 0/0。

- **分批叫起**：宴席常见「先上凉菜、叫起了再上热菜」，原型没有这个概念。
  30 道的单子光「看得全」还不够，实际后厨是按批次做的 —— 需要你定要不要加。
- 合菜 / 单菜卡不存在这个问题（一行一菜，一卡一菜）。

超范围会被 `render()` 夹回末页。

### 第二次重写展开测量：grid 的 `auto` 行不能「边撑边量」

宴席单进 mock 之后立刻暴露出 v2.21 的测量仍然是错的：**截图比 dump-dom 少一整行**
（28 行变 26/27 行，卡尾压掉最后一行）。两个根因叠在一起：

**① `--dump-dom` 的视口跟 `--screenshot` 不一样大。**
headless 窗口有装饰占位，设 `--window-size=1920,1080` 实测视口只有 **1890×938**。
而展开态行高写的是 `clamp(40px,4.4vh,56px)` —— `vh` 基准一变，行高就跟着变。
所以「探针里量着正好」在真机截图上就是不够。**测量和出图必须同一套视口基准**。

**② grid 的 `auto` 行会跟着容器高度变，所以「边撑边量」永远收敛不到真值。**
这是真正的元凶：

> 同一个 28 行，容器给 656px 高时量出来 691；给 856px 高时量出来 856。
> 容器矮 → 行被压到 `min-height` → 算出来更矮 → 更「装得下」→ 又是一次自我实现的预言。

跟 v2.21 那个 `cqh` 的坑是同一类病，只是藏得更深。解法是把行从容器里**摘出来**再量：

```js
box.style.height = maxH + 'px';                                  // 先撑到最大
bd.style.gridTemplateRows = `repeat(${rows}, max-content)`;      // 把行锁成内容高度
void box.offsetWidth;                                            // 强制布局落定
// …这时读到的才是内容自己的高度，一步到位，不用迭代
s += rs[i].getBoundingClientRect().height + (i ? g : 0);
```

量完再把 `gridTemplateRows` 清空交回 CSS 变量。
配套两处：

- **不能用 `offsetHeight`**，它取整。`4.4vh` 在 1080 高上算出 **41.27px**，
  取整成 41 后 14 行差 3.8px —— 最后一行正好被卡尾压掉半行。必须用 `getBoundingClientRect()` 的带小数高度。
- **`UI_EDGE = 8`**：卡头卡尾之外还要算的边（上下边框 2 + 卡头下边框 1 + 卡尾上边框 1 = 4），
  再加 4px 呼吸 —— 亚像素行高十几行累积后 `scrollHeight` 会向上取整 1~2px，
  不留这口气最后一行就贴着卡尾，看着像被裁掉。
- 展开后 **260ms 再实测兜底**一次：补偿首帧之后的字体回退 / 亚像素再漂移，
  只往上补、且不超过 `maxH`。

### 验收

V01 专项 **13 组**（1920 / 1366 / 1280×800 / 1024×768 / 2560 × 综合屏 × 六语 × 4列3行 / 6列4行）：
