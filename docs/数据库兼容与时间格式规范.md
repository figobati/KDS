# 数据库兼容透明化规则（SQL Server 2000 / SQLite）

> **状态**: 活跃（最后核验 2026-08-15）
> **适用**: [共享] 全项目数据库访问与时间格式（强制约束）
> **唯一信息源**: 是（数据库兼容/时间格式唯一入口）

## 1. 核心原则：业务代码无需感知数据库差异
- 所有 SQL 语句的兼容性处理，**由 `DataManager` 内部透明完成**。
- 业务层代码中，**不允许出现任何数据库特定语法分支**，也不允许手动调用 `ChangeSql`。
- 所有数据操作，必须通过 `DataManager.Instance` 的公开方法执行（如 `ExecuteNonQuery` / `ExecuteQuery` / `ExecuteBatch` 等）。

## 2. 兼容层已支持的自动转换（禁止业务层改写）
`DataManager.ChangeSql` 已在内部实现以下转换逻辑：

| 业务层写法（通用） | 自动转换为 SQL Server 2000 | 自动转换为 SQLite |
| :--- | :--- | :--- |
| `IFNULL(expr, default)` | `ISNULL(expr, default)` | 保持 `IFNULL` |
| `substr(col, 1, 3)` | `SUBSTRING(col, 1, 3)` | 保持 `substr` |
| `length(col)` | `LEN(col)` | 保持 `length` |
| `count()` | `count(*)` | 保持 `count(*)` |
| `WITH(NOLOCK)` | 保持（SQL Server 保留锁提示） | 自动移除（SQLite 不支持） |

- 业务代码中，必须使用**第一列的通用写法**，禁止直接写第二/三列的数据库专属语法。

## 3. 调用规范
- 所有新增/修改的数据访问代码，**必须使用 `DataManager.Instance` 的公开方法执行 SQL**，不允许：
  1. 绕过 `DataManager` 直接使用 `SqlClient` / `SQLite` 原生对象执行 SQL
  2. 在业务代码中手动进行 SQL 字符串替换、大小写转换
  3. 编写数据库特定的条件分支（如 `if (DataManager.UsingSqlServer)` { ... }）

- 示例（正确）：
  ```csharp
  // 业务代码中直接写通用 SQL，无需兼容判断
  string sql = "INSERT INTO t VALUES (IFNULL(@a, 0), substr(@b, 1, 10))";
  DataManager.Instance.ExecuteNonQuery(sql, new { a = 1, b = "test" });
  ```

## 4. 数据库时间字段硬性规则（仅限保存数据库字段时）
- **本规则仅适用于"保存数据库字段"的场景**，例如新增、更新、复制记录时写入 `AddTime`、`UpdateTime`、`SongDanTime` 等字段。
- **界面展示、日志展示、页面显示格式，不需要遵守本规则**，可以根据 UI 需要自由格式化。
- 所有写入数据库的时间字符串，必须统一为**秒级精度**，并且**日期与时间之间必须使用 `T`**。
- 标准格式为：

  ```text
  yyyy-MM-ddTHH:mm:ss
  ```

- JavaScript 中生成保存时间时，统一使用：

  ```js
  var now = new Date().Format("yyyy-MM-ddThh:mm:ss");
  ```

- C# 中生成保存时间时，统一使用：

  ```csharp
  string now = DateTime.Now.ToString("yyyy-MM-ddTHH:mm:ss");
  ```

- 明确禁止以下写库格式：
  1. `2026-06-04 10:35:30` 这种用空格分隔日期和时间的格式
  2. `2026-06-04T10:35:30.000` 这种带毫秒的格式
  3. 同一字段中混用空格格式、`T` 格式、毫秒格式
  4. 将未经格式化的原始 `DateTime` / `Date` 字符串直接写入数据库

- 这样规定的原因是：
  1. SQLite 中很多时间字段实际按**文本值**进行比较和排序
  2. 如果时间格式不统一，会导致 `ORDER BY AddTime`、`ORDER BY UpdateTime` 等结果异常
  3. 日期与时间之间加 `T`，并统一到秒级，是为了保证 SQLite 中字符串排序与时间先后顺序一致

- 所有新增/修改代码中，凡是写入以下字段，必须遵守本规则：
  - `AddTime`
  - `UpdateTime`
  - `SongDanTime`
  - 其他业务表中的时间字符串字段

- 特别要求：
  1. **只有保存数据库字段时必须遵守该规则**
  2. **界面展示时间不受该规则限制**
  3. 如果是复制旧记录再插入新记录，必须先把旧时间规范化后再写入
  4. 不允许把旧数据中的毫秒时间或空格时间原样带入新记录

- 历史数据库中如果已经存在空格格式或毫秒格式，属于历史数据问题，应通过单独的数据清洗处理；**新代码不得继续写入不规范时间格式**

## 5. JS 端时间解析规范（读取/展示/排序）

- **禁止**在 JS 中解析时间字符串时使用 `str.replace(/-/g, "/")` 这类把连字符强行替换为斜杠的写法。
- 原因：SQL Server 的 `datetime` 列经 `SqlLiteHelper.DateTableToJson`（`DataManager` 统一序列化）返回的格式是 **`yyyy-MM-ddTHH:mm:ss`**（ISO 8601，T 分隔）。把 `-` 替换为 `/` 后得到 `yyyy/MM/ddT...` 混合格式，`new Date()` 无法解析（Invalid Date），导致基于时间戳的**排序、比较、日期分组全部失效**。
- SQLite 的文本列原样返回存储字符串（历史数据多为 `yyyy-MM-dd HH:mm:ss` 空格格式，`replace` 后恰好可解析），因此该问题只在 **SQL Server 环境**暴露。
- 同一序列化出口还负责**文本控制字符转义**（TAB 等 0x00–0x1F → `\uXXXX`，**`\r`/`\n` 例外保持原字符**——单据预览按 `split('\r\n')` 切行），否则整条查询结果对 `JSON.parse` 非法；规则与故障案例见[浏览器与HTML桥接交互设计文档 §5.6](../../01-架构与设计/架构/浏览器与HTML桥接交互设计文档.md#56-查询结果-json-序列化与转义强制)。

- 统一使用公共函数 `parseDateTime`（`commontools.js`），其正确语义：
  1. 保留连字符 ISO 格式原样（`yyyy-MM-ddTHH:mm:ss` 及带毫秒变体）——原生 `new Date` 即可解析
  2. 仅将**空格分隔**的历史格式（`yyyy-MM-dd HH:mm:ss`）中的第一个空格转为 `T`
  3. `null` / 非字符串入参返回 `Invalid Date` 而非抛异常

  ```js
  // 正确示例（commontools.js parseDateTime 的语义）
  function parseDateTime(str) {
      if (str == null) return new Date(NaN);
      str = String(str);
      if (str.indexOf('T') < 0 && str.indexOf('-') > 0 && str.indexOf(' ') > 0) {
          str = str.replace(' ', 'T'); // 仅空格分隔的历史格式转 ISO
      }
      return new Date(str);
  }
  ```

- 使用建议：排序/比较时间字段时统一走 `parseDateTime(...).getTime()`，并保留 `isNaN` 兜底（非法值排前），避免单条脏数据导致整体渲染异常。
