# AI 在 KDS「排菜」上的空间 —— 架构师判断

> **需求来源**：用户 2026-10-25 19:57「AI 在 KDS 排菜上是否有用武空间，就是先做哪道菜、后做哪道，制定规则做最优化排菜」
> **依据**：`KDS-02` §2.3（合菜归集 / MergeKey / 7 项合并条件）、`KDS-03` §2.16（`Fired`/`Held` 计时）、`KDS-04` §3.1.1 / §3.3（展示排序）、`KDS-05` §4.4.3（标签优先级）、`KDS-07` §9.5（`StageStandardSeconds`）/ §9.21a（`StageLog`）、`KDS-10` §13.4
> **外部资料**：arXiv `abs:"job shop scheduling" AND abs:"reinforcement learning"` = 61 篇（2023–2026 持续活跃，但全部是 Taillard/DMU 基准算例）；`abs:"scheduling" AND abs:"restaurant"` = **仅 9 篇**；最接近的真实问题是 *The Restaurant Meal Delivery Problem with Ghost Kitchens*（2024-08）
> **结论**：**有空间，但"先做哪道菜"这个问法本身就设错了。** 真正的杠杆是「**哪些工序立刻点火 + 哪些能凑批**」，不是「菜品排成一列」。规则层能拿到 80% 收益且零风险；AI/OR 只在**滚动窗口的批次建议**这一处有不可替代的价值，而**它成立的前提是补三张现在完全没有的数据**。

---

## 1. 先说清现状：系统会「标红」，但从不「排菜」

我把 PRD 里所有排序相关条款过了一遍，**全部是展示层**，没有一处影响实际制作顺序：

| 位置 | 现在是什么 | 性质 |
|:---|:---|:---|
| `04` §3.1.1 桌台视图 | 一级 `SortOrderSnapshot`（门店配的动线序）+ 二级下单时间；可切「等待时长倒序」 | **只是把卡片换个位置** |
| `04` §3.3 单菜视图 | 默认按等待时长倒序 | 同上 |
| `05` §4.4.3 | 退菜 > 超时 > 催菜加急 > 等叫 > 起菜 > 赠菜 | **只是颜色和播报优先级**，不是调度 |
| `02` §2.3 | 合菜归集，7 项合并条件决定 `MergeKey` | **这是唯一的真·产能机制** |
| `03` §2.16 | `Held` 不计时、`Fired` 起算 | 数据正确，但只用于算超时 |

**一句话：系统知道谁急、谁等久了、哪些能合并，但从不表达"下一个动作是什么"。**

这个缺口是真实的。师傅现在的做法是拿眼睛扫一遍全屏 + 凭经验决定 —— 屏幕帮不了他，因为屏幕只告诉他"什么在响"。

## 2. 但「排成一列」一定会失败，五个硬理由

### 2.1 缺最关键的成本项：换锅 / 换灶

排菜的核心成本**不是做菜时间，是切换代价**：川菜炒完要洗锅才能做清淡的、蒸柜和炒锅不能同时用、炸完要换油。**这个数据系统一个字都没记。**

只要没有 setup time，"最优化"就是伪优化 —— 优化器会告诉你"按 EDD 顺序做"，而实际成本全在换锅上。

### 2.2 缺物理并行能力

`Station` 是**逻辑档口**（热菜制作 / 切配），不是**物理工位**。系统不知道这个档口今天开了 3 个灶还是 1 个蒸柜，也不知道几个师傅在岗。

而调度问题里，"有几台并行机"是**输入参数**，不是可推导的。缺它，任何排程结果都只是猜。

### 2.3 缺人的因素

刚在 AI 那份文档里提过 `OperatorName` 是名字不是 ID。排菜还多一层：**同一时刻谁在岗、谁擅长什么、谁在洗锅**。这些系统一概不知。

### 2.4 抖动会让师傅失去信任（这条最致命）

一位师傅同时看 3–4 个锅，**物理上就不可能严格照队列执行**。他一打断，系统按"最优"重排，屏幕上的顺序就变了 —— 变两次以上，师傅就再也不看建议了。

> 这是所有"作业指导类 AI"的通用死因：**建议若不能容忍被打断，就必然被无视。**

### 2.5 目标函数根本没法定

"最优排菜"优化什么？四个目标**互相冲突**：

| 目标 | 后果 |
|:---|:---|
| 平均等待最短 | 会**系统性饿死**某一桌 —— 投诉制造机 |
| 最晚完成最早（min-max） | 为了不让最后一桌等太久，前几桌会被拖慢 |
| 超时数量最少 | 快超时的插队，新单永远排最后 → 新单必超时（饥饿） |
| 批次最大（产能最高） | 单桌的菜被拆到不同锅次 → **"上了三个菜，第四个还在锅里"** |

**餐饮有一个经典调度的教科书里没有的目标：一桌菜的「齐套性」。** 上三个菜让客人干等第四个，比四道菜都晚 3 分钟出更糟。这个目标不在任何调度论文的目标函数里，但它是餐馆最在意的。

## 3. 一个例子说明「先做哪道」问错了

假设现在是 19:00，三桌同时在制：

| 桌 | 菜 | 份数 | 已等 | 工序与耗时 |
|:---|:---|:--:|:--:|:---|
| A | 宫保鸡丁 | 1 | 2 分 | 切配 2 分 → 炒 4 分 |
| B | 宫保鸡丁 | 2 | 1 分 | 切配 2 分 → 炒 4 分 |
| C | 清蒸鲈鱼 | 1 | **6 分** | 切配 1 分 → 蒸 **12 分** |

**按 FIFO（现在系统的等待时长倒序近似这个）**：先做 A 的宫保，再 B 的宫保（**换两次锅**），最后 C —— C 要等到 19:18 才能上桌，已经等了 24 分。

**按"最优化"的正确解法**：

```
19:00:00  C 立刻上笼（蒸 = 长工序、占设备不占人、期间无需干预）
19:00:30  A+B 宫保 3 份一起下锅（同一锅，零切换成本）
19:12:00  C 出笼；19:07 宫保 3 份已出
```

结果：C 的等待从 24 分降到 13 分，宫保省一次换锅，**而且没让任何一桌多等**。

**这个例子暴露的真相**：

> 排菜不是"给菜品排一个 1、2、3 的顺序"，而是**在「占设备的长工序」和「占人的短工序」之间做资源分配**。

- **长工序**（蒸 / 烤 / 炖 / 煲 / 卤）→ 占设备、不占人、期间可并行做别的事 → **必须最早启动**（这是 LPT / 关键链思路，不是 EDD）
- **短工序**（炒 / 炸 / 凉菜 / 摆盘）→ 占人 → **凑批 + 穿插填充**

而这套区分，**PRD 现在表达不了** —— `DishItem.StageStandardSeconds` 只有时长（`{"Prep":180,"Cook":300}`），没有"占人还是占设备"这个属性。**这是比上一轮那三个字段更要命的缺口。**

## 4. 所以正确的问题拆成三层（难度递增，价值递减）

### 第一层：批次识别 —— **规则可做，零 AI，收益最大**

厨房产能来自"一锅出 N 份"，**不是**"先做 A 后做 B"。这一点 `02` §2.3 的合菜归集已经证明了 —— 它是产品里唯一真正提升产能的机制。

但现在的合菜只做了**同一时刻的快照聚合**（把已有明细按 `MergeKey` 分组显示）。它没有回答：

- **要不要等**：桌上现有 2 份宫保，下一张单 40 秒后可能还有 1 份 —— 等不等？（等 = 少换一次锅，不等 = 那 2 份晚出）
- **凑够了没有**：门店可以设"同类满 3 份才起锅"，现在没有这个机制
- **哪些能同锅**：不同菜能不能一起炒/一起蒸 —— 完全没数据

**这是纯规则能解决的**，判据清晰、可测试、可回退。

### 第二层：不可行 / 冲突检测 —— **规则可做，价值很高，风险为零**

比"告诉他怎么做"更安全的，是"告诉他这样不行"：

| 检测 | 例子 |
|:---|:---|
| 跨阶段阻塞 | 单菜视图把一道还在切配的菜排在制作屏第一行 → 制作师傅以为该做了 |
| 齐套风险 | 某桌 4 道菜中 3 道已完成、1 道还没起锅 → "这一桌会干等" |
| 同灶冲突 | 两道都需长时间占灶的菜被建议同时开工 → 物理不可能 |
| 等叫误判 | `Held` 状态的菜本不该进作业队列（PRD 已正确排除），但若 POS 误推 `Fired` 就会串 |

**这类功能不需要任何模型，全部可写成单元测试，而且出错只多一个提示。**

### 第三层：批次建议 —— **这里才需要 OR / AI**

而且形式必须是「**接下来 4–6 分钟这一批做什么**」，不是「排完整队列」：

- **输入**：该档口当前在制明细（10–30 条）、每条的剩余工序、`SetupTimeMatrix`、并行度、目标权重
- **输出**：1–3 个批次方案（"这批：宫保 3 份 + 咕噜肉 2 份，理由：同灶同油温"），带可读理由
- **技术选择**：**CP-SAT / MILP 小规模精确解，不要 RL**

**为什么明确选 CP-SAT 而不是强化学习**（这条要说清，避免被论文带偏）：

| 维度 | CP-SAT / MILP | RL（论文主流） |
|:---|:---|:---|
| 规模 | 每屏 10–30 项、3–6 阶段、3–6 灶 → **毫秒到百毫秒级精确解** | 需要大量训练样本 |
| 可解释 | 约束即解释（"因为灶 2 在 19:05 前不可用"） | 黑箱，师傅不问为什么就不信 |
| 数据需求 | **零训练数据**，只需参数 | 需要上万条轨迹 |
| 边界 | 可证明最优 / 可证明不可行 | 无保证 |
| 我查到的现状 | 工程成熟 | 61 篇论文（2023–2026），**但全部在 Taillard / DMU 基准上刷分**，真实厨房的状态空间（人、锅、口味、打断）与基准完全不同 |

> arXiv `abs:"scheduling" AND abs:"restaurant"` **只有 9 篇** —— 这个交叉领域学术供给几乎空白。**意味着：谁先把自家数据攒成 Benchmark，谁就有话语权；也意味着：照搬论文一定要栽。**

## 5. 规则清单：现在就能定，不需要 AI

按"收益 ÷ 风险"排序。**每条都必须可关、可回退、默认关。**

| # | 规则 | 判据 | 风险 | 建议 |
|:-:|:---|:---|:---|:---|
| **R1** | **长工序抢先启动** | 蒸/烤/炖类工序 → 忽略 FIFO，立即进队列首位 | 短工序的菜被压后 | ✅ 强烈建议，收益最大 |
| **R2** | **凑批阈值** | 同 `MergeKey` 跨桌累计 ≥ N 份才起锅；可设"最长等待上限"防死等 | 单桌等更久 | ✅ 建议，默认 N=2 + 上限 90 秒 |
| **R3** | **齐套优先** | 同 `OrderId` 的菜，若已完成 ≥ half 且剩余 ≤ 2 道 → 剩余项插队 | 其他桌被压后 | ⚠️ 需门店开关，正餐店更需要 |
| **R4** | **剩余时间排序**（替换现在的"等待时长倒序"） | 按 `目标完成时刻 - 现在` 升序，而不是按"已等多久" | 无 | ✅ 现有排序键在数学上就是错的 |
| **R5** | **换锅惩罚** | 建议顺序避免"清淡 → 重辣"相邻 | 无 | ✅ 需 `SetupTimeMatrix` |
| **R6** | **等叫 / 未起菜过滤** | `Held` 不进队列（PRD 已有），补充"未 `Fired` 不进队列" | 无 | ✅ 补漏 |
| **R7** | **档口容量上限** | 单档口在制份数超阈值 → 停止推送新单提示（防压单） | 可能掩盖积压 | ⚠️ 需配合告警 |

> **R4 单独说一句**：现在 `04` §3.1.1 的"等待时长倒序"按"已经等了多久"排 —— 这是**沉没成本排序**。正确键是"还剩多少时间可用"。一道等了 5 分但还需 10 分钟的菜，和一道等了 2 分但还需 2 分钟的菜，谁该先做？后者。**改这一条不需要任何 AI，是一行排序键的替换，但能立刻减少超时。**

## 6. 必须先补的数据（否则上面全是空话）

| 数据 | 现状 | 为什么必须有 | 代价 |
|:---|:---|:---|:---|
| **工序资源类型**（占人 / 占设备 / 无人值守） | **完全没有**。`StageStandardSeconds` 只有秒数 | 决定"能否并行""是否该抢先" —— 是第 3 节那个例子的核心 | `StageStandardSeconds` JSON 加一个字段：`{"Cook":{sec:300,res:"Human"}}`；或独立 `StageResource` 列 |
| **`SetupTimeMatrix`**（品项或品类之间换锅成本） | **完全没有** | 排菜的第一成本项 | 新表 1 张（品类×品类即可，不需品项级）；实施时填默认矩阵 |
| **`Station.ParallelSlots`**（物理工位数） | 没有（`Station` 只是逻辑档口） | 并行机数量是调度输入 | 加 1 个 int 列 |
| **`BatchId`**（同锅出的明细归组） | **完全没有** | **没有它就永远无法回测"批量建议到底有没有用"** | `StageLog` 加 1 列，同锅时写同一 `BatchId` |
| `QueueDepthAtEnter` / `OperatorUid` / `StoreLoadAtEnter` | 上一个文档已提 | ETA 与负载 | 见 `2026-10-25-思考-AI能力演进路线.md` §2.1 |

> **这五项里，前三项是"排菜"的前提，第四项是"验证"的前提。没有 `BatchId`，做完了也说不清有没有变好 —— 这是最容易被跳过、后果最严重的一项。**

## 7. 怎么证明有效（不用等模型）

`EventLog` 能完整重放任意历史时刻的队列状态（08 §10 / 07 §9.13）。所以验证方法很干净：

1. 取过去 30 天，每天选 3 个高峰时段
2. 用规则重放同一份事件流，产出"建议顺序"
3. 对比**实际发生**与**假设照建议执行**（用 `StageLog` 的 P50 时长做保守估算）

**四个指标，缺一不可**：

| 指标 | 为什么 |
|:---|:---|
| P90 完成时间 | 尾部体验才是投诉来源 |
| 超时率 | 直接对应红灯疲劳 |
| **平均批次大小**（份 / 锅） | 排菜真正的产能指标 |
| **换锅次数** | 成本指标 |
| 齐套率（一桌菜全部完成的时间差） | **餐饮独有目标，必须单列** |

> 如果"平均批次大小"没涨，说明你只是把顺序换了换，**没拿到任何真实收益**。这一条是最诚实的判据。

## 8. 什么时候不值得做（判据）

排菜优化的收益**与合菜密度强相关**。判据：

| 条件 | 说明 |
|:---|:---|
| 单店日单量 **< 200** | 师傅凭经验排更好，任何建议都是干扰 |
| 同菜重复率低（合菜卡平均份数 < 1.5） | 没有批次空间，优化器无事可做 |
| 档口只有 1 个师傅 | 并行度为 1，调度退化为"排队"，人的判断更准 |
| 菜单 SKU > 150 且做法差异极大 | `SetupTimeMatrix` 填不完，建不准 |

**四条中命中两条以上，这条产品线就不该做。** 反过来说：快餐、团餐、宴席、中央厨房这几类门店，排菜价值极高 —— 它们才是目标客户。

## 9. 风险：这件功能最可能的死法不是算错

| 死法 | 机制 | 防法 |
|:---|:---|:---|
| **变成甩锅依据** | 出菜慢了 → "我是按系统建议做的" | 只记录"建议 vs 采纳"，**明确不进入任何考核**；界面写"建议"不写"应做" |
| **抖动后失去信任** | 建议被打断两次就变了 | 建议**只在批次完成时更新**，不逐条重排；采纳/忽略都保持稳定 |
| **目标函数政治化** | 店长调权重让某档口背锅 | 权重只允许在管理端由店长单点配置 + 记录变更日志 |
| **过度自信** | 数据不足时也给"最优"建议 | 样本不足 / 并行度未知 → **不输出建议**，只显示"数据不足，暂无法建议"。**空态比错误建议好一百倍** |

## 10. 我的结论（四句话）

1. **有空间，但不在"排一列"上。** 空间在「哪些工序立刻点火」+「哪些能凑批」这两个决策上。
2. **先做规则，别做模型。** R1（长工序抢先）+ R4（剩余时间排序）**两条今天就能写进 PRD、下周就能实现**，且不需要补任何数据，能立刻减少超时。
3. **要上模型只能上 CP-SAT 小规模精确解，不上 RL。** 真实厨房的数据量和可解释性要求，RL 一条都不满足；论文那 61 篇都在基准算例上。
4. **但有个前置：补「工序资源类型」和「`BatchId`」。** 前者不给，你连"蒸和炒能不能同时做"都表达不了；后者不给，做完了也说不清有没有变好。

**顺序建议**：R4 → R1 → 补 `SetupTimeMatrix` + `ParallelSlots` → R2 凑批 → 冲突检测（第二层）→ 最后才是 CP-SAT 批次建议。
