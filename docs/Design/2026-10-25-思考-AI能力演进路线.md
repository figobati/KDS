# AI 能在这个 KDS 上改善什么 —— 架构师判断

> **需求来源**：用户 2026-10-25 19:30「思考下未来 AI 可以在哪些方面改善本系统，查些资料」
> **依据**：PRD v6.99（07 §9.21a `OrderDetailStageLog`、§9.23 `DailyDimStat`、§9.5 `DishItem`；10 §13.4 性能；11 §14 上云；04 §3.5 只读）
> **外部资料**：arXiv API（`ti:"food waste"` 14 篇 / `abs:"restaurant demand forecasting"` **仅 2 篇** / `abs:kitchen AND abs:"computer vision"` 473 篇但无商用后厨方案）、Winnow 官网（3,500+ 门店、90+ 国家、专利 US 10290226）、GitHub API 实时星数与推送时间（ML.NET 9,362★ / semantic-kernel 28,697★ / sqlite-vec 8,214★ / Foundry Local 2,596★ / whisper.net 951★ / MCP C# SDK 4,601★，均 2026-10 有提交）
> **结论**：这套系统最该被 AI 改善的不是界面，是**时间**。而时间恰好是它**已经在记、但一颗都没用**的数据。

---

## 1. 一句话判断

KDS 里的所有矛盾最终都归结为**时间不确定**：

- 这道菜还要多久 → 客人问、前厅问、店长问
- 这个红灯是真超时还是阈值设错了 → 师傅直接无视
- 明天备多少 → 备多了报损，备少了沽清
- 这个档口是不是瓶颈 → 只能靠店长站那儿看

而这四个问题，**答案全都锁在 `OrderDetailStageLog` 里** —— 每道菜每个阶段的 `EnterAt` / `ExitAt` / `ElapsedSeconds` / `WaitSeconds` / `StationId` 都在，**还带 `IsReverted` 标记保证撤销不污染样本**。

> **这是 AI 项目里最贵的东西：干净的有监督标签，不需要人工标注。** 绝大多数 AI 项目死在标注上，这个系统免费拥有。

**但有三个前提必须先说清：**

1. **V1 不许碰 AI**。会炸验收矩阵（134 条用例还没跑通一条）。
2. **AI 的第一价值不需要模型**。把固定超时阈值换成动态分位数，一周工作量，风险为零 —— 这一步的价值大于后面所有模型加起来。
3. **唯一值得上模型的是 ETA 预测**，因为它有真实标签、失败可回退、效果可量化。

## 2. 它手里已经有什么（别人没有的）

| 资产 | 位置 | 为什么对 AI 关键 |
|:---|:---|:---|
| **阶段时间线** | `OrderDetailStageLog`（07 §9.21a） | 每阶段 `EnterAt`/`ExitAt`/`ElapsedSeconds`/`WaitSeconds`/`StationId`/`EnterSource`（Auto/Manual/Skip）/`ExitReason`/`IsReverted` —— **天然的监督标签 + 天然的难例标记** |
| **8 维日聚合** | `DailyDimStat`（07 §9.23） | `Station` / `StationStage` / `Item` / `ItemStation` / `OrderType` / `MealPeriod` / `Area` / `Hour`，含 `P90ElapsedSeconds`、`SumElapsedSeconds`、`ElapsedCount`（可加权） |
| **事件溯源** | `EventLog` + 17 入站 / 9 出站 | 可完整重放任意历史时刻的队列状态 —— **补数据不用改代码，回放即可** |
| **工序知识结构** | `Station` / `Workflow` / `StagePath` / `MergeKey` | 已把"这道菜走几道工序、在哪个档口"结构化，省掉 AI 最烦的知识抽取 |
| **单 Master 局域网** | 06 §5–§7 | AI 推理延迟 <1ms 级、无云配额、无隐私外流 —— **这在 AI 时代是优势不是劣势** |
| **多语言 + TTS 模板** | 761 key × 3 语、`VoiceTemplate`（07 §9.15a） | 语音**输出**已具备，缺的只是输入 |

### 2.1 但有三个缺口：现在补几乎零成本，以后补永久损失

| 缺什么 | 为什么致命 | 代价 |
|:---|:---|:---|
| `StageLog` 缺 **`QueueDepthAtEnter`**（进入该阶段时，该档口在制份数） | **ETA 最强的特征就是"当前排了几道"**。缺了它，模型只能学"这菜平均 5 分钟"，学不到"忙时要 12 分钟" —— 而忙时才是唯一的痛点。事后可从 `EventLog` 重放推导，但一年数据要重放一天 | 加 1 个 `int` 列，写入时读内存队列长度（该值热路径已有，零额外查询） |
| `StageLog.OperatorName` 是**名字**不是 ID | 重名、改名即断链，无法可靠关联 `UserAccount.Uid`；熟练度/负荷分析做不了 | 改存 `OperatorUid`，`OperatorName` 降为快照列 |
| 无"**当时门店总负载**" | 无法区分"这道菜慢"和"今天全店都慢"，模型会把两件事混成一个系数 | `StageLog` 或 `OrderHeader` 加 `StoreLoadAtEnter`（在制订单数） |
| `DishItem.StageStandardSeconds` 是**人工填的静态 JSON** | 该字段 PRD 明写"仅用于瓶颈分析，不参与超时判定" —— 说明已经知道它不准，所以没敢用 | 改由历史 `ElapsedSeconds` 自动校准，人工确认后写回 |

> **这三类字段合计约半天工作量，且不影响任何功能。但如果 V1 就上线而没记，一年后数据全在、却训不出有用模型 —— 那时补不回来。**

## 3. 五个层次的落点（按"可行性 ÷ 风险"排序）

### L0 —— 不需要 AI 的"AI"（纯 SQL，0 模型）

#### L0-1 动态超时阈值 ★最高 ROI★

**现状**：超时判定用 `DishItem.TotalTimeoutSeconds`（固定秒数，空则取 `StoreConfig.DefaultTotalTimeoutSeconds`）。A-12 设置页里就是两个输入框（预警阈值 / 超时阈值）。

**问题**：同一道菜闲时 3 分钟出、忙时 12 分钟出。固定阈值两头不讨好 ——
- 设 5 分钟 → 忙时**满屏红光**，师傅直接无视（红灯疲劳，比没有红灯更糟）
- 设 10 分钟 → 闲时**漏报**，真问题看不见

**改法**：超时判定改用 `(ItemId, StationId, MealPeriod)` 的滚动 14 天 **P90**，样本不足时向全局均值收缩。`TotalTimeoutSeconds` 从"业务值"降级为"兜底默认值 + 人工覆盖"。

**工作量**：一个聚合查询 + 内存缓存 + 夜间重算任务 ≈ **1 周**。**风险为零**（算不出来就回落固定值）。

**验收**：用 `StageLog` 回放对账 —— 红灯总数下降 **≥40%**，同时"真实超时捕获率"不下降（真超时的样本仍然变红）。

> 这是全系统我最推荐的第一件事。它不需要模型、不碰业务流、用户当天就能感觉到，而且**它把"阈值"这个永远吵不明白的配置问题彻底消灭了**。

#### L0-2 每卡"还需约 X 分"

同一套分位数：`剩余阶段 P50 × 当前负载系数`。**这是查表不是预测**，但已能解决 80% 的"这单还要多久"。

**注意**：显示必须给区间（"还需 8–12 分"）并带 `≈`。点估计一旦不准会被骂，区间反而显得专业。

#### L0-3 死单 / 卡单检测

规则即足：某 `DetailId` 在制时长 > 该品项 P99，且期间无任何 `OperationLog` → 提示"这单可能没人管"。

**这个用规则比用模型好一万倍** —— 可解释、可测试、可复现。

#### L0-4 档口均衡报表

`DailyDimStat(ItemStation)` 已能直接回答"某菜在 A 档口平均 4.1 分、B 档口 3.2 分"。一张 Top-N 报表即可，不需要任何模型。

> ⚠️ **但要提前想好政治问题**：这张报表一定会被当成档口 KPI。所以数据必须能自证（能下钻到具体明细、能排除撤销样本、能区分 Auto/Manual/Skip）。做不好 = 冤案。

### L1 —— 传统 ML（ML.NET，本地 CPU，无 GPU）

#### L1-1 ETA 预测（核心，唯一真正需要模型的）

| 项 | 内容 |
|:---|:---|
| **目标变量** | `OrderDetailStageLog.ElapsedSeconds`（按阶段）与整单完成时间 |
| **特征** | 品项、档口、餐段、星期、**当前队列深度**（L0 补的字段）、该品项历史 P50/P90、`IsRush`/`IsHold`/外卖、份数、`StagePath` 长度（工序数） |
| **模型** | **GBDT（ML.NET `LightGbm` / `FastTree`），不要上深度网络**。表格数据 + 中小样本 = GBDT 稳赢，且可解释（特征重要度直接能给人看） |
| **训练位置** | **总部**（跨店样本），推理在门店（`.onnx`，CPU 毫秒级） |
| **部署通道** | 复用 M13 上云 —— **但 M13 目前是单向上报，缺"模型下发"**。要加 `ModelPolicy` 下发 + 版本 + 校验 + 回滚 |
| **不做** | 不做在线学习。单 Master + SQLite 单写者，在线学习会和划单抢锁 |
| **验收** | P90 相对误差 < 20%；**预测区间覆盖率 ≥ 80%**（区间预测比点预测有用得多，师傅要的是"大概还要多久"不是"精确 7.3 分钟"） |

> **为什么这条能成而大多数餐厅 AI 不成**：标签免费（StageLog）、特征已有（上面那张表）、失败可回退（回落 L0-2 的分位数）、效果可量化（误差率）。四个条件缺一个都别做。

#### L1-2 备餐量预测 —— **边界必须说清**

KDS **没有 BOM**（PRD 明写不做库存），所以只能预测**菜品销量**，预测不了**原料备量**。

- ✅ 能给："明天午市宫保鸡丁约 42 份"
- ❌ 给不了："备多少鸡腿肉" —— 除非门店维护菜品→原料配方表（那是另一个产品线）

**而且别被"AI 预测"包装骗**：我查了 arXiv，`abs:"restaurant demand forecasting"` 全库**只有 2 篇**相关论文。这说明该领域学术供给几乎为零，业界靠的是工程实践（周期因子 + 节假日 + 天气 + 促销）。**一个乘法模型加三个修正项，效果通常不比 LSTM 差，且能解释。**

#### L1-3 报损归因

`SoldOutLog` / 报损原因 + `DailyDimStat.Item` + 时段 → "这道菜报损集中在周日晚市且集中在某档口"。

**输出必须是"假设"不是"结论"**（"疑似备料过量，建议核对周日备货表"）。小样本归因极容易过拟合，把噪声说成因果，比不说更糟。

### L2 —— 视觉 / 语音（要硬件，慎入）

#### L2-1 语音划单 —— 能做，但先问"比手点快吗"

**已有基础**：`VoiceTemplate` TTS 输出已在（07 §9.15a），缺的是输入。技术侧 `whisper.net`（951★，2026-10 活跃）端侧可行。

**但后厨是 85 dB 噪声 + 方言口音 + 菜名同音**（干锅/乾鍋、鸡丁/吉丁、鲈鱼/鲁鱼）。所以三条硬约束：

1. **受限词表** —— 只识别该屏当前在制菜品 + 桌号，绝不做开放域识别
2. **二次确认** —— 识别 → 高亮那张卡 → 再确认才写库
3. **永不自动写库** —— 划单不可逆（v6.96 铁律：划单是唯一流转触发）

> **诚实的取舍**：手点 48×48 触摸目标 1 秒内完成；语音说一句 + 确认 ≈ 2 秒。**语音只有在戴手套 / 手湿 / 手上有油时才有价值。** 建议先做一个店的实际测量，别为 demo 买单。

#### L2-2 摄像头自动判断"做完没" —— **V2 以后再看**

我查了现实：
- `abs:kitchen AND abs:"computer vision"` 有 473 篇，但主流是 **EPIC-KITCHENS / Assembly101** 这类**第一视角**或**装配线**场景
- 商用后厨是多灶头、第三人称、油烟遮挡、人员互相遮挡 —— **目前没有成熟商用方案**
- **关键细节**：Winnow（3,500+ 门店 / 90+ 国家 / 专利 US 10290226）的商业落地靠的是 **AI 摄像头 + 秤**的组合，**不是纯视觉**。加了物理传感器才可靠

> 结论：**别信"AI 看灶台自动划单"的演示**。真要做，先做**传菜口出餐核对**（一菜一单拍照比对），而不是灶台自动识别。

#### L2-3 出餐一致性核验（错菜/漏菜）

**价值真实** —— 错菜、漏菜是客诉第一大来源。但需要：每道菜标准图库（没有）+ 稳定光线（后厨没有）。

**建议路径**：先做"人工确认 + 拍照留证"（零 AI），积累 6 个月图片后再谈识别。**先攒数据，再上模型，别倒过来。**

### L3 —— LLM（本地小模型，零业务风险）

#### L3-1 配置稽核助手 ★我建议这是 AI 的第一个真实落点★

**为什么**：PRD 里反复出现同一类警告 ——
- "时区配错极难发现"（UI清单 L830）
- "`SearchBumpWholeTable` 无警示会被随手打开"（A-12 决策点⑥）
- "`UndoWindowSeconds` 60/120/300 三处冲突"（历史不一致）
- "未绑档口要降级，不能静默丢单"（D16）

**这些全是配置错误，而配置错误的共同后果是"查不出来"。**

**做法**：
1. 把 `StoreConfig` + `TerminalConfig` + 路由矩阵 + 打印规则序列化
2. **确定性规则引擎**做判定（绝不用 LLM 判断"有没有问题"，它会幻觉）
3. LLM **只**负责：生成人话解释 + 影响面 + 修复步骤 + 按严重度排序
4. 结果接进 B-18 健康检查（已有 30 项）作为第 31–50 项

**ROI**：直接减少实施返工。一个店装错回滚 = 几千块 + 一整天。**风险：零**（只读配置，只出建议）。

#### L3-2 装店助手（本周就能做，不依赖 V1）

- **输入**：POS 菜单导出（Excel / CSV）
- **输出**：`Station` 路由规则草案、`StageStandardSeconds` 初值、语言包覆盖表、`StagePath` 建议
- **用 MCP 暴露成工具**（MCP C# SDK 4,601★，2026-10-24 活跃）—— 实施同事对话即可用
- **不进城端，风险为零**，省的是实施人天

> 这条和 V1 开码**完全解耦**，是唯一现在就能动的 AI 项。

#### L3-3 排障对话

已有素材：13 个错误码 + B-18 的 30 项检查 + `PrintJob` 队列 + 看门狗日志。

"打印机不出单" → 引导式排查（`PrintRule` → 打印机 → 队列 → 网络）。

**比通用 LLM 强的地方：知识在库里，不在网上。** 通用模型不知道你的 `PrintRule` 怎么配的。

#### L3-4 自然语言查询 —— 最诱人，最危险

"上周三午市哪个档口最慢" → text-to-SQL。

**风险四条**：幻觉 SQL、权限越界（看到别店数据）、大查询打爆 SQLite、结果无据可查。

**如果做，正确姿势是：MCP server 暴露 15–20 个预定义查询，LLM 只做"选查询 + 填参数"，不做任意 SQL 生成。** 这是可靠性与灵活性的正确折中 —— 也是"能查的东西少一点，但每次都对"。

## 4. 架构接入铁律（决定 AI 是加分还是事故）

| # | 铁律 | 理由 |
|:-:|:---|:---|
| 1 | **AI 必须是旁路进程**，绝不进 Kestrel 请求路径 | 硬约束「热路径不查库」+ P95 < 1s。**推理可以慢，划单不能慢** |
| 2 | **AI 永不写业务表**，结果只进 `AiInferenceCache`（内存 + 可选独立 SQLite 文件） | SQLite 单写者，AI 写会和划单抢锁；且 AI 结果可随时丢弃重建 |
| 3 | **AI 只建议，不决策** —— 尤其划单、路由、报损 | 划单是唯一流转触发（v6.96 铁律），AI 改它 = 换了个业务模型 |
| 4 | **可关闭**：关掉后系统行为必须与关闭前**逐字节一致** | 作为新门禁 **G13**（AI 关闭回归） |
| 5 | **可解释**：每个预测能下钻看"用了哪些历史样本" | 师傅不信黑箱。这是采纳率的决定因素，不是锦上添花 |
| 6 | **降级即原路**：模型加载失败/超时 → 立刻回落固定阈值，且**只记 Warning 不算故障** | AI 绝不能成为新的单点故障 |
| 7 | **模型版本进 `ConfigVersion`** | 否则 A 屏和 B 屏预测不一致，会被当 bug 查一周 |
| 8 | **隐私**：跨店训练必须去标识化（`OperatorUid` → 内部哈希） | `StageLog` 含操作人，**员工效率画像在部分司法辖区属合规红线**。做之前先过法务 |

## 5. 不要做的六件（每条都有理由，不是保守）

| ✗ 不做 | 为什么 |
|:---|:---|
| **AI 自动划单** | 不可逆 + 违反"划单是唯一触发"；错一次就是客诉，且无法解释 |
| **AI 自动改路由矩阵** | 吃错菜远比慢 5 分钟严重；且路由错误是**静默的**，不会被发现 |
| **默认云端推理** | 违反"门店局域网"铁律；断网即瘫；餐饮网络质量不可控 |
| **AI 生成菜名/文案** | 菜名是 POS 资产（PRD 明写 KDS 不得做简繁转换），生成即错 |
| **人脸识别考勤** | 后厨戴帽戴口罩识别率低；且是合规红线 |
| **摄像头"监控"员工** | 技术可行，组织上必死。KDS 是帮师傅干活的工具，一旦被当成监工，所有功能都会被抵触 |

## 6. 路线与门禁

| 阶段 | 内容 | 前置条件 | 门禁 |
|:---|:---|:---|:---|
| **阶段 0**（现在，不写代码） | 补 3 个数据字段；定 `AiInferenceCache` 契约；`StageStandardSeconds` 定为"自动校准 + 人工确认" | 需你拍板 | 字段进 07 §9.21a + 两份 DDL 同步 |
| **阶段 1**（V1.1，**零模型**） | L0-1 动态阈值 → L0-2 还需多久 → L3-1 配置稽核 → L3-2 装店助手 | V1 上线跑满 3 个月、有真实 StageLog | G13 通过（关闭 AI 后 G1–G12 全绿） |
| **阶段 2**（V2，模型） | L1-1 ETA（总部训练 / 门店推理）→ L1-3 报损归因 → L3-3 排障对话 | M13 补"模型下发"能力 | P90 误差 < 20% + 端到端 P95 不退化 |
| **阶段 3**（V2.x，需硬件） | L2-1 受限语音 → L2-3 出餐核对 | 单店实测证明比手点快 | 误识别导致的错误划单 = 0 |
