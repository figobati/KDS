# 附录：v6.96 流转模型收敛（用户 2026-10-24 19:18 拍板）

> **来源**：用户口头定案两条 —— ① `AutoFlowStages` 废止；② 系统应有"启用流转工序"总开关，开关开启后再选流转模式（自动 / 手动），**自动模式是 V1 最重要的一部分，手动模式设计保留、V2 再实现**。

## 结论：三层 → 两层

| 层 | 字段 | 取值 | V1 状态 |
|:--:|:---|:---|:---|
| 第 1 层 | `StoreConfig.EnableWorkflowState` | `true` / `false` | ✅ 实现。`false` → 退化为"待出 / 已划单"二态 |
| 第 2 层 | `StoreConfig.FlowMode` | **`Auto`（默认）** / `Manual` | **`Auto` 实现；`Manual` 设计与数据结构保留，V2 实现** |
| ~~第 3 层~~ | ~~`Workflow.AutoFlowStages`~~ | — | ❌ **废止删列**（含 `DishItem.AutoFlowStages`） |

**原 `AutoFlowEnable`(bit) → `FlowMode`(Enum)**：旧名"是否自动流转"与真实语义（"用哪种流转模式"）不符，布尔量易误读。

## 关键定义（已写入 PRD）

- **流转触发条件 = 屏上划单，唯一**。不存在"等待 N 秒自动推进"，也不存在"按标准工时定时推进"。`StageStandardSeconds` / `TotalTimeoutSeconds` **仅用于超时预警与瓶颈分析**。
- **自动模式（V1）**：品项按 `StagePath` 逐级推进 → 每屏只看自己那一站 → 划单即完成本阶段 → Master 广播 `StageAdvanced` 推下一站 + `Revision` 轮询兜底。
- **手动模式（V2）**：透明流水线（下游可见上游）+ 越级代办（`SkippedStages` / `DirectDone` / `SkipDoneCount` 审计）。
- **V1 兜底**：管理端下拉只呈现 `Auto`；若配置出现 `Manual`（导入/改库/回滚），**引擎按 `Auto` 运行并记 `Warning`**，不得中断出餐。
- **首阶段**：`StagePath` 第一道有效工序（**非硬编码 `Prep`**）。`[Cook,Expo]` 下单即"待制作"，`[Expo]` 下单即"待传菜"；继承链 品项级 > 品类默认 > 系统默认。

## 为什么 `AutoFlowStages` 必须删（不是"留着不用"）

它设计为"逐边自动推进白名单"，本意是"`Prep>Cook` 自动，`Cook>Expo` 仍手划"。既然**每条边都必须划单**，"免划边"集合恒为空 → 字段无任何语义。且它**重复存两份**（`Workflow` + `DishItem`），本身违反单一来源。留着只会让后来者以为存在第三种模式。

## 连带关闭：附录 B-2

B-2 本来被 `KDS-05 §4.2` 那句"满足预设条件，系统自动流转"带出来的**伪待确认项**。现在触发条件写死为划单，该项关闭。

**附录 B：15 行 = 已决 4 + 真待定 11**（阻塞契约冻结 **5 → 4 条**，剩 B-9/B-11/B-12/B-13 全在 POS 侧）。

## 「只读」的准确定义（本次收拢的核心）

**只读 = 隐藏所有会写库或发事件的入口，不是整屏锁死。**

| 隐藏 | 保留 |
|:---|:---|
| 卡尾操作条 A-09（【叫号】【划菜】）整条不渲染 | 全景查看（跨全部工序） |
| 桌台模式行点击划单无响应 | **三视图随时切换** |
| 合菜【选中划】【全部划】【划单打印】 | 检索查询（桌号/单号/菜名） |
| 单菜行内划单 | 筛选（催菜/超时/等叫/起菜） |
| A-07【我的划单记录】入口 | 分页滚动、语言切换、状态条 |
| 撤销（含 `EnableManageUndo` 跨屏撤销） | 本机设置页中**不写库**的项 |
| 补打（`EnableReprint` 强制不可用） | — |
| **叫号**（写 `CallLog` + TTS 广播 = 操作） | — |

> 这条判据解决了原文档的模糊处：此前只有"卡尾整条不显示"一句，**叫号是否隐藏没写**。现在按"是否写库/发事件"一刀切，无歧义。

| 维度 | 工序屏 | 综合屏 |
|:---|:---|:---|
| `Role` | 必填 | **可空** |
| 可见阶段 | 仅本角色那一站 | **全部阶段** `Prep`/`Cook`/`Expo` |
| 三视图 | 桌台/合菜/单菜 | **同样全支持**，`BaseGroupMode` 同样二选一 |
| 绑档口 | 必须 ≥1 | 可多档口取并集，**也可不绑** |
| `EnableOperate` | 默认 `1` | 默认 `0`（开箱只读） |
| 用途 | 干活 | 总览/查询/（可选）叫号 |

**重要澄清（防误读）**：综合屏"能看到所有工序状态" **≠** 手动模式的"透明流水线"。

- 综合屏是**另一种屏类型**，V1 自动模式下就跨全部阶段；
- 手动模式讲的是**工序屏自己**也能看见上游未做完的菜（V2 实现）。
- 两者互不依赖——所以"V1 不实现手动模式"与"V1 综合屏能看全部阶段"**不矛盾**。

## 已知取舍（如实记录）

**V1 没有"只开叫号、不开划单"的中间态**。`EnableOperate` 是单一开关，打开即同时获得划单与撤销能力。

- 若门店**只要叫号不要划单**：建议当班传菜员用**传菜屏**叫号，综合屏保持只读；
- 若现场强诉求：可作为 **V1.1** 拆出 `EnableCall` 独立权限开关（数据结构已具备，加一个守卫条件即可）。

## 补充（v6.97）：综合屏与「是否启用工序流转」解耦

> **用户补充原话**："另外说明下，综合屏在未启动工序流转的情况下也是可以用的，只是品项不再显示当前工序"

### 核心口径

**关掉工序流转 ≠ 关掉综合屏。** 综合屏**不依赖** `StoreConfig.EnableWorkflowState`，两种配置下都能用、功能都完整。唯一变化是**品项不再显示"当前工序"**。

| 能力 | 启用工序 | **关闭工序** |
|:---|:---|:---|
| 屏幕可用性 | ✅ | ✅ **照常可用，不降级、不禁用** |
| 三视图 | ✅ | ✅ 同样全部支持 |
| 检索 / 筛选 | ✅ | ✅ 同样可用（超时 = **全局超时**，无"本阶段超时"） |
| 划单 / 叫号 / 撤销 | 按 `EnableOperate` | ✅ **同样按 `EnableOperate`，能力不变** |
| 品项当前工序 | 阶段名 + C9 徽标 + 本阶段时长 | ❌ **全部不渲染** |
| 等待时长 | 本阶段时长 | ✅ **只显示全局等待时长**（从下单起算） |
| 状态语义 | 8 态 + 4 阶段态 | **待出 / 已划单**（§4.1） |
| 划单后 | 推进下一工序 | **直接完成** |
| 卡片高度 | 含阶段行 | **变矮**（不占位不留白，同只读态处理） |

### 定位变化（重要）

关闭工序流转后，综合屏从「**工序大盘**」变成「**出品大盘**」——它的价值是**全店所有未出菜品的一览**（哪桌还差什么、等了多久、有没有催）。**这个价值与工序无关**，所以不能因为关掉工序就把屏停掉。

很多门店第一年只用"待出 / 已划单"这套最简流程，**综合屏正是它们最需要的那块屏**。

### 连带结论：失去意义的只有工序屏

| 屏 | 关掉工序流转时 |
|:---|:---|
| 切配 / 制作 / 传菜工序屏 | ⚠️ **失去意义**（无工序即无"我这一站"）；工程上建议不部署或少部署，但不禁止——屏仍能显示全部待出菜品，等于退化成一块小综合屏 |
| **综合屏** | ✅ **依然成立，且是该场景下的主力屏** |

# 附录：v6.98 联台加菜单号口径定案（用户 2026-10-24 21:26 拍板）

> **用户原话**："第9条，联台期间加菜，订单号不变，联台本身就是同一个订单"

## 结论：附录 B-9 关闭

**联台 ≠ 多个订单，联台 = 一个订单多张桌。** 因此联台期间加菜**订单号本来就不变**，不存在"另起新单"的问题。

```
OrderHeader (1) ──< OrderTableRel (N)     一单多桌 = 联台
OrderHeader (1) ──< OrderDetail  (N)      明细挂订单，不挂桌
                 └─ DishLine.SourceTableId 指明该行归属哪张桌
```

## 加菜的完整路径（已与契约对齐）

| 步骤 | 内容 |
|:---|:---|
| 1 | POS 推 `Order.Update`，`PosOrderNo` **不变** |
| 2 | `Lines[]` 里新菜用**新 `LineNo`**（同 `LineNo` 改数量属纠错，见下） |
| 3 | 新行带 `SourceTableId` → KDS 挂到对应 `OrderTableRel` |
| 4 | KDS 在**同一 `OrderId`** 下新增 `OrderDetail` 行 |
| 5 | 组卡按 `"G:" + OrderId` 分组 → **仍是同一张卡**，只多一行，行内标签 `[A05]` / `[A06]` 照常渲染 |

**已有的契约基础**（本次无需新增字段）：
- `Order.Update` 幂等语义早已写明"明细按 `LineNo` 匹配：存在则更新，不存在则新增"
- `DishLine.SourceTableId` 早已存在，原描述即"该行归属的桌台关联。联台/拼桌时逐行标注"

## 顺带确认的两个易错点

| 易错点 | 正确口径 |
|:---|:---|
| 联台加菜用旧 `LineNo` 只加数量 | ❌ 错。会更新原行、**不新增行**，记 `Warning`（§4.6.1）。加菜**必须**新 `LineNo` |
| 新行不带 `SourceTableId` | ❌ 错。组卡内"每行必带桌台标签"是**安全底线**（防送错桌），没归属就没标签。KDS 兜底按空 GUID 处理并记 `Warning` |

## 保留一个假设性兜底（不删）

若某些 POS **违约**对联台加菜另建订单，理论上会生成第二组 `OrderTableRel` → 出现第二张组卡。KDS **不猜测两单属同一桌组**（无依据，猜错会串桌）。

保留这段说明的理由：**联调首轮必须实测该路径**。用户口径明确了"订单号不变"，正好把它变成一条可验证的联调断言——如果对方系统实际另起新单，第一天就能抓出来，而不是上线后才发现。

契约可以冻结，M2 出站与 M7 报损均可开工。

## #11 部分完成 / 部分退

**① "部分退"这个操作不存在。**

`Action = ItemCancel` 早已从终端 Action 枚举移除（§4.7.2）。退菜**只能 POS 发起**（`Item.Remove` 带 `Qty`），退几份由 POS 定。KDS 从不主动发起部分退。

**② 顺带发现一个冗余：KDS 不该对 POS 发起的退菜回执 `Item.Cancelled`。**

既然 POS 是发起方，它自己知道退了几份。KDS 再发一遍是纯噪声，而且有双方重复扣账风险。所以口径改为：

> `Item.Cancelled` **只用于 KDS 主动取消**（跨日清理，`IsFullCancel = true`）。

**③ 部分完成 = POS 选择性接受。** KDS **始终发送** `IsFullComplete`，POS 二选一声明：

| POS 选择 | POS 侧动作 | KDS 侧 |
|:---|:---|:---|
| **A 接受** | 收到 `false` 立即记"部分出餐 2/3"，参与账单/出餐率统计 | 不处理 |
| **B 不接受** | 收到 `false` 自行累计，直到 `true` 才标"已出餐" | 不处理（仍照常发 `false` 供累计） |

两条硬底线：**不允许静默丢弃事件**（否则整行永远等不到 `true`，KDS 不补发）、**选择必须登记在对接文档**（否则联调分不清功能还是 bug）。

## #12 三个"新增出站事件"——其中一个是分类错误

**`Item.Notify` 根本不是出站事件。** 它的方向是 **POS → KDS**：POS 用它告诉 KDS「这道菜已下单 / 已起菜 / 等叫 / 已出品」（见 §10.3 入站表、§2.16.7 标题就写着"POS → KDS"）。

所以附录 B-12 问"POS 是否支持 KDS 发的 `Item.Notify`"——这个问题**本身不成立**。真正需要 POS 表态的出站只有两个：

| 事件 | POS 可否拒绝 | 拒绝后的降级（写死） |
|:---|:--:|:---|
| `Item.Undo`（撤销划单） | ✅ 可以 | ⚠️ **管理端 `EnableUndo` 强制禁用 + 置灰说明原因** |
| `Item.UnableToCook`（做不了） | ✅ 可以 | **隐藏「做不了」按钮**，改用沽清申请或口头通知（KDS 不改数量，无账务风险） |
| `Item.Notify`（入站） | — 不是出站 | 若不发：KDS 按"`Order.Create` 即起菜"处理（`NotifyState` 恒 `20`），无等叫语义 |

**为什么 `Item.Undo` 拒绝后必须禁用而不是降级**：如果 KDS 本地回退、POS 却认为已出餐，是最坏的组合——账实不符且事后无法追溯。**宁可没有撤销功能。**

## #13 报损原因由 KDS 填

报损是**内部成本归因**：只有厨房/管理端知道真实原因（做错、打翻、变质）。POS 只掌握"客人退了"这一层，硬要它按 KDS 号段填，结果一定是全填 `99 其他`。

落地口径：**POS 发 `Item.Void` 时 `VoidReasonCode` 可缺省**（schema 中本就是可选，无需改），KDS 由**发起报损的操作人**在屏上/管理端选；POS 若顺手填了合法序号则直接采用、不覆盖。

这是三条待确认项的共同根因——**POS 侧能力不一致**。与其在文档里反复猜，不如让 POS 显式声明，KDS 按声明自动降级或禁用。
