## 4. 需要修订 PRD 的 5 项（C-1…C-5）

### C-1 字号硬上限被突破（**必须改**）

| 项 | PRD（UI清单 §1.5 / 行 195/201/205） | 原型实测（`css/core.css`） |
|:---|:---|:---|
| 菜名 | **≤ 32px 硬上限**，任何配置都不能突破 | `:390` `clamp(11px, …, **40px**)`；单菜 `:699` 也是 `40px` |
| 桌号 | **≤ 40px 硬上限** | `:344` `clamp(11px, …, **48px**)` |

**冲突性质**：不是"原型做大了"，而是 PRD 的 `clamp` 上限没有对应到"响应式自适应"这种新做法。PRD 的三档字号（S/M/L）上限是为"固定档位"设计的；一旦改成随卡尺寸连续缩放，上限必须重新定义。

**建议**：PRD 改为**双约束** —— 菜名 `≤32px` **在 1920×1080 基准下**成立；超基准分辨率（2560/3840）按比例放宽到 `32 × (屏宽/1920)`，但**必须同时满足"一屏 ≥ 12 张卡"**。理由：4K 屏上锁死 32px 等于把字缩小，师傅更看不清。

**需你确认**：这条我倾向按原型改 PRD，但它是"安全信息"级约束（PRD 写明"字号过大 = 一屏卡变少 = 翻页变多 = 更慢"），不宜我单方面改。

### C-2 字号档位：**已对齐，无需改 PRD**（2026-10-25 复核对上一版的更正）

上一版我看到「75–135% 连续滑块」就判成与 PRD 冲突，**看错了层级**：

| 位置 | 是什么 | 参数 | 与 PRD 关系 |
|:---|:---|:---|:---|
| **A-12 屏端设置页**（产品） | 真正的门店配置入口 | **S / M / L 三档，并排小样预览 24 / 28 / 32px** | ✅ **与 PRD §1.5 三档一致**，且 32px 正好是菜名上限 |
| ⚙ 悬浮面板（`?panel=1`） | **评审/调参用**，不是产品功能 | 75–135% 连续滑块，按视图独立 | 不进产品，不构成冲突 |

**判定**：PRD 不用改。原型在 A-12 已按三档实现，而且做法比 PRD 更进一步——**三档各给一个并排小样**（`fontPreview()`），而不是下拉框让人闭眼选。这一条我建议**写进 PRD §1.5** 当实现要求（"三档必须并排小样预览"）。

> 教训：判断"是否违反 PRD"要先分清**产品屏**与**评审面板**。把原型自带的调参工具当成产品界面，会得出一堆不存在的冲突。

### C-3 显示模式分类（3 模式 vs 2 主题 × 1 开关）

| 维度 | PRD §1.5.1 / §1.5.2 | 原型 |
|:---|:---|:---|
| 体系 | **3 个内置显示模式**：标准（默认）/ 强对比 / 暗环境 | **2 主题**（A 夜航深色 / B 晨光浅色）+ `[data-contrast="hi"]` 强对比开关 |
| 默认 | **标准（浅色）** —— 后厨主流是亮环境 | `data-theme="b"`（晨光浅色）✅ 一致 |
| 归属 | `TerminalConfig`，每屏独立 | 屏内面板可切，未体现存储归属 |
| 状态色可改性 | `status-*` **6 个不可改**，仅允许"色盲友好强化" | 状态色写在 `theme-*.css` 内，**未开放给门店** ✅ |

**判定**：**语义等价，只是分类维度不同**（PRD 用"3 模式"，原型用"2 主题 × 对比度"）。覆盖组合：标准≈B / 暗环境≈A / 强对比≈B+hi，**唯一缺 A+hi（暗环境强对比）** —— 该组合实际无意义（暗环境本就是降亮度需求），可接受。

**建议**：PRD 不用改结构，只在 §1.5.1 补一句"实现上可用「基色主题 × 对比度开关」二维表达，组合数与三模式等价"。

**顺带发现**：PRD §1.5 明确"**不做浅色/深色两套主题**"，而原型文件命名就叫 `theme-a/theme-b`。**建议改名为 `mode-dark/mode-light`**，避免后来人按文件名以为 PRD 被推翻了。这是命名问题，不是设计问题。

### C-4 只读态边界：**PRD 写错了，原型是对的**（v2.16，重要）

**PRD 现行口径**（`KDS-04` §3.5 ② / `UI清单` L529、L634）：

> 卡尾操作条 A-09（含【叫号】【划菜】）→ **整条不渲染**（不是置灰），**卡片变矮**。

**原型 v2.16 的反驳**（`overview.md`）：`.sft`（卡尾）里装的是**等待时长 + 份数**——**那就是"进度"本身**。对一块专门拿来盯进度的屏，只读恰恰把最该看的东西抹掉了。

**原型的正确切法**：

| 只读态 | 处理 | 具体项 |
|:---|:---|:---|
| **收掉**（改状态） | 不渲染 | 点卡划单、已划 ✓、合菜勾选框、催菜、叫号/清台、批量划菜/清空、A-07「我的划单」入口 |
| **保留**（看 + 查） | 照常 | 桌号、菜名、做法、**等待时长**、**份数**、超时/催菜角标、档口标签、搜索 + 触摸键盘、筛选 chips、翻页 |

**根因是 PRD 把两件事塞进了一个组件**：`A-09` 同时是"信息段"（时长/份数）和"操作段"（叫号/划菜）。**"整条不渲染"在语义上必然连进度一起砍掉**。

**建议改法**：A-09 拆成两个编号 ——

| 编号 | 名称 | 只读态 |
|:---|:---|:---|
| **A-09** | 卡尾**信息条**（等待时长 + 份数） | **恒显示**（不再是"卡片变矮"） |
| **A-14**（新增） | 卡尾**操作条**（【叫号】【划菜】） | 只读态整条不渲染 |

连带改：`KDS-04` §3.5 ② 表格、`UI清单` L529（A-06 行）、L634（A-09 定义）、`KDS-00` 版本记录。**这条会影响 M10 的验收用例（M10-7 只读态「12 个写入口」要改成「操作段节点 = 0 且信息段节点 > 0」）。**

### C-5 综合屏：从「第四种屏」改为「范围维度」

| | PRD v6.97 | 原型 v2.16 |
|:---|:---|:---|
| 表达 | `TerminalType = Composite` 的**独立屏类型**，`Role` 可空，**可见全部阶段** | **同一块屏上的范围开关**：模式 Tab（3）× 范围（本工序 ⇄ 全工序），`3×2 = 6` 种组合 |
| 三视图 | 综合屏同样全支持 | 一致 |
| 差异点 | 屏类型 + Role 可空 + 默认 `EnableOperate=0` | **仅数据范围** + 默认只读 |

**原型的好处**（我认为该采纳）：原来是"4 个 Tab（桌台/合菜/单菜/综合）"，把"综合"和三种分组方式并列，**类别混了** —— 综合讲的是范围，不是分组。改成 3 Tab + 2 范围后，`ActiveView` 枚举**不用动**（原型原话：决策点①因此消失）。

**要落到 PRD 的是三个字段问题**，需你定：

| 方案 | `TerminalConfig` 字段 | 代价 |
|:---|:---|:---|
| **甲（贴原型）** | 保留 `TerminalType`，新增 `DefaultScope`（`Station`/`All`）+ `AllowScopeSwitch`（bit） | 加 2 列 → 碰 DDL |
| **乙（最小改动）** | `TerminalType = Composite` 时**强制** `Scope=All` 且屏上可切，工序屏不可切 | **不加列**，但"综合屏能切回本工序"这个能力没了 |
| **丙（原样）** | 维持 PRD 现状（综合屏 = 独立屏，无范围开关） | 与原型实现不一致，M10 要按 PRD 重做原型这块 |

**我的建议：甲**。理由：`Scope` 是**真正的产品维度**（一块挂传菜口的屏，忙时看本工序、闲时看全店，这诉求真实存在），而 `TerminalType` 只是"默认值 + 权限"的载体。加 2 列的成本远低于后面为"半块屏"打补丁。

## 5. 原型自主决策，建议照收的 6 项

| # | 决策 | 理由 | 建议 |
|:-:|:---|:---|:---|
| D-1 | **满铺自适应**（流式网格 + 自动密度，按目标卡宽反推列数），替代"1920 固定画布 + 等比缩放" | 16:9 锁死必然两端留白；实测 1280→3840 六档，单卡宽恒在 396–602px | **采纳**，写入 UI清单 §1.1，替换"1080p 浮动缩放"次选方案 |
| D-2 | **字号跟卡片走**（`container-type:size` + `cqw/cqh`），不跟屏幕 | 卡变窄变矮时字号同步降，任何密度都不撞行 | **采纳**，这是 D-1 的必要配套 |
| D-3 | **菜名默认单行截断**（PRD §3.2 要求两行 `line-clamp:2`） | 德语/俄语两行会把卡撑爆；面板留"1 行/2 行"开关 | **采纳为默认**，但**中文场景默认两行**（中文菜名短，两行几乎不占高）→ 按语言分默认值，非全局一刀切 |
| D-4 | **三视图独立行列数 + 独立字号缩放** | 桌台卡 560×400、合菜 360×250、单菜 272×186 是三种密度，共用一套参数必然有一方难看 | **采纳**，需在 `TerminalConfig` 增三个字段组（或一个 JSON 列）→ **涉及 DDL 变更，须另开子任务** |

### 6.2 对 761 条语言包的影响：**不作废**

我上一版把"语种选错"列为阻塞项，前提是原型面向港澳、要的是**粤语**。现在标签定为 `zh-TW`，**与我的交付方向一致**：

- 我的 `zh-TW.json` = **标准书面繁体**（桌位 / 合菜 / 換人 / 待製作 / 列印 / 儲存 / 匯出）。
- 原型字典 = **港式口语**（檯 / 併菜 / 交更 / 待整 / 凍 / 搵唔到 / 我嘅劃單 / 掣）。

**两者是同一语种下的两种风格，不是两个语种。** 所以：**761 条不用重做，key 集合与占位符已 100% 对齐**，M11 可以照原计划开码。

### 6.3 剩下的一处待定：词条风格（不阻塞开码）

原型自己在 `overview.md` 里也标了待确认：

> 词条目前是**港式**用词（檯 / 走單 / 少冰 / 交更）。若门店定位在台湾，需另过一遍台湾用词（桌 / 出菜 / 去冰 / 交班）。

这一条**我建议按 `KDS-09` §11.6 的既定架构解决，而不是二选一**：

| 层 | 用哪套 | 理由 |
|:---|:---|:---|
| **语言包 `zh-TW.json`**（内置基准） | **标准书面繁体**（我的 761 条） | 书面繁体是港澳台共同可读的最大公约数；`搵唔到`「我嘅劃單」对台湾用户是方言文，读得懂但不专业 |
| **门店覆盖 `ScreenLangPack`**（`StoreConfig`） | **港式口语覆写**（檯 / 併菜 / 交更 / 待整 / 凍 / 走單） | 这本来就是 `ScreenLangPack` 存在的理由——**个别用词的地区差异，用覆盖表解决** |

**这样两边都不用改架构**：港澳店导入一张 20–30 条的覆盖表就得到原型那套口语文案；台湾店开箱即用。

> ⚠️ **但要提醒**：`搵唔到`、`我嘅劃單`、`就快超時` 这类是**粤语语法**，不是"用词差异"。如果客户确实在香港，覆盖表条数会显著超过 30 条（可能 80+），那就该考虑 **V1.1 单设 `zh-HK`**，而不是把覆盖表撑成"半套语言包"。**这取决于客户在哪，请确认。**

### 6.4 顺带确认的两件

1. **`de` / `ru` / `ar` 仍在原型里**，但只是**抗换行压力测试语种**（×2.2 / ×2.3 / RTL），**不进 V1 交付**。原型入口已按 `zh-CN` / `zh-TW` / `en-US` 对齐主标签，这三个保留作为回归语料是对的。
2. **健康检查语言白名单**：`health.i18n.langNotAllowed` 现在是 `zh-CN` / `zh-TW` / `en-US`，**与原型标签一致**，`KDS-09` §11.1 无需改动 ✅。
